## The brief

Every studio so far ended with something that works on your machine. This one ends with something that works for other people, keeps working when things go wrong, and tells you when it doesn't. You will take your strongest earlier project and run it the way a team runs a product: deployed at a public URL, streamed, resilient, traced, costed, guarded, monitored with an online eval, and launched against a checklist where every item has evidence attached.

The deliverable is not the deployment. It's the **launch decision**: a write-up that says "this is ready for users, here is the evidence, here is what it costs, here is the main remaining risk, and here is what would make us turn it off", plus a demo that shows the evidence is real.

## Which project, and which repository

Deploy in the repository of the project you choose, so its history, tests, and evals come with it. The suggested repository name is **`doc-qa-rag`** because the Studio 2 question-answering system is the best default for most learners: it already has a versioned eval set, code graders, and a calibrated judge from Studio 3 (`rag-eval-harness`), which gives you the online eval and the launch gate almost for free, and retrieval over a public corpus gives you real trust boundaries to model.

Other good choices, if you'd rather:

- **Studio 1, `transcript-action-items`**: small and well tested; the guards are mostly about PII and evidence verification. You'll need to build an online eval from its gold set.
- **Studio 4, the PM workflow agent**: the richest security story (tools with side effects, approvals, injection through tool results). Choose it if you want lesson 11 to matter most, and budget extra time for the threat model.
- **Studio 5, the fine-tuned model**: serving your own model adds hosting and capacity work. Choose it if deployment and cost are what you want to learn.

Whichever you pick, keep that project's repository name and say why you picked it in the write-up.

## What you get

- **Week 1** (deployment): streaming, timeouts, retries, and degraded modes. Its lab gives you a resilient service skeleton.
- **Week 2** (cost and latency): budgets, caching, batching, and routing.
- **Week 3** (observability): tracing, redacted logging, dashboards, and the pieces for an online eval.
- **Week 4** (this week): lab 04's guard pipeline and red-team runner, lesson 11's threat model and OWASP walk, and lesson 12's launch checklist and incident table.

Hosting is your choice. A serverless platform, a container service, or a small virtual machine are all fine; check its request timeout against your longest streamed response, and keep secrets in the platform's secret store.

## Pitfalls

<Callout type="pitfall" title="A demo, not a deployment">
A public URL that works when you click it isn't the bar. If the provider returns 529s for ten minutes, if someone sends a 200 KB message, or if a script hits the endpoint 10,000 times overnight, what happens? Simulate each of these with a fake client or a test harness, and keep the tests.
</Callout>

<Callout type="pitfall" title="An open endpoint and an open wallet">
A public LLM endpoint without per-user limits and a spend cap is an invitation to unbounded consumption (OWASP LLM10). Put quotas in front of the model call, set a provider spend limit, and use a separate API key for this deployment so you can revoke it without breaking anything else.
</Callout>

<Callout type="pitfall" title="Guards measured only on attacks">
A guard that blocks every attack in your red-team set might also block a fifth of your real users. Always report the false-positive rate on benign cases next to the block rate, and include benign messages that look like attacks.
</Callout>

<Callout type="pitfall" title="Logging what you promised to protect">
Traces that store raw prompts and outputs will collect personal data and, eventually, a pasted secret. Redact before the log sink, test the redaction, set a retention period, and check that your dashboard queries still work on redacted data.
</Callout>

<Callout type="pitfall" title="A rollback you've never run">
If rolling back means a code change and a redeploy, it will be slow when you need it fast. Version prompts, model ids, guard settings, and index versions as configuration behind flags, and rehearse the rollback on camera for the demo.
</Callout>

## Constraints

- Use official SDKs for model calls, with keys in the hosting platform's secret store. No keys in the repository, the prompt, or the logs.
- The offline test suite (guards, redaction, red-team runner with a fake client, failure simulations) must run in CI without an API key.
- Set a hard monthly spend limit for the deployment's key and state it in the write-up. Keep the public demo cheap: a small daily request quota per user is fine.
- If your project uses data about real people, use only data you have the right to use, and say how you handle it.

## Write-up template

Put this in `WRITEUP.md` and fill it in. Aim for two pages, plus the checklist and runbook as appendices.

```markdown
# <Project name> in production: write-up

## Launch decision (read this first)
One paragraph for a non-engineer: what the service does and for whom, whether it is ready and why,
what it costs per user and per month at expected traffic, the main remaining risk, and what would make you
turn it off. Public URL and demo video link.

## What I deployed, and why this project
Which earlier project, which repository, and why it was the strongest candidate. Hosting choice and why.

## Architecture
Diagram, with trust boundaries marked. Where streaming, retries, guards, tracing, and flags sit.

## Evidence
| Area | Claim | Evidence (link) |
|---|---|---|
| Reliability | Survives provider errors and timeouts | Failure-simulation tests, load test |
| Quality | Offline eval passes the gate; online eval on sampled traffic | Eval run, dashboard panel (n, interval) |
| Safety | Guards block X% of attacks at Y% false positives | Red-team report by category |
| Security | Threat model and OWASP walk; no secrets in prompts or code | THREAT_MODEL.md, secret scanning |
| Cost and latency | $ per request, p50 and p95, budget and alert | Dashboard, alert screenshot |
| Operations | Rollback and kill switch tested | Demo timestamp, runbook |

## Guards and red-team results
Each guard: what it catches, block rate and false-positive rate, latency and cost it adds.
The misses you accepted, and why.

## Threat model summary
The top five risks, the response to each (mitigate, eliminate, transfer, accept), and the owner.

## Costs and latency
Measured cost per request and per day, p50 and p95, projection at 10x traffic, and any optimization you measured.

## Incidents and drills
Any real or drilled incident: timeline, mitigation, and the tests it left behind.

## Limitations and next steps
What isn't covered, what you would build next, and what would change your launch decision.

## How I used AI assistants
Which tools, for what, and what you had to check or correct.

## Appendices
LAUNCH.md (checklist with evidence), RUNBOOK.md (one page), THREAT_MODEL.md.
```

When you finish, score yourself with the rubric below (ideally a day later), paste your repo link and public URL, and mark the project submitted.
