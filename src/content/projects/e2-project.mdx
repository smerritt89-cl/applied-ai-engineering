## The brief

You've used a coding agent for a long time. This project asks a question most teams never answer with data: **does the setup work you'd do for an agent actually pay off on your code?** You'll make a repository agent-ready, using what the elective taught (short project memory, hooks that enforce checks, a protected path, a subagent or skill, and CI), and then measure it like an experiment. Same tasks, same prompts, same model, with and without the setup.

The deliverable isn't a configured repo. It's a credible answer, with numbers and honest uncertainty, that you could take to a team lead: here's what the setup costs to build and run, here's what it changed (success, rework, time, cost, safety), and here's what I'd recommend.

## What you get

- The lab at `labs/electives/e2-agent-ready-repo/`: a worked example of every piece (CLAUDE.md, hooks and their offline tests, a reviewer subagent, a workspace builder that hides answers, holdout tests, and a scoring script). Copy patterns from it freely.
- `templates/CLAUDE.md.template` in the lab, for requirement r2.
- Your lesson exercises: the CLAUDE.md linter (lesson 4), the PreToolUse guard (lesson 5), the test-tamper scan (lesson 7), the risky-diff scan (lesson 8), and the comparison summarizer (lesson 3). Several can become CI steps.

A practical way to run the bare condition is a branch or worktree with the setup files removed (`CLAUDE.md`, `.claude/`), started with the same model and effort. Don't use `--bare` for the setup condition: it skips CLAUDE.md and hooks. Do watch for **learning effects**: if you fix a task by hand between runs, or the setup condition always runs second, your later runs benefit from what you learned. Alternate the order of conditions across tasks.

<Callout type="tip" title="Budget before you start">
Ten tasks-by-condition runs times two repeats is twenty runs, more with the stretch goals. Cap each scripted run with `--max-turns` and `--max-budget-usd`, check `/usage` after the first few, and pick tasks that take an agent minutes, not hours. Small tasks give you more runs, and more runs give you a more honest answer.
</Callout>

<Callout type="pitfall" title="Grading the runs by the agent's summary">
"All tests pass" from the agent is a claim, not a result. Score each run yourself: run the acceptance checks, read the diff with the review checklist, and record whether tests were edited or safeguards removed. A setup that produces more "done" summaries but more quietly edited tests is worse, and only your scoring will show it.
</Callout>

## Constraints

- Keep keys and secrets out of the repository and out of agent-readable paths; deny reads of `.env` and similar files.
- Run unattended (`claude -p`) sessions only in repositories whose `.claude/` and `.mcp.json` you've read.
- Don't push agent changes to a shared main branch during the experiment; branch protection should require your review.

## Write-up template

Put this in `WRITEUP.md` and fill it in. Aim for two pages.

```markdown
# An agent-ready repository, measured

## The repository and the question
What the repo is, how its tests run, and the question you're answering (2 to 3 sentences).

## The setup
- Instruction file: what's in it and what you deliberately left out (line count)
- Hooks: events, matchers, what each runs, how long each takes
- Protected path(s): deny rule + hook, and the gaps neither covers
- Subagent or skill: what it does, and where you saw it change a run
- CI: what it enforces

## The tasks
| # | Task | Type | Acceptance criteria (short) |
|---|---|---|---|

## Method
Model and effort, permission mode, prompt text, how runs were isolated, run order, number of runs.

## Results
| Condition | Runs | Success rate | Cost / success | Mean rework (min) | Mean wall time (min) | Runs with test edits | Runs with removed safeguards |
|---|---|---|---|---|---|---|---|
| Bare | | | | | | | |
| With setup | | | | | | | |

Paired view: for each task, successes out of runs in each condition, and the tasks where the conditions disagreed.
Uncertainty: what this sample size can and can't distinguish.

## What changed, and why
Two or three runs where the setup clearly helped or hurt, with the evidence (a hook firing, a blocked edit, the reviewer's finding).

## Recommendation
Would you adopt this setup for your team? What would you keep, cut, or add, and what would you measure next?

## Limits and threats to validity
Task selection, learning effects, variance, the one repo, the one model.

## How I used AI assistants in this project
Which parts you delegated, which you did yourself, and how you checked the delegated parts.
```
