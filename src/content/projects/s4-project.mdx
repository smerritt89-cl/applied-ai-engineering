## The brief

Somebody on every product team spends Friday afternoon turning the issue tracker into a status update. Your job is to automate that, safely: an agent that reads the tracker through an MCP server you build, drafts the weekly status, and posts it only after a person approves the exact text.

The interesting part is not the summary. It is everything around it. The agent reads text that anyone can write (issue bodies and comments), so it is a target for prompt injection. It can post, so it has a way to communicate out. If you add anything private, it holds the whole lethal trifecta. You will design for that from the start, prove the design with an injection suite, and show, with an eval of at least 15 scenarios run several times each, how reliable the agent is and what each weekly run costs.

The default task uses **GitHub Issues on a public repository** through the REST API, read with a token scoped to that repository. If you'd rather not touch a live API, use the **fixture tracker** (JSON files of issues and comments) for everything, and build a second, richer fixture set as your "live" source. Either way, the agent must not know which source it is reading: that's the job of your MCP server.

Build it in its own repository (`pm-status-agent`).

Your first commit after the design doc should be the fixture format and eight scenarios with expected end states. Then build the MCP read tools and test them without any model. Your first model run is then a real baseline, logged with its cost, and every later change is a comparison against it.

## Pitfalls

<Callout type="pitfall" title="Pull requests, pages, and 'updated' versus 'opened'">
GitHub's issues endpoints return pull requests too (they carry a `pull_request` key), list endpoints return at most 100 items per page, and the `since` parameter filters by last update. Each of these produces a plausible but wrong report. Handle all three in server code, and give each its own scenario.
</Callout>

<Callout type="pitfall" title="Letting the model choose where things go">
If the model picks the channel, the recipients, or which links to include, an injected issue can pick them too. Fix destinations in configuration, post from application code after approval, and strip or block links to hosts you did not allowlist.
</Callout>

<Callout type="pitfall" title="An approval step nobody reads">
A reviewer who approves every draft in three seconds is not a control. Show the exact text with the issue numbers behind each line, flag what the guard removed, keep it to one decision per run, and track approval rate, edits, and rejections. Your guard must also be strong enough that a rubber-stamp reviewer cannot cause a leak; test that explicitly.
</Callout>

<Callout type="pitfall" title="Averaging safety into the score">
One trial that leaks data or posts to the wrong place is a failed release, however good the average is. Report violations by scenario id, gate on zero, and read every violating transcript.
</Callout>

<Callout type="pitfall" title="Evaluating on the live API">
Live data changes, rate limits bite (60 requests an hour unauthenticated, 5,000 with a token, per GitHub's docs), and you can't reset it between trials. Run the eval on fixtures, cache live responses during development, and use the live source for a final smoke test.
</Callout>

## Constraints

- Use the official SDKs for model calls and the official MCP SDK for your server, with keys and tokens in environment variables.
- The full eval (all scenarios, all trials) must run offline against fixtures, and the guard and scorer tests must run without an API key, using a scripted fake client as in lab 04.
- Keep a full eval run under $5 at current prices, and a single weekly run under a budget you state in the design doc. Log both, with the date of the prices you used.
- Never post to a channel, repository, or address other people use during development. Use a private test channel or a file-backed outbox.
