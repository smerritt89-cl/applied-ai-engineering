## The brief

Your team calls a frontier model to extract action items from meeting transcripts, and someone asks the question every AI team hears eventually: could a small model we fine-tune and host ourselves do this as well, for less? You are going to answer it with evidence.

You will fine-tune a small open model with LoRA (or QLoRA) on an extraction task, serve it, and benchmark it against two reference points: a frontier model through its API, and the same small model without your adapter. You will compare them on quality, cost per 1,000 tasks, and latency, on one frozen test set, with intervals. Then you will publish a model card for your adapter that tells the truth about what it does, how it was evaluated, and what the base model's license requires.

The deliverable is a **decision you can defend**, not a winning model. If the fine-tuned model matches the frontier model within your pre-registered margin at a third of the cost, say so. If it loses by 6 points, or if a cheap API model beats self-hosting at your volume, say that. Both are successful projects. What fails this project is a comparison that can't be trusted: a test set the model saw in training, systems scored on different inputs, failed outputs quietly dropped, or a margin chosen after the results came in.

Build it in its own repository (`small-model-extraction`), with the adapter in a separate model repository on the Hugging Face Hub if you publish it.

## What you get

- **The task, by default:** the Studio 1 action-item extraction (owner, due date phrase or resolved date, priority or another field you define, and an evidence quote), with your Studio 1 schema and verifier. Your Studio 1 samples are too few for training, so you need more transcripts: write and label your own, use meetings you have the right to use, or start from the AMI Meeting Corpus (CC BY 4.0, with attribution), whose transcripts are mostly scripted design-team meetings. Synthetic transcripts generated with a frontier model are fine for training, if you verify them and check that provider's terms (lesson 12).
- **Your own task instead,** if you prefer: any extraction with a fixed schema and fields you can score exactly, and data you are allowed to use.
- **Lab 04 (week 4)** gives you the benchmark scorer: fingerprint checks, per-field accuracy, exact match, bootstrap and paired intervals, cost per 1,000, latency percentiles, and a Markdown report. Reuse it.
- **Week 3's labs** give you the LoRA training loop; **lesson 11** gives you serving with vLLM, adapters, structured outputs, and the break-even calculator; **lesson 13** walks through the plan you write on day one.

<Callout type="tip" title="Freeze the test set on day one">
Before you generate a single training example, select the test meetings, label them, compute the fingerprint, and commit. Then write PLAN.md and commit that too. Every later step (training data, prompts, the adapter) can only be built from material that cannot leak into the test, and every result is judged by rules you set before you saw it.
</Callout>

## Pitfalls

<Callout type="pitfall" title="Test contamination">
The most common way this project goes wrong is a test set the fine-tuned model has effectively seen: test snippets from the same meetings as training snippets, synthetic examples seeded from test transcripts, or near-duplicates created by templated generation. The symptom is a fine-tuned model that beats the frontier model by a surprising margin. Split by meeting, build the test set first, keep its source documents out of every generation step, and run and report a similarity check anyway.
</Callout>

<Callout type="pitfall" title="Comparing systems on different prompts or inputs">
Each system may use its own best prompt (the adapter expects its training format; the frontier model does best with instructions and examples), but every system must see the same input text, produce the same schema, and be scored by the same code. Comparisons break when the frontier model gets extra context the small model doesn't, when one system's prompt is tuned on the test set, or when the base model is run with a different prompt or decoding constraint from the fine-tuned model, which makes the base-versus-tuned gap partly a prompt effect. Record every prompt version with its run, and serve base and fine-tuned models with identical settings.
</Callout>

<Callout type="pitfall" title="Dropping the failures">
Small models produce invalid JSON, truncated output, or empty replies more often than frontier models. If you score only the outputs that parsed, the weakest system looks best. Count every failure as wrong on every field, report the parse rate as its own column, and fix parse failures with constrained decoding (lesson 11), not by filtering them out.
</Callout>

<Callout type="pitfall" title="Cost numbers that assume a busy GPU">
A rented GPU bills by the hour whether or not requests arrive. Cost per 1,000 tasks computed from peak throughput assumes 100 percent utilization, which your traffic almost certainly won't deliver. State the utilization you expect, show how the cost changes across a range, and compare against the cheapest API model that passes, not only the frontier model.
</Callout>

## Constraints

- Use official SDKs for API calls, with keys in environment variables. Set a spending cap: the full frontier-model benchmark on a few hundred cases should cost a few dollars at most at current list prices. Log it and prove it.
- Rented GPU time should stay within a budget you state in PLAN.md. Shut instances down between sessions.
- The offline test suite (scoring, fingerprint checks, statistics, cost math, report rendering) must run without an API key or GPU, using recorded runs.
- Respect licenses: the base model's license for the adapter and its name, the dataset's license for anything you publish, and the API provider's terms for any outputs you train on.
