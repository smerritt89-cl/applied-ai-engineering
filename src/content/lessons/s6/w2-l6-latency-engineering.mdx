## What a wait is made of

A latency complaint is not one number. Four measurements name where a wait comes from:

- **Time to first token (TTFT):** from sending the request until the response starts. It covers the network, queueing, and reading whatever part of the prompt isn't cached.
- **Time to first visible output:** until the first text or tool call a person or program can use. When the model thinks first, this comes only after the thinking, so it can be many seconds after TTFT. Many people say "TTFT" when they mean this one, so check which your logs actually measure.
- **Time to finish:** until the response is complete. For an agent, the wait that matters is the whole task: every call in the loop plus everything between them.
- **Output speed (OTPS):** tokens per second between the first token and the last, thinking included.

Anthropic's latency cookbook ties these together with a first-order equation for a task:

> task time is about calls times TTFT, plus output tokens divided by output speed, plus everything outside the model

"Everything outside" means tool execution, network hops, queues, retries after rate limits, and your own processing. The equation gives you five ways to shorten a task: **fewer calls**, **shorter TTFT**, **fewer output tokens** (thinking included), **faster output**, and **less time outside the model**. It sets the order in which to look; only measurement says which lever wins on your workload.

Anthropic's own reducing-latency page adds a warning worth taping to your monitor: engineer a prompt that works well first, then reduce latency. Optimizing too early can stop you from discovering what top performance looks like.
</Listen>

## Output length is the main driver

Because output tokens are generated one at a time, their count usually dominates. OpenAI's latency guide puts the asymmetry in numbers: cutting output tokens by half may cut latency by about half, while cutting input tokens by half may improve it by only 1 to 5 percent. Anthropic's latency cookbook measured the input side directly on its sample agent: about a quarter of a second of TTFT per 100,000 extra input tokens.

The levers on output, roughly from least to most risky:

- **Shape the answer.** Ask for a specific format with an example ("two lines: decision, then reason"), or return structured fields instead of prose. In the cookbook, asking for a two-line decision format cut one decision from 46.4 seconds to 4.9, and its thinking tokens from 2,083 to 296. Anthropic's page also notes that asking for a number of sentences or paragraphs works better than a word count, because the model counts in tokens.
- **Remove commentary between tool calls**, where the agent narrates what it is about to do.
- **Lower effort** on routine routes. In the cookbook, `low` effort cut median task time by 13 percent with a small accuracy drop; `high` added 7 percent to the median and 12 percent to the p90.
- **Turn thinking off** where the model allows it. This is the steepest capability trade; in the cookbook's Haiku run, accuracy fell from 97.5 to 73.5 percent while the median wait fell only from 4.9 to 3.7 seconds.

Every one of these changes what the model writes, so each needs your eval before you keep it. A shorter answer that drops a required caveat is a regression, not an optimization.
</Listen>

## Streaming changes the wait people feel

Streaming sends the response as server-sent events while it is generated. It doesn't shorten time to finish, but for a person watching, it moves the felt wait from "until done" to "until the first useful words." Anthropic's latency page lists streaming as one of three core strategies, and OpenAI's guide calls it the most effective way to make users wait less.

Three details make streaming work in practice. **Thinking comes first.** On current Claude models the thinking display defaults to omitted, so a streamed response can show a long silence before text while the model reasons; you can request summarized thinking, or show a status line ("checking your order history...") driven by tool-call events. **Measure the right timestamps.** Log the time you sent the request, the `message_start` event (a client-side stand-in for TTFT), the first text delta (first visible output), and the end. **Keep the final message.** The SDK's streaming helper still gives you the complete message and its `usage` at the end, so you lose nothing for cost accounting.
</Listen>

```python
import time
import anthropic

client = anthropic.Anthropic()

def timed_stream(**params):
    sent = time.perf_counter()
    marks = {"ttft": None, "first_text": None}
    with client.messages.stream(**params) as stream:
        for event in stream:
            now = time.perf_counter() - sent
            if event.type == "message_start" and marks["ttft"] is None:
                marks["ttft"] = now
            elif (event.type == "content_block_delta" and event.delta.type == "text_delta"
                  and marks["first_text"] is None):
                marks["first_text"] = now
        message = stream.get_final_message()
    marks["total"] = time.perf_counter() - sent
    return message, marks   # log marks beside message.usage and the task id
```

## Fewer calls, and calls that overlap

The first term of the equation multiplies TTFT by the number of calls, and in an agent each call also adds the time spent between calls. Two families of fixes:

**Fewer calls.** Combine sequential steps into one prompt when the model can do them together. **Prefetch** what your application already knows the agent will need (the customer's account, the order) and put it in the first request instead of waiting for a tool call. Make list tools return more per page. In the cookbook, prefetching cut calls per task from 3.5 to 2.4 and median time by 13 percent; bigger pages cut it by 10 percent.

**Overlap the calls you keep.** Claude can request several tool calls in one turn. Run independent, read-only tools concurrently, and return all the results together in a single user message (splitting them across messages teaches the model to stop calling in parallel). Run independent subtasks as concurrent requests, each with its own model and effort: the cookbook's parallel Haiku subagents cut one task from 9.5 to 5.7 seconds with the same decisions. Two cautions: concurrency raises cost when each subtask rereads its own context, and parallel requests with identical prefixes don't share a cache until the first one has started responding, so fire one, wait for it to start streaming, then fire the rest.
</Listen>

```python
import asyncio
import anthropic

aclient = anthropic.AsyncAnthropic()

async def summarize(section: str) -> str:
    msg = await aclient.messages.create(
        model="claude-haiku-5-5",
        max_tokens=2000,
        output_config={"effort": "low"},
        messages=[{"role": "user", "content": f"Summarize in three bullet points:\n\n{section}"}],
    )
    return next((b.text for b in msg.content if b.type == "text"), "")

async def summarize_all(sections: list[str]) -> list[str]:
    # Independent subtasks: total time is roughly the slowest one, not the sum.
    return await asyncio.gather(*(summarize(s) for s in sections))
```

## Faster models, fast mode, and precomputation

**Smaller models** generate faster per token. The cookbook measured output speed on its workload at about 581 tokens per second for Haiku, 236 for Sonnet, and 153 for Opus. But per-task time is what matters, and it measured Sonnet's median task at 3.5 seconds and Haiku's at 4.0, because the smaller model wrote more tokens and accuracy fell. A faster model is not automatically a faster task, and switching models is a migration: re-run the eval.

**Fast mode** runs the same model with a faster inference configuration. Anthropic's docs list up to 2.5 times higher output tokens per second, focused on output speed rather than TTFT, on Claude Opus 5.5 (generally available) and a few other models, at a premium (8 and 40 dollars per million input and output tokens on Opus 5.5 at the time of writing, twice the standard rate). It has its own rate limit, isn't available with the Batch API, and requests at different speeds don't share cached prefixes, so falling back to standard speed on a 429 is also a cache miss. In the cookbook it cut median and p90 task time by 53 to 59 percent at every effort level, at roughly double the cost. When you report a paid lever like this, always show beside it what the no-cost changes achieved on their own.

**Precompute** whatever doesn't need to happen while the user waits. OpenAI's guide ends its list with "don't default to an LLM": hard-coded responses, precomputed outputs, and ordinary caching where they fit. In practice: generate summaries and classifications in a nightly batch job (half price, lesson 5) and serve them from your database; cache final answers in your own application keyed by a normalized input, with an expiry and an invalidation rule; and pre-warm the prompt cache before traffic arrives. Anthropic's caching docs describe sending a request with `max_tokens` set to 0, which writes the cache without generating output; the cookbook measured a first turn on a 146,000-token prompt falling from 1.0 to 0.8 seconds this way. Pre-warming costs a cache write, so it pays only when the first request's latency is user-visible and the prefix is large.
</Listen>

<Callout type="pitfall" title="Comparing against yesterday's number">
Service speed drifts by the hour, so a change measured today against a baseline measured last week tells you nothing. Time the current setup and the change **in the same run**, on the same tasks, interleaved (A, B, B, A), from a client in the same region as production, with the cache warmed the way production warms it. Run the baseline twice: the gap between its two runs is your noise floor, and a difference smaller than that is "can't tell," not "no change." And keep quality in the same table: a faster configuration that fails more tasks is slower per completed task.
</Callout>

## Measure percentiles, not averages

Latency distributions are skewed: most requests are quick and a few are very slow. The Google SRE book's chapter on service level objectives makes the case directly: an average can hide the tail and changes in it, while the median shows the typical case and high percentiles (the 99th, the 99.9th) show a plausible worst case. Report **p50, p95, and p99** (the values below which 50, 95, and 99 percent of requests fall).

The same chapter gives the vocabulary for targets. A **service level indicator** (SLI) is a carefully defined measure, such as the time to first visible output of chat responses. A **service level objective** (SLO) is a target for it, such as "99 percent of chat responses show text within 2 seconds." A **service level agreement** is a contract with consequences for missing an SLO. The chapter suggests stacking targets at several percentiles to capture the shape of the curve, which suits LLM features well: one target for the typical wait and one for the tail.

Two pieces of math matter. **Sample size:** the p99 of 100 samples is decided by the one or two largest values, so you need roughly ten observations beyond a percentile before it means much: on the order of 20 samples for p50, 200 for p95, and 1,000 for p99. Repeated runs of the same task don't count as new samples of your traffic. **Fan-out:** Dean and Barroso's "The Tail at Scale" (2013) argued that rare slow events, harmless in small systems, come to dominate as a request depends on more components. If each call in an agent has a 1 percent chance of being very slow, a task with 10 calls hits at least one slow call with probability 1 minus 0.99 to the 10th, about 9.6 percent. Agents turn a call-level p99 into a task-level p90. The paper's tail-tolerant techniques include hedged requests (sending a backup copy of a slow request); with LLMs a hedge bills a second attempt and must never duplicate a side effect, so reserve it for idempotent, read-only calls with high variance.
</Listen>

<GoDeeper title="Percentile definitions and confidence intervals">
There is more than one definition of a sample percentile. Nearest rank (used above) always returns an observed value; linear interpolation, the default in NumPy, returns a weighted average of the two values around the rank. On large samples they agree closely; on small samples they can differ noticeably, so state which one your dashboard uses and don't compare numbers computed different ways.

To say how sure you are of a percentile, bootstrap it (Efron, 1979): resample your measurements with replacement many times, compute the percentile on each resample, and take the middle 95 percent of those values as an interval. For comparing two configurations, resample paired tasks and look at the ratio. Anthropic's latency cookbook uses a bootstrap test of this kind and counts a change as real only when the difference clears it. Chip Huyen's *AI Engineering* (chapter 9) covers the serving-side picture: the inference metrics, and how batching and hardware choices trade throughput against per-request latency.
</GoDeeper>

## What to carry forward

Decompose the wait before you change anything: calls times TTFT, plus output over speed, plus time outside the model. Attack output first, with shapes, less commentary, and measured effort. Stream for people who watch, and log the right timestamps. Cut and overlap calls, precompute what can wait, and reserve fast mode for when the no-cost levers are exhausted, reporting its price beside its gain. Measure p50, p95, and p99 with enough samples, against an SLO, comparing within one run. Next week you'll put these measurements on a dashboard with tracing.
