## Launch is a decision you make with evidence

By now your system streams, retries, routes models by cost, emits traces, and sits behind guards you've measured. None of that answers the question your stakeholders will ask: is it ready? Google's SRE book includes a launch coordination checklist that covers architecture, capacity, failure and failover, monitoring, security, automation, external dependencies, and rollout planning. Its value isn't the specific questions; it's the habit of answering each one with evidence before launch, in writing, so the launch is a decision rather than a hope.

LLM features need that checklist plus a few items specific to models. The output is probabilistic, so "it works" means "the evals pass at a stated rate." The failures are often semantic, so an error-rate dashboard can be green while the feature says something harmful or wrong. A third party controls a critical dependency (the model), and it can change behavior, refuse, or be deprecated. And costs scale with usage in a way that can surprise you within hours.

The checklist below is what this studio has built toward. Each item names the evidence you attach. If you can't attach the evidence, the item isn't done.
</Listen>

```markdown
# Launch checklist: <feature name>    Owner: <name>    Target date: <date>

## Quality
- [ ] Offline evals pass the written gate on the held-out set (link to the run: metric, interval, n)
- [ ] Regression and red-team suites pass in CI on the release commit (link)
- [ ] Online eval ready: a calibrated grader runs on a sample of production traffic (sampling rate, judge version)

## Safety and security
- [ ] Guards measured on the red-team set: block rate and false-positive rate by category (link)
- [ ] Threat model reviewed: trust boundaries, OWASP LLM Top 10 walk, accepted risks with owners
- [ ] No secrets in prompts, code, or logs; secret scanning on; keys split by environment
- [ ] Model output escaped for every destination (HTML, SQL, shell, email)

## Reliability and operations
- [ ] Timeouts, retries with backoff, and a degraded mode when the provider is down (tested)
- [ ] Dashboards: latency p50 and p95, error rate, refusal rate, guard block rate, cost per request (link)
- [ ] Alerts with owners: error rate, latency, refusal or block-rate jumps, spend over budget
- [ ] Rollback is a config change: prompt, model id, guard config, and index versions behind flags (tested)
- [ ] Kill switch for the feature and for each tool with side effects (tested)

## Cost
- [ ] Cost per request and per active user measured; monthly projection at expected and 10x traffic
- [ ] Provider spend limits and per-user quotas set; alert at 50% and 80% of budget

## People
- [ ] Human escalation path in the product (how a user reaches a person, and how fast)
- [ ] On-call owner and runbook: how to disable, roll back, revoke keys, and who to call for privacy or legal
- [ ] Rollout plan: stages, success criteria per stage, and who decides to proceed
```

## Make rollback a config change

The most valuable item on that list is the one teams skip: rollback that takes seconds and needs no deploy. In an LLM system, behavior is determined by more than code. The prompt, the model id, the effort setting, the guard thresholds, the retrieval index version, and the tool list all change what users see. If any of them can only be changed by shipping code, your rollback is as slow as your deploy pipeline, at the moment you can least afford it.

So version all of them as configuration, record the active versions on every trace (week 3), and put them behind flags. A rollback then means pointing the flag at the previous version. Two details bite in practice. First, keep the previous model available: if you migrated because the old model is being deprecated, know its retirement date, because after it you can't roll back to it. Second, test the rollback before launch. A rollback path that has never been exercised is a hypothesis.

Pair rollback with **kill switches**: a flag that disables the whole feature (showing a static message or routing to a person) and a flag per tool with side effects. Mitigation in an incident is often "turn off the booking tool" rather than "turn off the assistant", and you want that to be one click, not a code change.
</Listen>

## Staged rollouts: shadow, canary, ramp

Don't move from zero users to all users. Common stages for an LLM feature:

**Internal use.** Your own team uses it on real work. You'll find embarrassing failures quickly and cheaply.

**Shadow mode.** The new version runs on real traffic, but users still see the old behavior (or nothing). You compare outputs offline with your graders. This is the safest way to test a new prompt or model on production inputs, at the cost of paying for two calls per request during the shadow period.

**Canary.** A small share of real users get the new version. Google's SRE workbook describes how to do this well: the canary must be large enough and run long enough to be representative, including peak load; compare canary against a control group running the old version at the same time, rather than comparing before and after (time of day and day of week confound that); break metrics down by population, because a bad canary hides in whole-service averages; prefer metrics tied to what users experience; and run one canary at a time so the signals don't mix.

**Ramp.** Increase the share in steps, with written success criteria at each step and a named person who decides whether to proceed. If canary metrics diverge from control, pause and roll back first, then investigate.

For LLM features, add semantic metrics to the canary comparison: online eval pass rate on sampled traffic, refusal rate, guard block rate, escalation-to-human rate, thumbs-down rate, and cost per conversation. Several of these move when quality changes even though nothing errors.
</Listen>

## A/B tests for AI features

A canary asks "is the new version broken?" An **A/B test** asks "is it better?" Both compare randomized groups at the same time, and the same discipline applies with a few additions.

**Randomize by user, not by request.** A user who gets a different assistant on every message has an incoherent experience, and their behavior in one arm contaminates the other.

**Choose one primary metric before you start**, tied to the outcome the feature exists for: tickets resolved without a human, tasks completed, time to answer. Then list **guardrail metrics** that must not get worse even if the primary metric improves: refusal rate, guard false-positive rate, escalations, cost per conversation, p95 latency, complaint rate. A variant that resolves more tickets by confidently inventing policies will show up in the guardrails long before it shows up in revenue.

**Size the test.** Decide the smallest effect worth detecting and estimate the sample size you need for it, using the interval reasoning from Studio 3. Small differences on noisy metrics take far more traffic than intuition suggests.

**Watch for novelty and learning effects.** Users react to anything new at first, and they adapt to a model's quirks over time. Run long enough to see past the first days.

**Use online evals alongside behavior.** Users' clicks tell you what they did; a calibrated grader on sampled traffic tells you whether the answers were right. You need both, because users often can't tell when an answer is wrong.
</Listen>

## When it goes wrong: AI-specific incidents

Your incident process can borrow almost everything from SRE practice. Google's workbook describes incident command roles (an **incident commander** who coordinates and holds any role not delegated, a **communications lead** who keeps stakeholders updated, and an **operations lead** who applies the fixes), and two rules worth memorizing: **declare early** (a managed incident resolves faster than an unmanaged one) and **mitigate first** (stop the impact before you understand the cause). Once several people are involved, keep a living incident document with the timeline, working theories, and what has been ruled out.

What's different for LLM systems is how incidents are detected and what mitigation looks like. Semantic failures don't raise errors, so they're often found by users, support staff, or social media. Refusals return HTTP 200, so error-rate alerts miss refusal spikes; track refusal rate on its own. And the causes include things outside your code: a provider model update, a change in the traffic mix, a newly indexed document, a new attack technique.

Five failure types cover most AI incidents. For each, have the mitigation built and tested before launch.
</Listen>

| Failure | How you find out | First mitigation (pre-built) | Follow-up |
|---|---|---|---|
| Harmful or offensive output | User report, output guard alerts, online eval on samples | Tighten the output guard for the route; disable the feature if needed | Add the inputs to red-team set; review guard thresholds and prompt |
| Data leak (another user's data, secrets, PII) | User report, output PII alerts, log scanning | Kill switch for the tool or feature; revoke and rotate any exposed key | Fix access control in code; involve privacy and legal; assess who was affected from traces |
| Runaway cost | Spend alert, cost-per-request dashboard, rate-limit hits | Lower quotas, cap loop iterations, route to a cheaper model, or pause the feature | Find the cause (abuse, a loop, a prompt that grew); add a budget test |
| Prompt injection exploited | Red-team or user report, unusual tool calls in traces | Disable the affected tool or data source; tighten scopes | Remove a leg of the lethal trifecta; add the attack to the regression set |
| Silent quality drop | Online eval pass rate, thumbs-down rate, escalation rate | Roll back the prompt, model, or index version by flag | Find what changed (including the provider's model); add failing cases to evals |

<Callout type="pitfall" title="An incident you can't measure">
The first questions in any LLM incident are "how many users saw this?" and "since when?". If your traces don't record the output (redacted), the guard decisions, and the active prompt, model, and index versions per request, you can't answer them, and the honest answer becomes "we don't know." Decide before launch what you log and for how long, redact personal data before it reaches the log store, and test that you can run the query "all conversations where this guard fired, last 7 days" in minutes.
</Callout>

## After the incident: postmortems that leave tests behind

Google's SRE book describes **blameless postmortems**: written records of an incident, its impact, the actions taken, the contributing causes, and follow-up actions, written on the assumption that everyone acted in good faith with the information they had. Blame makes people hide problems, so the focus is fixing systems and processes. It also recommends agreeing on triggers in advance, such as user-visible degradation past a threshold, any data loss, on-call intervention like a rollback, or a monitoring failure that meant a problem was found by hand.

For LLM incidents, add three items to every postmortem's action list. **A test:** the inputs that triggered the failure, and close variants, go into the eval set or the red-team set with the expected safe behavior, so the failure can't return silently. **A signal:** the monitor or alert that would have caught it sooner, whether an online eval, a guard alert, or a cost threshold. **A control:** the guard, access check, or limit that was missing or failed, with an owner and a date. Then rerun the full eval suite against the fix, because a fix for one failure often shifts behavior elsewhere.

Public incident collections, such as the AI Incident Database, are useful reading when you write your threat model: they show how real AI systems have failed in public, and which of those failures your own launch checklist would have caught.
</Listen>

<GoDeeper title="Incident response as a practiced skill">
Incident response is a skill teams practice, not a document they write once. PagerDuty publishes its incident response process openly, with pages on roles such as the incident commander and scribe, severity levels, and incident call etiquette, and it's a good template to adapt. The SRE workbook's incident response chapter includes case studies of incidents that went well and badly, including one where waiting to declare cost weeks. A useful exercise before launch: run a 30-minute tabletop drill where someone describes one of the five failure types above, and the team walks through who does what, which flag they flip, and how they find the affected users. Every gap you find in a drill is one you don't find at 9 p.m.
</GoDeeper>
