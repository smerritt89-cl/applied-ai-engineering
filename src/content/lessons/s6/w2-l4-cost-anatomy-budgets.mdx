## The unit is a completed task

Week 1 put your service into production. This week is about what it costs to run and how long people wait. Start with the unit of measure, because the wrong unit leads to the wrong decision.

Per-token prices are what the pricing page shows, and per-request cost is what a log line shows. Neither is what the business pays for. The business pays for **completed tasks**: a ticket resolved, a document summarized correctly, a pull request that passes review. Anthropic's cost guidance makes this its organizing idea: optimize cost per completed task, not per token. A model with a higher sticker price can be the cheaper choice if it finishes in fewer turns, and a cheaper model that fails still bills its tokens, then the retry, then whatever the failure costs downstream.

The definition is simple and worth writing down for your team:

> cost per completed task = total spend on all attempts, including retries and failed tasks, divided by the number of tasks that met the quality bar

Two consequences follow. First, you can't compute it without an outcome check. A log of tokens tells you spend; only your eval or a production signal (resolved, accepted, not reopened) tells you completion. Second, cost and quality become one number you can compare across configurations. Anthropic's published runs show why that matters: on one coding benchmark, Claude Sonnet 5.5 at high effort and Claude Opus 5.5 at low effort solved about the same share of tasks, with the Opus configuration costing about 7 percent more per solved task, even though Opus's per-token prices are twice Sonnet's. Per-token prices alone would have predicted a much bigger gap.
</Listen>

## Where the tokens go

Open any request your system sends and sort its tokens into six buckets. Each one has a different fix.

1. **System prompt.** Instructions, policies, examples. Stable across requests, so it is the natural thing to cache (lesson 5).
2. **Tool definitions.** Every schema you attach is input on every call. On top of your schemas, the API adds a tool-use system prompt whenever tools are present; the pricing page lists 286 tokens for the current Opus, Sonnet, and Haiku models with automatic tool choice. Small per request, large across millions.
3. **History.** The API is stateless, so a multi-turn conversation resends every earlier turn. This is the bucket that surprises people.
4. **Tool results.** Search hits, file contents, database rows. Sent once, then reread on every later turn of the loop.
5. **Thinking.** Reasoning tokens are billed as output tokens even when the thinking text isn't returned to you, according to Anthropic's thinking docs. A short visible answer can carry a long, invisible bill.
6. **Visible output.** The answer, plus any tool-call arguments the model writes.

The history bucket deserves a closer look, because it changes the shape of the cost curve. Suppose an agent's prefix (system prompt plus tools) is P tokens and each turn appends about d tokens (the model's reply and a tool result). Turn k sends P plus k times d. Over n turns the total input is n times P plus d times n(n minus 1)/2, which grows like n squared. Anthropic's cost guide says the same thing in words: a 40-turn task sends its first turn 40 times. Caching doesn't stop the resending, but it reprices the already-seen part at the cache-read rate, which is why caching is the largest single cost lever for agents.
</Listen>

## Measure from the usage fields, not from the text

Every Claude response carries a `usage` object, and it is the only ground truth for what a request cost. Four meters matter for pricing:

- `input_tokens`: input processed at the full price. With caching on, this is only the **uncached remainder** after the last cache breakpoint.
- `cache_creation_input_tokens`: input written to the cache this request, billed at a premium (1.25 times base input for the five-minute lifetime, 2 times for one hour). The `cache_creation` object splits it by lifetime.
- `cache_read_input_tokens`: input served from the cache, billed at a small fraction of base input (0.05 times on Opus 5.5 and Sonnet 5.5, 0.1 times on most other models, at the time of writing).
- `output_tokens`: everything the model generated, thinking included.

The prompt-caching docs give the identity to remember: total input equals the three input meters added together. If a dashboard charts `input_tokens` alone, a well-cached agent looks like it sends almost nothing.

Three habits make the numbers trustworthy. **Log every response's usage with a task id**, so you can roll requests up into tasks. **Price from a table with a "checked on" date**, kept in configuration, because prices change. **Reconcile monthly** against the provider's own numbers: Anthropic's Usage and Cost API (which needs an Admin API key) reports usage by model, workspace, API key, and service tier, and costs in USD, typically within about five minutes of a request completing. If your computed total and the provider's total disagree by more than rounding, something in your logging is wrong, and you want to know before finance does.

Other providers expose the same idea with different names. OpenAI reports cached input as `usage.input_tokens_details.cached_tokens`, for example. When you compare providers, normalize every response into one record shape first.
</Listen>

client = anthropic.Anthropic()

    response = client.messages.create(
        model="claude-sonnet-5-5",
        max_tokens=16000,

        messages=[{"role": "user", "content": question}],
    )
    u = response.usage
    log.append({
        "task_id": task_id,
        "model": response.model,
        "stop_reason": response.stop_reason,
        "usage": {
            "input_tokens": u.input_tokens,
            "cache_creation_input_tokens": u.cache_creation_input_tokens or 0,
            "cache_read_input_tokens": u.cache_read_input_tokens or 0,
            "output_tokens": u.output_tokens,
        },
    })
    return next((b.text for b in response.content if b.type == "text"), "")

<Callout type="pitfall" title="Using max_tokens as a cost control">
Lowering `max_tokens` feels like a budget, but the model never sees it. When a response hits the cap it is cut off mid-thought with `stop_reason: "max_tokens"`, the truncated tokens are still billed, and the task usually needs a retry. Anthropic's cost guide reports that raising the cap from 16,384 to 64,000 raised one model's solved tasks on an internal benchmark from about 20 percent to about 77 percent without raising cost per solved task. Treat `max_tokens` as a backstop against runaway output, and control length through the prompt (an output shape, an example) and the effort setting instead.
</Callout>

## Budgets and alerts, in layers

A budget is only useful if something enforces it and someone hears when it trips. Think in layers, each catching a different failure:

- **Per response: `max_tokens`.** A backstop against a runaway generation, set generously (the cost guide suggests 64,000 for agentic work, with streaming). It caps damage, not spend.
- **Per task: your own loop guard, plus an advisory budget.** In an agent loop, accumulate the cost of each response as it arrives and stop (or escalate to a person) when a task crosses a dollar limit you chose from the observed distribution, such as a multiple of the 95th percentile. Anthropic also offers task budgets in beta, which show the model a token budget so it can pace itself; the docs describe them as advisory, so keep your hard guard.
- **Per workspace or key: spend limits.** The Claude Console's workspace spend limit is the final backstop. Separate workspaces or API keys per product or environment are also what make spend attributable, because a shared key blends everyone's traffic.
- **Alerts on rates, not only totals.** A monthly total alert fires after the damage. Alert on cost per completed task, on the share of tasks hitting your per-task guard, and on the cache read fraction (lesson 5). Each of those moves within hours of a bad deploy.

The checks-and-balances habit applies here too. A budget guard is code that changes what users get, so test it: replay a logged runaway task and confirm the guard stops it, and confirm a normal task doesn't trip it.
</Listen>

TASK_BUDGET_USD = 0.50   # chosen from the logged distribution, roughly 3x the p95 task cost

def run_task(task_id, messages, log):
    spent = 0.0
    for turn in range(MAX_TURNS):

        record = to_record(task_id, response)    # the log shape from earlier

## Unit economics a product leader can defend

Engineering talks in cost per task. Finance and leadership talk in cost per user per month and gross margin. Your job, as the person who understands both, is to connect them without hiding the assumptions.

The core identity is multiplication: **cost per user per month = tasks per user per month times cost per completed task**, plus the costs that aren't tied to a user action (scheduled batch jobs, evaluation runs, retries of failed background work). Then compare it to what a user pays, or to the cost of the human process it replaces.

Three refinements separate a credible number from a slide that falls apart in the first question.

**Show the distribution, not just the mean.** Usage is usually skewed: a few heavy users run many more tasks than the median user, and some tasks are far more expensive than the median task. Anthropic's cost guide makes the task-level version of this point with a striking example, one research run where two problems out of twenty carried 43 percent of the spend. Price the tail. If your plan has a flat price, the heavy tail decides your margin.

**State the volume and mix assumptions.** Tasks per user, the share that hits the expensive path, cache hit rate, and which model each route uses. Each is a lever you can pull later, and each is a risk if it drifts.

**Attach a date and a sensitivity.** Prices change, and new models change the per-task cost (often downward, sometimes not). Show what happens to margin if cost per task rises 50 percent, or if heavy users double.
</Listen>

<GoDeeper title="Counting before you send, and pulling the provider's numbers">
**Before the request.** The token counting endpoint returns the input-token count for a request (system prompt, tools, images, PDFs) without running the model. The docs say it is free to use, with its own rate limits, and that the count is an estimate that can differ slightly from billing. Two uses in production: an ingestion gate (count an uploaded document, then truncate, summarize, or reject it before it hits the expensive path) and migration planning (count the same prompt under the old and new model, since the docs note that newer models use a tokenizer that produces roughly 30 percent more tokens for the same text than models before Claude Opus 4.7).

**After the fact.** The Usage and Cost API exposes `/v1/organizations/usage_report/messages` (token counts in 1-minute, 1-hour, or 1-day buckets, groupable by model, workspace, API key, service tier, and more) and `/v1/organizations/cost_report` (USD, daily). It needs an Admin API key, not a regular one. The docs mark these endpoints as legacy but supported and point new integrations to the newer Usage and Cost Analytics API, so check the current page before you build on either.

**Further reading.** Anthropic's cost optimization cookbook walks a full audit on a sample agent, and Chip Huyen's *AI Engineering* covers cost as part of the overall architecture and monitoring picture.
</GoDeeper>
