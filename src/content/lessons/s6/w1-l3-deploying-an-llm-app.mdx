## What an LLM workload asks of a host

A typical web request spends a few milliseconds of CPU and returns in under a second. An LLM request is different in three ways, and they decide which hosting options fit.

**It is long and mostly waiting.** A model call can take seconds to minutes, and almost all of that time your code is idle, waiting on the network. Platforms that bill or limit by CPU time treat that very differently from platforms that limit wall-clock time.

**It streams.** A chat reply is a response body that keeps arriving for tens of seconds. The host has to support streamed responses, and its limits have to count streaming time in a way you can live with.

**It carries a valuable secret.** The model API key can spend real money and, depending on its permissions, read your organization's data. It has to reach the server without ever touching the browser, the repository, or a log line.

This lesson looks at three common hosting shapes through those three lenses, with one documented example each: **serverless functions** (Vercel Functions), **edge workers** (Cloudflare Workers), and **containers** (Google Cloud Run). These are examples, not endorsements; many other hosts follow the same shapes, and the questions you ask of them are the same. The numbers below were checked against each platform's documentation on the review date. Limits change, so check them again when you deploy.
</Listen>

<Listen>
## Serverless functions: Vercel Functions as the example

A serverless function is code the platform runs on demand per request and scales automatically. You deploy a handler; the platform handles servers.

The limit that matters most is **maximum duration**. Vercel's limits page (with Fluid compute, the default for new projects) gives a default of 300 seconds on every plan; Hobby can't go higher, while Pro and Enterprise can configure up to 800 seconds, with a 1,800-second maximum in beta. The page is explicit that the duration includes time spent sending the response, **including streamed responses**, and that a function that runs out of time gets a 504 `FUNCTION_INVOCATION_TIMEOUT`. Functions on Vercel's separate Edge runtime have a different rule: they must begin sending a response within 25 seconds and can then stream for up to 300 seconds.

Two other details on that page are LLM-relevant. The 4.5 MB request and response body limit does not apply to streamed responses. And Vercel bills Functions by active CPU time plus provisioned memory time, where waiting for I/O, such as calling AI models, does not count toward active CPU time.

What this means for you: a five-minute ceiling, by default, on everything a request does, retries and fallbacks included. Short chat replies and extraction calls fit comfortably. A multi-step agent that sometimes runs for eight minutes does not, and should be a background job (lesson 1) regardless of host.
</Listen>

<Listen>
## Edge workers: Cloudflare Workers as the example

An edge worker runs your code in many locations close to users, in a lightweight runtime (JavaScript and related languages, with a restricted set of APIs). Cold starts are small and global latency is low, which makes workers popular for API gateways and proxies, including proxies in front of model APIs.

The surprise in Cloudflare's limits page is that the primary limit is **CPU time**, not wall-clock time: 10 milliseconds per HTTP request on the Free plan, and on Paid a default of 30 seconds that you can raise to 5 minutes. The docs state that waiting on network requests does not count toward CPU time, and that there is no hard limit on duration for HTTP-triggered Workers: as long as the client stays connected, the Worker can keep processing and streaming. A Worker that forwards a model stream does very little computation per chunk, so it can stream a long reply while using little CPU.

Two cautions. First, the docs warn that when the client disconnects, tasks associated with that request may be canceled, so work that must finish after the user closes the tab (logging, billing records) needs `ctx.waitUntil()`, which the docs say can run for up to 30 seconds after the response is sent or the client disconnects, or a queue. Second, the runtime is not a general server: heavy Python dependencies, long-running loops, and background workers belong elsewhere.
</Listen>

<Listen>
## Containers: Google Cloud Run as the example

A container platform runs your own image, so you choose the language, the libraries, and the server (the lab's FastAPI app with uvicorn, for instance). Cloud Run scales containers per request, down to zero when idle.

Its request limit is a **request timeout**: Cloud Run's docs give a default of 300 seconds, configurable up to 3,600 seconds (60 minutes), with a 504 when a service doesn't respond within the limit. The page describes the timeout as the time a service has to return a response and does not single out streaming, so measure a long stream against your configured timeout before you rely on it.

Containers fit when you need control: a Python service with dependencies that won't fit a function, long agent runs, a worker process that drains a queue, or the same image running locally, in CI, and in production. The trade is more to own: the image, its base-layer patches, its health checks, its concurrency settings.
</Listen>

<Callout type="pitfall" title="The platform limit is shorter than your SDK timeout">
The Anthropic SDKs default to a 10-minute request timeout, retried twice. Every platform default in the table above is shorter. If you deploy SDK defaults, a slow or hung call outlives the function: the platform kills the request with its own 504, and your retries, fallbacks, degraded message, and log line never run. Timeouts must nest, each with margin: **SDK attempt timeout, inside your request deadline, inside the platform's limit.** For a chat endpoint on a 300-second platform, something like a 20-second attempt timeout and a 60-second deadline leaves plenty of room. For longer work, move it to a background job instead of raising every limit.
</Callout>

## Secrets: where the key lives

The Twelve-Factor App's rule is the usual starting point: config, including credentials, varies between deploys and belongs in the environment, not the code; its test is whether you could open-source the repository right now without leaking a credential. OWASP's Secrets Management Cheat Sheet adds the caveats: centralize secrets in a managed store, rotate them, scope each one to what needs it, keep them out of source code, Docker images, and CI logs, scan for leaks, and remember that environment variables are visible to every process and can end up in logs and crash dumps.

Each example platform has a secret store that injects values at runtime. Vercel environment variables are encrypted at rest and can be typed as Config or Secret, where Secret values are write-only after saving; changes apply only to new deployments. Cloudflare secrets are set with `wrangler secret put`, hidden after creation, and read from the Worker's `env` binding, with a `.dev.vars` or `.env` file (git-ignored) for local development. Cloud Run reads from Google Secret Manager, either as an environment variable resolved when the instance starts (the docs recommend pinning a version) or as a mounted volume read at access time, which suits rotation.

On the Anthropic side, the authentication docs recommend storing keys in a secrets manager, rotating them, and disabling any key you suspect has leaked. They distinguish personal keys (for your own development) from **service account keys** (for shared and production workloads, so the key doesn't break when a person leaves), let you set an **expiration** when you create a key, and describe **Workload Identity Federation** for production workloads on cloud platforms: the service exchanges its cloud identity for a short-lived token, so there is no long-lived API key to leak at all. Prefer federation where your platform supports it, and a scoped service account key from a secret store where it doesn't.
</Listen>

<Listen>
## Environments: development, preview, production

Most teams run at least three environments: **development** on a laptop, **preview** or staging deployments for each branch or pull request, and **production**. Vercel, for example, scopes each environment variable to Production, Preview, Development, or custom environments. For an LLM service, separating them is about more than databases.

**Separate keys and spend.** Give each environment its own API key, ideally in its own Anthropic workspace. The rate-limits docs describe per-workspace spend and rate limits below the organization's, so a runaway preview deployment or a load test can't consume production's rate limit or budget. A preview build should never hold the production key: preview deployments often run code that hasn't been reviewed yet.

**Model ids are config, and changing them is a deploy.** Pin exact model ids per environment in reviewed configuration, keep an allowlist of models you've evaluated, and promote a model change the way you promote code: run the Studio 3 eval and regression gate in preview, then ship. A model swap that arrives through an unreviewed environment-variable edit is a behavior change nobody tested.

**Same image, different config.** Build once and promote the same artifact from preview to production, changing only configuration. That is what makes "it worked in staging" mean something.

**Know which environment answered.** Log the environment, model id, and deploy version with every request (week 3 builds this into traces), so an incident review can tell a preview experiment from production traffic.
</Listen>

## Choosing a host: a heuristic

Start from measurements, not from a favorite platform. Take a few hundred realistic requests (your eval set is a good source), log their end-to-end durations including retries, and look at the slow end, not the average. Then ask, in order:

**Does any request need longer than a few minutes?** Then that work is a background job with a queue and a worker, whatever else you choose. Workers usually run best in containers, where you control the process lifetime.

**Is the service mostly a thin layer over model calls, next to a web front end?** Serverless functions are the low-effort default: deploys tied to your repository, per-branch previews with their own environment variables, and streaming support. Check that your 99th-percentile duration, plus a margin, sits well inside the function's duration limit.

**Is it a global gateway or proxy with little computation?** An edge worker's CPU-time model suits it: forwarding a stream costs little CPU. Make sure work that must finish after a disconnect (usage records, logs) is handed to `waitUntil` or a queue.

**Do you need Python libraries, long runs, custom servers, or the same image everywhere?** Use containers, and accept the operational work that comes with them.

Most products end up with two of these: a function or container serving the request path, and a container worker draining a queue. And whatever you pick, a host's limits are a moving target. Record the limits you depend on in your deploy configuration (the `platform_max_duration` above), so the preflight check fails loudly if someone changes the plan or the platform.

## The deploy checklist

Run through this list before the first release, and automate what you can in CI.

**Secrets.** The API key comes from the platform's secret store or federation, never the repository or the image. No public-prefixed variable holds anything secret, and your built client assets contain no `sk-ant` string. Each environment has its own key, in its own workspace with its own spend and rate limits. Keys have an owner (a service account), an expiration or rotation plan, and a revocation runbook.

**Timeouts and retries.** SDK attempt timeout, inside the request deadline, inside the platform limit, each with margin. Retries in exactly one layer. Streams enforce a total deadline.

**Failure handling.** Errors are classified; breakers per model; a fallback chain whose quality you've measured; a degraded mode you have exercised on purpose.

**Models and prompts.** Model ids pinned per environment and on an evaluated allowlist; the eval and regression gate passed on this build.

**Streaming.** Streaming verified end to end on the real platform, through any proxy or CDN in front of it, with a reply longer than your longest expected one.

**Observability.** Each request logs environment, deploy version, model actually used, token usage, latency, the API's `request-id`, and whether a fallback or degraded mode ran (week 3 turns this into traces and dashboards).

**Abuse and limits.** Per-user rate limits and input size limits at the edge of your service; the OWASP LLM Top 10 review (week 4) scheduled before you widen access.

**Rollback.** You know how to return to the previous deploy, and a model or prompt change can be rolled back the same way as code.
</Listen>

<GoDeeper title="Rolling out changes to an LLM service">
Code, prompts, and model ids all change behavior, and an LLM service has fewer guarantees than most that a change which passed tests behaves the same on real traffic. Three practices from conventional release engineering carry over well. **Canary releases**: send a small share of production traffic to the new version and compare its error rate, latency, cost per request, and online quality signals (week 3) with the old version before widening. **Shadow traffic**: run the new prompt or model on a copy of real requests without showing users the result, then score both outputs with your Studio 3 graders. **Fast rollback**: keep the previous version deployable and its configuration intact, so undoing a bad model swap is one action, not a debugging session. Some platforms build parts of this in (Cloudflare's secrets docs, for instance, describe separate commands for gradual deployments of Worker versions), but the decision rule is yours: define in advance which metric movements stop a rollout.
</GoDeeper>

## Week 1 in one paragraph

Put the model call on your server, and pick the request shape from the task: synchronous for short machine-facing work, streaming for a person watching, background jobs for long work, batch for work that can wait. Classify failures, retry only transient ones at one layer with jittered backoff inside a deadline, break circuits on dead dependencies, fall back to models whose quality you've measured, and degrade on purpose. Deploy where the platform's limits contain your deadlines with room to spare, keep secrets in secret stores and out of browsers, separate environments down to the API key, and gate every release on checks a machine runs. Next week is about making all of this cheaper and faster: caching, batching, routing, and budgets.
</Listen>
