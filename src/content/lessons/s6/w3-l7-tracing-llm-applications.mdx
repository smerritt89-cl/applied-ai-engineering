## Why logs stop being enough

In Studio 1 a request was one model call, and one log line per call told you most of what you needed. The systems you've built since are not like that. A RAG answer is retrieval, maybe reranking, a model call, and a citation check. An agent is a loop: model call, tool call, model call, tool call, until it stops. A single user request can become a dozen operations across your code, a model provider, and a few tools.

When that request is slow, wrong, or expensive, the question you need answered is about the **request**, not any single call. Which step took the time? Which tool returned the bad data? How many model calls did the agent make, and why so many? Separate log lines can hold all the facts and still make these questions slow to answer, because nothing ties the lines of one request together or says which step caused which.

**Tracing** is the standard answer from distributed systems. Every request gets an identifier, every step records its start, end, and outcome under that identifier, and each step points to the step that called it. The result is a tree you can read like a timeline. For LLM systems tracing has a second payoff: the traces you collect are the raw material for error analysis and evals (Studio 3). Hamel Husain and Shreya Shankar's evals FAQ puts reading real traces at the center of error analysis, and you can only read what you recorded.
</Listen>

## Traces and spans, precisely

OpenTelemetry (OTel), the vendor-neutral observability standard that most tools now speak, defines the vocabulary.

A **span** is one unit of work: a model call, a tool call, a database query, a whole request. It has a name, a start and end time, **attributes** (key-value metadata such as the model id or token counts), optional **events** (timestamped notes, such as an exception), a **status** (Unset, Ok, or Error), and a **kind** (Client for an outgoing call, Server for an incoming one, Internal for in-process work, plus Producer and Consumer for queued work).

A **trace** is all the spans that share one **trace id**. Each span also has its own **span id** and the id of its **parent**; the span with no parent is the **root**. Together, the trace id and span id form the **span context**, which is what gets passed along when one service calls another, so that the callee's spans join the caller's trace. Across HTTP this travels in the W3C `traceparent` header.

Two consequences matter in practice. First, durations nest: a parent's duration includes its children, so you find where time went by looking for the child with the largest share, and the parent's **self time** (its duration minus its children) is time spent in your own code. Second, the trace id is a join key. Put it on every log record, every eval result, and every user-feedback event, and you can move from a bad thumbs-down to the exact trace that produced it.
</Listen>

## What to record on every model call

The test for a field is simple: will you filter, group, or alert on it, or will you need it to reproduce a problem? For a model call, these pass the test.

- **Model requested and model returned.** They can differ (aliases, fallbacks, provider routing). When quality shifts, the first question is whether the model changed.
- **Prompt name and version.** Your prompts are code; a version string on every call is what lets you say "quality dropped when triage-v4 shipped." Without it, a regression is a mystery.
- **Tokens**, split by kind: uncached input, cache reads, cache writes, and output, plus reasoning tokens where the provider reports them. Claude's usage object reports `input_tokens` separately from `cache_read_input_tokens` and `cache_creation_input_tokens`, and each kind has its own price.
- **Latency**: total duration, plus time to first token for streamed calls, because that's what a user feels.
- **Cost**, computed by your code from tokens and a versioned price table. Providers don't put a price on each response, and prices change, so the table belongs in version control.
- **Finish reason** (`end_turn`, `max_tokens`, `tool_use`, `refusal` on Claude; other providers use other names). Truncations and refusals are failures that return HTTP 200.
- **Tool calls**: the tool name and outcome on a child span, with arguments only if your privacy rules allow (lesson 8).
- **Errors**: a low-cardinality error type (such as `rate_limit_error` or a timeout), and Error status on the span.
- **Context ids**: trace id, a pseudonymous user or session id, the feature or route, and the experiment arm if you're running one.

Notice what's missing: the prompt and response text. That's a deliberate default, and the next section explains it.
</Listen>

## The GenAI semantic conventions

If every team invents its own attribute names, every tool has to be told what `llm_model` or `modelName` means. OpenTelemetry's **semantic conventions** fix the names. For generative AI they define, among others:

- An inference span named `{gen_ai.operation.name} {gen_ai.request.model}`, such as `chat claude-opus-5-5`, with kind Client.
- Required `gen_ai.operation.name` and `gen_ai.provider.name`; `gen_ai.request.model`, `gen_ai.response.model`, `gen_ai.response.finish_reasons`, `gen_ai.usage.input_tokens`, and `gen_ai.usage.output_tokens` as recommended attributes; `gen_ai.prompt.name` and `gen_ai.prompt.version` for named templates; `error.type` when the call fails.
- A tool span named `execute_tool {gen_ai.tool.name}`, with kind Internal, and agent spans such as `invoke_agent`.

One detail bites people. The conventions define `gen_ai.usage.input_tokens` to include cached tokens, and record cache reads and writes in separate attributes as well. Claude's own `usage.input_tokens` counts only uncached input. If you copy the provider's field straight into the convention's attribute, every cache hit makes your input counts look smaller than they are.

**Status, verified for this lesson.** The GenAI conventions are marked **Development**, OpenTelemetry's label for conventions that may still change in breaking ways. In June 2026, release v1.42.0 of the core semantic conventions deprecated all `gen_ai.*` definitions there and moved them to a dedicated repository, `semantic-conventions-genai`; the old pages on opentelemetry.io now point to it. Names are still moving: a 2026 OpenTelemetry blog post charts `gen_ai.client.operation.duration`, while the current spec says inference calls should report `gen_ai.client.inference.duration` instead. Treat the names as a versioned dependency: pin your instrumentation and convention versions, and re-test the dashboards and alerts that query them when you upgrade.
</Listen>

<Callout type="pitfall" title="Content capture is opt-in for a reason">
The conventions include attributes for the full conversation (`gen_ai.system_instructions`, `gen_ai.input.messages`, `gen_ai.output.messages`), and the spec warns that they are likely to contain sensitive information including personal data. Instrumentations SHOULD NOT capture them by default. The spec lists three patterns: don't record content (the default); record it on spans (suited to pre-production, or when the telemetry store meets your privacy rules); or store it externally and put only a reference on the span, which it recommends for production because the content store can have its own access controls. Turning on a "capture prompts" flag sends every customer message to your tracing vendor, under that vendor's retention. Decide that on purpose (lesson 8).
</Callout>

Here is a hand-instrumented Claude call using the OpenTelemetry Python API. With only `opentelemetry-api` installed these calls are no-ops; register a tracer provider from `opentelemetry-sdk` to export the spans.

```python
from anthropic import Anthropic
from opentelemetry import trace
from opentelemetry.trace import Status, StatusCode

tracer = trace.get_tracer("support-desk")
client = Anthropic()
PROMPT_VERSION = "reply-v7"

def draft_reply(ticket: str) -> str:
    model = "claude-opus-5-5"
    with tracer.start_as_current_span(f"chat {model}") as span:
        span.set_attribute("gen_ai.operation.name", "chat")
        span.set_attribute("gen_ai.provider.name", "anthropic")
        span.set_attribute("gen_ai.request.model", model)
        span.set_attribute("gen_ai.prompt.name", "reply")
        span.set_attribute("gen_ai.prompt.version", PROMPT_VERSION)
        try:
            response = client.messages.create(
                model=model,
                max_tokens=4096,
                system="You draft short, polite replies for a human agent to review.",
                messages=[{"role": "user", "content": ticket}],
            )
        except Exception as exc:
            span.set_attribute("error.type", type(exc).__name__)
            span.record_exception(exc)
            span.set_status(Status(StatusCode.ERROR))
            raise
        u = response.usage
        cache_read = u.cache_read_input_tokens or 0
        cache_write = u.cache_creation_input_tokens or 0
        span.set_attribute("gen_ai.response.model", response.model)
        span.set_attribute("gen_ai.response.finish_reasons", [response.stop_reason])
        # The convention counts cached tokens as input; Claude's input_tokens does not.
        span.set_attribute("gen_ai.usage.input_tokens", u.input_tokens + cache_read + cache_write)
        span.set_attribute("gen_ai.usage.output_tokens", u.output_tokens)
        return "".join(b.text for b in response.content if b.type == "text")
```

## Claude traces itself, and how not to count twice

You may not need to write that wrapper for every call. Anthropic's SDKs and the Claude API can emit OpenTelemetry spans themselves; the feature is in **beta** at the time of writing, so its span names and options can change. There are two halves. **SDK tracing** runs in your process and exports through your own OpenTelemetry setup: register a tracer provider and the SDK's spans appear, nested under whatever span is current. **API tracing** is emitted by Anthropic's servers and delivered to an OTLP endpoint that an organization admin configures; it can see things your process can't, such as each model request inside one API call and the server tools the API ran. Both use the GenAI attribute names, so backends that understand the conventions read them without mapping.

Two of Anthropic's design choices are worth copying in your own instrumentation. Content is off by default: the default mode is "metadata only" (ids, timing, status, token counts), and "full content" is a deliberate switch whose docs remind you that your backend then stores prompts under its own access and retention settings. And the docs spell out how to **count tokens once**. A request traced by both halves has an SDK span (kind Client) and an API span (kind Server) with the same name and overlapping usage; sum one source per request, not every span that carries a token count. The same trap appears when you wrap an SDK-traced call in your own `chat` span: decide which span is the source of truth for cost, and make your dashboard query only that.

Other providers have their own instrumentation, often as OpenTelemetry instrumentation libraries that patch the provider's SDK. Check each provider's current docs, and check that you don't run a patching library and the SDK's built-in tracing at the same time, or every call appears twice.
</Listen>

## Tracing agents

Agents make tracing essential rather than nice to have. The semantic conventions model an agent run as an `invoke_agent` span whose children are `chat` spans for model calls and `execute_tool` spans for tool calls, and the OpenTelemetry team's 2026 walkthrough shows exactly that tree. Three agent questions become easy once you have it. How many iterations did the loop take, and is that number creeping up release over release? Which tool fails or times out most, and does the agent recover or spiral? Where did the context grow: a trace with per-call input tokens shows the moment a large tool result entered the conversation and every later call paid for it.

Record tool spans even for tools that "can't fail." An agent that called the same search tool eight times with slightly different queries is a prompt or tool-description problem, and it looks like nothing at all in a dashboard of model calls alone.
</Listen>

## Choosing a tracing tool

You need somewhere to send spans and a way to read them. The choice is less risky than it used to be, because the major LLM tracing tools accept OpenTelemetry data, so instrumentation you write against the OTel API isn't locked to one of them. A few, described from their own documentation:

- **Langfuse** is an open-source platform you can self-host or use as a cloud service. Its data model is traces made of nested observations, plus scores for quality, and it runs evaluations, including LLM-as-judge, on production traces. It accepts OTLP.
- **Arize Phoenix** is an open-source observability and evaluation tool built on OpenTelemetry and the OpenInference instrumentation. It covers tracing, evaluations with LLM, code, or human graders, datasets and experiments for comparing versions, and prompt management. Arize also sells a separate managed platform (Arize AX).
- **LangSmith**, from LangChain, works with many frameworks and providers, not only LangChain. It offers dashboards and alerts, online evaluations, and annotation queues for human feedback, with cloud, hybrid, and self-hosted deployment options.
- **Your existing backend.** Anthropic's docs list many general observability platforms (Datadog, Grafana Cloud, Honeycomb, New Relic, Sentry, and others) that accept these spans over OTLP. If your company already runs one, LLM spans next to your HTTP and database spans is a real advantage.

Decide the way you'd decide on a model: with your own data. Send a week of real traces (with content policy settled first) to two candidates and check what matters to your team: can a reviewer read a full agent trace comfortably, can you filter by prompt version and join user feedback, where is the data stored and for how long, can you self-host if your privacy rules require it, and what does it cost at your span volume.
</Listen>

<GoDeeper title="Sampling: you may not keep every trace">
At high volume, storing every trace is expensive, so tracing systems **sample**. OpenTelemetry distinguishes **head sampling**, decided when the trace starts (for example, keep 5 percent of trace ids), from **tail sampling**, decided after seeing most or all of the trace's spans, which can implement rules like "keep every trace with an error or with latency above two seconds." The OTel docs note that head sampling alone can't guarantee you keep every error trace, and that tail sampling is harder to run: it needs stateful components that buffer large volumes, its rules need maintenance, and good options are often vendor-specific.

For LLM systems, two extra considerations. Traffic is usually lower-volume and higher-value per request than typical web traffic, so keeping everything (metadata only) is often affordable, and it makes cost accounting exact. And your online evals and review queues (lesson 9) need a **random** sample that is independent of errors and latency. If you tail-sample "interesting" traces into storage, keep a separate uniform sample, or your quality estimates will be biased toward failures. Also note what Anthropic's docs say about exported spans: delivery is best effort, so for billing-grade usage numbers use the provider's usage and cost reporting, not a sum over spans.
</GoDeeper>

## What a working team does

Put a root span on every request at the edge of your service, and pass the trace id into every log record and eval result. Record the fields above on every model and tool call, with prompt versions as a first-class attribute. Keep content off spans by default, and settle your content policy before you turn it on. Pick one span type as the source of truth for tokens and cost. Pin your instrumentation versions, because the conventions are still in development. Then use the traces: the next two lessons turn them into logs you can keep safely, and into dashboards, alerts, and online evals that tell you when the system needs a person.
</Listen>
