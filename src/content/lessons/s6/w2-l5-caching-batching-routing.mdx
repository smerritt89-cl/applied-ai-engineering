## Free wins first, trades second

Anthropic's cost guidance sorts every cost lever into two groups, and the order matters. **Free wins** lower what you pay without lowering output quality: prompt caching (usually the largest), trimming input, and batch processing. **Tradeoffs** exchange capability for cost: effort, model choice, and multi-model designs such as routers and cascades. Do the free wins first and leave caching on permanently. Pull the trades last, one at a time, against an eval, because each one can quietly cost you answers.

This lesson follows that order. It spends the most time on caching, because caching is where most teams lose money without noticing, and it ends with routing, because routing is where most teams spend engineering effort before measuring whether a simpler option would do.
</Listen>

## Caching is a prefix match

When you mark part of a request with `cache_control`, the API stores the processed prefix up to that point. A later request whose prompt starts with **exactly the same bytes** up to that point reads the stored prefix instead of processing it again. Three rules govern everything else.

**Render order is tools, then system, then messages.** The cache key covers everything before a breakpoint in that order. A breakpoint on the last system block therefore caches your tool definitions and system prompt together.

**Any byte change invalidates everything after it.** A different timestamp, a reordered JSON key, one extra tool: the prefix no longer matches from that point on. The docs' invalidation table adds settings to the list. Changing tool definitions invalidates the whole cache; changing `tool_choice` or adding an image invalidates the message part; changing thinking or effort settings always invalidates the message part; and requests at different speeds (fast mode versus standard) don't share cached prefixes. Caches are also scoped per model, and isolated per workspace on the Claude API.

**Small prefixes don't cache, silently.** Each model has a minimum cacheable length (512 tokens on the current Opus, Sonnet, and Haiku models, per the caching docs at the time of writing). Below it, the request runs uncached with no error, and both cache meters read zero.

Mechanically you have two ways to mark the cache. **Automatic caching** is a top-level `cache_control` field; the API places the breakpoint on the last cacheable block and moves it forward as a conversation grows. **Explicit breakpoints** go on specific content blocks, up to four per request. Use explicit breakpoints when the end of the prompt is unique per request (a one-off question, retrieved rows): put the marker at the end of the **shared** part, or every request writes an entry nobody reads.
</Listen>

```python
import anthropic

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=16000,
    system=[
        {"type": "text", "text": SUPPORT_INSTRUCTIONS},
        # Breakpoint at the end of the shared part: tools + instructions + policy manual.
        {"type": "text", "text": POLICY_MANUAL, "cache_control": {"type": "ephemeral"}},
    ],
    messages=[
        # Varies per request, so it sits after the breakpoint.
        {"role": "user", "content": f"Today is {today}. Customer question: {question}"},
    ],
)

u = response.usage
total_input = u.input_tokens + (u.cache_creation_input_tokens or 0) + (u.cache_read_input_tokens or 0)
print("read from cache:", (u.cache_read_input_tokens or 0) / total_input)
```

## Lifetimes and the break-even

The default cache entry lives for **five minutes**, and every read refreshes it at no extra cost. A **one-hour** lifetime is available with `"ttl": "1h"`. The lifetime is measured from the start of the request that writes or reads the entry, so a long generation eats into it.

The prices make the decision arithmetic. On Claude, a five-minute write costs 1.25 times the base input price and a one-hour write costs 2 times. A read costs 0.05 times base on Opus 5.5 and Sonnet 5.5 and 0.1 times on most other models, at the time of writing. So a five-minute entry pays for itself the first time it is read (1.25 plus a read is less than 2 full-price sends), and a one-hour entry needs two reads.

Which lifetime to pick depends on the **gaps between requests that share a prefix**, not on their average. If requests start less than five minutes apart, each one refreshes the five-minute entry and it stays warm indefinitely, so the one-hour lifetime buys nothing but a pricier write. If gaps of five to sixty minutes are common (a user who replies after twenty minutes, a batch job that takes longer than five minutes), the one-hour entry avoids repeated writes. Anthropic's cost guide offers a rule of thumb: prefer the one-hour lifetime when about one gap in twenty falls between five minutes and an hour. Beyond an hour, neither helps; you either re-warm on a schedule or accept the cold miss.

Caching also helps latency, though less than cost on short prompts. Anthropic's latency cookbook measured caching cutting cost per task by 85 percent on its sample agent with no significant change in wait, while on a two-turn conversation with a 146,000-token prompt the second turn's wait fell from 1.7 seconds to 0.5. Long prefixes are where caching shows up in seconds.

<Callout type="pitfall" title="Silent invalidators">
Caching failures don't raise errors; requests succeed and the bill is just higher. Grep the code that builds your prompt prefix for these: `datetime.now()` or a request id in the system prompt; `json.dumps` without `sort_keys=True` (or iterating a set) when serializing context; a per-user tool list (tools render first, so nothing caches across users); conditional system sections that create a different prefix for every flag combination; switching model, speed, or top-level effort mid-conversation; and fanning out many identical requests at once (a cache entry becomes readable only after the first response starts, so parallel twins all pay full price; send one, wait for it to start streaming, then send the rest). The fix for the first group is always the same: move the dynamic piece after the last breakpoint, make it deterministic, or delete it. Then add a standing test that a second identical request shows `cache_read_input_tokens` above zero.
</Callout>

## Batch: half price for work nobody is waiting on

The Message Batches API takes a list of ordinary Messages requests, processes them asynchronously, and bills every token at 50 percent of the standard price, according to Anthropic's pricing page. The discount stacks with caching discounts. The docs give the operating envelope: up to 100,000 requests or 256 MB per batch, most batches complete within an hour, and anything not finished in 24 hours expires. Results stay downloadable for 29 days.

Batch fits evaluation runs, backfills, nightly classification or enrichment, and report generation: anything where a person isn't waiting on one item. It doesn't fit chat, agent loops (a batch request is single-shot, so there is no tool loop inside it), or fast mode and streaming, which the batch docs list as unsupported.

Three engineering details catch teams out. **Results arrive in any order**, so key them by `custom_id`, never by position. **Each result has its own status** (succeeded, errored, canceled, expired), so a batch that "ended" can still contain failures you must retry or report. **Caching inside a batch is best-effort**: requests run concurrently, so not every request can read what another wrote. Because batches can run longer than five minutes, the batch docs suggest the one-hour lifetime when many requests share a prefix.
</Listen>

## Effort: the first trade

Effort (`output_config.effort`) tells the model how much work to put in: how deeply to think and how many tool calls to make. Current Claude models accept `low`, `medium`, `high`, `xhigh`, and `max`. Defaults differ by model, which is a trap when you migrate: Opus 5.5 and Haiku 5.5 default to `medium`, while Sonnet 5.5 defaults to `high`. Set it explicitly per route.

Effort is a real trade, so measure it. Anthropic's published runs of Opus 5.5 on a coding benchmark show the shape: `low` solved 87.4 percent at about $0.11 per task, `medium` 92.8 percent at $0.21, `high` 95.3 percent at $0.29, and `xhigh` 96.7 percent at $0.74. On research and knowledge work the guide reports much flatter curves, where lower effort gives up little. Your curve belongs to your workload.

When you have a cheap failure signal (tests, a validator, a checker), a useful pattern is to **run everything at low effort and re-run only the failures at a higher one**. In the same published runs this reached about 97 percent solved for about $0.17 per task, against 95.3 percent for $0.29 running everything at `high`. Two caveats: price in the checker and the extra wall-clock time on failures, and sweep each effort level in a separate session, because changing top-level effort mid-conversation invalidates the message cache.
</Listen>

## Routing and cascades, and the simpler thing to try first

A **router** sends each request to one of several models based on a prediction of difficulty. A **cascade** tries a cheap model first and escalates to a stronger one when a check fails. Both have research behind them. Chen, Zaharia, and Zou's FrugalGPT (2023) learned which combination of models to query and reported matching GPT-4's performance with up to 98 percent cost reduction on their benchmarks. RouteLLM (Ong and colleagues, 2024) trained routers on human preference data to choose between a strong and a weak model, and reported cost savings of over two times in certain cases without degrading response quality on the benchmarks they evaluated.

Those results are real, and they are measured on the authors' tasks and the model prices of their time. Before you build one, measure the simpler alternative Anthropic's guidance recommends: **the strongest model you'd consider, at lower effort, on your own tasks.** Its reasoning is concrete. A newer model at lower effort often matches or beats a previous-generation model at high effort; one model means one cache namespace, while a cascade splits traffic across models whose caches are separate; and a router adds a component that can be wrong. The guide's rule: tune one model before you add a second, and build a pairing only if it beats the single model's whole curve of score against spend.

If a router does earn its place, treat it like any model output and check it. Log every routing decision, measure quality separately on the traffic routed down (the cheap path is where silent regressions hide), track the escalation rate, and keep a fixed eval that runs both paths on the same inputs.
</Listen>

<GoDeeper title="The break-even, in general">
Let w be the write multiplier, r the read multiplier, and suppose a prefix is sent n times with every request after the first a cache hit. The cached cost is w plus (n minus 1) times r, in units of one uncached send, against n uncached. Caching wins when w + (n - 1)r is less than n, that is when n is greater than (w - r)/(1 - r). With w = 1.25 and r = 0.05 that bound is about 1.26, so two sends are enough. With w = 2 (the one-hour lifetime) it is about 2.05, so three sends. The real-world complication is that hits aren't guaranteed: gaps longer than the lifetime turn reads back into writes, which is why simulating your actual timestamps (the exercise above) beats any average.

On FrugalGPT-style cascades, the same algebra applies to models. If a cheap model costs c, a strong one costs C, and the cheap model's answer is accepted with probability a, the expected cost per request is c + (1 - a)C. That beats the strong model alone only when c is less than aC, and only if the accepted answers are actually right, which is a property of your checker, not of the cascade.
</GoDeeper>

## What to carry forward

Caching is a byte-exact prefix match over tools, system, and messages: keep the prefix frozen, put breakpoints at the end of the shared part, choose the lifetime from real gaps, and verify with the usage fields after every change to prompt assembly. Send work nobody waits on through batch, keyed by `custom_id`. Treat effort as a measured trade, and before you build a router, measure the strongest model at lower effort. The next lesson turns from dollars to seconds.
</Listen>
