## Prompts are code, so treat them like code

A prompt that runs in production is part of your software. It changes behavior when it changes, it can break things, and someone will need to know why it is worded the way it is. OpenAI's prompting guide now says this plainly: keep production prompts in your application code so they get typed inputs, code review, tests, and your normal deployment process, and add representative fixtures and evaluation checks before changing a production prompt. The same guide recommends pinning production apps to specific model snapshots and building tests that measure prompt behavior, because different snapshots, even within one model family, can produce different results.

In practice that means a few habits. Keep each prompt in version control, next to the code that calls it. Give each published version a name (v1, v2) and treat it as immutable: to change it, add a new version and compare. Record the model and settings the prompt was tested with, since a prompt plus a model is the unit that works or doesn't. And write down why each change was made, in the commit message or a short change log, so the next person doesn't undo a fix they don't understand.

As a PM, you already know this pattern from requirements: a spec has versions, changes go through review, and every change has a reason. The difference here is that you can also run the spec against tests, automatically, in seconds.
</Listen>

## Decide what "better" means before you start

Anthropic's prompt engineering overview opens with a precondition, not a technique: before you engineer a prompt, have a clear definition of success for your use case, some way to test against it empirically, and a first draft. Its guide to success criteria asks that criteria be **specific**, **measurable**, **achievable** (realistic for current models), and **relevant** to what users need. It also notes that most uses need several criteria at once, not one.

"The summaries should be good" fails every one of those tests. Compare: "On our 50 test status updates, at least 95% of summaries name every milestone whose date changed, none contain a date absent from the source, 100% parse as our JSON schema, and the median response time stays under 4 seconds." Now you know what to measure, and so does anyone reviewing your change.

Then build the **test set** before you touch the prompt. Anthropic's eval guide gives three design principles that fit this stage. Make tests task-specific, mirroring your real input distribution, including edge cases: irrelevant or missing input, overly long input, poor or harmful input, and ambiguous cases where even people would disagree. Automate grading where you can (exact match, string checks, code). And prefer more test cases with automated checks over a few cases graded by hand. Hamel Husain's widely read essay on evals makes the same argument from practice: start with cheap assertion-style tests that run on every change, the way unit tests do, and save expensive human and model-based review for a regular cadence.
</Listen>

## Change one thing at a time, and rerun everything

The temptation after a bad output is to rewrite half the prompt. Resist it. If you change the role, add three examples, and reorder the instructions at once, and the score goes up, you don't know which change helped, or whether one of them hurt and was masked by the others. This is ordinary experimental design: vary one factor, hold the rest fixed, compare against the baseline.

Two more rules follow from week 1's lesson that output varies between runs. First, rerun the **whole** test set after every change, not just the case you were fixing. Prompts are tangled: a sentence that fixes the ambiguous-ticket case can make the model over-cautious on three others. Track **fixes** (failed before, pass now) and **regressions** (passed before, fail now) per case, not only the overall pass rate. Second, be suspicious of small differences. If a case flips between pass and fail when you rerun the same version, a one-case improvement is noise. Studio 3 covers how many repeats you need; for now, rerun anything that looks like a marginal win.

Finally, keep your test set honest. If you tune a prompt against the same 20 cases for a week, you will eventually fit those 20 cases rather than the task. Hold some cases back, add new ones from real failures, and never delete a case because it fails.
</Listen>

## Read the failures before you change anything

When cases fail, the most valuable thing you can do is the least glamorous: read the outputs. Hamel Husain's essay argues that looking at real outputs is where most improvement comes from, and that teams skip it because it feels slow. It is faster than guessing.

As you read, sort each failure into a bucket. A starting set that works for most prompts: **format** (the output didn't parse or broke the contract), **wrong answer** (parsed, but the label or fact is wrong), **ignored instruction** (a stated rule was not followed), **missing context** (the model couldn't have known; the prompt never said), and **bad test** (the check or the expected answer is wrong). Count the buckets. Then fix the biggest bucket first, with one change.

The last bucket matters more than people expect. Sometimes the model's answer is defensible and your expected label is the mistake, or the case is ambiguous and needs two acceptable answers. Fixing the test is legitimate, as long as you write down why. Anthropic's real-world prompting course (adapted here) frames this as a lifecycle: create an initial prompt, test it and identify issues, select the techniques that address those issues, implement the improvements, and iterate. This bucket-and-count habit is a light version of **error analysis**, which Studio 3 develops into a full method with model graders and dashboards.
</Listen>

<Callout type="pitfall" title="Declaring victory on one good output">
The most common iteration mistake is testing a new prompt on the one input that was failing, seeing it pass, and shipping. You have learned that the prompt works on one input, once. Rerun the whole set, check for regressions, and rerun marginal wins. The second most common mistake is the mirror image: abandoning a good change because one run of one case failed.
</Callout>

## Switching models means re-running the tests

You will often want to move a prompt between models: to a cheaper tier for volume, to a newer version, or to another provider for a capability or a price. Treat every such move as a change that needs the full test set.

The reasons are documented by the providers themselves. Anthropic's best-practices page says that where a technique was measured on one model, you should re-check it against your own evals before applying it to another. OpenAI notes that even different snapshots within one family can respond differently. The few-shot ordering research from lesson 5 found that a good example order for one model did not transfer to another.

Some differences are mechanical and fail loudly: parameter names for the instruction channel and for reasoning effort, sampling parameters that one API rejects (the current Claude API version), another ignores with a warning (recent Gemini models, per Google's docs), and a third accepts, or prefill that one stack supports and another rejects. Others are behavioral and fail quietly: one model is more literal, another more verbose, a third more likely to add a preamble before your JSON. Only a test set catches the quiet ones.

So a cross-model comparison is the same loop as a prompt comparison: same cases, same checks, one variable changed. Compare pass rate, the specific fixes and regressions, cost per completed task, and latency. Then decide. This is how you will make model-selection decisions all program: with a table of evidence, not a reputation.
</Listen>

## A first look at prompt injection

Everything in this week assumes the text in your prompt says what you meant. **Prompt injection** is what happens when it doesn't: someone places instructions inside content your application sends to the model, and the model follows them. Simon Willison gave the attack its name in a September 2022 post, written after Riley Goodside showed GPT-3 abandoning a translation task because the text to translate told it to. Willison's ongoing series is the best single record of the problem.

Anthropic's docs describe two threat models. In **direct** injection (closely related to jailbreaking), your own user is the adversary and types the attack. In **indirect** injection, the user is trusted, but the model processes third-party content (a webpage, an email, a document, a tool result) that contains instructions. The lab's test set includes a mild version: a support ticket that tells the classifier to reply "APPROVED."

The root cause, in Willison's framing, is that models follow instructions found in content, which is also what makes them useful. That is why the separation you practiced in lesson 4 matters: instructions in one channel, untrusted data clearly marked, tagged, and escaped in another. Anthropic's injection guidance adds concrete measures: deliver third-party content in tool results rather than in the system prompt, say where the content came from, state in the system prompt that retrieved content is data and never overrides your instructions, and JSON-encode untrusted strings so they cannot break out of their container.
</Listen>

<Callout type="claim" title="Is prompt injection solvable with better prompting?">
**Claim:** Simon Willison, May 2023, in [Delimiters won't save you from prompt injection](https://simonwillison.net/2023/May/11/delimiters-wont-save-you/): "Prompt injection remains an unsolved problem." His post shows how easily an attacker can work around delimiters meant to fence off untrusted text.

**Evidence for:** OWASP's entry on prompt injection (LLM01, the top risk in its Top 10 for LLM Applications) says it is unclear whether fool-proof prevention methods exist, given how models work, and lists mitigations rather than a fix.

**Evidence against, or at least for progress:** Anthropic's docs describe Claude as inherently resilient to such attacks and say Claude is trained to treat instructions inside tool results with skepticism. Resilience is a rate, though, not a guarantee, and vendors' own guidance still recommends layered defenses.

**How to act on it:** design as if some injections will succeed, and limit what a successful one can do.
</Callout>

## Checks and balances: limit what the output can do

If you can't guarantee the model will ignore injected instructions, control the consequences. OWASP's mitigation list reads like a checks-and-balances charter. Constrain the model's role and task in the system prompt. Define the expected output format and validate it with deterministic code. Filter inputs and outputs. Give the application, not the model, the credentials it needs, with least privilege. Require human approval for high-risk actions. Clearly separate and label external content. And test adversarially, treating the model as an untrusted user of your own system.

Willison's "lethal trifecta" (June 2025) gives a quick risk test for anything with tools. If one system combines access to private data, exposure to untrusted content, and a way to communicate externally, an attacker who controls the content can try to make it send the data out. Remove any one leg and that attack loses its path.

For this studio, the practical upshot is modest but important. Never let model output trigger an action directly. Parse it, validate it against a contract (week 3), and gate side effects behind code checks or human approval (week 4). Include injection attempts in your test set, as the lab does, so you notice when a prompt or model change makes them succeed more often. Studio 5 returns to this in depth.
</Listen>

## The habit to keep

Every prompt change is a hypothesis. The test set is how you check it, the per-case fixes and regressions are the evidence, and the change log is the record. Keep untrusted text separate from instructions, validate what comes back, and never let raw model output act on its own. That is the checks-and-balances discipline the rest of this program builds on, whichever model or provider you end up using.
</Listen>
