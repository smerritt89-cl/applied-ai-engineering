## The model asks, your code acts

Everything you have built so far ends with text: the model writes, your code reads. Tool calling (OpenAI and Google call it function calling) adds one move. You describe some functions to the model, and instead of answering in prose it can reply with a structured request: "call `lookup_teammate` with name equal to Priya." Your code runs the function and sends the result back, and the model continues with the new information.

The important word is *request*. For tools you define, the model executes nothing. It cannot reach your directory, your calendar, or your database. It produces a tool name and a JSON object of arguments, and your application decides whether that call happens. Anthropic's docs put the split simply: Claude returns a structured call that your application runs.

Microsoft's Generative AI for Beginners course frames the benefit in two parts, and both apply to the Studio 1 project. First, consistent shape: the arguments arrive as structured data instead of free text you have to parse. Second, outside data: the model can use facts it never saw in training, like who is on your team or what date "next Friday" is relative to a meeting. In the meeting-notes tool you will build, a transcript says "Marcus will take it." Only a lookup tells you which of your two Marcuses that is.
</Listen>

<Listen>
## A tool definition is a contract

You describe each tool with three fields. A **name**, which is how the model refers to it. A **description**, which is how the model decides when to use it. And an **input_schema**, a JSON Schema object that says what arguments the tool takes. JSON Schema is a standard vocabulary for describing JSON: types, required fields, enums, and nested objects.

Treat the description as a prompt, because it is one. It is loaded into the model's context on every request, together with a short tool-use system prompt the API adds for you (a few hundred tokens on current Claude models, per the pricing section of the tool use docs). Anthropic's guidance is to say what the tool does, when to call it, what each parameter means, and what the tool will not do. Lesson 11 goes deep on this.

Two schema settings matter from day one. Mark the fields you need as `required`, and use `enum` when a value comes from a fixed list. And consider `strict: true` on the tool, which makes the API constrain generation so the arguments always match your schema. Strict mode guarantees the *shape* of the input. It does not guarantee the input is *true*: a perfectly formed email address can still belong to nobody on your team.
</Listen>

```python
lookup_teammate = {
    "name": "lookup_teammate",
    "description": (
        "Look up a teammate in the team directory by full name, first name, or alias. "
        "Call this whenever a transcript mentions a person who might own an action item. "
        "Returns every match; if more than one person matches, ask which one was meant. Read-only."
    ),
    "strict": True,
    "input_schema": {
        "type": "object",
        "properties": {
            "name": {"type": "string", "description": "The name as spoken, e.g. 'Priya'."}
        },
        "required": ["name"],
        "additionalProperties": False,  # strict mode requires this
    },
}
```

## The loop, step by step

Anthropic's tool use course builds this up over several notebooks; here is the whole cycle in one place.

One. You send a request with your messages and a `tools` list. Two. The model either answers directly or decides to use a tool. If it uses one, the response has a `stop_reason` of `tool_use`, and its content includes one or more `tool_use` blocks. Each block has an `id`, a `name`, and an `input` object. The content may also include text, such as "Let me look that up," and on current models, thinking blocks.

Three. You append the assistant's *entire* content to your message history, tool_use blocks included. Four. For each tool_use block, you run the matching function. Five. You send a new user message whose content is a list of `tool_result` blocks, each carrying the `tool_use_id` it answers and the result as `content`. Six. You call the API again with the longer history. The model reads the results and either requests more tools or finishes, in which case `stop_reason` is `end_turn`.

Because the API is stateless (lesson 1), the history you resend is the only memory the model has of what it asked for. Two formatting rules from the docs trip people up. The user message with results must come immediately after the assistant message that requested them. And within that user message, the tool_result blocks must come first, before any text you add.

Finally, put a ceiling on it. A model can keep asking for tools, and each round trip costs tokens and time. A maximum iteration count is cheap insurance.
</Listen>

```python
import anthropic

client = anthropic.Anthropic()
messages = [{"role": "user", "content": notes}]

for _ in range(8):  # a hard ceiling on round trips
    response = client.messages.create(
        model="claude-opus-5-5",
        max_tokens=16000,
        tools=TOOLS,
        messages=messages,
    )
    messages.append({"role": "assistant", "content": response.content})  # full content

    if response.stop_reason == "end_turn":
        break
    if response.stop_reason != "tool_use":
        raise RuntimeError(f"stopped early: {response.stop_reason}")

    results = []
    for block in response.content:
        if block.type == "tool_use":
            content, failed = run_tool(block.name, block.input)  # your dispatcher
            result = {"type": "tool_result", "tool_use_id": block.id, "content": content}
            if failed:
                result["is_error"] = True
            results.append(result)
    messages.append({"role": "user", "content": results})  # all results, one message

final_text = "".join(b.text for b in response.content if b.type == "text")
```

## Parallel calls: several requests, one reply

Current Claude models may ask for several tools in a single turn. A transcript line like "Priya will send the deck by next Friday" can yield two tool_use blocks at once: look up Priya, and resolve next Friday. The docs leave execution order to you. Independent, read-only calls are usually safe to run concurrently. Calls with side effects or ordering requirements are often better run one at a time.

Whatever order you choose, the reply has one fixed shape: one tool_result per tool_use, all together in the next user message, matched by id. The parallel tool use docs list splitting results across separate user messages as the most common formatting mistake, and say it teaches the model to stop making parallel calls. If you decide not to run one of the calls, perhaps because an earlier one failed, you still return a tool_result for it, marked as an error, with a short explanation.

If you need at most one call per turn, you can set `disable_parallel_tool_use` inside `tool_choice`. Usually you don't need to. Parallel calls save round trips, and round trips are where latency lives.
</Listen>

## Errors are results, not exceptions

Tools fail. The person isn't in the directory, the date phrase is "sometime soon," the downstream API times out. The wrong reaction is to let the exception kill your loop, or to swallow it and return an empty string. The right reaction is to tell the model, in a tool_result with `is_error` set to true and a message it can act on.

Anthropic's docs give two reasons. The model can incorporate the failure into its answer instead of inventing one. And with an instructive message, it can often recover: the docs suggest saying what went wrong and what to try next, rather than a bare "failed." "No teammate matches Jordan. Known teammates: Priya Raman, Marcus Lee..." gives the model a path forward. The docs also note that when Claude sends a call with missing parameters and you report it as an error, it typically retries a few times with corrections before giving up. With strict mode on, malformed calls of that kind should not reach you at all, but your own semantic checks still produce errors, and they follow the same rule.

This is also your first checks-and-balances habit for tools: every call and its error status is a line you can log. When you build evals in Studio 3, "how often does the model call a tool with input that my validator rejects?" is one of the most useful numbers you can have.
</Listen>

<Callout type="pitfall" title="Four ways the loop breaks">
1. **Appending only the text.** If you append `response.content[0].text` instead of the full `response.content`, the tool_use blocks vanish from history and the next request fails, because results answer requests the API cannot see.
2. **Text before results.** In the user message that carries results, tool_result blocks come first. Text you want to add goes after them.
3. **Forcing a tool on a model that rejects it.** `tool_choice` with type `any` or `tool` returns a 400 on Claude Opus 5.5 and Claude Sonnet 5.5. Keep `auto`, name the tool you expect in the instructions, use `strict: true` for valid arguments, and check that a call actually happened.
4. **No ceiling.** Without a maximum iteration count, a confused model and a tool that keeps returning errors can loop until your budget notices.
</Callout>

## Client tools and server tools

Everything above describes **client tools**: tools that run in your application. That includes tools you define and tools whose schema Anthropic publishes but you still execute, such as the bash and text editor tools. **Server tools**, such as web search, web fetch, and code execution, run on Anthropic's infrastructure. You declare them in the `tools` list by type, and their results arrive inside the same response, with no handler code on your side. Server tools can bill extra on top of tokens; web search, for example, charges per search.

Server tools add one stop reason you should handle: `pause_turn`. The API runs server tools in its own internal loop, and if that loop reaches its iteration limit, the response stops with `pause_turn`. To continue, you send the conversation back as it is, including the paused assistant turn, without adding a "please continue" message, and the server resumes.

The distinction matters for checks and balances. With client tools you hold the gate: nothing runs until your code runs it. With server tools, the model's decision to search or fetch happens on the server, so your controls are the declaration itself (whether you include the tool, and options such as allowed domains and maximum uses) and what you do with the results.
</Listen>

## The tool runner, or your own loop

The Anthropic SDKs include a **tool runner** (in beta at the time of writing). You write ordinary functions, decorate them, and the runner generates the schemas, calls the API, runs your functions when the model asks, feeds results back, and stops when the model stops calling tools. When a tool raises an exception, the runner returns it to the model as an error result, the same pattern you just learned. You can cap it with a maximum number of iterations, and you can intervene on each turn: inspect the pending tool calls, take over the message history, or modify results before they go back.

So which should you use? The docs give both answers depending on the page: the runner for most custom-tool agents, and the manual loop when you want complete control over approval, logging, or conditional execution. A reasonable rule: write the manual loop once, by hand, so you know what the runner is doing (that is this week's lab). In production, use the runner when its hooks cover your needs, and keep a manual loop when you want to own every step, or when you would rather not depend on a beta helper.

Either way, remember that a runner runs your functions *automatically*. Any tool that changes something in the world needs its own gate, inside the function or in the per-turn hook. That is lesson 11.
</Listen>

```python
import json

import anthropic
from anthropic import beta_tool

client = anthropic.Anthropic()

@beta_tool
def lookup_teammate(name: str) -> str:
    """Look up a teammate by name or alias. Read-only.

    Args:
        name: The name as spoken in the meeting, e.g. 'Priya'.
    """
    return json.dumps(find_people(name))  # your implementation

runner = client.beta.messages.tool_runner(
    model="claude-opus-5-5",
    max_tokens=16000,
    tools=[lookup_teammate],
    messages=[{"role": "user", "content": notes}],
)
final = runner.until_done()  # the last message, after the model stops calling tools
```

## The same idea at every provider

Tool calling is not a Claude-specific trick. The vocabulary changes; the protocol does not.

OpenAI's function calling guide describes the same five-step flow: send tools, receive a tool call, run your code, send the output back, receive the final answer. In its Responses API, a call arrives as a `function_call` item with a `call_id`, and you return a `function_call_output` item with the same id. Parallel calls are on by default, and a `parallel_tool_calls` flag limits the model to zero or one call.

Google's Gemini docs describe function calls returned with a name and arguments, which you execute and send back. They cover parallel calling (several functions in one turn) and compositional calling (a chain, where one call's output feeds the next), and modes that let the model decide, force a call, forbid calls, or enforce schema adherence. xAI's Grok docs follow the same request, execute, return pattern, with parallel calls enabled by default.

Two practical consequences. First, your tool *implementations* and your gating logic are portable; only the adapter that translates blocks differs. Second, behavior is not portable. How eagerly a model calls tools, how often it calls them in parallel, and how well it recovers from errors all vary between model families and versions. When you switch models, re-run your tool evals rather than assuming.
</Listen>
