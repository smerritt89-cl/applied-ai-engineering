## Free text is a contract nobody signed

This week you'll build the core of the studio project: reading a meeting transcript and producing action items your code can act on. The moment a model's output feeds another program (a tracker, a database, a dashboard), its job changes. A person reading "Priya will send finance the budget, probably by the 20th" understands it. A program needs to know which field is the owner, which is the date, and what format the date is in.

Ask a model for "the action items as JSON" in plain prose and you'll see a familiar set of failures. Sometimes there's a friendly sentence before the JSON, or the JSON arrives wrapped in a Markdown code fence. A key is called `owner` on one run and `assignee` on the next. A date arrives as "next Friday." A field your code needs is simply missing. Anthropic's structured outputs documentation lists the same categories: invalid JSON syntax, missing required fields, inconsistent data types, and schema violations that force you to write error handling and retries.

None of this means the model is bad at the task. It means nothing told it, or checked, what shape the answer must have. Every one of these failures is about **shape**, and shape is something you can specify exactly and verify mechanically. That's the job of a schema. Lesson 8 shows how to make the API enforce a schema during generation. This lesson covers the schema itself and the validation you run no matter which API you use, because validation is your check on any output, from any provider.
</Listen>

## JSON Schema: a vocabulary for describing data

**JSON Schema** is a standard for describing what valid JSON looks like. The current version is Draft 2020-12, and its validation vocabulary is a short list of keywords that you'll see in every model provider's docs. A schema is itself a JSON object. The keywords you'll use most:

- `type`: string, number, integer, boolean, object, array, or null.
- `properties`: for an object, a schema for each named key.
- `required`: the list of keys that must be present. Keys not listed may be absent.
- `enum`: the value must be one of a fixed list.
- `additionalProperties`: whether keys not named in `properties` are allowed. Setting it to false makes the object closed.
- `items`: for an array, the schema every element must match.
- `format`: a named format such as `date` or `email`.
- `description`: human-readable text. It doesn't constrain anything, but as you'll see, models read it.

Two details trip people up. First, `required` and nullability are independent: a key can be required but allowed to be null (the type is a union with null), or optional but non-null when present. Second, by default JSON Schema objects are open: extra keys pass validation unless `additionalProperties` is false. Closed objects are what you want for model output, because a stray `assignee` key usually means the model misunderstood the contract.

You'll rarely write these schemas by hand. You'll generate them from code.
</Listen>

This is the schema for one action item. Read it before you see the Python that produces it.

```json
{
  "type": "object",
  "properties": {
    "task":     { "type": "string", "minLength": 1, "description": "What will be done, as a short imperative phrase" },
    "owner":    { "anyOf": [{ "type": "string" }, { "type": "null" }], "description": "Person responsible, or null if no one was named" },
    "due_date": { "anyOf": [{ "type": "string", "format": "date" }, { "type": "null" }], "default": null },
    "priority": { "enum": ["high", "medium", "low"] }
  },
  "required": ["task", "owner", "priority"],
  "additionalProperties": false
}
```

## Pydantic: one class, four jobs

**Pydantic** is a Python library that validates data against type hints (its docs describe it as the most widely used one). You declare a class whose attributes have types, and Pydantic gives you four things from that one declaration: a validator for incoming data, typed Python objects, a JSON Schema (from `model_json_schema()`, which targets Draft 2020-12), and documentation through field descriptions. The structured-output examples from Anthropic, OpenAI, Google, and xAI all accept a Pydantic model (directly, or through its generated schema), so the same class serves your prompt, your API call, and your tests.

That's why you should treat the model class as the **single source of truth**. If the schema lives in a prompt string, a JSON file, and a parsing function, they'll drift apart. If all three are generated from one class, they can't.

The building blocks map directly onto JSON Schema:

- **Types.** `str`, `int`, `bool`, `datetime.date`, lists, and nested models. A `date` field parses "2026-11-20" into a real `datetime.date`.
- **Enums.** `Literal["high", "medium", "low"]` (or a Python `Enum`) becomes a JSON Schema enum.
- **Required versus optional.** A field with no default is required. A field with a default may be omitted. Allowing null is a separate choice: `str | None`.
- **Constraints.** `Field(min_length=1)`, `Field(ge=0)`, and friends add checks beyond the type.
- **Descriptions.** `Field(description="...")` lands in the schema. Write descriptions as instructions to the model, because they are.
- **Closed objects.** `model_config = ConfigDict(extra="forbid")` rejects unknown keys and sets `additionalProperties` to false.
</Listen>

```python
from datetime import date
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field

class ActionItem(BaseModel):
    model_config = ConfigDict(extra="forbid")

    task: str = Field(min_length=1, description="What will be done, as a short imperative phrase")
    owner: str | None = Field(description="Person responsible, or null if no one was named")
    due_date: date | None = Field(default=None, description="ISO date, only if a specific date was stated")
    priority: Literal["high", "medium", "low"]

print(ActionItem.model_json_schema())
```

<Callout type="pitfall" title="Optional means two different things">
`owner: str | None` is **required** in Pydantic v2: the key must be present, though its value may be null. Only a default (`= None`) lets the key be left out. Choose deliberately. For extraction, required-but-nullable is often right, because it forces the model to say "nobody was named" instead of silently dropping the field, and a missing key then signals a real contract failure.
</Callout>

Lax mode is convenient; strict mode is a sharper detector of a model drifting from the contract.

## Validate, then report errors someone can act on

Validation is the check that turns "it looked fine" into "it matched the contract." With Pydantic, `ActionItem.model_validate_json(text)` either returns a typed object or raises a `ValidationError`. That error is structured: `errors()` returns a list with one entry per problem, and each entry has a `type` (a machine-readable code such as `missing` or `literal_error`), a `loc` (the path to the field, such as `("priority",)`, or a nested path like `("items", 2, "owner")`), and a `msg` for humans. Invalid JSON itself is reported too, with an empty location, because the problem is the whole document.

Pydantic reports **every** problem in one pass rather than stopping at the first, which matters for two reasons. You get a complete picture for logs and dashboards ("12 percent of failures are bad priorities"). And you can hand the full list back to the model in a retry, which you'll build in this week's lab. A message like "priority: Input should be 'high', 'medium' or 'low'" is something a model can fix; "parse failed" is not.

Decide up front what happens on failure: retry once with the errors, drop the item and log it, or send it to a person. What you must not do is catch the exception and carry on with a half-parsed dictionary. That's how a pipeline goes quietly wrong.
</Listen>

<Callout type="tip" title="Validate in your code, whatever the provider promises">
Next lesson you'll see APIs that constrain output to a schema during generation. Keep the validation step anyway. Providers support different subsets of JSON Schema, and some ignore constraints they don't support. Google's Gemini docs, for instance, say certain keywords such as `minLength` are not enforced and advise validating values in your application. Your Pydantic model is the check that travels with your code across providers and model versions.
</Callout>

<GoDeeper title="Validators: rules a type can't express">
Some rules involve logic rather than types: "a due date can't be before the meeting date" or "if status is done, completed_on is required." Pydantic handles these with `@field_validator` (one field) and `@model_validator` (the whole object, after field validation), which raise a `ValueError` that Pydantic folds into the same `ValidationError` format. Keep two kinds of rule apart, though. Rules about the data's internal consistency belong in validators. Rules that need outside facts (is this person on the team? does the quote appear in the transcript?) need context the model doesn't have, and are clearer as separate verification functions, which is how lesson 9 builds them. Pydantic's docs also cover strict mode per field, custom error messages, and `TypeAdapter`, which validates plain types such as `list[ActionItem]` without a wrapper class.
</GoDeeper>

## What to carry forward

Three habits from this lesson run through the rest of the studio. Define output shape once, as a Pydantic model, and generate everything else from it. Make choices about required, nullable, and closed explicit, because each one changes what a failure looks like. And always validate, then decide what happens to failures instead of letting them slide through. Validation tells you the output has the right shape. It says nothing about whether the owner, the date, or the task is correct. Lesson 8 makes the right shape nearly automatic; lesson 9 deals with whether it's true.
</Listen>
