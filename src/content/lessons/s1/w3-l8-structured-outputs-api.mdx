## Three generations of getting JSON out of a model

**Generation one: ask nicely.** Put "respond only with JSON matching this format" in the prompt, parse the text, and retry on failure. It works most of the time, which is the problem: you saw in lesson 7 how the remaining failures look (preambles, code fences, renamed keys). Every team that shipped this way also shipped a pile of cleanup code.

**Generation two: borrow tool calling.** Tool calling (week 4 covers it properly) lets you describe a function with a JSON Schema for its arguments, and the model returns a structured call. Engineers noticed they could define a fake tool whose "arguments" were the output they wanted, then force the model to call it. Tool arguments came back as parsed JSON, which removed most syntax failures. But the arguments were not guaranteed to match the schema: a required field could still be missing or the wrong type. And forcing a particular tool is no longer available everywhere. On Claude Opus 5.5 and Claude Sonnet 5.5, a `tool_choice` that forces a tool (`any` or a named `tool`) is rejected; Anthropic's guidance is to use structured outputs when you only wanted JSON back.

**Generation three: constrain the decoder.** Instead of hoping the model writes valid output, the serving system makes invalid output impossible. Anthropic's docs describe compiling your JSON Schema into a grammar and restricting generation to it. The technique is general: Willard and Louf (2023) showed how to turn a regular expression or grammar into a finite-state machine and precompute, for each state, which vocabulary tokens are allowed, so the check adds little overhead per token.
</Listen>

## How constrained decoding works, in one paragraph of math

Recall from lesson 1 that each step produces a probability for every token. With a grammar, the system tracks which state of the automaton the output so far has reached. At each step it sets the probability of every token that would leave the language of valid documents to zero, renormalizes the rest, and samples. If your schema says the next thing must be one of "high", "medium", or "low", tokens that start any other string are masked out.

Two consequences follow, and both matter for trust. First, the output is valid by construction: you can't get a missing brace or an unknown key. Second, the model must choose among the options you allowed, even if none of them fits. Masking redistributes probability over the legal tokens; it doesn't create a "this doesn't apply" option. If the transcript never states a priority and your enum has no way to say so, the model will pick one, and the result will look exactly as confident as a real answer. That's why schema design, not just the feature, decides whether structured output is honest.
</Listen>

## Structured outputs on Claude today

Claude offers two related features. **JSON outputs** constrain the response itself: you pass a schema in `output_config.format` with type `json_schema`, and the reply's text block is JSON matching it. **Strict tool use** constrains tool arguments: you add `strict: true` to a tool definition, and calls to that tool always validate. You can use both in one request. The older top-level `output_format` request parameter is deprecated; the current home is `output_config.format`.

In Python, the recommended path is `client.messages.parse()`. You pass your Pydantic class (the SDK's `parse()` helper takes it as `output_format`), the SDK converts it to a schema and sends it as `output_config.format`, and the response carries a validated instance in `parsed_output`. The SDK also adapts the schema: the API supports a subset of JSON Schema, and the docs list what's out, including recursive schemas, numeric bounds such as `minimum`, string length bounds such as `minLength`, and any `additionalProperties` other than false. The SDK helpers move unsupported constraints into the field description and then check your original constraints when they validate the response. That's another reason to keep the Pydantic model as your source of truth.

Some operational details from the docs. The first request with a new schema pays a one-time compilation cost; compiled grammars are cached for 24 hours from last use. Changing the format invalidates the prompt cache for that conversation. Structured outputs can't be combined with citations. And the guarantee has stated exceptions: if `stop_reason` is `refusal` or `max_tokens`, the output may not match the schema, so check the stop reason before you trust `parsed_output`.
</Listen>

```python
import anthropic
from pydantic import BaseModel, ConfigDict, Field

class ActionItem(BaseModel):
    model_config = ConfigDict(extra="forbid")
    task: str = Field(description="What will be done, as a short imperative phrase")
    owner: str | None = Field(description="Person who committed to it, or null if no one was named")

class ActionItems(BaseModel):
    model_config = ConfigDict(extra="forbid")
    items: list[ActionItem] = Field(description="Every commitment in the transcript; empty if none")

client = anthropic.Anthropic()
response = client.messages.parse(
    model="claude-opus-5-5",
    max_tokens=16000,
    system="Extract action items from the meeting transcript the user provides.",
    messages=[{"role": "user", "content": transcript}],
    output_format=ActionItems,
)

if response.stop_reason in ("refusal", "max_tokens"):
    raise RuntimeError(f"no usable output: {response.stop_reason}")
for item in response.parsed_output.items:
    print(item.owner, "->", item.task)
```

## The same idea at other providers

Every major API now offers schema-constrained output. The names differ, and so do the subsets of JSON Schema they enforce, so read each provider's limits before you port a schema.

**OpenAI** calls it Structured Outputs. In the Responses API you set a text format of type `json_schema` with `strict: true`; the Python SDK's `responses.parse()` accepts a Pydantic model and returns `output_parsed`. OpenAI distinguishes it from the older JSON mode, which guarantees valid JSON but not adherence to your schema. Refusals arrive as a separate content item you check before parsing.

**Google's Gemini API** takes a JSON Schema with an `application/json` MIME type; the Python examples pass `Model.model_json_schema()` and validate with `model_validate_json()`. The docs say some keywords, such as `minLength` and `maxLength`, are ignored rather than enforced, and they warn about schema-compliant but semantically incorrect outputs.

**xAI's Grok API** accepts a `json_schema` response format and Pydantic models, states that output is guaranteed to match when you use supported features, and lists other features as best effort.

**Open models** get the same capability from the serving layer. vLLM, a widely used open-source inference server, supports JSON Schema, regex, fixed choices, and context-free grammars through backends such as xgrammar and guidance. Libraries such as Outlines (from the Willard and Louf paper) do the same in your own process. This is a real advantage of open models: you control the grammar engine and can constrain to formats a hosted API doesn't offer.
</Listen>

## What the guarantee covers, and what it doesn't

Constrained decoding guarantees **shape**: the JSON parses, required keys exist, types are right, enum values are legal, and no unknown keys appear (within the schema features the provider enforces). That eliminates a whole class of bugs and most of your cleanup code.

It guarantees nothing about **values**. A valid `owner` can name the wrong person. A valid `due_date` can be a date nobody said. An `items` array can include discussion that was never a commitment, or miss a real one. Google's docs say it plainly: validate values in your application. Claude's docs add a smaller caveat worth knowing: enum values can come back with different capitalization than the schema, so compare them case-insensitively.

There is also a live debate about whether constraining format hurts quality. Tam and colleagues (2024) reported that reasoning performance dropped under strict format restrictions. The team behind the Outlines library published a rebuttal arguing that the study compared different prompts across conditions and conflated structured generation with JSON mode, and that their reruns showed structured generation helping. Treat this as unsettled, with a practical takeaway either way: let the model think (thinking blocks, or a separate step) and constrain only the final answer, then measure on your own data.
</Listen>

<Callout type="claim" title="Do format constraints degrade reasoning?">
**Claim (Tam et al., 2024, arXiv 2408.02442):** restricting LLMs to formats like JSON significantly reduced performance on reasoning tasks, and stricter constraints hurt more.

**Counterpoint (Will Kurt, .txt, "Say What You Mean"):** the prompts differed between conditions and the JSON prompts were inadequate; with matched prompts, structured generation improved results. Note that .txt sells structured-generation tooling, so it is an interested party.

**What to do:** don't take either side on faith. Run your own eval with and without constraints on the same prompts. For extraction tasks like this week's, the cost of unparseable output usually dominates.
</Callout>

## Designing schemas that extract well

A schema is a prompt as much as a contract. Five rules cover most of what goes wrong.

**Describe every field.** Descriptions go to the model with the schema. Say what belongs in the field, in what form, and what to do when the source is silent: "Person who committed to the task, as written in the transcript; null if no one was named."

**Enumerate closed sets.** Priority, status, category: if your code branches on it, make it an enum. Free strings drift ("High", "high priority", "P1").

**Make "not found" legal.** Every field the source might not cover should be nullable, or have an explicit "unknown" value. Otherwise constrained decoding forces an invention. Required-but-nullable, from lesson 7, is the usual pattern: the model must address the field, and null is a valid answer.

**Keep it shallow.** Nest only where the data is really nested (a list of items, each with fields). Deep trees of small objects are harder to fill correctly, and providers impose complexity limits; Claude's docs, for example, cap optional parameters and union-typed parameters per request.

**Keep the API schema to the supported subset.** Close every object, and leave numeric and length bounds to your validator. The SDK does this for you when it starts from Pydantic, but hand-written schemas sent to `output_config.format` must follow the rules or the request fails.

On model choice: structured outputs are available across current Claude tiers (Opus, Sonnet, Haiku), so the guarantee doesn't force you onto the largest model. Whether a smaller, cheaper model gets the values right as often is an empirical question for your eval set; the project's optional stretch goal asks you to measure exactly that.
</Listen>

<GoDeeper title="Strict tool use, and when to prefer it">
Use JSON outputs when you want the model's reply to be data. Use strict tool use when the structured thing is an action: the model decides to call `create_ticket`, and `strict: true` guarantees the arguments validate before your code runs them. In agent loops you'll often use both: strict tools for actions along the way, and a JSON output format for the final report. Strict tool schemas follow the same rules (closed objects, every required key listed). Anthropic's docs also cover the per-request limits on strict tools and the compilation timeout for very complex schemas; if you hit "schema too complex," flatten it or split the task into two calls.
</GoDeeper>

## What to carry forward

Use the API's structured-output feature whenever a program consumes the result; it is the cheapest reliability win in this studio. Define the schema in Pydantic, check `stop_reason` before trusting the result, and keep validating in your own code, because providers enforce different subsets. Most of all, remember what you bought: valid shape. The values inside that shape are still model output, and the next lesson is about catching the ones that are confidently wrong.
