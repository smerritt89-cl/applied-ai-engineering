## The feature, and the mistake to avoid

The Studio 1 project is a tool that takes a meeting transcript and produces action items: what needs doing, who owns it, when it is due, and the words in the meeting that prove someone committed to it. A person reviews the list, and only approved items reach a task tracker.

The tempting first version is one prompt: "Here is a transcript. List the action items as JSON." It will produce something plausible on the first try, and that is the danger. Lesson 1 warned that fluent output is not evidence of correctness. A single prompt gives you no place to check anything: if an owner is wrong, you cannot tell whether the model misheard the transcript, guessed between two people with the same first name, or invented the item entirely.

This lesson lays out a design instead. Each stage has one job, produces output you can inspect, and is followed by a check. It is not the only valid design, and the project leaves the details to you. But every choice below is one you should be able to defend with the concepts from lessons 1 through 11.
</Listen>

<Listen>
## Workflow, not agent

Anthropic's "Building effective agents" post separates **workflows**, where code decides the sequence of steps and models fill in particular steps, from **agents**, where the model decides what to do next and which tools to use. It recommends starting with the simplest solution that works and adding autonomy only when the task needs it.

This feature is a workflow. The steps are known in advance and always the same: read the transcript, find candidate items, check them, normalize them, merge duplicates, ask a human. Letting a model choose the order buys nothing and costs you predictability, testability, and cost control. You will still use tool calling from lessons 10 and 11, but inside a stage, with a bounded loop, for the specific job of resolving owners and dates.
</Listen>

## Stage by stage

**Ingest and chunk (code).** Parse the transcript into speaker turns with timestamps, and keep the original text untouched so quotes can be checked against it. Current frontier models have context windows large enough for most single meetings, so chunking is not always required. It still helps: smaller chunks put the evidence close to the instruction (recall the "lost in the middle" findings from lesson 1), and they let you run chunks in parallel. If you chunk, overlap chunks slightly so a commitment split across a boundary is not lost, and expect the overlap to create duplicates that a later stage must merge.

**Extract candidates (model, structured output).** This is the stage that needs judgment: telling "I'll send the deck Friday" (a commitment) from "someone should look at the deck" (not one, or an unowned item). Use the structured outputs you built in week 3 so each candidate has the same fields: a title, the owner as mentioned, the due phrase as spoken, a verbatim evidence quote, and the speaker and timestamp. Ask for the phrase as spoken ("next Friday"), not a resolved date. The model is not the right place for calendar arithmetic, and keeping the raw phrase makes the next stage checkable.

**Verify evidence (code).** For each candidate, confirm the evidence quote occurs in its chunk, after normalizing whitespace and case. A candidate whose quote does not appear is either a paraphrase or an invention, and either way it is not evidence. Reject it with a reason and log it. This one check, which costs nothing, catches a whole class of confident-but-wrong output.

**Normalize owners and dates (tools).** Resolve "Marcus" to a directory entry and "next Friday" to a date, measured from the meeting date. Notice the choice here. If normalization were fully deterministic, you would call these functions directly in code and skip the model. Tools earn their place when judgment is needed, such as two teammates named Marcus, where the surrounding conversation decides which one was meant, or when the right answer is "unassigned." Whichever way you go, the rules from lesson 11 apply: read-only tools, strict schemas, your own checks, instructive errors.

**Deduplicate (code first).** The same commitment often appears twice: restated at the end of a meeting, or duplicated by chunk overlap. Start with a deterministic key (same owner, same due date, highly similar title) and send only the ambiguous pairs to a model, which keeps that call small and rare.

**Human review, then write.** Show the reviewer each item with its evidence quote, the resolved owner and date, and anything the pipeline was unsure of. Approve, edit, or reject in one pass. Only approved items go to the tracker, through a gated, idempotent write. This is the single meaningful approval lesson 11 argued for, and the reviewer's decisions are labeled data you will use later.
</Listen>

<Callout type="pitfall" title="Checks that are not really checks">
Three patterns look like verification but are not. Asking the same model "are you sure?" about its own output, and accepting yes. Letting structured output stand in for correctness: valid JSON with a made-up quote is still made up. And testing the whole pipeline on one transcript you wrote yourself, which proves only that it works on that transcript. Real meetings have crosstalk, people who say "I can probably look at that," and names the transcription service got wrong. Collect several real or realistic transcripts early, including messy ones.
</Callout>

## Which model for which stage

Different stages need different amounts of capability, and the price spread between tiers is large. On the Claude pricing page as of today, per million tokens, Claude Opus 5.5 costs $4 for input and $20 for output, Claude Sonnet 5.5 costs $2 and $10, and Claude Haiku 5.5 costs $0.10 and $0.50 (for prompts up to 100,000 tokens). The Batch API halves those prices for work that can wait. Prices change, so check the page before you rely on these.

Now a back-of-envelope estimate, with every assumption stated. Assume a one-hour meeting transcript of about 9,000 words. Using OpenAI's rough rule of about three quarters of a word per token, that is about 12,000 tokens; add about 2,000 for instructions and the output schema, so 14,000 input tokens per meeting. Assume the extraction returns 20 candidates at about 75 tokens each, so 1,500 output tokens. Then one extraction call costs about 8.6 cents on Opus 5.5, 4.3 cents on Sonnet 5.5, and about 0.2 cents on Haiku 5.5. At 200 meetings a month, that is roughly $17, $8.60, and $0.43.

Two cautions keep this honest. First, on current Claude models thinking tokens are billed as output, and Opus 5.5 always thinks, so real output usage can be well above 1,500 tokens. The effort setting changes how much. Measure usage from real responses (every response reports it) and replace these guesses. Second, look at what the numbers say. At this volume, the most expensive option likely costs less per month than an hour of a reviewer's time, and a missed commitment can cost far more than that. Cost is a constraint here, not the deciding factor.

So decide with evidence. Label a set of transcripts with the action items a careful person would extract. Run the extraction stage on two or three candidate models, and compare recall (did it find the real items?), precision (are the items it found real?), and the quote-verification pass rate. Pick the cheapest model that meets your bar. Then do the same per stage: deduplicating ambiguous pairs is a much smaller judgment than extraction, and a small model often suffices there. The same method applies if you compare Claude with GPT, Gemini, Grok, or an open-weight model you host yourself, which some teams choose when transcripts must not leave their own infrastructure. Behavior and cost differ by family and version; your eval is what tells you which differences matter for this task.
</Listen>

## Log now, evaluate later

In Studio 3 you will build evals, and the raw material is the record of what your system actually did. Hamel Husain's post on evals makes the case that looking at real traces is where improvement starts, and that you cannot look at traces you never saved. So decide now what every run writes down.

For each run: a transcript id (and a content hash, so you know exactly what was processed), the prompt version, the model id and settings such as effort, and the request id the API returns. For each stage: the raw model output, the parsed items, validation failures with reasons, and token usage and latency. For each tool call: the name, the input, the output, and whether it was an error. For human review: what the reviewer approved, edited (and what they changed), and rejected. Those review decisions are free labels. An edited owner tells you the normalization stage was wrong; a rejected item with a verified quote tells you the extraction stage over-reached.

One caution. Transcripts are sensitive: they contain names, plans, and sometimes personnel or customer information. Store logs with the same access controls as the transcripts themselves, keep only as long as you need, and remember that a transcript is also untrusted input, so treat anything in it that looks like an instruction as data (lesson 11).
</Listen>

## A definition of done

Write the definition of done before you build, so you are testing against something. Here is a starting point for the project; tighten it as you learn.

The pipeline runs end to end on a set of realistic transcripts, including messy ones, with no unhandled errors. Every item shown to the reviewer has an evidence quote that appears verbatim in the transcript. Owners resolve to directory entries or are explicitly unassigned, never guessed; dates resolve by documented rules or are flagged. Nothing is written to the tracker without approval, writes are idempotent, and the model has no tool that can send data outside the system. On your labeled set, recall and precision meet bars you chose in advance, and you report them with the size of the set. Cost per meeting is measured from real usage, not estimated. Every run produces the log described above. And you can explain, for each model choice, what evidence led to it.
</Listen>

<GoDeeper title="Where this design goes next">
Three extensions are worth knowing about, even if the project does not require them. **Batch processing:** if action items can arrive an hour after the meeting instead of instantly, the Batch API halves token prices. **Confidence routing:** have the extraction stage mark uncertain items, and route only those to a larger model or straight to the reviewer with a flag, which is a cheaper way to buy accuracy than running the largest model on everything. **Evaluation-driven iteration:** once the logs exist, every prompt or model change can be scored against the same labeled set before it ships. Eugene Yan's "Patterns for Building LLM-based Systems and Products" surveys these and related patterns, and Chip Huyen's *AI Engineering* covers model selection as an evaluation problem in depth.
</GoDeeper>
