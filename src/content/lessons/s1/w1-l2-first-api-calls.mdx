## One endpoint, one request shape

Almost everything you will build in this program goes through a single HTTP endpoint: the Messages API. You send a JSON body describing a conversation, and you get back one assistant message. Tools, structured outputs, images, and documents are all features of that same request, not separate APIs. Learn its shape once and the rest of the studio is variations on it.

A minimal request has three required fields. **`model`** names the exact model, for example `claude-opus-5-5`. **`max_tokens`** is a hard ceiling on how many tokens the model may generate in this response; it is a ceiling, not a target, and the model does not try to fill it. **`messages`** is the conversation so far: a list of turns, each with a `role` of `user` or `assistant` and some `content`. The first turn must be from the user.

Two more fields matter on day one. **`system`** is a top-level field (not a message) that holds your standing instructions: the role, the rules, the output format. And **`content`** can be either a plain string or a list of typed **content blocks**. A text block is the simple case. Images, PDF documents, tool calls, and tool results are other block types, and you will meet them in weeks 2 and 3. If you have used older chat APIs, notice that the system prompt is not a message with role "system" here; it lives in its own field.
</Listen>

```python
import anthropic

client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from the environment

resp = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    system="You are a release-notes editor. Reply in plain English, under 120 words.",
    messages=[
        {"role": "user", "content": "Rewrite for customers: fixed N+1 query in /orders, p95 down 40%."},
    ],
)

for block in resp.content:          # content is a list of typed blocks
    if block.type == "text":
        print(block.text)

print(resp.stop_reason)             # why generation stopped
print(resp.usage)                   # token counts you are billed for
print(resp._request_id)             # log this; support asks for it
```

## Reading the response

The response is one assistant message with a handful of fields you should treat as part of your contract. **`content`** is the list of blocks the model produced, in order. On current Claude models that list can include **thinking** blocks as well as text, because these models reason before answering; on Claude Opus 5.5, thinking is always on and its text is omitted by default, so you may see a thinking block with an empty string. That is why the example loops over blocks and picks the text ones instead of reading `content[0]`.

**`stop_reason`** tells you why generation ended, and it is the field beginners skip most often. **`usage`** reports token counts: `input_tokens`, `output_tokens`, and, when you use prompt caching, `cache_creation_input_tokens` and `cache_read_input_tokens`. Two details catch people. First, with caching, `input_tokens` counts only the tokens after your last cache breakpoint, so total input is the sum of all three input fields. Second, thinking tokens are billed as output tokens even when you never see their text, so `output_tokens` can be much larger than the visible answer. Finally, every response carries a **request id** (the `request-id` header, exposed by the Python SDK as `_request_id`). Log it with every call; it is how you and the provider find a specific request later.
</Listen>

<Callout type="pitfall" title="Prefill and sampling knobs are gone">
Two habits from older tutorials now cause 400 errors on current Claude models. Ending `messages` with a partial assistant turn ("prefill") to force a format is rejected; use instructions or structured outputs (week 2) instead. And on the current API version, `temperature`, `top_p`, and `top_k` are rejected; you steer depth with an effort setting instead. If a tutorial's code fails on a field like these, check its date before debugging your own code.
</Callout>

## Multi-turn is resent history

The API is stateless. It does not remember your previous request, so a "conversation" is something your code builds: after each reply, append the assistant's turn to your list, append the user's next turn, and send the whole list again. The model sees the full history every time, which is exactly why it can refer back to earlier turns.

That design has two consequences you should plan for. Cost and latency grow with every turn, because you pay for the entire history as input on each request; a 30-turn support chat bills its first message 30 times. And you control memory completely: you can drop, summarize, or edit old turns, which is powerful and also a way to confuse the model if you rewrite history carelessly. When you append the assistant's turn, append the full `content` list the API returned (all blocks, unchanged), not just the text you extracted. Current models check that returned blocks such as thinking come back exactly as they were produced. Prompt caching (week 2) is the standard way to make long, stable prefixes cheap.
</Listen>

```python
history = []

def ask(user_text: str) -> str:
    history.append({"role": "user", "content": user_text})
    resp = client.messages.create(model="claude-opus-5-5", max_tokens=16000, messages=history)
    history.append({"role": "assistant", "content": resp.content})  # keep every block, unchanged
    return "".join(b.text for b in resp.content if b.type == "text")

ask("Our churn went from 3.1% to 4.0% this quarter. Is that a big change?")
ask("Express that as a relative increase.")  # works only because turn 1 was resent
```

## Streaming: same work, sooner feedback

By default the SDK waits until the whole response is finished and then returns it. With **streaming**, the API sends server-sent events as tokens are produced, so your code can show text while the model is still writing. The total time to produce the response is about the same. What changes is **time to first token**, the delay before anything appears, which is what users perceive as responsiveness. For a long answer, the difference between a blank screen for twenty seconds and text appearing after one second is the difference between "broken" and "working."

Streaming is also a reliability tool, not only a UX choice. Anthropic's docs recommend streaming (or the Batches API) for long requests, because some networks drop idle connections, and the Python SDK refuses non-streaming requests that it expects to exceed a ten-minute timeout. A useful default: stream whenever output might be long or `max_tokens` is large. The SDK's stream helper accumulates the events for you and can hand back the same final message object a non-streaming call would, so you lose nothing.

The raw event sequence is worth knowing for debugging. A stream starts with `message_start` (carrying the message shell and initial usage), then for each content block a `content_block_start`, a series of `content_block_delta` events with the new text, and a `content_block_stop`. A `message_delta` carries the `stop_reason` and final output token count (cumulative), and `message_stop` ends the stream. `ping` events may appear anywhere. And an error can arrive mid-stream, after the HTTP 200, as an `error` event such as `overloaded_error`, so stream handling needs its own error path.
</Listen>

```python
import time

start = time.perf_counter()
first_token_at = None
with client.messages.stream(
    model="claude-opus-5-5",
    max_tokens=64000,
    messages=[{"role": "user", "content": "Draft a one-page incident postmortem template."}],
) as stream:
    for text in stream.text_stream:
        if first_token_at is None:
            first_token_at = time.perf_counter() - start
        print(text, end="", flush=True)
    final = stream.get_final_message()   # same Message object as a non-streaming call

print(f"\nTTFT {first_token_at:.2f}s, total {time.perf_counter() - start:.2f}s, stop={final.stop_reason}")
```

## Stop reasons: the success cases you must still handle

A 200 response means the request succeeded, not that the answer is usable. Check `stop_reason` after every call and decide explicitly what each value means for your code.

**`end_turn`** is the normal case: the model finished. **`max_tokens`** means the response hit your ceiling and is truncated. If you were expecting JSON, it is probably invalid; if you show it to a user, mark it as cut off. The fix is to raise `max_tokens` or continue the response, not to retry the identical request. **`stop_sequence`** means one of your custom stop strings fired. **`tool_use`** means the model wants you to run a tool and send back a result, which is week 3. **`pause_turn`** appears with server-side tools such as web search when a long tool loop pauses; you send the paused turn back to continue. **`refusal`** means the model declined, and it arrives as HTTP 200, so it never reaches your exception handler. On current models a `stop_details` object names the policy category. Anthropic's guidance is to retry on a fallback model, which the API can do for you on several models, or to rephrase. Treat refusals as a product event you log and review, because a pattern of refusals on legitimate traffic is a prompt or routing problem you can fix. **`model_context_window_exceeded`** means the output filled the context window; treat it like truncation.
</Listen>

## Errors: classify, then retry only what is transient

When a request fails, the API returns an HTTP error with a JSON body naming an error `type`, and the Python SDK raises a typed exception for each one. Sort them into two groups. **Do not retry** client mistakes: 400 `invalid_request_error` (a bad field, a missing parameter, a prefill), 401 `authentication_error` (bad or revoked key), 403 `permission_error`, 404 `not_found_error` (often a mistyped model id), and 413 `request_too_large`. Retrying these sends the same mistake again, so fail fast and surface the message.

**Do retry** transient failures: 429 `rate_limit_error`, 500 `api_error`, 529 `overloaded_error`, timeouts, and connection errors. Rate limits are per organization, measured in requests, input tokens, and output tokens per minute, and enforced with a token bucket, so capacity refills continuously and short bursts can trip a limit even when your per-minute average is fine. A 429 usually carries a `retry-after` header telling you how many seconds to wait; earlier retries will fail. One important exception: when your organization hits its monthly spend cap, the API returns a 429 with **no** `retry-after`, and retrying cannot succeed until access resumes. A retry loop without an attempt limit will spin on that forever.

The official SDK already retries connection errors, 408, 409, 429, and 5xx errors with exponential backoff, twice by default, honoring `retry-after`. You configure it with `max_retries` on the client or per request. Write your own wrapper only when you need different behavior, such as more attempts for a batch job, a fallback model, or logging of each attempt. Catch the SDK's typed exceptions, most specific first, rather than matching on error message strings.
</Listen>

## Backoff with jitter, and why the jitter matters

The standard retry schedule is **exponential backoff**: wait a base delay, then double it on each attempt, up to a cap. If attempt 0 waits up to 0.5 seconds, attempt 3 waits up to 4. The doubling gives an overloaded service room to recover.

Backoff alone has a flaw that Marc Brooker described on the AWS Architecture Blog: if many clients fail at the same moment, they all retry on the same schedule and arrive together again, in synchronized waves. Adding randomness, called **jitter**, spreads them out. His "full jitter" variant picks the delay uniformly between zero and the exponential value, and his simulations showed it reduced both total work and completion time compared with no jitter. In symbols: delay for attempt n is a uniform random number in the interval from 0 to min(cap, base times 2 to the n). If the server sent `retry-after`, wait at least that long.
</Listen>

<Callout type="pitfall" title="Retries that double your bill or your writes">
Retrying is safe for a pure question-and-answer call. It is not automatically safe when the call triggers side effects, such as a tool that sends an email or writes a row. Make those operations idempotent (safe to repeat, for example by keying writes on a request id) before you wrap them in retries. And remember that retries multiply worst-case latency: with a 60 second timeout and two retries, a caller can wait three minutes.
</Callout>

## Keep keys out of your code

An API key is a bearer credential: anyone who has it can spend your money and read whatever your organization's data settings allow. Treat it like a password. The SDK reads `ANTHROPIC_API_KEY` from the environment when you construct the client with no arguments, so the key never needs to appear in source code. For these labs, put it in `labs/.env`, which is gitignored, and let the shared test setup load it. In deployed services, use your platform's secret manager and inject the key as an environment variable at runtime.

Three rules cover most real incidents. Never commit a key, including in notebooks, test fixtures, or a "temporary" script; if one leaks, revoke it in the Console and issue a new one, because deleting the commit does not remove it from history or from anyone who cloned it. Never put a key in a prompt, a log line, or an error message you send to a user. And use separate keys, ideally in separate workspaces with their own spend limits, for development and production, so a runaway test loop cannot drain your production budget. The Console lets you set a monthly spend limit below your tier's cap for exactly this reason.
</Listen>

## Checks and balances for every call

Before you move on, fix one habit in place. Every call your code makes should end with three checks: did the request succeed (exceptions handled, transient ones retried with a limit), did the model finish (`stop_reason` is what you expected), and what did it cost (usage recorded with the request id). Those three lines are cheap, and they are what turns a demo into something you can operate. The next lesson uses the usage numbers to compare models on cost and latency, and to decide which model a task deserves.
