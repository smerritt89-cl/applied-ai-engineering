## The one idea everything else rests on

A large language model does one thing: given some text, it predicts what comes next. More precisely, it reads a sequence of **tokens** and outputs a probability for every token in its vocabulary being the next one. The application picks one token from that distribution, appends it, and asks again. A paragraph of output is this loop run a few hundred times.

That framing sounds too simple to explain what these models can do, and it is worth holding two things at once. The mechanism really is next-token prediction. And predicting the next token well, across trillions of words of human writing, requires the model to pick up grammar, facts, styles, and some ability to follow reasoning. Most of what you will build in this program sits on top of that loop, so understanding it pays off every time an output surprises you.
</Listen>

## Tokens: the unit you pay for

Models don't read characters or words. They read **tokens**: chunks of text from a fixed vocabulary, typically tens of thousands to a few hundred thousand entries, learned from data. Common words are usually one token. Rare words, names, code identifiers, and non-English text get split into several pieces. OpenAI's rule of thumb for English is about four characters, or three quarters of a word, per token; treat that as a rough estimate, because every model family uses its own tokenizer and the counts differ.

Tokens matter to you as a builder for three reasons. First, you are billed per token, separately for input and output, and output tokens usually cost several times more. Second, limits are expressed in tokens: the context window, and the maximum length of a response. Third, some odd failures come from tokenization. A model that sees "strawberry" as two or three chunks has no direct view of the individual letters, which is why letter-counting questions were a famous weak spot.
</Listen>

<Callout type="tip" title="Count, don't guess">
When cost or limits matter, measure. Providers expose token counts in every response (for example, the usage field in the Claude Messages API) and most offer a token-counting endpoint, so you can count before sending. You'll build a cost calculator in lesson 3.
</Callout>

## Sampling: why the same prompt gives different answers

At each step the model produces a score, called a **logit**, for every token in the vocabulary. The softmax function turns those scores into probabilities. Then something has to pick a token.

Always taking the most likely token (greedy decoding) sounds safe, but it tends to produce repetitive, flat text. Sampling from the distribution produces more natural text, at the cost of run-to-run variation. Two classic controls shape that sampling. **Temperature** divides every logit by a number before the softmax: below 1 sharpens the distribution toward the top choices, above 1 flattens it. **Top-p** (nucleus sampling, introduced by Holtzman and colleagues in 2019) samples only from the smallest set of tokens whose probabilities add up to p, which cuts off the long tail of unlikely tokens.

If you have a math background, temperature is a familiar object: it is the same parameter as in the Boltzmann distribution. Probability of token i is proportional to e raised to the logit over T. As T approaches zero you recover the argmax; as T grows you approach uniform.
</Listen>

<Callout type="note" title="Sampling controls are moving out of your hands">
Newer reasoning models increasingly manage sampling themselves. On the current Claude API version, requests that set temperature, top_p, or top_k are rejected, and you steer behavior through instructions and an effort setting instead. Other providers' reasoning models often restrict these parameters too. The concept still matters, because it explains run-to-run variation, but check each provider's docs before reaching for a temperature knob.
</Callout>

## The context window: everything the model can see

For each request, the model sees a single sequence of tokens: your system prompt, the conversation so far, any tool definitions and tool results, and the tokens it is generating. That sequence is the **context**, and its maximum length is the **context window**. Current frontier models offer windows from a few hundred thousand tokens up to a million or more.

Two consequences shape real applications. First, the API is stateless. The model doesn't remember your last request; chat applications create the feeling of memory by resending the history every time, and you pay for those tokens on every turn. Second, a big window is not free attention. Longer inputs cost more and take longer, and research such as "Lost in the Middle" (Liu and colleagues, 2023) found that models used information at the start and end of long inputs more reliably than information buried in the middle. Newer models have improved, but the engineering lesson holds: put the most important instructions and evidence where they are easy to find, and send only what the task needs.
</Listen>

## How models are trained, and why you should care

Modern assistants are built in stages. **Pretraining** teaches a model to predict the next token across a huge corpus of text and code; the result is a powerful document-completer with a **knowledge cutoff**, the date its training data ends. **Post-training** then shapes it into an assistant: supervised fine-tuning on example conversations, followed by reinforcement learning from human feedback and related methods. The 2022 InstructGPT paper by Ouyang and colleagues showed how much this stage matters: people preferred outputs from a much smaller instruction-tuned model over those from a far larger base model. Recent models add reinforcement learning on tasks with checkable answers, such as math and code, which is a large part of why they reason better than models from a couple of years ago.

Three practical consequences follow. One: the model doesn't know anything after its cutoff unless you give it that information, which is the whole motivation for retrieval in Studio 2. Two: post-training rewards answers that look helpful, so a model may produce a fluent, confident answer when it should say it doesn't know. Fluency is not evidence of correctness. Three: behavior varies between model families and versions, because their post-training differs. A prompt tuned on one model is a hypothesis on the next, which is why this program treats evaluation as a core skill rather than an afterthought.
</Listen>

<Callout type="pitfall" title="Treating the model like a database or a pure function">
Two habits cause most early bugs. Asking the model for facts it may not have, and trusting the answer because it sounds sure. And assuming that the same input always gives the same output, so one good test run feels like proof. The fixes come later in this studio: give the model the facts (context and retrieval), constrain the output (structured outputs), and check the result (validation now, evals in Studio 3).
</Callout>

<GoDeeper title="What is actually inside the model?">
The network that produces those probabilities is a **transformer**, introduced in "Attention Is All You Need" (Vaswani and colleagues, 2017). Each token becomes a vector; layers of **attention** let every position gather information from earlier positions; and a final layer maps the last vector to a score for every vocabulary entry. You don't need these internals to build applications, but they explain a lot: why cost grows with context length, and why the model "sees" only tokens. ## What this means for the code you write

Hold on to five working rules as you start building. Budget in tokens, because tokens are cost, latency, and limits. Expect variation, so validate every output your code depends on. Treat context as something you design: what goes in, in what order, and what stays out. Know your model's cutoff, and supply current facts yourself. And evaluate on many examples, because one good answer proves very little. The next lesson puts these rules to work in your first API calls.
</Listen>
