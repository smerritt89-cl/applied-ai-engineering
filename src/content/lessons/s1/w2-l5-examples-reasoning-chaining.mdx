## Examples are the strongest lever you have, so aim them

Showing beats telling. A few examples of input and desired output (called few-shot or multishot prompting) are, in Anthropic's words, one of the most reliable ways to steer format, tone, and structure. Google's Gemini guide goes further and recommends including few-shot examples in prompts as a default, noting that clear examples can sometimes replace instructions entirely.

Anthropic's docs give three properties to aim for. Examples should be **relevant**, mirroring your real inputs rather than toy cases. They should be **diverse**, covering edge cases and varying enough that the model doesn't latch onto an accidental pattern. And they should be **structured**, wrapped in `<example>` tags (inside an `<examples>` block) so the model can tell them apart from instructions. The docs suggest three to five examples as a starting point. Google adds two cautions: keep the format identical across examples, and don't include so many that the model starts copying them too closely.

For a PM-flavored case, say you want status updates labeled on_track, at_risk, or blocked. Good examples would include a short update and a rambling one, one where the risk is buried in the last sentence, and one that sounds alarming but is actually on track. Each label appears at least once, and no single label dominates.
</Listen>

<Listen>
## What models actually take from examples

Research on few-shot prompting is humbling, and worth knowing because it changes how you choose examples.

Min and colleagues (2022) replaced the labels in classification examples with random ones and found accuracy barely dropped, across 12 models. What mattered more was that the examples showed the **set of possible labels**, the **kind of input text**, and the **format** of the answer. In other words, models lean heavily on examples as a template. That is good news for format control and bad news for accidents: if every example summary opens with "Overall," or runs exactly three sentences, your outputs will too. Call this **format leakage**, and prevent it with deliberate variety in everything you don't want copied.

Order matters too, at least on the models of that era. Lu and colleagues (2021) showed that simply reordering the same few examples could move a model from near state-of-the-art accuracy to near chance, and that a good order for one model did not transfer to another. Zhao and colleagues (2021) traced part of this instability to biases toward answers that appear near the end of the prompt or appear often in the examples.

These studies used GPT-3-era models, and today's instruction-tuned models are generally more robust. But the engineering conclusions hold: balance your labels, vary the surface features, and when results matter, test the same prompt with the examples in a shuffled order. If the score moves, your prompt is fragile.
</Listen>

<Callout type="pitfall" title="Examples that teach the wrong lesson">
Three common accidents: every example has the same label, so the model over-predicts it; every example has the same length or opening phrase, so outputs copy it; or the examples are all easy, so the model has never seen what to do with a messy input. Review your examples the way you would review a test set, because that is effectively what they are.
</Callout>

## Letting the model reason: where chain of thought came from

In 2022, Wei and colleagues published "Chain-of-Thought Prompting Elicits Reasoning in Large Language Models." The method was simple: include a few worked examples whose answers show intermediate reasoning steps, not just the final answer. On arithmetic, commonsense, and symbolic reasoning tasks, this improved accuracy substantially, and the gains appeared in sufficiently large models. Their headline result: a 540-billion-parameter model prompted with eight chain-of-thought examples reached state-of-the-art accuracy on GSM8K, a benchmark of grade-school math word problems.

The practical version became a staple: ask the model to think step by step before answering, and to put its final answer inside `<answer>` tags so code can extract it. Anthropic's tutorial teaches exactly this, under the name "precognition." The mechanism makes sense given week 1: the model generates one token at a time, so writing out intermediate steps gives later tokens something to build on, rather than forcing the answer to come out in the first few tokens.

That is the history. The present is different, because the major providers now train models to reason before answering on their own.
</Listen>

## Now: adaptive thinking and effort levels

Current Claude models produce **thinking** content blocks before their visible answer. In adaptive mode, which Anthropic recommends for current models, the model decides when to think and how much, based on the request's difficulty and on the **effort** setting. Effort, set as `output_config.effort`, ranges from `low` through `medium`, `high`, and `xhigh` to `max` (not every model supports every level). It is a behavioral signal rather than a strict budget, and it applies to the whole response, not only the thinking: lower effort also means terser text and fewer tool calls. If you need a hard ceiling on spending, `max_tokens` is the strict limit. Defaults differ by model; on Claude Opus 5.5, thinking is always on and the default effort is `medium`, so set effort explicitly rather than relying on the default.

Two details matter when you write code against this. First, the text in a thinking block is a summary of the reasoning, not the raw chain of thought, and on many current models it is omitted (an empty string) unless you ask for summaries. Second, thinking blocks arrive before the text, so select blocks by type, never by position.

Other providers have converged on similar controls, under different names. At the time of writing, OpenAI's reasoning models take a `reasoning` setting with an effort level, Google's Gemini models take a `thinking_level`, and xAI's Grok reasoning models take `reasoning_effort` (defaulting to high, with reasoning that cannot be turned off). Check each provider's current docs before relying on specific levels or defaults; they change with model releases.

What does this mean for prompting? Anthropic's guidance is that general instructions such as "think thoroughly" often work better than a hand-written step-by-step plan, because the model's own reasoning frequently beats the plan you would prescribe. Manual chain-of-thought prompting is now a fallback for when thinking is off; on models with thinking always on, the docs say to rely on thinking, at a lower effort level if cost matters. OpenAI's guide offers a memorable analogy: a reasoning model is like a senior colleague you can give a goal to, while a non-reasoning model is like a junior one who needs explicit instructions.
</Listen>

    if block.type == "thinking":
        print("[reasoning summary]", block.thinking)
    elif block.type == "text":
        print(block.text)

## When visible reasoning helps, and when it hurts

Reasoning, visible or hidden, costs tokens and time. It earns that cost on multi-step problems: calculations, planning, reconciling conflicting sources, debugging. For a simple lookup or a short classification, it mostly adds latency, which is why the docs recommend low effort for simple, high-volume work, and why the right level is something to measure.

Asking for reasoning **in the visible answer** has its own trade-offs. It helps when you want an audit trail a reviewer can read, or when the reasoning is itself the deliverable, such as quoting the evidence before giving a verdict (the quote-first pattern from lesson 4, which you can check with a string search). It hurts when code has to parse the output, since prose mixed into an answer breaks parsers unless you fence the final answer in tags. And it can mislead.

That last point deserves care. Turpin and colleagues (2023) showed that chain-of-thought explanations can systematically misrepresent why a model gave its answer: when they biased models toward an answer (for example, by making the correct option always "(A)" in the examples), the models changed answers and then wrote explanations that never mentioned the bias. Anthropic's 2025 research on its own reasoning models found the same kind of problem: models often used a hint planted in the prompt without saying so in their reasoning. The engineering conclusion: treat written reasoning as useful evidence for debugging, not as proof. Verify the answer itself.
</Listen>

## Prompt chaining: split the work into steps you can check

Even with strong reasoning models, some tasks are better split into several calls, each with one job. Anthropic's best-practices page says explicit chaining remains useful when you need to inspect intermediate outputs or enforce a particular pipeline. Anthropic's "Building effective agents" essay describes prompt chaining as a workflow where each call processes the previous call's output, with programmatic checks (it calls them gates) between steps, trading some latency for accuracy.

Back to the status-report example. One giant prompt that reads a week of updates and writes the executive summary gives you one output to judge, and when a date is wrong you can't tell why. A chain gives you three checkable steps. Step one extracts every milestone, owner, and date as JSON. A code gate checks that the JSON parses and that each date string actually appears in the source updates. Step two writes the summary from the checked list only. Each step has its own test cases, and you can run the cheap extraction on a smaller model if your tests show it holds up.

The most common chain, according to Anthropic's docs, is **self-correction**: draft, then have the model review the draft against explicit criteria, then revise based on the review. Each step is a separate call, so you can log it, score it, or stop early.
</Listen>

## Bigger model, more effort, or a chain?

When output quality falls short, you have three main levers beyond rewording the prompt, and they cost different things.

**Raise effort** first when the task needs more reasoning and you are already on a capable model. It is a one-line change, it keeps you on one model, and Claude's effort docs recommend tuning it per workload and testing rather than assuming. **Build a chain** when the failure is specific and checkable, when different steps need different tools or context, or when you need a log of where things went wrong. **Use a bigger model** when errors persist across effort levels and the task needs capability the current model lacks. Anthropic's prompt engineering overview makes the reverse point too: some problems, such as latency and cost, are better solved by choosing a different model than by more prompting.

Notice the shared requirement. You can only choose between these with evidence, meaning the same test cases run under each option, compared on quality, cost per completed task, and latency. Without a test set, every lever looks like it helped, because you happened to try it on an input where it did. Lesson 6 builds that test set and the habit of using it.
</Listen>

<GoDeeper title="Calibration, self-consistency, and the open questions">
Zhao and colleagues proposed **contextual calibration**: ask the model for its prediction on a content-free input such as "N/A", measure its bias toward each label, and correct for it. You rarely do this with API models today, since you often don't get the probabilities, but the idea is a useful mental model for why balanced examples matter.

A related technique, **self-consistency** (sampling several reasoning paths and taking the majority answer), comes up in week 3 as a way to estimate confidence.

On reasoning faithfulness, the research is active. Anthropic's 2025 post describes both the testing method (planting hints and checking whether the reasoning admits using them) and its limits. If your product shows users the model's reasoning, read it: it affects how much weight a reviewer should give that reasoning.
</GoDeeper>
