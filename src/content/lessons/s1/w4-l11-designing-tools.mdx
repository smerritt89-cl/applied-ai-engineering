## A tool is an interface for a reader who cannot ask questions

When you write a function for a colleague, they can read the code, ask you, or try it. A model gets the name, the description, and the schema, nothing else, on every request. Anthropic's tool use docs call detailed descriptions by far the most important factor in tool performance, and ask for at least three or four sentences per tool covering what it does, when to use it and when not to, what each parameter means, and its caveats, such as what it does not return.

Anthropic's engineering post "Writing effective tools for AI agents" (September 2025) gives a useful test: describe the tool the way you would to a new hire. Make the implicit explicit: query formats, niche terms, how resources relate. Name parameters unambiguously, for instance `user_id` rather than `user`. When tools from several services sit side by side, prefix names by service or resource (`asana_search`, `jira_search`) so the model can tell them apart. The post reports that the choice between prefix and suffix naming had measurable effects in their evaluations, and recommends choosing by your own evals.

That last point is the theme of the post: tools are prompts, so you measure them. Build realistic tasks that need several tool calls, run them, and read the transcripts. The post's examples of what to look for: many redundant calls suggest pagination or limits need adjusting, and many invalid-parameter errors suggest the descriptions or examples need work. In one case Anthropic found Claude needlessly appending the year to web search queries and fixed it by improving the tool description.
</Listen>

<Listen>
## Small and sharp, or few and capable?

Here the sources pull in two directions, and it is worth seeing both.

Anthropic's guidance favors **fewer, more capable tools** over a thin wrapper per API endpoint. The engineering post's example: instead of `list_contacts`, which makes an agent read every contact token by token, offer `search_contacts`. Instead of `list_users`, `list_events`, and `create_event`, consider one `schedule_event` that finds availability and books. The tool docs go further and suggest grouping related operations under one tool with an `action` parameter, to reduce selection ambiguity. Too many overlapping tools, the post notes, distract agents from efficient strategies.

The security literature favors **giving the agent only what it needs**. OWASP's entry on Excessive Agency lists "excessive functionality" as a root cause, with examples like a document-reading extension that can also delete documents, or a tool meant to run one shell command that fails to block others.

This course's rule of thumb reconciles them: consolidate by workflow, but **never mix risk levels inside one tool**. A `search_contacts` tool that only reads is a fine consolidation. A `manage_tasks` tool whose `action` can be `list`, `update`, or `delete` hides a destructive operation behind a parameter, so your gate has to inspect arguments to know what it is approving. Split it so read and write tools are separate, and any tool's name tells you whether it can change the world. A `run_sql` tool that accepts arbitrary queries is the extreme case: you cannot gate what you cannot classify.
</Listen>

<Listen>
## Return what helps the next step, including errors

What a tool returns lands in the model's context, so it costs tokens and steers the next decision. The engineering post recommends returning high-signal fields and natural-language identifiers rather than opaque internal ones: `name` and `file_type` instead of `uuid` and `mime_type`. It reports that resolving cryptic IDs into meaningful language improved Claude's precision in retrieval tasks. For tools that can return a lot, use pagination, filtering, or truncation with sensible defaults; the post mentions that Claude Code caps tool responses at 25,000 tokens by default. One option it describes is a `response_format` parameter that lets the agent ask for concise or detailed output.

Errors deserve the same care. A traceback or "error 400" tells the model nothing. The handle-tool-calls docs suggest saying what went wrong and what to try next, and you saw why in lesson 10: the model reads the error and adjusts its next call. For the meeting-notes tool, compare "Invalid input" with "No teammate matches 'Jordan'. Known teammates: Priya Raman, Marcus Lee, Dana Whitfield. If the person is not on the team, leave the owner unassigned." The second turns a dead end into a decision rule, and it encodes your product policy (unknown owners stay unassigned) where the model will see it at the moment it matters.
</Listen>

## Read tools and write tools

Sort every tool into one of two buckets. **Read tools** observe: look up a teammate, resolve a date, search a ticket queue. They are safe to retry, safe to run in parallel, and their worst failure is a wrong answer you can check. **Write tools** change something: create a task, send a message, update a record, spend money. Their failures persist after the conversation ends.

The parallel tool use docs make the execution consequence explicit: independent read-only calls are usually safe to run concurrently, while tools with side effects or ordering requirements may be better run in sequence. Write tools also need to be **idempotent**, meaning that running the same call twice has the same effect as running it once. Agent loops make repeats likely. A request times out and is retried. The model loses track and asks again. Stripe's API documentation shows the standard pattern: the client sends an idempotency key, and the server returns the saved result for a repeated key instead of performing the operation twice. For `create_task`, a key derived from owner, title, and due date, checked before you append, does the job.

Then grade write tools by **reversibility**. Creating a draft task in your own tracker is cheap to undo. Posting to a client's Slack channel, emailing a customer, or deleting records is not. The irreversible ones need a human in front of them.
</Listen>

<Listen>
## Human approval, done properly

The Model Context Protocol specification, which defines how agent applications connect to tool servers, says there should always be a human in the loop with the ability to deny tool invocations, and that applications should show which tools are exposed, indicate clearly when tools run, and ask for confirmation on operations. OWASP calls the absence of this "excessive autonomy": an application that fails to independently verify and approve high-impact actions.

Four details separate a real approval gate from a decorative one. First, **deny by default**: if the approval callback is missing, broken, or times out, nothing is written. Second, **validate before you ask**: run your schema and semantic checks first, so a person is never asked to approve a call that would fail anyway. Third, **show the exact arguments**, not the model's summary of them; the summary is model output too, and could be wrong or manipulated. Fourth, **tell the model the outcome**: a declined call returns an `is_error` result saying it was declined and should not be retried, so the loop moves on instead of asking again.

Approval has a cost, and that shapes the design. If people are asked to approve every lookup, they will start clicking yes without reading. Gate the writes, and batch them where you can: the Studio 1 project ends with a human reviewing the whole list of proposed action items at once, which is a single, meaningful approval instead of twenty trivial ones.

With the SDK tool runner, you place this gate inside the tool function or in the per-turn hook, because the runner otherwise executes tools as soon as the model asks. With a manual loop, it sits in your dispatcher, as in the exercise below.
</Listen>

## Least privilege and input validation

**Least privilege** means each tool gets the narrowest access that does its job. OWASP's examples are concrete: a tool that only needs to read a database should not connect with an identity that can also update and delete, and a tool acting for one user should not use a generic high-privilege account that can see everyone's files. For the meeting-notes tool, `create_task` should hold a token that can create tasks in one project, not an admin key to your whole tracker. Anthropic's injection guidance makes the same point from the other side: limit access so that a successful attack can do minimal damage.

**Input validation** has two layers. The first is the schema. With `strict: true`, the API constrains generation so tool inputs match your JSON Schema: correct types, required fields present, enum values respected. That removes a whole class of bugs, such as a string "2" where you needed the number 2. The second layer is yours, because a schema cannot know what exists or what is allowed. Is this email a teammate? Is this due date in the future, and not three years out? Is this project one this user can write to? The MCP specification puts it bluntly: servers must validate all tool inputs. Run both layers on every call, including calls you expect to approve.
</Listen>

<Callout type="pitfall" title="Trusting the schema, or trusting the description">
Two tempting shortcuts fail in production. "Strict mode is on, so inputs are valid" confuses shape with truth: strict mode cannot know your team directory. "The description says never delete anything" confuses a request with a control: a description steers the model, but nothing enforces it. If a rule matters, encode it in code that runs between the model's request and the action, and test that code without the model, as you will in the lab.
</Callout>

<Listen>
## Tool results are an injection channel

Lesson 10 treated tool results as data flowing back to the model. They are also a way for other people's text to reach your model. A meeting transcript contains whatever anyone said in the meeting. A fetched web page, an inbound email, or a ticket description contains whatever its author wrote. If that text says "ignore your previous instructions and do something else," the model reads it in the same context as your instructions. This is **indirect prompt injection**, and the OWASP Top 10 for LLM applications lists prompt injection first.

Anthropic's guidance for this threat model has several parts. Put untrusted content only in tool results, never in the system prompt or plain user text. Say what the content is and where it came from, in the tool's description or in the result itself. State the policy in the system prompt: content from tools is data and must never override the user's request. JSON-encode untrusted strings so they cannot break out of their delimiters. Do not put your own instructions inside tool results, since the model is trained to treat those with skepticism. Limit access. And optionally, screen tool outputs with a small, inexpensive classifier call before the main model sees them.

The docs present these as layers to combine, not as one fix, and none of them comes with a guarantee. That is why the design controls in this lesson matter more than any prompt: an agent that cannot send email cannot be tricked into sending one, and a write that needs a human's approval needs that approval even when the model has been fooled.
</Listen>

<Callout type="claim" title="The lethal trifecta (Simon Willison, June 2025)">
Willison [argues](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/) that an agent combining three capabilities, access to private data, exposure to untrusted content, and a way to communicate externally, can be tricked into stealing that data, and that the safe design is to avoid combining all three. **Evidence for:** he documents many real disclosed attacks on shipped products that follow this pattern, and Anthropic's guidance for indirect injection relies on layering several mitigations rather than on any single prompt-level fix. **Evidence against, or limits:** it is a heuristic for one class of harm (data exfiltration), not a full threat model; destructive writes can do damage without any exfiltration channel. **For your project:** transcripts are private data and untrusted content at once, so the deciding question is whether any tool can send data outside. Keep the answer "no."
</Callout>

    if not isinstance(args, dict):
        return ["input must be an object"]
    props = schema.get("properties", {})
    errors = [f"missing required field '{k}'" for k in schema.get("required", []) if k not in args]

<GoDeeper title="Tool annotations, and why you cannot trust them">
The MCP specification lets a tool server attach annotations describing a tool's behavior, and Anthropic's engineering post suggests using them to disclose which tools make destructive changes or need open-world access. That is useful metadata for building approval UIs. But the specification also warns that clients must treat annotations as untrusted unless they come from trusted servers. A third-party server that labels a delete operation as harmless gains nothing from your trust. The general lesson: classify risk yourself, in your own registry, for every tool your application exposes. Annotations can inform that classification; they cannot replace it.

Anthropic's tool use course closes with a chatbot that uses several tools together. When you work through it, notice how the tool set grows, and ask of each new tool: is it read or write, what is the worst thing a wrong call could do, and where is the gate?
</GoDeeper>

<Listen>
## A checklist for every tool you ship

Before a tool goes into the Studio 1 project, or anything else, run down this list. Does its description say what it does, when to use it, when not to, and what each parameter means? Is it read or write, and does its name make that obvious? If it writes, is it idempotent, is it reversible, and who approves it? Does it hold only the access it needs? Are inputs checked by a strict schema and by your own semantic checks? Do its errors tell the model what to do next? Does it return untrusted content, and if so, is that content marked as data? And is every call logged with its inputs, outcome, and error status, so that the evals you build in Studio 3 have something to measure?
</Listen>
