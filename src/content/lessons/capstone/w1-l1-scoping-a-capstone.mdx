## A capstone is an argument, not a feature list

Every studio project so far came with a problem already chosen. The capstone doesn't, and that is the hardest part. Most weak capstones fail in week 1, not week 5: they pick a technology ("I want to build a multi-agent system with MCP") and then look for a user, or they pick a problem so broad ("help instructional designers") that no amount of testing could show it works.

Think of the capstone as an **argument** you will make to a skeptical reviewer: for this user, doing this job, my system beats the honest alternative by this much, at this cost, with these known risks. Every scoping decision this week either makes that argument possible or makes it impossible. You can't argue "beats" without a baseline. You can't argue "by this much" without an eval set and metrics. You can't argue "known risks" without having looked for them.

This lesson walks through the five decisions that set up the argument: the problem, the metrics, the baseline, the eval set, and the risk register. None of them needs code, and all of them should be finished before you write any system code. That ordering feels slow. It is the reason the remaining five weeks go fast, because every later decision ("should I add hybrid search?", "is the cheaper model good enough?") becomes a measurement instead of a debate.
</Listen>

<Listen>
## Choosing the problem

Good capstone problems share four properties.

**A named user with a job.** Not "educators" but "an instructional designer checking a course page against WCAG before handoff." Google's problem-framing course asks you to state the ideal outcome independently of any model: what the product should do for the user, before you think about how. If you can't describe the outcome without saying "AI," you haven't found the problem yet.

**A current process you can describe with a number.** How long does it take today, and how often does it go wrong? Your own experience in course development and delivery is a legitimate source here, as long as you describe patterns rather than clients. The number doesn't have to be precise, but it anchors your success metric and makes the write-up land with non-engineers.

**Checkable outputs.** Retrieval, extraction, compliance, and status questions have answers you can label: the requirement is in the document or it isn't, the citation supports the claim or it doesn't. Open-ended generation ("write a better course description") is much harder to evaluate in six weeks. If you can't imagine writing 100 test cases with expected outcomes, narrow the problem until you can.

**Public or synthetic data only.** The repo is public, so client documents, learner records, contracts, and internal trackers are off the table, including in screenshots and traces. Public standards, open courseware, government RFPs, and synthetic corpora you generate (and label as synthetic) all work. Check each source's license and record it.

Finally, choose the simplest architecture that could work. Anthropic's guidance on effective agents recommends starting with the simplest solution and adding agentic autonomy only when it demonstrably helps. The capstone requires an agent with tools, so find the part of the job that genuinely needs judgment about what to do next, and keep the rest as a fixed workflow.
</Listen>

## Success metrics, failure metrics, and non-goals

A metric turns "it works" into something you can compare. Google's problem-framing course makes a distinction worth adopting: **product success metrics** describe what changes for the user (time saved, errors avoided, tasks completed) and are separate from **model metrics** such as accuracy or recall. You need both, and you should check that improving the model metric would actually move the product metric. If better retrieval recall wouldn't change whether the designer trusts the output, recall isn't your headline.

The same course recommends defining a **failure metric** alongside success, with targets for both, so the space between them is small and explicit. For a compliance-matrix builder: success is a complete matrix in under an hour with no missed mandatory requirements on held-out RFPs; failure is any missed mandatory requirement, or a matrix that takes longer to check than to write by hand. Writing the failure condition down in week 1 protects you from redefining success in week 6.

Martin Zinkevich's Rules of Machine Learning, written from Google's production experience, puts metrics second only to "don't be afraid to launch without machine learning," and recommends a simple, observable, attributable first objective. For a capstone, that means one headline metric you can compute on every eval case, plus a small number of guard metrics (cost per task, p95 latency, attack success rate, wrong-abstention rate) that must not get worse.

Then write the **non-goals**. Malte Ubl's description of design docs at Google treats non-goals (things that could reasonably be goals but that you are deliberately excluding) as a core section, and Google's Technical Writing One course gives the same advice for any document: state the scope and the non-scope. "Does not support scanned PDFs." "Does not send email; drafts only." "English only." Each non-goal is a feature you have already said no to, which makes the next request to add it easy to decline.
</Listen>

<Callout type="tip" title="Your scope doc, on one page">
User and job. Current process, with a number. Ideal outcome in one sentence, with no mention of AI. Headline success metric and target. Failure metric. Guard metrics. Baseline. Non-goals. Data sources and licenses. The top five risks. If it doesn't fit on one page, the scope is too big.
</Callout>

## The baseline: the comparison a reviewer will accept

A number without a comparison can't be defended. "81 percent task success" invites the obvious question: compared with what? The baseline is your answer, and choosing it is a judgment call that a reviewer will check.

A good baseline is the **simplest credible alternative** the user could have instead. Usually that is one of three things. The current manual process, measured on a sample (how long it takes and how many errors a careful person makes). A non-AI tool: keyword search, a linter, a spreadsheet filter. Or a single model call with no retrieval, no tools, and no verification, which tells you what your architecture adds on top of the raw model.

Pick the one that a skeptical reviewer would consider the real competition, and if two are plausible, run both. Run the baseline on the same eval cases with the same graders as your system, so you can report **paired** differences, the method from Studio 3. The baseline also protects you. If it already meets your success target, you have learned that in week 1 rather than week 6, and you can move to a harder slice of the problem where your system has room to prove itself.
</Listen>

<Listen>
## The eval set comes before the system

The most important ordering rule in the capstone: build the eval set before you build the system. There are two reasons.

The first is bias. Once a system exists, you unconsciously write test cases it can handle, because those are the cases you have been looking at. Cases written first describe the user's job; cases written later describe your system. Anthropic's guide to agent evals makes the same practical point from the other side: evals get harder to build the longer you wait, and you don't need hundreds of tasks to start. It suggests that 20 to 50 tasks drawn from real failures is a good beginning, and that the manual checks you already run during development are a natural source.

The second reason is that the eval set **is** the specification. Writing 100 cases with expected outcomes forces decisions you would otherwise defer: what counts as a correct answer, when the system should abstain, which mistakes are worse than others.

For the capstone, aim for at least 100 cases in week 1 and grow it through week 4. Tag each by source: realistic cases written from the user's job, synthetic cases generated for coverage (and spot-checked), **should-abstain** cases the system must decline, and **adversarial** cases such as injected instructions. Split it into dev and a sealed held-out set of at least a quarter of the cases, as Hamel Husain's evals FAQ and Studio 3 describe, and decide now how rarely you will run held-out (end of weeks 2, 4, and 6 is a good rule). Prefer binary pass or fail labels with a written reason, because they are faster to label consistently and easier to put an interval on.
</Listen>

## The premortem and the risk register

Gary Klein's premortem, described in the Harvard Business Review in 2007, is a simple exercise with a useful twist. Instead of asking "what could go wrong?", you assume the project has **already failed** and ask each person to write down why. Klein's argument is that starting from the failure makes it easier for people with doubts to voice them during planning, when they are still cheap to act on.

For a solo capstone, run it on yourself and, if you can, with a peer or mentor. Imagine it is week 6 and the defense went badly. Why? Typical answers: the labels turned out to be wrong; the corpus license didn't allow redistribution; the agent worked on dev and collapsed on held-out; costs were ten times the estimate; a reviewer hid an instruction in a retrieved document and the agent followed it; you ran out of time because the scope grew.

Turn each reason into a row in a **risk register**: the risk, likelihood and impact (1 to 5 each), exposure (their product), an owner (you, for most), a mitigation, and a trigger that tells you the risk is materializing ("held-out score more than 10 points below dev"). NIST's AI Risk Management Framework is a good reference for the wider set of risks AI systems carry, from validity and reliability to security and privacy; you don't need its full process for a capstone, but skim its categories so your register isn't only technical.

Rank by exposure and spend week 1 mitigating the top three. Revisit the register at each milestone, and publish its final state in your write-up: reviewers trust a project more when it shows the risks it looked for and what happened to each.
</Listen>

<Callout type="pitfall" title="Scoping by ambition">
The most common week-1 mistake is choosing scope by what would be impressive rather than what can be measured in six weeks. Seven tools, three user types, and a web UI look like a stronger project in a proposal and produce a weaker one at the defense, because none of it gets evaluated properly. A good test: for every feature, name the eval cases that cover it. A feature with no cases is a feature you can't defend, so cut it or write the cases now.
</Callout>

## Model selection starts in week 1, too

Scoping is also where you set up the evidence for model choices. Your eval set and baseline let you answer questions that otherwise turn into opinion: does the frontier model beat a cheaper tier on this task, does an open-weight model running locally meet the bar for a privacy-sensitive user, does a long-context call do as well as retrieval? Write down the candidates you expect to compare (for example, two tiers from one provider and one model from another provider or an open model), and the guard metrics that would decide between them, such as cost per task and p95 latency.

Don't run that comparison yet. The point in week 1 is that you will be **able** to run it later, on the same cases, with paired statistics, instead of picking a model because it is the one you used last. That is the habit a working team needs most: a standing eval set that turns "should we switch models?" from a meeting into a one-command run.
</Listen>

<GoDeeper title="Proxy metrics and Goodhart's problem">
Many capstones can't measure the product outcome directly in six weeks: you can't observe a real proposal team for a month. So you measure a **proxy** (requirement recall on labeled RFPs) and argue it predicts the outcome (fewer missed requirements in real bids). Google's problem-framing course notes that no proxy is perfect and suggests choosing the one with the fewest drawbacks. Be explicit about the gap in your write-up: state the proxy, why you believe it tracks the outcome, and what evidence would show it doesn't. And watch for optimizing the proxy at the outcome's expense, for example raising recall by flagging every sentence as a requirement, which a good guard metric (precision, or time to check the output) will catch. For a longer treatment of planning AI applications, including setting expectations and milestones, see chapter 1 of Chip Huyen's *AI Engineering*.
</GoDeeper>
