## What "fair" means

Sooner or later someone asks: should we switch to the new model from another provider? It's on top of a leaderboard, it's cheaper, a competitor uses it. Lessons 7 and 8 gave you the measuring instruments. This lesson is about using them so the comparison measures the models and not your setup.

Start by naming what you're comparing. Users don't experience a model; they experience a **system**: model plus prompt plus settings (reasoning effort, max output tokens, tools) plus harness (retries, parsing, how tool results are fed back). Two systems can share a model and behave very differently, and the question "is model X better than model Y?" only has an answer for specific configurations on a specific task. So the unit of comparison is a configuration, and the claim you're entitled to make is "on our task, configuration A beats configuration B by this much, with this interval."

Fairness has four parts. **Same task and data**: every candidate answers the same questions, graded by the same graders, so the comparison can be paired (lesson 7). **Equal effort**: each candidate gets a comparable chance to be at its best, which is the subject of the next two sections. **Same conditions**: same time window, same region where possible, the same retry and timeout rules, and pinned model ids. And **a decision rule written down before you look**: the quality bar, the cost and latency limits, and how big a difference must be to matter. The last one is easy to skip and does the most to keep you honest, because everyone, engineers included, finds reasons to prefer the result they hoped for.
</Listen>

<Listen>
## Per-model prompt tuning, with equal budgets

A prompt tuned for months on one model carries that model's quirks: the phrasing it responds to, the formatting it needs spelled out, the failure modes you patched with extra instructions. Run it unchanged on another model and you're comparing a fitted system with an unfitted one. Each provider publishes its own prompting guide (Anthropic's prompting best practices, OpenAI's prompt engineering guide, Google's prompt design strategies for Gemini), and their advice differs in emphasis, as Studio 1 showed. The incumbent advantage is real, and it biases most informal comparisons toward whatever the team already uses.

The fix is an **equal tuning budget**. Split your questions into a development set and a held-out test set. Give each candidate the same allowance on the dev set: the same number of prompt iterations, or the same engineer-hours, starting from the same task description and following that provider's guidance. Mechanical adaptations (each API's parameter for the system prompt, its structured-output mechanism, its tool format) don't count against the budget, because they are porting, not tuning. Then freeze every configuration and score each **once** on the test set.

Two rules make this work. The test set is touched once, at the end; if you iterate on it, the winner is partly the configuration that best fits those particular questions (lesson 7's GoDeeper on searching). And record the budget each candidate actually used, so a reader can see the comparison was even. When a team can't afford equal tuning, the honest report says "the incumbent prompt, unmodified, on the challenger" and treats a loss as inconclusive rather than as a verdict.
</Listen>

<Listen>
## Equal effort budgets: reasoning settings and harnesses

Current models expose a dial for how much they think before answering, under different names. Claude takes an effort setting (low through max), OpenAI's reasoning models take a reasoning effort, Gemini models take a thinking setting, and xAI's Grok reasoning models take a reasoning effort as well. Defaults differ between providers and even between models from the same provider. A comparison of one model at its maximum setting against another at its default isn't a comparison of models; it's a comparison of budgets.

There are two defensible designs. **Matched cost**: pick settings so each candidate spends roughly the same per task, measured from usage on the dev set, then compare quality. **Sweep and compare frontiers**: run each model at two or three effort levels and plot quality against cost per task. The second is more work and much more informative, because the answer is often "model A at low effort matches model B at high effort for a third of the price," which no single run would show. Count thinking tokens in cost and latency; providers generally bill them as output tokens, so check each pricing page.

The harness needs the same scrutiny. Use the same max output tokens (or the documented maximum for each, if your task needs long answers), so no candidate fails by truncation. Use the same retry policy and timeouts, and count retries in cost. Use each provider's native structured outputs or tool format rather than forcing one provider's convention onto another. And log failures by type (wrong answer, refusal, malformed output, timeout): a model that loses on timeouts has a different problem, with a different fix, from one that loses on accuracy.
</Listen>

## Cost per successful task, and latency as a constraint

Price per million tokens is an input, not an answer. What you pay for is **completed work**: cost per successful task is total spend (input, output and thinking tokens, retries, any judge calls) divided by the number of tasks that passed. A model with a third of the price per token can cost more per success if it uses more tokens, needs more retries, or fails more often. Measure from usage records on your own tasks rather than computing from list prices, since token counts per task differ across models and tokenizers.

Then include what failure costs downstream. If a failed answer is caught and sent to a person, add the review cost per failure. If it reaches a customer, the cost is harder to price, and that is usually the argument for a higher quality bar rather than a cheaper model. For self-hosted open-weight models, there is no per-token fee, but the cost moves to GPUs (amortized over expected volume, including idle time), operations, and staff time; a fair comparison prices it per successful task at your realistic traffic.

Latency usually works as a **constraint** rather than a score: the product needs p95 under some number of seconds, and configurations above it are out regardless of quality. Measure percentiles from your region, at your prompt sizes, with streaming on or off as the product uses it. Independent services such as Artificial Analysis publish speed and latency measurements across providers' endpoints, which are useful for a shortlist; your own measurements decide.

With quality, cost, and latency in hand, plot each configuration as a point with pass rate up and cost per task to the right. The **Pareto frontier** is the set of configurations that no other configuration beats on both axes at once. Anything off the frontier is dominated and can be dropped. The choice along the frontier is a business decision: how much is another point of quality worth?
</Listen>

## Reading public benchmarks and leaderboards critically

Public results are useful for deciding what to test. They rarely decide what to use. Studio 1 introduced the main sources; here are the five failure modes to check, with the evidence for each.

**Contamination.** Public test items leak into training data. Deng and colleagues (2023) found models could guess masked answer options on common benchmarks far above chance. Zhang and colleagues (2024) wrote GSM1k, a fresh set matched in style and difficulty to the GSM8k math benchmark, and found some models scored up to 8 points lower on it, with signs of systematic overfitting in several model families. They also found frontier models showed minimal overfitting. Contamination is real and uneven, so a fresh, private test set is worth more than an old public one.

**Saturation.** Once top models score above 90 percent, the remaining differences are a handful of questions, and lesson 7's intervals say a handful of questions isn't much. The Humanity's Last Exam paper (Phan and colleagues, 2025) was motivated by exactly this, noting that models exceeded 90 percent on MMLU. Anthropic's agent eval guide describes SWE-bench Verified rising from roughly 40 percent to over 80 percent in about a year. A saturated benchmark tells you a model is competent; it can't rank competent models.

</Listen>

<Listen>
## Three more ways a public number misleads

**Implementation sensitivity.** The same benchmark run through different code gives different numbers. Hugging Face's 2023 analysis of its Open LLM Leaderboard found that three implementations of MMLU gave substantially different scores for the same models and even reversed the order of two of them. Prompt format, answer extraction, and the number of examples shown all matter. Numbers from different harnesses aren't comparable.

**Selective reporting.** "The Leaderboard Illusion" (Singh and colleagues, 2025) reported that some providers privately tested many variants on the Arena leaderboard before release and could choose which scores to publish. Launch posts naturally feature the benchmarks a model does well on. Arena's own style-control analysis found answer length and formatting sway human votes. None of this makes the numbers false; it makes them a selected sample.

**Vendor-run results.** Most headline numbers are run by the vendor, with the vendor's scaffold, prompts, settings, and sometimes several attempts per task or a custom agent harness. Check the footnotes for the number of attempts, the effort setting, the tools allowed, and whether the comparison numbers came from the competitors' own reports or a common harness. Independent replications and leaderboards that run every model through one common harness help. Even a carefully curated benchmark, such as SWE-bench Verified (a human-filtered subset of SWE-bench tasks made with OpenAI), measures its task, not yours.

And one statistical check on all of them: if a leaderboard shows no intervals, apply lesson 7 yourself. Two models 1 point apart on a 500-question benchmark are almost certainly not distinguishable.
</Listen>

<Callout type="pitfall" title="Switching on the launch-day number">
The expensive mistake is not trusting a benchmark; it's acting on one without running your own eval. A model can lead a coding benchmark and be worse on your codebase's conventions, lead an arena and be wordier than your users want, or top a math leaderboard and refuse more of your support tickets. Migration costs (re-tuning prompts, re-validating structured outputs, updating tests, re-certifying with security) are real, so let public results move a model onto your shortlist and let your held-out test set, run as a paired comparison, decide.
</Callout>

## Choosing among Claude, GPT, Gemini, Grok, and open models

Studio 1 (lesson 3) surveyed what each provider documents as its focus. For a switching decision, turn that survey into **hard constraints** first, because they remove candidates before any eval runs:

- **Data and deployment.** Where may your data go, and under what terms? If it can't leave your infrastructure, the candidates are open-weight models you host (for example Llama, Qwen, gpt-oss, or Mistral's open-weight models; read each license). If you need a specific cloud, check which providers' models it offers.
- **Features the task needs.** Structured outputs with the schema features you use, tool use, long context, multimodal inputs, search or real-time data tools, batch processing. Check each provider's current docs; they change with every release.
- **Operational limits.** Rate limits at your volume, regional availability, and the provider's deprecation schedule for the model you'd adopt.

Then run the eval on what's left. Use at least one configuration from each serious contender at two effort levels, plus your incumbent and one cheaper tier of the incumbent's family, because the strongest alternative to switching is often a smaller model from the provider you already use. Analyze with paired statistics against the incumbent, compute cost per success and p95 latency, and draw the frontier.

A diversity argument also applies. If you use a model as a judge or checker (week 2), a judge from a different model family than the generator shares fewer of its blind spots. A multi-provider setup has an operational benefit too: when one provider has an outage or deprecates a model, you have a tested fallback. Both are reasons to keep a second provider's configuration in your eval suite even when you don't switch.
</Listen>

## A decision template: should we switch models?

Write this down, in this order, and keep it with the eval results. It fits on one page.

1. **Trigger.** Why now? A new release, a price change, a quality problem, a deprecation notice, a contract renewal.
2. **Decision rule, written before results.** For example: switch if the candidate's paired difference against the incumbent has a 95 percent lower bound above minus 1 point, its cost per success is at least 25 percent lower, and its p95 latency stays under 6 seconds. Or: switch if quality improves by at least 3 points with a lower bound above zero, at no more than 1.5 times the cost.
3. **Shortlist and constraints.** Which configurations, from which providers (Claude, GPT, Gemini, Grok, open-weight), and what was excluded and why.
4. **Protocol.** Dataset version and size, dev and test split, tuning budget per candidate, effort levels, harness settings, trials per question, and the power of the test (the smallest difference it can detect).
5. **Results.** For each configuration: pass rate with interval, paired difference with interval and McNemar p-value against the incumbent, cost per success, p95 latency, failure types. The frontier plot.
6. **Migration cost and risk.** Prompt and test changes, structured-output and tool differences, security and legal review, monitoring changes, vendor concentration, and the deprecation timeline.
7. **Decision and rollout.** The rule's verdict, any judgment call made on top of it and why, a canary or shadow period with a live metric to watch, and the rollback trigger.
8. **Re-evaluation date.** When you'll run the suite again, because the answer has a shelf life.

Two outcomes are common and both are fine. "No detectable difference" is a result: keep the incumbent, or take the cheaper option if the rule says so. "The incumbent's smaller tier wins" happens often enough to be worth the extra row in every bake-off. What's not fine is a decision with no rule, no intervals, and a launch-day screenshot as evidence.
</Listen>

<GoDeeper title="When the comparison has to include people">
Some qualities don't reduce to a pass or fail: tone, helpfulness on open-ended requests, how an answer reads to a frustrated customer. For those, pairwise human preference (show two anonymous answers, ask which is better) is the standard design, and it is what the Arena leaderboard does at scale. Run it on your own prompts with your own raters, blind to which configuration produced which answer and with the left-right position randomized, since judges of both kinds show position bias. Analyze win rates with an interval (each comparison is a Bernoulli trial, with ties reported separately), and control for length, since Arena's style-control analysis found that longer answers win more votes. A model judge calibrated against your raters (week 2) can extend the human sample, as long as you report its agreement with them.
</GoDeeper>

<Listen>
## The checklist

Compare configurations, not brand names. Fix the task, data, graders, and conditions; give every candidate the same tuning budget on dev data; score once on held-out data, paired against the incumbent. Match or sweep reasoning effort and keep harness settings equal. Price per successful task from measured usage, including thinking tokens, retries, and the cost of failures; treat latency as a constraint; draw the frontier. Read public benchmarks for contamination, saturation, implementation sensitivity, selective reporting, and who ran them, and use them only to build a shortlist. Write the decision rule before you look, and roll out with a canary and a rollback plan. The lab this week gives you the analysis half of this as code you can reuse in every future comparison.

One last habit, the one that makes the rest cheap: keep the bake-off suite after the decision. Store the frozen configurations, the test set, the results, and the decision record together. When the next model is released, rerunning is an afternoon's work, and the decision record tells you exactly which rule to apply. Teams that skip this have the same argument every quarter, with less evidence each time.
</Listen>
