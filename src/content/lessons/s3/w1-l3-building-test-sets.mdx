## What a test set is for

Lesson 2 gave you a ranked list of failure modes. A **test set** turns that list into something you can run: a versioned collection of inputs, each with what a good output must (and must not) do, that you score every time the system changes.

Two kinds are worth keeping separate from the start. A **golden set** is a curated, representative sample of the work, with expert-approved expected outputs or criteria. It changes rarely and deliberately, and it is what you report as "quality." A **regression set** is a growing collection of cases that once failed and were fixed. It should pass at or near 100 percent, and a failure there means something you fixed has broken again. This mirrors Anthropic's distinction between capability evals (room to climb) and regression evals (should stay near 100 percent), and the evals FAQ makes the same point that evals, like unit tests, catch problems that come back after a fix.

Start small and real. Anthropic's evals post says 20 to 50 simple tasks drawn from real failures is a good start, and that a good task is one where two domain experts would independently reach the same verdict. Your first golden set can be the 36 traces from this week's lab, with the expert's labels as the expected outcomes.

There are three places cases come from, and a good set uses all three.
</Listen>

<Listen>
## Source 1: real logs

Production traces are the best source because they are what users actually send: the phrasing, typos, mixed questions, and odd requests no one would invent. They also give you **frequencies**, which nothing else can. Only real traffic tells you that a quarter of failures are invented features.

To turn logs into cases, sample deliberately. Stratify by the dimensions that matter (feature, channel, plan, language) so rare but important slices aren't drowned out by the most common request. Add every trace that error analysis flagged as a failure; those become regression cases once fixed. Pull from support tickets and user complaints too, which are pre-filtered for things that went wrong.

Two cautions from team practice. Scrub personal data before a trace enters a test file, because test sets get copied into repos, CI logs, and vendor dashboards. And attach the expected behavior to each case at the time you add it, while the context is fresh: "must offer a handoff," "must not mention QuickBooks Desktop," or a reference answer. A case without an expected behavior is just a log line.

Logs have one blind spot: they contain only what has already happened. A feature you're about to launch, or an attack no one has tried yet, isn't in them. That is what the other two sources are for.
</Listen>

<Listen>
## Source 2: expert-written cases

A domain expert can write cases that logs don't contain yet: the policy edge (an annual plan on day 14 versus day 15), the rule that only applies to one plan, the request that looks routine but must be escalated. These are often the most valuable cases per line, because each one encodes a piece of product knowledge.

Anthropic's evals post recommends writing unambiguous tasks with reference solutions, and letting domain experts contribute tasks directly. In practice that means a simple format the expert can edit (a spreadsheet or a YAML file reviewed in a pull request), one behavior per case, and a short note on why the case exists. The note matters more than it seems: six months later, someone will ask whether a failing case is still right, and "added after the March chargeback incident" answers it.

Experts are also your check on the other two sources. Have them review a sample of log-derived and synthetic cases for wrong expected outputs. A test set with a wrong answer key will punish the system for being right, and you won't notice until someone reads the failures.
</Listen>

<Listen>
## Source 3: synthetic generation, along dimensions

When you need more coverage than logs and experts provide (new features, rare slices, pre-launch), you can generate inputs with a model. Done naively it produces a pile of near-identical polite questions. The evals FAQ describes a more disciplined method, which this week's lab implements:

1. **Choose dimensions** that capture how real inputs vary, starting from your failure hypotheses: for the support bot, topic, plan, and the customer's style (terse, frustrated, multi-part).
2. **Write about 20 tuples by hand**, one value per dimension, to check that the dimensions make sense.
3. **Scale up** with either a cross product of the values (filtering out combinations that make no sense) or by asking a model to propose tuples. The FAQ notes the trade-off: the cross product is systematic, while model-proposed tuples can be more realistic but may skip rare combinations.
4. **Generate in two steps**: first the structured tuples, then a separate call that turns each tuple into a natural message. Separating them reduces repetitive phrasing.

Husain's field guide frames the same idea as features, scenarios, and personas, and adds two checks: ground generated inputs in your real system (real product names, real constraints), and verify that each one actually triggers the scenario it was meant to. Anthropic's eval docs also suggest using Claude to expand a hand-written baseline set into many more cases.

Then read them. A "frustrated" message that reads as calm doesn't test frustration. And remember the limits the FAQ spells out: synthetic data can't tell you how common a failure is, and it is unreliable in specialized or high-stakes domains where the model generating the cases doesn't know the edge cases either. One precaution worth taking on model selection: when you can, generate with a different model family than the one under test, so the test inputs don't share the system's blind spots. That reduces the risk; it doesn't remove it.
</Listen>

```python
import itertools

DIMENSIONS = {
    "topic": ["refund", "integration", "feature how-to", "account security"],
    "plan": ["Starter", "Pro"],
    "style": ["terse", "frustrated", "multi-part question"],
}

def make_tuples(dimensions, exclude=None):
    names = list(dimensions)
    for values in itertools.product(*(dimensions[n] for n in names)):
        t = dict(zip(names, values))
        if exclude is None or not exclude(t):
            yield t

# 4 x 2 x 3 = 24 tuples. Each one becomes a separate generation call in the lab.
```

## Coverage: edge cases and adversarial inputs

A test set that only contains typical requests will tell you the system handles typical requests. Plan coverage on purpose. Anthropic's eval docs list kinds of edge cases worth including: irrelevant or nonexistent input, overly long input, poor or harmful user input, and ambiguous cases where even people would disagree. Add to those:

- **Balanced cases.** Anthropic's evals post warns that one-sided evals produce one-sided optimization. If every escalation case should hand off, a bot that hands off everything scores perfectly. Include cases where the behavior must not happen.
- **Indirect phrasings.** "Please remove everything you have on me" is a privacy request without the word GDPR.
- **Multi-part requests**, where answering one part and dropping the other is a known failure (the lab's answered_wrong_question mode).
- **Adversarial inputs.** Users trying to talk the bot past a rule, and prompt-injection attempts in pasted content, which Studio 1 introduced. Label these with the behavior you expect, just like any other case.

A useful artifact is a **coverage matrix**: failure modes down the side, dimensions across the top, and a count of cases in each cell. Empty cells for important modes are where the next cases go. Chip Huyen's *AI Engineering* (chapter 8, on dataset engineering) treats coverage, quantity, and deduplication as separate properties of a dataset, which is a helpful way to review a test set: does it cover the space, is there enough of it, and is it free of near-duplicates that inflate apparent size?
</Listen>

## Size versus statistical power

Your math background makes this part quick. A pass rate on n independent cases is an estimate of a proportion, with standard error the square root of p times (1 minus p) over n. Two consequences shape test-set design.

First, **what you can detect depends on n.** A 50-case set at 80 percent has a 95 percent margin of about 11 points. It will catch a broken release; it won't tell you whether a prompt tweak gained 3 points. The size you need depends on the decision. For finding failure modes, a few dozen well-chosen cases is plenty. For a regression gate, you need enough cases per critical behavior that one failure is meaningful. For comparing two models or prompts on overall quality, you typically need hundreds, or repeated trials, or a paired design.

Second, **cases aren't always independent.** Twenty synthetic variations of one tuple are closer to one case than to twenty, and near-duplicates from logs behave the same way. Deduplicate, and when you report results, report per slice as well as overall, so a big slice can't hide a collapse in a small one.

Week 3 turns this into confidence intervals, clustered errors for related cases, and paired tests. For now, keep one rule: never report a pass rate without its n.
</Listen>

## Golden sets, regression sets, and versioning

Treat test sets like code, because they are part of your system's specification.

**Store them in the repo** as plain files (JSONL or YAML), one case per record with a stable id, the input, the expected behavior, the source (log, expert, synthetic), the failure mode it targets, and a short reason. Review changes in pull requests like any other change.

**Version them.** When you add, remove, or relabel cases, bump a version and record why. Every eval result should record which set version it ran on, alongside the prompt and model versions; a score from v3 of the set is not comparable to a score from v4. The evals FAQ discusses updating a gold dataset as the product changes, and that update is exactly when versioning earns its keep.

**Never edit a case to make a failure go away** without a recorded reason. Sometimes the expected answer really was wrong (an expert should confirm). Sometimes the product changed. Both are fine with a note. Quietly loosening a case because a release is due is how a regression set rots.

**Graduate and retire.** Regression cases stay as long as the behavior matters. When a capability eval's pass rate gets high, Anthropic's post suggests promoting its cases into the regression suite and adding harder ones, since a saturated set no longer tells you how to improve.
</Listen>

## Keeping test cases out of your prompts

The quietest way to ruin a test set is to let it leak into the thing it tests. If a graded case, or its answer, appears in the system prompt or as a few-shot example, the score partly measures whether the model can repeat what it was just shown. It is the same problem as benchmark contamination, which Deng and colleagues (2023) found evidence of in public benchmarks, except that here you caused it yourself.

Leaks happen innocently. Someone fixing a failure pastes the failing case into the prompt as an example. A prompt-optimization loop is tuned against the test set until it memorizes it. A judge prompt (next week) is given a few labeled examples from the same pool it is later scored on.

The fix is the discipline from machine learning: separate pools. The evals FAQ describes it for LLM judges: a small training split whose examples may go into the judge's prompt, a development split you iterate against, and a test split you leave untouched as a final check. Repeatedly tuning against the development split slowly overfits to it, which is why the test split exists. Apply the same rule to your system prompt: few-shot examples come from a development pool, never from the golden or regression sets.

Then check mechanically, because good intentions don't scale. The exercise below flags any test input that shares a long run of words with the prompt.
</Listen>

<Callout type="pitfall" title="A synthetic set that grades itself">
A common shortcut is to have one model write the test inputs, the expected answers, and then grade the system (often the same model family that powers it). Every step looks productive, and the eval can still be blind to exactly the failures that matter, because the cases, the answer key, and the grader all share the system's assumptions. Break the chain: base expected behaviors on your help center and an expert's review, read a sample of every generated batch, and calibrate any model grader against human labels before trusting it (week 2).
</Callout>

## A test set your team can live with

Put it together into a routine. After each round of error analysis, add the confirmed failures as cases with expected behaviors, tagged by failure mode and source. Have the domain expert write cases for policies and edge cases that logs don't show, and review a sample of everything else. Use synthetic generation along explicit dimensions to fill empty cells in the coverage matrix, and read what it produces. Keep golden, regression, and development pools separate, version them in the repo, and record the set version with every result. And keep the n next to every number.

This also sets up model selection for the rest of the program. A versioned golden set built from your own traffic is what lets you compare a Claude model against a GPT, Gemini, Grok, or open-weight model on your work, instead of on someone else's benchmark. Next week you'll build the graders that score it: code assertions first, then LLM judges, calibrated against the expert's labels from this week.
