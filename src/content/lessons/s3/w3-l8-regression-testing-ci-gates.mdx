## From an eval to a test suite

An eval you run by hand when you remember to is a measurement. An eval that runs automatically and can block a merge is a **regression test**, and it changes how a team works: nobody has to remember, and nobody can quietly ship a prompt that breaks last month's fixes.

Anthropic's guide to agent evals draws a useful line between two kinds of suite. **Capability evals** ask what the system can do and should start with a low pass rate, giving you a hill to climb. **Regression evals** ask whether it still does what it used to and should sit near 100 percent. As capability tasks become reliably solved, they graduate into the regression suite. The two kinds want different handling: a capability score is something you report with an interval and discuss; a regression suite is something you gate on.

What goes into the regression suite? The failure modes you found in error analysis (week 1), each turned into a few concrete cases. Every production bug that reached a user, as a case that would have caught it. Must-pass cases: safety refusals, the account-deletion flow, anything where one failure is unacceptable. And a broad sample of ordinary traffic, so the suite reflects what users actually ask. Hamel Husain and Shreya Shankar describe this repeatable eval set growing over time, often to 100 or more examples, with coverage of important workflows and known failures deciding its size, not a target number.

This is where engineering habits pay off. The suite is code: versioned, reviewed, and run by CI (continuous integration, the system that runs your tests on every change). Its graders are code too, and they need their own unit tests.
</Listen>

<Listen>
## What runs when

The constraint that shapes everything is cost. A deterministic assertion runs in microseconds for free; a model-graded check on a long answer costs real money and seconds per case, and adds its own noise. So you tier the suite by cost and speed, the same way the pytest docs recommend splitting fast, reliable tests from slower integration tests and gating CI on the fast ones while monitoring the rest.

**On every commit (offline, seconds, free).** Unit tests for prompt templating and output parsing. Unit tests for every grader, on hand-written good and bad outputs. And, most valuable, **replays**: recorded model responses fed through your current parsing and grading code. If someone changes a grader, a regex, or a parser, replays show the effect immediately and deterministically.

**On every pull request that touches prompts or models (minutes, cents to dollars).** A smaller live set, a few dozen to a couple of hundred cases, focused on the must-pass list and recent bugs, compared against the baseline from main. Cache responses keyed on the full request, so unchanged prompts don't pay twice.

**Nightly or on a schedule (longer, the real bill).** The full suite, live and uncached, with model-graded checks and several trials per question, analyzed with the paired statistics from lesson 7. This is what catches model-side drift you didn't cause.

**Before a release or model switch.** The full suite plus a human spot check of a random sample of outputs, because graders drift too.

Anthropic's guide notes that automated evals can run on every commit and model upgrade as a first line of defense. The tiering is what makes that affordable. Hamel and Shreya add the other half: retire or run less often the evals that keep passing, and be most aggressive about it with expensive ones such as LLM judges.
</Listen>

## Thresholds, and why naive gates flake

The obvious gate is "fail if the pass rate is below 90 percent." On a live suite, that gate is a statistical test with a hidden error rate. With 60 questions and a true pass rate of 92 percent, the standard error is about 3.5 points, so the observed rate falls below 90 percent on about one run in five (54 or more passes out of 60 are needed) with nothing wrong. Engineers learn to rerun until green, and then the gate catches nothing.

The pytest docs describe flaky tests as tests that fail intermittently without a clear reason, and name the cost: people stop trusting results and real failures get overlooked. Their suggestions translate directly to evals. Gate CI on the reliable suite and monitor the others. Use a temporary quarantine (an `xfail` mark that doesn't fail the build) for a known-flaky case, but don't leave it there, since the docs warn against keeping that permanently. Plugins that rerun failures exist; for evals, automatic reruns are an especially bad idea, because rerunning a noisy measurement until it passes is selecting on the outcome.

</Listen>

## Gates that measure what you mean

Better gates use what you learned in lesson 7:

- **Must-pass cases** fail the build on any failure. Keep this list short and run those cases deterministically where you can.
- **A non-inferiority gate** for everything else: compare the candidate with the baseline on the same questions, compute the paired difference and its standard error, and fail only if the **lower** confidence bound falls below minus a margin you chose in advance (say, 3 points). This asks "could the candidate plausibly be worse by more than we tolerate?", which is the question a release decision needs.
- **Size the margin and the suite together.** From lesson 7, the bound's half-width is about 1.96 times the square root of (discordance rate over n). A 200-question suite where systems disagree on 5 percent of questions gives a half-width of about 3 points, so a 3-point margin would fail identical systems half the time. Either enlarge the suite, accept a larger margin on PRs, or keep the strict gate for the nightly run.

Promptfoo builds thresholds into its assertions (a test case can pass when its weighted score meets a threshold), and Inspect reports per-sample scores you can feed into the same analysis. Whatever the tool, make the decision rule explicit, write it next to the suite, and don't change it after seeing a result you dislike.
</Listen>

## Caching model responses

Caching here means **record and replay**: you store each model response keyed by everything that determined it, and later runs with an identical request read the stored response instead of calling the model. It is different from provider prompt caching (Studio 1), which makes repeated prompt prefixes cheaper but still runs the model.

Record and replay gives you three things. Speed and cost, since unchanged cases don't pay twice. Determinism, since a replayed suite gives the same result every time, so any change in score was caused by your code. And a fixed corpus for developing graders: you can rewrite a judge prompt or a parser and rescore last night's outputs for free.

The hard part is the **key**. It must change whenever the output could legitimately change, and only then. Include the pinned model id, the full rendered system prompt and messages, every request setting that affects output (effort, max_tokens, tools and tool choice, output format), and the trial number when you sample a question several times. Exclude timestamps and request ids. Serialize with sorted keys, or two equal requests will hash differently. Inspect's documented cache key covers the same ground: model name and base URL, message history, epoch, generation config, and active tools. Its responses expire after one week by default, and its docs recommend explicitly versioned model names so a new deployment under an alias doesn't silently reuse old responses. Promptfoo caches by default too (on disk, 14 days by default), with `--no-cache` to bypass it.

Know what a cache **can't** see. If the provider changes the model behind an alias, or a dated model behaves differently over time, a replayed suite stays green. That's why the nightly tier runs uncached. A sound rule: replays answer "did my code change the result?", and live runs answer "did the system change?".
</Listen>

```python
import hashlib
import json
import pathlib

import anthropic

client = anthropic.Anthropic()
CACHE = pathlib.Path(".eval-cache")

def cached_create(request: dict, epoch: int = 0) -> dict:
    """Return a recorded response for this exact request and trial, calling Claude only on a miss."""
    blob = json.dumps({"request": request, "epoch": epoch}, sort_keys=True, separators=(",", ":"))
    path = CACHE / f"{hashlib.sha256(blob.encode()).hexdigest()}.json"
    if path.exists():
        return json.loads(path.read_text())
    response = client.messages.create(**request)
    record = {"request": request, "epoch": epoch, "response": response.model_dump(mode="json")}
    CACHE.mkdir(exist_ok=True)
    path.write_text(json.dumps(record))
    return record

record = cached_create({
    "model": "claude-haiku-5-5",
    "max_tokens": 1024,
    "output_config": {"effort": "low"},
    "system": "Classify the support ticket as billing, bug, or other. Reply with the label only.",
    "messages": [{"role": "user", "content": "I was charged twice this month."}],
})
```

<Callout type="pitfall" title="A green replay suite that tests nothing">
Two mistakes make a cache lie. The first is a key that leaves something out: if `effort` or the tool list isn't in the key, a request that changed still reads the old response, and your PR looks safe because it never ran. Test the key: change each setting and assert the key changes, as the exercise does. The second is replaying in a job that is supposed to detect drift. Mark the nightly job uncached in its configuration, and have the report state cache hits and misses, so "100 percent pass, 100 percent cache hits" is visible for what it is.
</Callout>

## Where the suite lives: tools

You don't need a framework to start. **pytest** is enough for many teams: one parametrized test per case (the docs show `@pytest.mark.parametrize` for running one test function over many inputs), deterministic assertions inline, a custom marker such as this course's `live` marker for tests that call a model, and a small script that computes paired statistics from a results file. Its advantage is that the eval suite runs with the rest of your tests, in the same CI, with tools everyone knows. The labs in this program are built that way.

**Promptfoo** is an open-source (MIT) command-line tool and library for evaluating and red-teaming LLM apps. Cases live in a YAML config (`promptfooconfig.yaml` in its examples) with assertions per test: deterministic ones such as `equals`, `contains`, `is-json`, `regex`, and custom `python` or `javascript` checks, model-graded ones such as `llm-rubric` and `factuality`, plus `cost` and `latency`. Its GitHub Action runs a before-and-after comparison when a pull request edits a prompt and posts a link to the results.

**Inspect** is an open-source (MIT) framework for LLM evaluations developed by the UK AI Security Institute with Meridian Labs. An eval is a **task** that combines a dataset of samples, a **solver** that produces answers (from a single `generate()` call to a full agent), and a **scorer**. You run tasks with `inspect eval`, browse logs with `inspect view`, and it ships a large set of prebuilt evaluations. It suits agentic and multi-step evals, and teams who want detailed logs of every sample.

**OpenAI Evals** is an open-source framework and registry of benchmarks from OpenAI. OpenAI also built a hosted Evals product on its platform, and its docs now say that the hosted Evals platform became read-only for existing users on October 31, 2026 and is scheduled to shut down on November 30, 2026. That's a lesson in itself: keep your cases, graders, and results in your own repository in a portable format (JSONL plus code), so a vendor's product decision can't take your regression suite with it.

How to choose: start with pytest unless a tool gives you something you need. Promptfoo is quick for prompt-level comparisons across several providers with a PR workflow. Inspect fits agent evals and research-grade logging. Whatever you pick, the statistics in lesson 7 and the decision rules above are yours to apply; none of these tools makes a noisy score significant.
</Listen>

## Version everything that changes the result

An eval result is a function of at least five things: the **prompt** (template and any few-shot examples), the **model** (an exact id, not an alias), the **request settings** (effort, max tokens, tools), the **dataset** (which questions, which reference answers), and the **graders** (including the judge model and its prompt). Change any one and the score can move. Change two at once and you can't say which one moved it.

Practical habits:

- **Pin model ids** in config, and record the id the API reports in each response. Anthropic's models overview lists the current ids; aliases are convenient for prototypes and wrong for a baseline.
- **Keep prompts in files**, in the repository, reviewed like code. Give each a version or a content hash.
- **Version the dataset.** Store it as JSONL in the repository (or with a content hash if it's large). Never edit a case in place without bumping the version: a "fixed" reference answer is a different eval.
- **Write a manifest with every run**: git commit, prompt hashes, model ids, settings, dataset hash, grader versions, number of trials, cache hit rate, and date. Results without a manifest can't be compared later.
- **Change one thing per comparison.** If you migrate a model and must re-tune the prompt, measure the new model with the old prompt first, then the new prompt, so you know what each change bought.

This is also what makes the gate fair. The baseline must be the same suite, same dataset version, and same graders as the candidate, rerun under the same conditions, or the paired comparison is pairing different experiments.
</Listen>

## Wiring it into CI

In GitHub Actions, the tiers map onto workflow triggers. A `pull_request` trigger with a `paths` filter runs the live smoke set only when prompts, model config, or the eval itself change. A `schedule` trigger with a cron expression runs the nightly suite, and `workflow_dispatch` lets someone run it by hand before a release. Three details from GitHub's docs are worth knowing. Cron schedules run in UTC unless you set a time zone, and they run only on the latest commit of the default branch. Scheduled runs can be delayed at busy times, especially the top of the hour, so pick an odd minute. And in public repositories, scheduled workflows are disabled automatically after 60 days without repository activity, which can silently stop a nightly eval on a quiet project.

API keys go in the repository's encrypted secrets, never in the workflow file. Upload the results file and manifest as a build artifact so anyone can rerun the analysis. The lab for this week includes a complete example workflow that runs the offline gate; it sits in the lab folder rather than in `.github/workflows`, so it documents the pattern without running on this repository.
</Listen>

<GoDeeper title="Evals for agents and multi-step systems">
For agents, a test case is a task with an environment, and grading usually checks the final state (was the ticket created with the right fields? do the repository's tests pass?) rather than the text. That makes each trial slower and noisier, so the tiering matters more: replay recorded tool results offline where you can, run a handful of tasks live on PRs, and run many trials per task nightly. Anthropic's guide recommends starting with 20 to 50 tasks drawn from real failures, and warns that a task nobody passes across many trials more often signals a broken task than an incapable agent, so read failing transcripts before trusting a zero. Inspect's solvers and sandboxing were built for this style of eval. Report pass^k when the product needs consistency.
</GoDeeper>

## The checklist

Split the suite into capability and regression evals, and gate on regression. Tier checks by cost: deterministic tests and replays on every commit, a live smoke set on PRs that change model behavior, the full uncached suite on a schedule, a human sample before releases. Gate on must-pass cases and a paired lower bound with a margin you fixed in advance, and size the suite so identical systems pass. Never rerun until green. Key cached responses on everything that changes the output, pin model ids, and run something uncached regularly. Keep prompts, datasets, graders, and results in your repository with a manifest for every run.
