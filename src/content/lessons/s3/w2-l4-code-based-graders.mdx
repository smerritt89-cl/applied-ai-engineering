## A grader is a function, so write it like one

Week 1 ended with failure modes: concrete ways your system goes wrong, found by reading real outputs. A **grader** turns one of those failure modes into a function: it takes an output (and sometimes the input and a reference answer) and returns a score, usually pass or fail. An eval is a set of cases plus the graders that score them.

There are three kinds of grader, and the order you reach for them matters. Anthropic's guide to building evals ranks them plainly: **code-based grading** is the fastest, most reliable, and most scalable, but lacks nuance; **human grading** is the most flexible and highest quality, but slow and expensive; **LLM-based grading** is fast and flexible but has to be tested for reliability before you scale it. Anthropic's engineering team makes the same trade-off explicit in its write-up on agent evals: code graders are cheap, objective, reproducible, and easy to debug, and their weakness is brittleness when a valid answer looks different from what the code expects.

The practical rule follows: **make every check you can deterministic**, and save model judges (next lesson) for criteria code genuinely can't decide. A deterministic grader gives the same answer every run, costs nothing, and can itself be unit-tested. That last property is underrated. A grader is code that decides whether you ship, so it deserves tests as much as anything in your product.

This lesson works through the toolbox from simplest to most involved: exact and normalized matching, regular expressions, fuzzy matching, schema checks, executing generated code, and reference-overlap metrics, with what each one can and can't tell you.
</Listen>

## Exact match, and the normalizations you choose

The simplest grader compares the output with an expected answer: `output == expected`. It fits any task whose answer space is closed: a label from a fixed set (refund, exchange, warranty), a number, a yes or no, an ID. Anthropic's sentiment-classification example does exactly this over a labeled set and reports accuracy.

Raw equality is usually too strict, so you normalize first: strip surrounding whitespace, lowercase, maybe collapse internal whitespace. Each normalization is a decision about what counts as the same answer, and you should be able to say why it's safe. Lowercasing a category label is safe. Lowercasing a product code might merge two different products. Stripping punctuation from a number can turn "1,000.5" into "10005".

A close cousin is the **contains** check: does the output include a required phrase ("5 to 7 business days"), or exclude a forbidden one ("guaranteed")? These are useful guardrails, with a known weakness: substring checks can't see negation or context. "We do not offer a full refund" contains "full refund."

Two habits make these graders trustworthy. First, grade **one property per check** and keep the results separate (`category_correct`, `order_id_correct`, `no_promises`), rather than one blended pass. When a score drops you'll know which property broke. Second, decide in advance what the grader does with outputs it can't interpret, such as text that isn't valid JSON. Count those as a separate failure, never as a silent pass, and never "repair" them in the grader without counting how often you had to.
</Listen>

## Regular expressions and fuzzy matching

When the answer has a format rather than a fixed value, use a **regular expression**: order IDs like `TP-` followed by six digits, ISO dates, currency amounts, a citation marker. Python's `re` module offers three ways to apply a pattern, and graders get them wrong constantly. `search` finds the pattern anywhere in the string, `match` only at the start, and `fullmatch` requires the whole string to match. For validating a field, you almost always want `fullmatch`. With `search`, "TP-4829137" (seven digits) passes, because six of its digits match.

Patterns fail in both directions, so test both. A pattern that is too strict rejects valid outputs (a date written "2026-11-04" when you expected "11/04/2026"); one that is too lenient accepts junk (a pattern where everything is optional matches the empty string). Write the cases first: three strings that must match, three that must not.

**Fuzzy matching** scores similarity instead of equality. Python's `difflib.SequenceMatcher` gives a ratio between 0 and 1 based on matching subsequences; edit-distance libraries do similar work. Fuzzy matching helps when the expected answer is a name or short phrase that can be spelled or formatted slightly differently ("Tallow and Pine" versus "Tallow & Pine"). It's risky anywhere a small character change is a big meaning change: "5 days" and "15 days" are very similar strings. If you use a threshold, pick it from data. Score a handful of pairs you've labeled as same and different, and choose the cutoff that separates them, instead of guessing 0.8.
</Listen>

## Schema checks: valid, then correct

Many LLM features return structured data, and Studio 1 built extraction with schemas, validation, and evidence checks. In an eval, the same tools become graders. A **schema check** parses the output and validates it against a model of what it must look like (with Pydantic, `Model.model_validate_json(text)`), then you check field values separately.

Keep three outcomes apart, because they have different causes and fixes:

- **Unparseable**: not JSON at all, or wrapped in prose or code fences. With structured outputs this should be rare, so a jump in it usually means truncation, a refusal, or a broken configuration.
- **Schema-invalid**: parses, but a required field is missing, an extra field appears, or a value has the wrong type or falls outside an allowed set.
- **Schema-valid but wrong**: the shape is perfect and the category or date is incorrect. Only comparison with the expected answer (or a judge) catches this.

Reporting these as three numbers instead of one "correct" rate is the difference between a dashboard that says "quality dropped 4 points" and one that says "4 points of outputs stopped parsing after the model change," which tells you exactly where to look.

The exercise below puts these pieces together for a support-ticket triage feature: the model must return a category, the order ID mentioned in the ticket (or null), and a short reply that makes no promises the policy doesn't allow.

<Callout type="pitfall" title="The grader that passes everything">
Graders fail silently. A regex with `search` instead of `fullmatch`, a contains-check on an empty required phrase (`"" in text` is always True), a schema check that catches the exception and returns True, a JSON repair step that turns anything into an object: each one inflates your pass rate and no test you'd naturally write will notice. Before you trust a grader, run it on an output that must pass and on outputs that must fail (an empty string, the wrong answer in the right format, the right answer wrapped in junk). If it doesn't fail the bad ones, it isn't a grader yet.
</Callout>

## Executing generated code

When the output is code, the strongest grader is to **run it**. Chen and colleagues at OpenAI argued this in the 2021 paper that introduced the HumanEval benchmark: match-based metrics can't account for the huge space of programs that are functionally equivalent to a reference solution, so they evaluated **functional correctness** instead, counting a sample as correct if it passes a set of unit tests. They pointed out that this mirrors how developers already judge code, through tests.

The paper also introduced the standard way to report it, **pass@k**: the probability that at least one of k sampled solutions passes. To estimate it with low variance, generate n samples (n at least k), count the c that pass, and compute 1 minus C(n minus c, k) over C(n, k). The obvious shortcut, 1 minus (1 minus the pass rate) to the k, is biased, which the paper shows in an appendix.

Executing model-written code is a security decision. Generated code can delete files, read secrets from your environment, open network connections, or loop forever. The HumanEval authors built a sandbox for exactly this reason. In practice, run generated code in a disposable container or a managed sandbox with no credentials, no network unless the test needs it, a CPU and memory limit, and a timeout, and grade what the run left behind (test results, files written, exit code). Anthropic's agent-evals write-up makes the same point for agents generally: grade the outcome in the environment, not the transcript's description of it.
</Listen>

<GoDeeper title="Where the pass@k estimator comes from">
Fix one problem with n generated samples, c of which pass. Draw k distinct samples uniformly at random. The draw contains no passing sample exactly when all k come from the n minus c failures, which happens with probability C(n minus c, k) / C(n, k). So the chance of at least one pass is 1 minus that ratio, and averaging this quantity over problems gives an unbiased estimate of pass@k for samples drawn this way.

Why is the shortcut biased? Write p-hat for c / n. The shortcut computes 1 minus (1 minus p-hat) to the k. The function f(p) = 1 minus (1 minus p) to the k is concave for k greater than 1, so by Jensen's inequality the expected value of f(p-hat) is at most f(p): the shortcut underestimates pass@k on average, and the gap grows with k. Chen and colleagues also give a numerically stable implementation that avoids computing huge binomial coefficients, by evaluating the ratio as a running product.

For your own work, the estimator matters when you report "best of k" success, for example when a coding agent may retry. For most product evals you'll report pass@1, which is just the pass rate.
</GoDeeper>

## Reference-based metrics: BLEU, ROUGE, and their limits

Before LLMs, text generation was mostly scored by comparing outputs with human-written references. **BLEU** (Papineni and colleagues, 2002) was built for machine translation: it measures modified n-gram precision (how many of the candidate's word sequences appear in the references, with clipping so repeats don't count twice) and multiplies by a brevity penalty so very short outputs can't game precision. **ROUGE** (Lin, 2004) was built for summarization and is recall-oriented: ROUGE-N counts how many of the reference's n-grams the candidate recovers, and ROUGE-L uses the longest common subsequence.

Both were real advances, because they made frequent, cheap evaluation possible where human review took weeks. Both measure surface overlap, and the evidence on what that tells you is sobering. Reiter's 2018 structured review of 284 correlations from 34 papers found support for BLEU as a diagnostic for machine translation systems, but not for other generation tasks, not for evaluating individual texts, and not for scientific hypothesis testing. For code, the HumanEval paper computed BLEU for correct and incorrect solutions and found the distributions overlapped heavily: functionally wrong programs often scored higher than correct ones.

The failure is easy to see. A correct answer in different words ("you'll see the money in about a week") shares almost nothing with the reference "refunds arrive within 5 to 7 business days." A wrong answer that copies the reference's words ("refunds never arrive within 5 to 7 business days") scores almost perfectly. So treat overlap metrics as, at most, a cheap trend line across many outputs, never as a per-output grader or a release gate for open-ended text.
</Listen>

## How a working team uses code graders

In a real team, code graders live in the repository next to the feature, run in CI on every change, and are reviewed like any other code. A few practices separate useful suites from noisy ones.

**Start from failure modes, not from metrics.** Each grader should map to a failure you found in error analysis ("replies promise exceptions the policy doesn't allow"), so a failing check points at a known problem with a known owner. Hamel Husain describes this layer as the unit tests of an LLM product: scoped, fast assertions that run constantly.

**Decompose before you delegate.** "Is this reply good?" sounds like a job for a model judge. Much of it isn't. Does the reply mention the order ID? Is it under 120 words? Does it avoid the forbidden promise list? Does every number in it appear in the policy? Each of those is code. What remains (does it actually answer the question?) is a much narrower judgment, which makes the judge in the next lesson cheaper and easier to calibrate.

**Watch for brittleness.** When a code grader starts failing outputs that a person would accept, that's a grader bug, and you fix it with a new test case, not by loosening the check until the dashboard turns green.

On model selection: deterministic graders are model-agnostic, which is what makes them valuable when you compare providers. Swap in a cheaper model or another provider's model, rerun the same checks, and the difference you see comes from the model, not from a judge that might prefer its own family's style.
</Listen>
