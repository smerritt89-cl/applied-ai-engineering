## You've been driving it; now look under the hood

If you've used Claude Code for a year, you know what it feels like: you describe a problem, text scrolls past, files change, tests run, and a summary appears. This lesson slows that down so you can see the parts. Once you can name the parts, you can tell which one failed when a session goes wrong, and you can choose deliberately instead of hoping.

Anthropic's docs describe a coding agent as two components. The **model** reasons: it reads code, decides what to do next, and writes edits. The **harness** is everything around the model: the tools it can call, the permission system that decides which calls run, and the machinery that manages what the model sees. Claude Code is a harness around Claude models. Codex, Gemini CLI, Copilot's agents, and Cursor's Agent are harnesses around their own model choices. Much of what distinguishes these products is harness design, which is why the same model can behave differently in two tools, and why a benchmark score for "model X" depends on which harness ran it (lesson 2).

The loop the docs describe has three phases that blend together: **gather context** (search, read files, run commands to learn the state), **take action** (edit files, run commands), and **verify results** (run the tests, read the output). A question about your codebase might only gather. A bug fix cycles through all three many times. You can interrupt at any point, and that matters: the cheapest moment to correct a misunderstanding is in the first minute, before it has been built on.
</Listen>

## The tools: five kinds of agency

Claude Code's docs group the built-in tools into five categories: **file operations** (read, edit, create, rename), **search** (find files by pattern, search contents with regular expressions), **execution** (shell commands, servers, tests, git), **web** (search, fetch documentation), and **code intelligence** (type errors after edits, jump to definition, which needs a language-server plugin). There are also orchestration tools for spawning subagents and asking you questions.

Two design choices are worth noticing because they explain everyday behavior.

First, the agent **searches like a developer** rather than querying a pre-built index. When you say "fix the failing tests," a typical sequence is: run the suite, read the error, search for the relevant source, read those files, edit, run the tests again. Each tool result is new evidence for the next decision. This is why agents are good at unfamiliar code (they go and look) and why they can be slow or expensive in a huge repo (looking costs tokens).

Second, **the shell is the universal tool**. Anything you can do from the command line, the agent can do: build, migrate, deploy, delete. That power is why permission design matters so much, and why a task with a runnable check (a test, a build, a linter) suits an agent so well: the shell lets it close the loop itself. Simon Willison's practitioner advice says the same from the other direction: the problems that suit agentic loops have clear success criteria and reward trial and error, such as debugging, performance tuning, and dependency upgrades.
</Listen>

## The context window: the agent's working memory

Everything the model knows during a session sits in its context window. The Claude Code docs list what goes in: the conversation history, file contents it has read, command outputs, your CLAUDE.md files, auto memory, loaded skills, system instructions, and the names of available MCP tools (their full schemas load on demand). Claude Code also adds its own context, such as a note when a file it read earlier changed on disk. Running `/context` shows what is using space.

Three facts follow, and each changes how you work.

**Tool output is the big consumer.** A full test log, a wide search, or a large file can cost far more than your prompts. Anthropic's context-engineering post calls the problem context rot: as context grows, the model's ability to use any one piece of it degrades, so more is not free even when it fits.

**Long sessions get compacted.** As the window fills, Claude Code summarizes the conversation. The summary keeps your requests and key code, but the docs warn that detailed instructions from early in the conversation may be lost. The memory docs add the counterpart: the project-root CLAUDE.md is re-read from disk and re-injected after compaction. So a rule you typed in chat at minute five is fragile, and the same rule in CLAUDE.md is durable. You can steer compaction with `/compact` plus a focus, or a "Compact Instructions" section in CLAUDE.md.

**Sessions are independent.** A new session starts with a fresh context. Continuity comes from files (CLAUDE.md, auto memory, your git history, a spec), not from the model remembering yesterday. That is a feature: `/clear` between unrelated tasks is free, gives better answers, and costs less, because every request resends the whole conversation.
</Listen>

<Callout type="note" title="How big is the window?">
At the time of writing (November 2026), Claude Code's docs say most current models have a 1M-token window and compaction runs automatically, so running out is rare. Paying for context you don't need, and the model losing track of early details, are the practical problems. Window sizes change with models; check the model configuration page rather than memorizing a number.
</Callout>

## Undo and permission: what is actually protected

Claude Code has two safety mechanisms with very different scopes.

**Checkpoints** snapshot a file before Claude's file tools edit it, so pressing Escape twice (or `/rewind`) can roll back code, conversation, or both. The checkpointing docs are explicit about the edges: files changed only by a Bash command aren't restored, and actions on remote systems (databases, APIs, deployments) can't be checkpointed at all. Checkpoints work alongside git; they don't replace it.

**Permissions** decide what runs without asking. At the time of writing, the modes are Manual (Claude asks before edits and non-read-only commands), Accept edits (file edits and common filesystem commands run freely), Plan (explore and propose, no source edits), Auto (a separate classifier model reviews actions and blocks risky ones), `dontAsk` (only pre-approved tools, for locked-down scripts), and `bypassPermissions` (everything, for isolated containers only). Recent versions start interactive sessions in Auto mode.

The most useful idea in the best-practices doc is the split between **non-deterministic** and **deterministic** instructions. Your prompt, CLAUDE.md, and skills are read by the model, which usually follows them but isn't guaranteed to. Hooks, deny rules, the sandbox, and managed settings are executed by the harness every time, whatever the model decides. Auto mode sits in between: it's a model making a judgment, which the docs caution can be wrong, so "never" rules belong in deny rules or hooks. Keep this split in mind for the whole elective. Every time you want something to always (or never) happen, ask which side of the line your control is on.
</Listen>

<Callout type="pitfall" title="Treating checkpoints as a safety net for everything">
A common year-one habit: let the agent run, and if it goes wrong, "just rewind." That works for edits made with the file tools in your main conversation. It does nothing for a `git push`, a migration against a shared database, a deleted cloud bucket, or a file a shell script rewrote. Before any session that can touch remote systems, commit your work, decide what the agent may run (permission rules, a sandbox, scoped credentials), and keep irreversible steps for a person to approve.
</Callout>

## Same anatomy, different products

Every mainstream coding agent has the same five parts: an instruction file the model reads, a tool set, an approval system, some form of sandbox, and an undo story. Here is how the official docs describe each product at the time of writing. Treat the details as fast-moving; the anatomy is the stable part.

**OpenAI Codex** reads `AGENTS.md` files, walking from the project root down to the current directory (with an `AGENTS.override.md` option and a default 32 KiB cap on combined instructions). Its security docs separate two controls: a **sandbox mode** (`read-only`, `workspace-write`, `danger-full-access`) that sets what is technically possible, and an **approval policy** that sets when it must ask. Network access is off by default, and web search defaults to a cached index, with the docs telling you to treat web results as untrusted.

**Gemini CLI** reads `GEMINI.md` files (global, workspace, and subdirectory files loaded just in time) and can be told to read `AGENTS.md` too. Its tools include `read_file`, `write_file`, `replace`, `glob`, `grep_search`, `run_shell_command`, and `web_fetch`, and the shell and write tools require confirmation. Note the status change: the Gemini CLI docs carry a banner saying that for unpaid-tier and Google One users, Gemini CLI was replaced by **Antigravity CLI** on June 18, 2026. Antigravity's migration guide says it keeps Gemini CLI's core constructs and reads both `GEMINI.md` and `AGENTS.md`.

**GitHub Copilot** has two shapes. In VS Code, agents run locally with tools, approvals you configure, and diffs to review; the docs note that stopping a request doesn't undo completed actions. On GitHub, the cloud agent works in a GitHub Actions environment or a cloud sandbox, on one branch at a time, opening one pull request per task, with Actions sessions capped at 59 minutes. Copilot reads `.github/copilot-instructions.md`, path-specific instruction files, and the nearest `AGENTS.md`.

**Cursor's Agent** combines search, edit, and terminal tools, lets you choose the model per task, and saves local checkpoints before significant changes, separate from git.
</Listen>

<GoDeeper title="The same loop, as a library">
Claude Code's loop is also available as the Claude Agent SDK, and its docs describe the loop in programmer's terms: each turn the model either answers or requests tools; read-only tools can run in parallel; you can cap turns and spend (`max_turns`, `max_budget_usd`); and automatic compaction kicks in near the limit. Studio 4 builds this loop yourself. Reading those docs once makes the interactive tool less mysterious: the "agent" is a while-loop over model calls, tool executions, and a context that you (or the harness) manage. The intelligence is in the model; the reliability is mostly in the harness and in the checks you give it.
</GoDeeper>

## What to take into the rest of the elective

When a session disappoints you, locate the failure. Missing context (the agent couldn't see a decision or convention) is fixed with better prompts and project memory, week 2. No way to check its work (it stopped when the code looked done) is fixed with tests and hooks, week 3. A rule broken that must never break is fixed by moving it from text the model reads to a control the harness enforces. And too much time or money for the task is fixed by changing the model, effort, or tool, which is lesson 3. Before that, lesson 2 asks how anyone knows which agents are good in the first place.
</Listen>
