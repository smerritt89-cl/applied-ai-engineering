## Why agent code needs a different kind of review

Reviewing a colleague's pull request and reviewing an agent's diff look the same on screen, but the risks differ. Agents produce more code, faster, than people review comfortably. The code is usually plausible: well formatted, idiomatic, with confident comments and a tidy summary. And the failure modes are distinctive: doing more than asked, quietly weakening a safeguard to make something work, adding a dependency, satisfying a test rather than the requirement, or following an instruction that came from a file rather than from you.

The DORA 2025 report's central finding is a useful frame: AI acts as an amplifier of an organization's existing strengths and weaknesses. A team with disciplined review and good tests gets faster; a team that rubber-stamps gets more unreviewed code, faster. Review is where that difference is decided. This lesson gives you a checklist built for agent diffs, a reading order that makes large diffs tractable, honest guidance on model reviewers, and the security picture specific to agents.
</Listen>

## The checklist

Google's engineering practices list what reviewers look for: design, functionality, complexity, tests, naming, comments, style, and documentation. Keep that as the base. For agent-written changes, add six questions, in this order:

1. **Does it match the spec, and only the spec?** List the files you expected to change; compare with the files that did. Every extra file needs a reason. "For consistency" refactors, renamed variables, and reformatted files are scope creep: they enlarge the review and hide the real change.
2. **Did any test change?** Read test diffs first (lesson 7). A changed expectation, a new skip, or a deleted test needs your judgment before anything else means anything.
3. **Were safeguards removed or weakened?** Look at removed lines, not just added ones: input validation, permission and auth checks, expiry checks, rate limits, error handling replaced by a bare `except: pass`, a `timeout` raised to "fix" a flaky test, a security header dropped. Agents remove obstacles; some obstacles are the point.
4. **New dependencies?** Any change to `requirements.txt`, `pyproject.toml`, `package.json`, or a lockfile. Spracklen and colleagues (2024) tested 16 code-generating models and found hallucinated package names in at least 5.2% of suggestions on average for commercial models and 21.7% for open-source models; a name that doesn't exist can be registered by an attacker. Check that each package exists, is maintained, and is actually needed.
5. **Security-sensitive patterns?** Shell commands built from strings, `eval`, disabled certificate checks, secrets or tokens in code, broadened CORS or permissions, SQL built by concatenation, new network calls, changes to CI workflows or agent configuration (`.github/workflows/`, `.claude/settings.json`, hooks).
6. **Would you understand this in six months?** Agents can write code that works and is still wrong for your codebase: a second way of doing something you already do one way, an abstraction nobody asked for. If you couldn't explain it to a teammate, you can't maintain it.
</Listen>

## Reading a big diff efficiently

You can't read every line of every agent diff with equal care, so read in an order that puts your attention where risk is.

**Triage first.** `git diff --stat` (or the file list in your review tool) shows what changed and how much. Compare it with the spec before reading any code. Unexpected files are the first finding.

**Tests before code.** Read the test changes and confirm they encode the requirement (lesson 7). Then you can read the code asking "does this satisfy these tests for the right reason?" rather than "what is this doing?"

**Risky files next.** Anything on checklist items 3 to 5: auth, payments, data deletion, migrations, dependency manifests, CI and agent configuration. Read these line by line.

**Mechanical changes last, and separately.** Renames and formatting hide logic changes. Ask for them in separate commits, and use `git diff -w` to ignore whitespace-only changes when reading logic.

**Run it.** Check out the branch and exercise the behavior, especially for user-facing changes. Claude Code's bundled `/verify` skill builds and runs the app to look at the result, which catches problems tests miss, but you should still look yourself at anything a user will see.

**Ask for evidence, not reassurance.** If the agent's summary says "handled the edge case," find the test that proves it.
</Listen>

<Callout type="pitfall" title="Reviewing the summary instead of the diff">
Agent summaries are fluent and organized, and they describe what the agent intended, which is not always what it did. The most common review failure with agents is reading the summary, skimming the diff for anything alarming, and approving. Use the summary as a map of claims to verify: for each claim, find the line or test that backs it. Anything in the diff the summary doesn't mention deserves the closest look.
</Callout>

## A second reviewer: fresh sessions, subagents, other models

An independent reviewer catches what the author missed, and with agents you can get one cheaply. The best-practices page describes three ways. Claude Code's `/code-review` reviews the diff in a fresh subagent that never saw your conversation, so it isn't swayed by the reasoning that produced the code. A custom read-only reviewer subagent (lesson 5) does the same with your own brief, and can't edit anything. Or open a second session, have it review the files, and carry the findings back yourself: the writer-reviewer pattern.

Three things make model review useful rather than noisy. **Give it the spec**, and ask it to check that every requirement is implemented and each listed edge case has a test. **Narrow the question** to correctness and the checklist items above, and tell it to skip style. The docs warn that a reviewer asked to find problems will always find something, and fixing every finding leads to needless abstraction and tests for impossible cases. **Make it independent**: a fresh context at minimum, and for high-stakes changes, consider a different model family, whose errors are less likely to be correlated with the author's.

Then remember what Studio 3 established about model judges: they have biases, they agree with people often but not always, and they need calibration against human labels before you rely on them. A model reviewer is a filter that raises issues for you to judge. It is not the approval. The best-practices page's own table puts "a person who approves the merge" and branch protection in the deterministic column; the model's summary of its work is in the other one.
</Listen>

## Security risks specific to coding agents

A coding agent combines three things that are each manageable alone: it reads untrusted text, it has access to your code and often your secrets, and it can run commands and reach the network. Simon Willison's **lethal trifecta** names the dangerous combination: private data, exposure to untrusted content, and the ability to communicate externally. When all three meet, an attacker who controls some of the content can try to steer the agent into sending the data out.

**Prompt injection through what the agent reads.** Greshake and colleagues (2023) showed indirect injection: instructions planted in content an LLM application retrieves can hijack it. For a coding agent, the content is everywhere: a README or code comment in a dependency, an issue or pull request description, a web page it fetched for documentation, a tool result from an MCP server. Invariant Labs reported an attack on the GitHub MCP integration in which a malicious issue in a public repository led an agent to pull data from the user's private repositories into a public pull request. Codex's docs make the same point from the vendor side: they default web search to a cached index to reduce exposure, and tell you to treat web results as untrusted.

**What Claude Code does about it**, per its security docs: network commands like `curl` and `wget` aren't auto-approved by default; most web fetches go through a separate model call that summarizes the page rather than handing Claude the raw text; a workspace trust dialog appears in folders you haven't trusted; project MCP servers need their own approval. In auto mode, the classifier blocks by default things like downloading and executing code, sending sensitive data to external endpoints, production deploys, force pushes, and destructive git commands, and the best-practices page lists actions that look driven by content Claude read rather than by you among the things it watches for. The docs are also clear that no system is immune and that auto mode is a model's judgment, so your "never" rules belong in deny rules and hooks.

**Secrets.** Deny rules such as `Read(./.env)` and `Read(./secrets/**)` block Claude's file tools and recognized shell file commands, but not a script that opens the file itself; the sandbox adds OS-level enforcement for the commands it wraps. Better still, keep production secrets off the machine the agent runs on, and give it scoped, revocable credentials for test environments. Willison's advice for running agents with few prompts is to use exactly that: credentials for test or staging, tight budgets on anything that can spend money, and a container or remote environment rather than your laptop.

**Destructive commands.** Checkpoints don't undo remote effects (lesson 1). Keep force pushes, migrations, deploys, and deletions behind a person: deny or ask rules for the commands, branch protection on `main`, and, for unattended runs, a disposable environment. And remember that repository configuration is itself an attack surface: a cloned repo's hooks run in `claude -p` sessions without a trust dialog, so read `.claude/` and `.mcp.json` before running an agent on code you didn't write.
</Listen>

<GoDeeper title="Breaking the trifecta in practice">
The durable defense is architectural: make sure the three legs don't meet without a person. Options, from least to most disruptive: remove the outbound channel during sessions that read untrusted content (deny network commands and web fetches, or use the sandbox's network allowlist); remove the private data (run the agent in a container or cloud environment that holds only the repository it needs and test credentials); or separate the roles (a read-only agent summarizes untrusted issues for you, and a different session with write access acts only on what you approve). Studio 4's security lessons cover the design patterns behind these choices in depth. The same habits that limit injection also limit plain mistakes: least privilege, reversible actions, and a human on every irreversible step.
</GoDeeper>

<Listen>
## Your review routine

Before reading: compare the file list with the spec. Then: test changes, removed lines in risky files, dependency and config changes, security patterns, then the rest, with whitespace ignored. Run the change. Use a fresh-context reviewer with the spec and a narrow brief as a filter, and make your own decision. For security: assume anything the agent reads from outside may contain instructions, keep the trifecta from meeting, protect secrets with deny rules plus isolation, and keep irreversible actions for a person. The goal isn't to distrust the agent's code more than a colleague's. It's to review it the way its specific failure modes demand.
</Listen>
