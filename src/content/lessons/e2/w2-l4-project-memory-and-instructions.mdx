## The file you write once and the agent reads every time

Every coding agent starts a session knowing nothing about your project except what it can read. Project memory is how you hand over the rest: a Markdown file the harness loads at the start of each session. In Claude Code it's `CLAUDE.md`; in Codex, Copilot's agents, and many others it's `AGENTS.md`; in Gemini CLI it's `GEMINI.md`. The idea is the same everywhere, and so are the mistakes.

The Claude Code memory docs make one point that reframes everything else: Claude treats these files as **context, not enforced configuration**. The content is delivered as a message after the system prompt, and Claude reads it and tries to follow it, with no guarantee of strict compliance, especially for vague or conflicting instructions. The more specific and concise the instructions, the more consistently they're followed. So there are two jobs here: put the right things in the file, and write them in a way that changes behavior. Anything that must happen every time goes elsewhere (lesson 5).
</Listen>

## Where the files load from

Claude Code reads `CLAUDE.md` from several scopes and concatenates them rather than letting one override another. In load order, broadest first: an organization's managed policy file, your user file at `~/.claude/CLAUDE.md`, the project file at `./CLAUDE.md` or `./.claude/CLAUDE.md` (shared through git), and `./CLAUDE.local.md` for personal project notes you keep out of git. Files in the directories above where you launched load at startup; files in subdirectories load on demand, when Claude reads or edits something there. Instructions closer to your working directory are read last.

A few mechanics are worth knowing. `@path` imports pull another file in, but the docs note imports organize content without reducing its context cost. Block-level HTML comments are stripped before loading, so you can leave notes for human maintainers for free. `.claude/rules/` holds topic files, and a rule with `paths:` frontmatter loads only when Claude works on matching files. After `/compact`, the project-root CLAUDE.md is re-read from disk. To confirm what loaded, run `/context all` and look under Memory files. And `/init` drafts a starting file from your codebase; the best-practices page says that from there "the work is mostly removing lines."

**AGENTS.md.** Recent Claude Code versions read `AGENTS.md` directly, but by default only when there is no `CLAUDE.md`, `.claude/CLAUDE.md`, or `CLAUDE.local.md` in your working directory or above. That has a sharp edge: adding a personal `CLAUDE.local.md` to an AGENTS.md project silently stops Claude reading the AGENTS.md. The robust pattern for a mixed-tool team is one shared `AGENTS.md` plus a `CLAUDE.md` whose first line is `@AGENTS.md`, followed by any Claude-specific notes.
</Listen>

## What belongs in the file

The best-practices doc gives a two-question test before you write anything down: could the agent find this by reading the code, and would it actually go and look? If both answers are yes, leave it out. Current models read repositories well; they discover your layout, conventions, test framework, and component patterns faster than you'd explain them. What they can't find is information that was never in the repo.

Things that pass the test:

- **How to confirm work**: the exact test, typecheck, and lint commands, and how to run one test file. The docs call the check command "the single most useful line."
- **Places where the code misleads**: an old pattern that's everywhere but mustn't be copied, a directory that looks dead but isn't.
- **Decisions made outside the code**: which error helper the team chose, how deploys work, what needs migration review.
- **Anything you've corrected twice.** The memory docs list the triggers: the same mistake a second time, a review comment the agent should have known, the same correction typed again, context a new teammate would need.

Things that fail it: directory tours, dependency lists, architecture overviews the code already shows, generic advice ("write clean code"), and personal preferences (those go in `CLAUDE.local.md` or your user file).

Things that belong somewhere else: multi-step procedures (a release, an incident runbook) go in a **skill**, which loads only when needed. Rules for one part of the codebase go in a path-scoped **rule**. Rules with zero exceptions go in a **hook or deny rule**. The features overview has a useful trigger table for this, covered in lesson 5.

The target size is under 200 lines per file; longer files cost context on every request and the docs say they reduce adherence. Simon Willison adds a practical note for tooling: a few examples of how to run your project's scripts in the instruction file is usually enough for an agent to adapt them.
</Listen>

```markdown
# Commands
- Install: uv sync
- All tests: uv run pytest -q
- One test file: uv run pytest -q tests/path/to/test_x.py
- Typecheck: uv run mypy src

# Conventions
- Errors: raise the classes in src/app/errors.py; never raise bare Exception
- src/legacy/ is still in production; don't copy its patterns into new code

# Gotchas
- Integration tests need DATABASE_URL (see .env.example); unit tests don't
- Money is integer cents; Decimal only at the API boundary

# Boundaries
- Ask before adding a dependency or changing a public API
- Don't edit or skip tests to make them pass; if a test looks wrong, stop and say why
```

## Writing instructions that change behavior

Most instruction files fail not because they're missing a rule but because their rules can't be acted on. The memory docs' examples are the model to copy: "Use 2-space indentation" instead of "Format code properly"; "Run `npm test` before committing" instead of "Test your changes"; "API handlers live in `src/api/handlers/`" instead of "Keep files organized." Each rewrite is something you could check.

Four more principles from the docs:

**Specific over emphatic.** The best-practices page lists "add IMPORTANT or ALL CAPS" under advice you can stop following: current models follow a plainly worded line, and emphasis mostly makes them over-apply the rule. If a line keeps getting missed, either the file is too long or the rule can't bend and belongs in a hook.

**Consistent.** If two instructions contradict each other, the docs say Claude may pick one arbitrarily. Review nested files and rules together; `/doctor prompt-audit` looks for stale, contradictory, or dead references.

**Explain the why when it isn't obvious.** "Don't use `round()` for money: it rounds half to even and our rule is half up" lets the agent handle the case you didn't foresee. That's one reason the `/doctor` checkup keeps pitfalls and rationale while trimming what the code already shows.

**Test the instruction.** Treat a new line like a code change: start a fresh session, give a task where the line should matter, and watch. If behavior doesn't change, the line is dead weight or wrongly worded.
</Listen>

<Callout type="pitfall" title="Keeping /init's draft as written">
A generated CLAUDE.md is a starting point that describes what the generator could see in your repo, which is exactly the content the agent could find itself. Teams often commit it unchanged and then add to it for a year, ending with hundreds of lines of directory tours and stale commands. Delete everything the code already shows, keep commands and gotchas, and set a calendar reminder to prune. A line that hasn't prevented a mistake in months is a candidate for deletion.
</Callout>

    out, inside = [], False
    for ch in line:
        if ch == "\`":
            inside = not inside
            continue
        if not inside:
            out.append(ch)
    return "".join(out)

def _has_test_command(text):
    for line in text.splitlines():
        parts = line.split("\`")
        if any("test" in parts[i] for i in range(1, len(parts), 2)):
            return True
    return False

def lint(text, max_lines=200):
    lines = text.splitlines()
    findings = []
    if len(lines) > max_lines:
        findings.append((0, "too-long"))
    if not _has_test_command(text):
        findings.append((0, "no-test-command"))
    for n, line in enumerate(lines, start=1):
        if line.lstrip().startswith("#"):
            continue
        plain = _strip_code(line)
        words = [w.strip(".,:;()!?\\"'") for w in plain.split()]
        if "IMPORTANT" in plain or any(len(w) >= 4 and w.isalpha() and w.isupper() for w in words):
            findings.append((n, "shouting"))
        low = plain.lower()
        if any(p in low for p in VAGUE):
            findings.append((n, "vague"))
        lower_words = [w.lower() for w in words]
        absolute = any(a in lower_words for a in ABSOLUTE if " " not in a) or any(a in low for a in ABSOLUTE if " " in a)
        if absolute and any("/" in w for w in plain.split()):
            findings.append((n, "enforce"))
    return sorted(findings)`}

## One file, many agents

Teams rarely use a single tool. The open AGENTS.md format, now stewarded by the Agentic AI Foundation under the Linux Foundation, describes itself as a README for agents, with no required fields, and is read by a long list of tools including Codex, Copilot's coding agent, Cursor, Gemini CLI, and many others. Some details differ by tool:

- **Codex** walks from the project root to the current directory, taking at most one file per directory (an `AGENTS.override.md` wins over `AGENTS.md`), concatenates them, and stops adding at a size limit that defaults to 32 KiB. It builds the chain once per session, so restart after edits.
- **Copilot** uses `.github/copilot-instructions.md` for repository-wide instructions, `.instructions.md` files with `applyTo` globs for paths, and the nearest `AGENTS.md`; a single root `CLAUDE.md` or `GEMINI.md` can stand in for it.
- **Gemini CLI** reads `GEMINI.md` by default and can be configured (`context.fileName`) to read `AGENTS.md`. Antigravity CLI, its successor for many users, reads both.
- **Claude Code** reads `AGENTS.md` only when no CLAUDE.md is present, so import it explicitly.

A practical layout: `AGENTS.md` holds everything tool-neutral (commands, conventions, boundaries); `CLAUDE.md` contains `@AGENTS.md` plus a few Claude-specific lines; enforcement lives in each tool's own configuration, because hooks, deny rules, and sandboxes are product-specific.
</Listen>

<GoDeeper title="Auto memory, and when to use it">
Claude Code also keeps **auto memory**: notes Claude writes itself from your corrections and preferences, stored per repository and loaded each session (the first 200 lines or 25KB of its index). It's useful for personal working preferences, and risky as a substitute for team knowledge: it's yours alone, Claude chose what to record, and it can go stale. Run `/memory` to read it. A good habit is a monthly look: promote anything the whole team needs into the committed CLAUDE.md or AGENTS.md, and delete anything wrong. The same discipline applies to the shared file: it's code, so changes to it deserve review like any other change.
</GoDeeper>

## Your checklist for project memory

Under 200 lines. Commands to check work at the top, including how to run one test. Only what the agent can't learn by reading, plus what it would waste time rediscovering. Concrete, checkable wording, no shouting. Rationale for non-obvious rules. Procedures in skills, path-specific rules in `.claude/rules/`, zero-exception rules in hooks or deny rules. One shared `AGENTS.md` for a mixed-tool team, imported from `CLAUDE.md`. Verified with `/context all` and a fresh-session test. Pruned on a schedule. The project for this elective asks you to measure whether your file actually changes outcomes; most people are surprised how few lines matter.
</Listen>
