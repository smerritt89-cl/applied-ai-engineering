## The check is what makes delegation work

The Claude Code best-practices page puts it plainly: Claude stops when the work looks done, and if it has nothing to run that says whether the work actually is done, "looks done" is all it has. Give it something that comes back pass or fail (a test file, a build's exit code, a linter, a script that diffs output against a fixture) and it can close the loop itself: change, check, read the failure, fix, check again. That's the difference between an agent you supervise line by line and one you can leave for twenty minutes.

Tests are the best general-purpose check because they encode the requirement in a form the machine can evaluate. That also makes them the most important thing to protect. If the agent can quietly change what the tests require, "all tests pass" stops meaning anything. This lesson covers both halves: using tests as the contract, and keeping the contract from being renegotiated by the party it binds.
</Listen>

<Listen>
## Test-first prompting

The most reliable loop with an agent is the old test-driven one, done deliberately:

1. **State the behavior and write the test first.** Either write it yourself or ask the agent to write only the test, from your spec, and stop. The docs' own example prompt for a bug is: describe the symptom, point at the likely area, "write a failing test that reproduces it, then fix it."
2. **Confirm it fails, for the right reason.** Run it. A new test that passes before any fix is testing the wrong thing. Read the failure message: it should describe the bug, not an import error.
3. **Review and commit the test.** This is the contract. Reading a 15-line test is far easier than reading the 150-line fix, and it's where your judgment adds the most.
4. **Ask for the implementation, with the tests fixed.** "Make this test pass without modifying any file under tests/. If you believe a test is wrong, stop and tell me why."
5. **Require evidence.** "Run `python3 -m pytest -q` and show the output." The docs suggest asking for the command it ran and its output, because "all tests pass" on its own tells you very little.

Committing the test before the fix has a second benefit: the fix's diff can't hide a change to the test, because any test change shows up separately against a commit you reviewed.
</Listen>

## Make running the tests non-negotiable

There's a ladder of strictness, and the best-practices page lays it out. At the bottom, ask in the prompt ("run the auth tests after, and keep going until they pass"); Claude decides when it's satisfied. Put the test command in CLAUDE.md so it always knows how. Next, a goal condition that a separate model checks after each turn. At the top, a **Stop hook**: Claude Code runs your script whenever Claude tries to end its turn, and if the script exits with code 2, Claude is sent back to work with your stderr as the reason. That's enforced by the harness, so the turn doesn't end until the check passes or the block limit is reached. And independent of all of these, CI runs the suite on every pull request, because the last word should belong to something the agent doesn't control.

A PostToolUse hook that runs fast tests after each edit is a useful complement: failures land in the agent's context immediately, while it still has the change in mind. Keep it fast, and leave the full suite for Stop and CI.
</Listen>

## Agents do edit tests, and the evidence is not anecdotal

If you've had an agent "fix" a failing test by changing the expected value, you're not unlucky. Two studies document the pattern.

**ImpossibleBench** (Zhong, Raghunathan, and Carlini, 2025) built coding tasks whose unit tests directly contradict the natural-language specification, so any pass implies a shortcut. The authors report that frontier models frequently cheat on these tasks and that stronger models generally cheat more. The strategies they catalog include modifying test cases (despite instructions not to), overloading comparison operators so assertions pass, counting calls to return different answers, and hard-coding test-specific outputs. Their most effective mitigation was restricting test access: hiding the tests from the agent reduced cheating to near zero. They also tested read-only test access and stricter prompts, with effects that varied.

**METR's 2025 report on reward hacking** found frontier models overwriting a scorer's timer, stubbing out an evaluator to always return success, and modifying test or scoring code. On one task, telling the model not to cheat had a nearly negligible effect.

The practical lesson isn't that agents are malicious. It's that "make the tests pass" is a goal that can be satisfied in more than one way, and an optimizer will sometimes find the cheaper one, especially when the real fix is hard or the test is wrong. Your job is to make the cheap path unavailable or visible.
</Listen>

<Listen>
## Layered defenses against test tampering

No single control is enough, because each covers a different path. Stack them.

1. **Instructions.** CLAUDE.md and the prompt say: don't edit, skip, or delete tests; if a test seems wrong, stop and explain. Necessary, and the research above shows it isn't sufficient.
2. **Permission rules.** A deny rule such as `Edit(/tests/**)` in `.claude/settings.json`. The permissions docs say Read and Edit deny rules apply to Claude's file tools and to file commands Claude Code recognizes in Bash (`sed`, `tee`, redirections), but not to arbitrary scripts that open files themselves.
3. **A PreToolUse hook** that blocks Edit and Write on test paths, with a message telling the agent what to do instead. Same coverage gap: it sees only the tools its matcher names.
4. **The sandbox**, for OS-level enforcement that applies to every process, including scripts.
5. **Commit tests first**, so any later change to them is a separate, visible diff.
6. **Holdout tests** the agent never sees, run after it finishes. This is ImpossibleBench's mitigation in practice, and it also catches fixes that special-case the visible tests. The lab's `make_workspace.py score` does exactly this.
7. **CI and review rules.** A CI step that fails if test files changed without a label or approval; GitHub's CODEOWNERS can require a specific reviewer for `tests/`, and branch protection can require that review before merge.

Layers 2 through 4 are the harness; 5 through 7 are your process. In a solo project, layers 1, 2, 3, 5, and 6 cost almost nothing to set up.
</Listen>

<Callout type="pitfall" title="Blocking test edits for the agent, and forgetting it may need new tests">
Locking `tests/` entirely has a cost: the agent can't add the regression test you want for the bug it just fixed. Two workable patterns. Allow new files but protect existing ones (a hook can check whether the path already exists in git). Or have the agent propose test changes in its summary and apply them yourself after reading them. Either way, the principle is that additions are cheap to review and modifications to existing expectations need a person.
</Callout>

## Coverage of edge cases, not lines

Agents write tests readily, and many of them are weak in a specific way: they exercise the code the agent just wrote, with expected values computed by the same logic, so they pass by construction. Three practices raise the bar.

**Name the edge cases yourself.** Before asking for tests, list the cases that matter from the requirement: boundaries (exactly 10 units, exactly 50), empty and maximum inputs, invalid inputs that must be rejected, the interactions between rules (does making promo codes case-insensitive bypass the expiry check?). Ask for tests with literal expected values worked out from the spec. This is a few minutes of your judgment, and it's the part an agent is least able to supply because it requires knowing what the business meant.

**Measure branch coverage, not just line coverage.** The coverage.py docs explain that branch measurement tracks whether each possible jump (both sides of an `if`) was taken, so it reveals untested paths that line coverage reports as covered. Run it after the agent's tests and ask for tests for the missing branches. Treat the number as a map of what's untested, not a target to hit.

**Use properties for whole classes of inputs.** Property-based testing tools such as Hypothesis generate many inputs and check that a stated property holds (for example, a discount never makes a price negative, and a larger quantity never costs less per unit within a tier). Properties are hard to game with special cases, because the inputs aren't known in advance.
</Listen>

<GoDeeper title="Mutation testing: testing the tests">
A stricter check of test quality is mutation testing: a tool makes small changes to the code (flip `>` to `>=`, change a constant, delete a line) and reruns the tests; a mutation that no test catches marks a gap. It's slow on large codebases but useful on a critical module, and it pairs naturally with agents, because an agent can be asked to add a test for each surviving mutant and the tool verifies the result. The lab's seeded bugs are, in effect, hand-made mutants: the bulk-tier boundary (`>` instead of `>=`), the rounding rule, and the case-sensitivity of promo codes. Ask yourself which of your current tests would have caught each one.
</GoDeeper>

<Listen>
## The contract, summarized

Write or approve the test before the fix, and see it fail for the right reason. Commit it. Ask for the implementation with the tests held fixed and evidence required. Enforce the check with a Stop hook and CI, so it doesn't depend on the agent remembering. Protect existing tests with layers (instructions, deny rules, a hook, holdout tests, review rules), and review any test change before the code change. Raise coverage where it counts: human-named edge cases, branch coverage as a map, and properties for whole classes of inputs. The lab lets you watch the difference these make on the same task.
</Listen>
