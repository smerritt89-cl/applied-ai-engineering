## The agent reads your request conservatively

The Claude Code best-practices page names a pattern you've probably seen: Claude tends to read a request conservatively and build the smallest thing that satisfies it, because it can't see how much you were hoping for. Its other failure is the opposite: confidently building the wrong thing, because the request was ambiguous and it picked an interpretation without asking. Both come from the same gap. The request didn't contain the information the agent needed, and the agent filled it in.

Planning closes that gap before code exists, when changes are cheap. You already have the skills for this. A PM who writes a crisp ticket, with a goal, acceptance criteria, and what's out of scope, gets better work from engineers; the same ticket gets better work from an agent, for the same reasons. Simon Willison makes the point directly in his list of practices that make coding agents effective: planning, clear instructions, good tests, and review are management skills, and people with them get more out of agents.
</Listen>

## Plan mode and the explore, plan, implement rhythm

Claude Code's **plan mode** makes the separation explicit. You enter it with Shift+Tab, `/plan`, or `--permission-mode plan`. In it, Claude reads files and runs shell commands to explore, then writes a plan, but doesn't edit your source. When the plan is ready, you choose: approve and continue in auto mode, approve and approve each edit manually, or keep planning. Ctrl+G opens the plan in your editor so you can change it before approving. There's also an `opusplan` model alias that uses Opus while planning and Sonnet while executing.

Read a plan the way you'd read a design doc from a new hire. Does it name the right files? Does it identify the risky part (a migration, a public API, concurrency)? Does it say how the change will be verified? Does it propose anything you didn't ask for? The plan is also where you notice the agent misunderstood the problem, which is far cheaper to fix than a 400-line diff built on the misunderstanding.

When you don't know exactly what you want yet, the best-practices page suggests flipping the roles: ask Claude to interview you until it could write the spec, then write it to `SPEC.md`. It will ask about the parts you haven't pinned down. Then start a fresh session to build from the spec, so the build begins with clean context and a written definition of done, and point a reviewer at the same spec afterwards.
</Listen>

## Specs and acceptance criteria that an agent can check

A spec for an agent is a short document, not a requirements tome. Four parts do most of the work.

**Goal.** One or two sentences on the outcome and who it's for. "Customers with expired cards can update their card at checkout without losing their cart."

**Acceptance criteria.** Specific, observable, checkable. Each should translate directly into a test or a command. Good criteria name inputs and outputs ("a 101st request within 60 seconds gets HTTP 429 with a Retry-After header"), edge cases the agent can't guess ("the health checker is never limited"), and the check that defines done ("the new test file and the existing suite pass").

**Non-goals.** What not to do: no new dependencies, no change to the public API, no refactor of the payments module. Non-goals prevent the scope creep that shows up later as an unreviewable diff. They're also how you tell the agent where your ambition ends, the counterpart to the docs' "be ambitious" phrase.

**Constraints and context.** The things it can't see: a decision from a meeting, a performance budget, a file that must not be touched, where similar code lives ("follow the pattern in `HotDogWidget.php`", in the docs' example).

The spec does double duty. It guides the build, and it's the yardstick for review. The best-practices page's suggested review prompt has a subagent check the diff against the spec, confirm every requirement is implemented and the listed edge cases have tests, and report only gaps that affect correctness, explicitly skipping style, because a reviewer asked to find problems will always find something.
</Listen>

```markdown
# SPEC: per-key rate limiting for the public API

## Goal
Protect the public API from a single noisy client without affecting normal use.

## Acceptance criteria
- 100 requests per rolling 60 seconds per API key; the 101st gets HTTP 429 with a Retry-After header (seconds).
- Limits are per key, not per IP. Requests without a key are rejected before limiting (existing behavior).
- Health checks (user agent `hc/1`) are never limited.
- Limit state survives a single app restart (use the existing Redis connection in src/infra/redis.py).
- Done: tests/test_rate_limit.py covers every bullet above; `uv run pytest -q` passes.

## Non-goals
- No new dependencies. No changes to the response format of existing endpoints. No admin UI.

## Context
- Middleware pattern to follow: src/middleware/request_id.py.
- Ops decided (2026-11-03 meeting) that limits are per key because enterprise customers share IPs.
```

## Decompose into steps a person can review

Google's engineering practices guide on small changes argues for keeping each change to one self-contained idea: small changes are reviewed faster and more thoroughly, are less likely to introduce bugs, are easier to roll back, and are less wasted work if rejected. It also suggests separating refactors from behavior changes. Every one of those reasons applies more strongly to agent-written code, because an agent can produce a large diff faster than you can read it.

So break the work into steps where each step has its own check and its own commit. A useful default order: tests or fixtures first, then the core change, then integration and wiring, then cleanup. Keep mechanical changes (renames, moves, formatting) in separate commits from logic changes, so the logic diff is small enough to read.

For long tasks, Anthropic's post on harnesses for long-running agents describes what made multi-session work reliable: an explicit feature list kept in a file (they used JSON) with each item's status, a progress file the agent updates, and git commits as checkpoints, with the agent working on one feature at a time and verifying it before marking it done. Their named failure modes are worth remembering: trying to one-shot the whole thing, and declaring victory before the work is verified. Those are management failures too. The fix in both worlds is the same: a written list of deliverables, one in progress at a time, and status backed by evidence.
</Listen>

<Callout type="pitfall" title="Approving the plan without reading it">
Plan mode only helps if you engage with the plan. The common failure is treating approval as a formality: skimming, pressing approve, and then discovering in the diff that the agent planned to restructure a module you never mentioned. Read for the four things above (files, risks, verification, extras), cut anything outside the spec, and split anything you couldn't review in one sitting. If you wouldn't approve a design doc this vague from a colleague, don't approve it from an agent.
</Callout>

## Parallel sessions and worktrees

Once work is decomposed, some steps are independent, and you can run them at the same time. Each needs its own checkout, or the sessions' edits collide. Git worktrees give you exactly that: additional working directories attached to one repository, each on its own branch, sharing history. In Claude Code, `claude -w feature-auth` starts a session in a new worktree; subagents can set `isolation: worktree`; and `/batch` splits a large mechanical change into units, each in its own worktree, after showing you the plan.

The best-practices page notes a few practical details. A worktree is a fresh checkout, so gitignored files like `.env` aren't there and dependencies aren't installed; list small files to copy in a `.worktreeinclude`, and keep the install command in CLAUDE.md. Clean-up is mostly automatic for interactive sessions, but `claude -p --worktree` runs are yours to remove with `git worktree remove`.

Then the constraint that actually binds: **your review capacity**. Three parallel sessions produce three diffs that all need a careful read. Parallelism pays off when the streams are truly independent (different modules, no shared interfaces) and each has strong automated checks, so your review is a confirmation rather than an investigation. When two streams touch the same code, sequence them or extract the shared change first; otherwise you inherit a merge that nobody checked against both specs.
</Listen>

  solution={`def waves(tasks, depends_on, touches, max_parallel=3):
    done, remaining, out = set(), list(tasks), []
    while remaining:
        wave, files = [], set()
        for t in remaining:
            if len(wave) >= max_parallel:
                break
            if not set(depends_on.get(t, [])) <= done:
                continue
            f = touches.get(t, set())
            if f & files:
                continue
            wave.append(t)
            files |= f
        if not wave:
            raise ValueError("dependency cycle or unsatisfiable dependency among: " + ", ".join(remaining))
        out.append(wave)
        done |= set(wave)
        remaining = [t for t in remaining if t not in done]
    return out`}
>
This is dependency planning, the PM skill, applied to agent sessions. Write `waves`, then press **Check my answer**. Notice the two constraints beyond dependencies: shared files (two sessions editing `api/routes.py` at once means a merge conflict, so one waits) and `max_parallel`, which stands for how many diffs you can review well at once. Try `max_parallel=6` and see how little it changes; dependencies and shared files usually bind first.

<GoDeeper title="Unattended runs: the five questions">
For work you leave running (a nightly job, a CI task, a long background session), the best-practices page gives five questions to answer for the specific task: Does it know what done looks like (a goal, a spec, a failing test to turn green)? Can it check its own work (tests, a Stop hook, a review step)? What may it touch (permission rules, `dontAsk` mode, the sandbox, a worktree, the one branch it may push to)? What stops it (`--max-turns`, `--max-budget-usd`, a spend limit)? Where does the result go and who signs off (a pull request, then a person approving the merge)? They're the same questions you'd ask before handing a task to a contractor you can't supervise. The docs add a warning for scheduled cloud tasks: protect `main` with a branch rule the task can't bypass, and watch the first few runs before trusting it.
</GoDeeper>

<Listen>
## The PM skills that transfer

If you've led product or projects, you already have most of what directing agents needs; it just has to be applied more literally, because an agent won't ask the hallway question a colleague would. **Scoping**: say what's in and out, in writing. **Acceptance criteria**: make done observable and testable. **Dependency planning**: sequence work that shares interfaces, parallelize what doesn't. **Work breakdown**: deliverables small enough to review in one sitting. **Status with evidence**: a step is done when a check passed and the commit exists, not when someone says it's done. **Risk management**: identify the irreversible steps and keep them for a person. The difference from managing people is that agents are tireless, fast, literal, and confidently wrong at times, so the documents you write and the checks you require carry more of the load.
</Listen>
