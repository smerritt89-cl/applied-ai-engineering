## Three dials and a budget

When a session is too slow, too expensive, or not good enough, there are three things you can change, and they are easy to conflate.

The **tool** is the harness: Claude Code, Codex, Copilot, Cursor, Gemini CLI or its successor Antigravity CLI. It decides what tools the model has, how context is managed, what is enforced, and where the work runs (your machine, a cloud sandbox, a CI runner). Switching tools changes the loop, not just the model.

The **model** is the reasoner. Each vendor offers tiers: a most-capable model, a cheaper near-peer for everyday work, and small fast models for simple, high-volume jobs.

The **effort level** controls how much the model deliberates before acting. In Claude Code it runs from `low` to `max`, set with `/effort` or per skill or subagent.

Then there's the **budget**: money, your time, and your attention. A cheaper setup that needs twice the review is not cheaper. This lesson gives you starting points for each dial, honest about how thin the public evidence is, and then the method that actually settles it: a small comparison on your own work.
</Listen>

## What the vendors say, at the time of writing

These are fast-moving facts, checked on November 11, 2026. Recheck the linked pages before relying on them.

**Claude Code.** The model configuration docs say the default on most plans and on the Anthropic API is Opus 5.5, at medium effort. The best-practices page says the default Opus handles most coding well, Sonnet costs less on routine work, and Haiku is a good fit for subagents doing simple jobs such as collecting the files that import a module. The `fable` alias selects the Fable model, described as being for the hardest, longest-running tasks; it is never the default and can bill to usage credits. There's also `opusplan`, which uses Opus while planning and Sonnet while executing.

**Effort, per the same docs.** `low` for quick exchanges you review closely (brainstorming, a small rename). `medium` for day-to-day work with a clear scope. `high` or `xhigh` where getting it right depends on cases that are easy to overlook: a bug in code you didn't write, a flaky test, a schema change that must find every reader of the old shape. `max` for hard problems you want worked through without you, with a warning that it tends to overthink ordinary tasks. The docs also say phrases like "think hard" are ordinary text, not switches; `ultrathink` requests deeper reasoning for one turn.

**OpenAI Codex.** The Codex models page lists a most-capable model, a lower-cost model with near-top performance aimed at repeated, long-running work, and efficient models for focused, high-volume tasks, plus reasoning-effort settings from light to max (and an "ultra" level that splits work across subagents).

**xAI.** The xAI models page, at the time of writing, recommends its flagship Grok model for code.

Notice the pattern: every vendor recommends its strongest model as the default for coding and a smaller one for narrow, repetitive subtasks. That's a reasonable prior. It is not evidence about your tasks.
</Listen>

## Matching settings to task types

No public benchmark cleanly ranks today's models by task type, and claims that "model X is best at refactoring" are mostly anecdote. What you can do is reason from what each task demands, then test. Here are defensible starting points.

**Large refactors and migrations.** The risk is missing a caller or breaking a contract across many files. Start with the strongest model at high effort, plan first (lesson 6), and insist on a check that covers the whole surface (the full test suite, a typecheck, a grep that must come back empty). For many mechanical, independent edits, fan-out beats one long session: Claude Code's `/batch` splits a change into units in separate worktrees. Per-unit work is often fine on a cheaper model; review sampling matters more than model choice there.

**Greenfield prototypes.** The risk is building the wrong thing, not subtle bugs. Lower effort and fast iteration are fine while you steer. The Claude Code docs note that Claude tends to build the smallest thing that satisfies a request, and that saying "be ambitious" tells it about scope you want.Prototypes are also where you can let an agent run most freely, because the code is meant to be thrown away; the danger is a prototype quietly becoming production code without the review it never got.

**Debugging.** Agents are strong here when the bug is reproducible, because the loop has a check: reproduce, hypothesize, change, rerun. Simon Willison lists debugging among the problems that suit agentic loops for exactly this reason, alongside performance tuning and dependency upgrades: clear success criteria plus trial and error. Raise effort for unfamiliar or intermittent bugs. If you can't reproduce the bug, the agent can't either; spend your effort on a reproduction first.

**Code review.** The model matters less than independence: a reviewer that didn't write the code and didn't see the reasoning that produced it (lesson 8). A different model family can add independence, at the cost of more noise.

**Data work and analysis.** Correctness is hard to see, because a wrong join still produces a plausible table. Prefer settings that make the agent show its work (queries, row counts, sanity checks), and verify the numbers against something you trust. Effort helps less than checks.

Across all of them, METR's time-horizon research is the best general guide to scope: success falls as tasks get longer, so a task you can break into checkable pieces is a task you can delegate more safely, whatever the model.
</Listen>

<Callout type="pitfall" title="Max everything">
After a bad session it's tempting to switch to the biggest model at maximum effort and leave it there. You'll pay more and wait longer on every routine edit, and the docs warn that `max` can overthink ordinary tasks without doing better than `high`. Raise the dials per task when the task calls for it, and fix the real cause of most bad sessions, missing context or a missing check, with the setup work in weeks 2 and 3.
</Callout>

<Listen>
## Where the money goes

On API pricing, an agent session costs input tokens plus output tokens on every turn, and every turn resends the conversation so far. Four things drive the bill. **Session length**: a long session that has accumulated three unrelated tasks re-reads all of them on each turn of the fourth (prompt caching discounts this while the cache is warm, and the docs say the cache lasts about five minutes on API keys and about an hour on subscriptions). **Tool output**: large files and full test logs. **Effort**: thinking tokens are billed even when hidden. **Subagents**: the docs say every subagent sends its own requests against the same usage, and a fresh one first has to rebuild context the main session already had.

Three habits keep it visible and bounded. Run `/usage` to see where usage went, broken down by skill, subagent, and MCP server on subscription plans. In scripts, `claude -p ... --output-format json` returns a `total_cost_usd` estimate per run, and `--max-turns` and `--max-budget-usd` cap a run. And use `/clear` between unrelated tasks; it costs nothing.
</Listen>

## Run your own comparison

Here is a design you can run in an afternoon, and that the lab and the project formalize.

1. **Pick five to ten tasks before you run anything.** Use real, recent work from your repo with a known good outcome: closed bugs with a fixing commit, small features with tests. Mix types. Write each as the prompt you'd actually give.
2. **Fix everything except the variable.** Same tasks, same prompt text, same starting commit. Change one thing: the model, the effort, the tool, or the repo setup.
3. **Isolate each run.** A fresh session in a fresh worktree or clone, so no run sees another's context or edits.
4. **Repeat.** At least three runs per task per setup. Agent runs vary, and lesson 2 showed how wide the uncertainty is on small samples.
5. **Record outcomes, not feelings.** For each run: did it succeed by your check (tests, plus your review), how much rework you needed, wall time, and cost.
6. **Decide on cost per successful task and rework,** not on the best single run.

The exercise below computes the summary you'd look at. Keep the conclusion modest: with ten tasks you can detect a large difference, not a small one.
</Listen>

<GoDeeper title="Why one good run proves little">
If a setup succeeds on a task with probability p per run, the chance it succeeds on all of k independent runs is p to the power k. A setup with p = 0.8 passes a single trial 80% of the time but passes three in a row only about half the time (0.512). That's the pass-at-k versus pass-to-the-k distinction from Studio 3, and it's why your comparison needs repeats: you're estimating p, and the setup you can trust unattended is the one whose p is high enough that repeated success is likely. It also explains a common experience: a new tool "worked great" in a demo and then disappointed in daily use. The demo was one draw.
</GoDeeper>

<Listen>
## A default policy you can start with

Until your own measurements say otherwise: use the tool your team already has, configured well (weeks 2 and 3 matter more than switching). Leave the model and effort at their defaults for everyday work. Raise effort for bugs in unfamiliar code, intermittent failures, and changes that must find every usage. Lower it for fast, closely watched iteration. Route simple, repetitive subagent work to a small model. Watch `/usage` weekly. And whenever someone proposes a switch, ask for five tasks, three runs each, and cost per success.
</Listen>
