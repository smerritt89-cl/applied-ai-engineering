## The stage you didn't build last lesson

Your Shakespeare GPT read characters: a vocabulary of a few dozen symbols, one per character. Production language models don't. They read **tokens** from a vocabulary of tens or hundreds of thousands of chunks, produced by a separate component, the tokenizer, which has its own training data and its own training algorithm. The lecture's description stresses that it is a completely separate stage of the pipeline, with exactly two jobs after training: encode strings to tokens, and decode tokens back to strings.

This lecture is about that stage, and it's the most directly useful one in the series for an applied engineer. Token counts are what you pay for, what context windows are measured in, and what latency scales with. And, as the lecture shows in its last half hour, a surprising number of odd model behaviors trace back to how text was cut into tokens.

The lecture builds the GPT-2 tokenizer from scratch. Its companion repository, `minbpe` (MIT), contains the finished code, and its `exercise.md` lays out the build in stages so you can try each one before watching the answer.
</Listen>

## Code points and bytes

A Python string is a sequence of Unicode **code points**, integers assigned to characters by the Unicode standard (`ord("a")` is 97, and an emoji's code point is above 100,000). There are well over a hundred thousand assigned code points, and the standard keeps growing, so code points make an awkward base vocabulary.

**UTF-8** encodes each code point as 1 to 4 bytes: ASCII characters take 1 byte, most Latin, Greek, and Cyrillic letters with accents take 2, most Chinese, Japanese, and Korean characters take 3, and emoji take 4. It's backward compatible with ASCII and dominant on the web, which is why the lecture prefers it over UTF-16 and UTF-32.

The GPT-2 paper (Radford and colleagues, 2019, section 2.2) gives the argument for a byte-level base: a tokenizer working on code points would need a base vocabulary of over 130,000 symbols before adding any multi-symbol tokens, whereas bytes need only 256, and any string at all can be represented. Feeding raw bytes straight into a model would make sequences long (one token per byte), so BPE compresses them. The lecture's "daydreaming" aside at 22:47 notes that deleting tokenization and modeling raw bytes would be cleaner if the sequence-length cost could be solved.
</Listen>

```text
BPE training (byte level), target vocabulary size V:
  ids    = list(text.encode("utf-8"))           # integers 0..255
  merges = {}                                   # (a, b) -> new id
  for new_id in 256 .. V-1:
      pair   = most frequent adjacent pair in ids
      ids    = ids with every occurrence of pair replaced by new_id
      merges[pair] = new_id

encode(text):  start from UTF-8 bytes; repeatedly merge the adjacent pair with the LOWEST merge id
               present, until no pair in the sequence is in merges
decode(ids):   concatenate each id's bytes; bytes.decode("utf-8", errors="replace")
```

## Byte Pair Encoding

BPE started as a data compression method and was brought to NLP for subword units by Sennrich, Haddow, and Birch (2016). The training algorithm is greedy and simple: count every adjacent pair of tokens in the training text, merge the most frequent pair into a new token, and repeat until the vocabulary reaches the target size. Each merge shortens the sequence; the ratio of bytes to tokens is the compression ratio, which the lecture tracks as training proceeds (34:58).

The vocabulary is then 256 byte tokens plus one token per merge, and each merged token stands for a byte string (the concatenation of its two parts, recursively). GPT-2's vocabulary has 50,257 entries, which the lecture breaks down as 256 bytes, 50,000 merges, and one special token, `<|endoftext|>`, which marks document boundaries.

Encoding new text replays the merges, and the order matters: merges must be applied in the order they were learned (lowest new id first), because later merges are built out of earlier ones. Decoding is a lookup plus a byte concatenation, with one catch the lecture highlights at 42:47: an arbitrary sequence of token ids may not form valid UTF-8 (for example, a lone continuation byte), so decoding must handle errors, typically by inserting the replacement character.
</Listen>

    out, i = [], 0
    while i < len(ids):
        if i < len(ids) - 1 and (ids[i], ids[i + 1]) == pair:
            out.append(new_id)

        else:

## The vocabulary-size trade-off

At 01:43:27 the lecture returns to its GPT to ask how big the vocabulary should be, and the answer is a genuine trade-off you can reason about with the model you built. A larger vocabulary compresses text into fewer tokens, so the same context window covers more text and generation needs fewer steps. But the token embedding table and the final linear layer each grow by one row per vocabulary entry, so parameters and the cost of the output softmax grow linearly with V. And each token appears less often in the training data, so rare tokens' embeddings get few updates and may be poorly trained.

Characters (V around 65 for Shakespeare) sit at one extreme: tiny embedding table, long sequences. GPT-2's 50,257 sits far toward the other. The lecture also shows that you can extend a trained model's vocabulary with new tokens by adding rows to those two matrices and fine-tuning, which is how special tokens for chat formats or tools can be introduced later.

This is a design choice that model providers make for you, but it shows up directly in your numbers: the same document has a different token count, and so a different cost and context footprint, under each provider's tokenizer.
</Listen>

## Regex splitting and special tokens

Pure BPE on raw bytes makes wasteful merges. The GPT-2 paper's example is "dog" followed by different punctuation: BPE would learn separate tokens for "dog.", "dog!", and "dog?", spending vocabulary on combinations. GPT-2's fix (section 2.2) is to prevent merges across character categories, with an exception for spaces. In practice, as the lecture shows at 57:36, the text is first split by a regular expression into chunks (letters, numbers, punctuation, whitespace, with a leading space attached to words), and BPE runs within each chunk only. The lecture compares GPT-2's pattern with GPT-4's, which changes details such as how runs of digits and whitespace are split. minbpe's `RegexTokenizer` implements this stage, and its README reports that its GPT-4 variant reproduces tiktoken's `cl100k_base` encoding exactly.

**Special tokens** are vocabulary entries that never come from merges and are inserted by the application: `<|endoftext|>` in GPT-2, and in chat models a family of tokens that mark roles and turn boundaries. The tokenizer must handle them separately so that ordinary user text can't produce them by accident, which is a small piece of the prompt-injection story from Studio 4.
</Listen>

<Callout type="pitfall" title="Tokenization quirks that look like reasoning failures">
Several behaviors the lecture tours at 01:51:41 are tokenization artifacts rather than failures of intelligence. **Spelling and letter counting**: a word that is one token gives the model no direct view of its letters. **Arithmetic**: numbers are split into chunks that don't align with place value, so digit-level operations are harder than they look. **Non-English text** often splits into more tokens, so it costs more and uses context faster. **Leading and trailing whitespace** changes which tokens appear (" hello" and "hello" are different tokens), so a prompt that ends in a stray space can behave oddly. When you see a strange failure, inspect the tokens before blaming the model's reasoning, and for character-level tasks, consider doing that part in code and giving the model the result.
</Callout>

## What this means when you choose and use models

Three working rules follow from this lecture.

**Measure tokens, per model.** Every model family has its own tokenizer, so the "about four characters per token" rule of thumb is only a rough guide for English with one tokenizer. When cost or context matters, count with the provider's own tooling on a sample of your real data, broken down by language and content type. Studio 1 showed where providers report token usage; this lecture explains why the numbers differ.

**Route character-level work to code.** Exact string operations (counting letters, reversing text, checking an ID format) are easy in Python and needlessly hard for a model that sees chunks. This is a model-selection decision in the broad sense: the best "model" for a subtask is sometimes a regular expression.

**Treat token boundaries as an input-format concern.** Whitespace, formatting, and the way you serialize structured data all change the token sequence. When a prompt's behavior shifts after an innocuous formatting change, tokenization is a reasonable first hypothesis, and an A/B comparison on your eval set is how you confirm it.
</Listen>
