## Why do this by hand

PyTorch computes every gradient for you. The lecture's opening argument (00:00:00 to 07:26) is that this convenience is a leaky abstraction: when training misbehaves, the cause is usually in how gradients flow through some operation, and you can only reason about that if you can compute it yourself. It also recounts how hand-written backward passes were simply normal practice in the field until fairly recently.

For you, the payoff is different and very concrete. Lesson 1 gave you backprop on scalars. Real models do it on tensors, where a single node is a matrix multiply over a batch. Working out those tensor-level rules once, carefully, means that when you read a paper's update rule or a fine-tuning library's custom kernel, the math is legible. And the method you'll use, index notation plus a shape check plus a gradient check, works for any operation anyone invents.

The video description is blunt that this lecture is not meant to be simply watched. Do the exercise in the linked notebook alongside it, pausing before each answer. The notes below give the derivations so you can check your work.

## Two rules that do most of the work

**The shape rule.** The gradient of the loss with respect to a tensor has exactly that tensor's shape. If W is 30 by 200, so is dW. This sounds trivial, and it's the most useful debugging tool in the lecture: when you're unsure whether a product needs a transpose or which axis to sum, the shapes usually leave only one option.

**Broadcast and sum are duals.** If the forward pass replicates a value (adding a bias of shape (H) to every row of an (N, H) matrix, or subtracting a per-feature mean from every example), each copy is a separate use, and the backward pass must sum the gradients over the replicated axis. Conversely, if the forward pass sums over an axis (a row sum to normalize probabilities), the backward pass broadcasts the incoming gradient back along it. This is the tensor form of lesson 1's "the chain rule sums over paths."

With those two rules plus each operation's local derivative, the rest is bookkeeping.
</Listen>

```text
linear layer        Y = X W + b          X: (N, D)  W: (D, H)  b: (H)  Y: (N, H)

index form          Y_nk = sum_j X_nj W_jk + b_k

dW_jk = sum_n dY_nk X_nj        =>   dW = X^T dY          (D, H)
dX_nj = sum_k dY_nk W_jk        =>   dX = dY W^T          (N, D)
db_k  = sum_n dY_nk             =>   db = dY.sum(axis=0)  (H)     b was broadcast over n

tanh                h = tanh(u)          du = (1 - h^2) * dh          elementwise

embedding lookup    emb[n] = C[X[n]]     dC[X[n]] += demb[n]          scatter-add: rows can repeat
```

## The linear layer, the nonlinearity, and the embedding

The linear layer's gradients come straight from index notation. Each output Y_nk is a sum over j of X_nj times W_jk, plus b_k. Differentiating with respect to W_jk picks out X_nj from every row n that used it, so dW_jk sums dY_nk X_nj over n, which is the (j, k) entry of X transpose times dY. Differentiating with respect to X_nj picks out W_jk for every output k that used it, giving dY times W transpose. And b_k was broadcast over all n rows, so db sums dY over the batch axis.

There's a pleasing symmetry here: the backward pass of a matrix multiply is two matrix multiplies. That's why a training step costs roughly three times a forward pass in compute (one forward multiply, two backward), a rule of thumb you'll see in training-cost estimates.

The tanh backward is elementwise: multiply the incoming gradient by 1 minus the squared *output*. And the embedding lookup is the one place where indexing creates subtlety. The forward pass copies row C[ix] into each example that uses character ix. The same character appears in many contexts, so the backward pass must **add** each example's gradient into that row, not assign it. In NumPy or PyTorch this is a scatter-add (or an explicit loop), and assignment silently drops all but one contribution, the tensor version of lesson 1's overwrite bug.
</Listen>

## Cross-entropy for a batch, in one line

Exercise 2 collapses the cross-entropy backward, which exercise 1 did through a dozen intermediate tensors, into one expression. You derived the single-example version in lesson 3: the gradient of minus log softmax(z)_y with respect to z is softmax(z) minus the one-hot vector for y. The loss for a batch is the **mean** over N examples, so each example's term is scaled by 1/N.

The result: dlogits equals (softmax(logits) minus one-hot(Y)), divided by N. Each row sums to zero, so the gradient only redistributes probability mass, pulling it toward the correct class. That zero-sum structure is a free sanity check on any implementation.

This is also why frameworks fuse softmax with the loss. Backpropagating separately through exp, sum, divide, log, and index works, but it allocates several N by V intermediates and multiplies small numbers together. The fused formula is one subtraction and one division. With a 50,000-token vocabulary, as in GPT-2, that difference is very real.
</Listen>

```text
BatchNorm forward (one feature, batch of n; the lecture's version uses n-1 in the variance):
  mu = (1/n) sum_i x_i
  var = (1/n) sum_i (x_i - mu)^2
  xhat_i = (x_i - mu) / sqrt(var + eps)
  y_i = gamma * xhat_i + beta

backward, with s = sqrt(var + eps):
  dgamma = sum_i dy_i xhat_i
  dbeta  = sum_i dy_i
  dx_i   = (gamma / (n s)) * ( n dy_i  -  sum_j dy_j  -  xhat_i sum_j dy_j xhat_j )

with Bessel's correction (var divided by n-1), the last term gains a factor n/(n-1).
```

## BatchNorm backward, and what the formula says

Exercise 3 derives BatchNorm's backward pass as one expression. The derivation is a good workout: x_i affects the output through three paths, directly through x hat i, through the mean (which every x hat depends on), and through the variance (likewise). Summing the three, as the chain rule demands, and simplifying gives the compact formula above. Ioffe and Szegedy's paper states the same chain-rule decomposition in its section 3.

Read the formula as a projection. Inside the parentheses, n dy_i minus the sum of dy removes the component of the gradient that would shift all examples equally, because BatchNorm's output is invariant to such a shift (the mean is subtracted). Then minus x hat i times the sum of dy x hat removes the component along x hat, because the output is also invariant to rescaling all inputs (the variance divides it out). The gradient that reaches x is the upstream gradient with exactly those two directions projected away. That's a nice example of the math explaining the behavior: BatchNorm makes a layer insensitive to the scale of its inputs, so gradients can't push along those directions.

The Bessel digression at 01:05:17 matters for the details. The unbiased variance estimator divides by n minus 1. PyTorch's `BatchNorm1d` normalizes with the biased version (divide by n) during training but tracks the unbiased version for the running variance used at inference, so training and inference use slightly different statistics. The lecture argues for using the unbiased estimate consistently, and its formula carries the corresponding n over (n minus 1) factor. For a batch of 32, the difference is about 3 percent.
</Listen>

<Callout type="pitfall" title="The four slips that a falling loss won't reveal">
**Missing 1/N** in dlogits scales every gradient by the batch size, which looks like a learning-rate problem. **Summing the bias gradient over the wrong axis** gives the wrong shape (the shape rule catches it) or, for square matrices, the right shape and wrong values (only a gradient check catches it). **Using the pre-activation in tanh's derivative** is nearly right for small values. **Assigning instead of adding** for embedding rows drops gradient for repeated characters. Every one of these trains, a little. Every one fails a gradient check on random inputs immediately.
</Callout>

## How this changes the way you read models

After this lecture, a few things about large models stop being mysterious. The cost of training relative to inference: each matrix multiply in the forward pass implies two in the backward pass, so a training step costs about three forward passes, plus the memory to store activations (lesson 1's point about reverse mode). Why fused kernels matter: the cross-entropy over a vocabulary of tens of thousands is a large tensor operation, and fusing it saves real memory and time. And why normalization layers and residual paths are designed the way they are: they control how gradients move.

It also sharpens your judgment as an applied engineer. If a vendor or a paper claims a new layer or training trick, you can ask the questions that matter. What is its backward pass? Does it add batch coupling? Does it preserve gradient scale? Was it gradient-checked, and does the reported improvement hold with a fair hyperparameter search for the baseline? Those questions are checks and balances for research claims, in the same spirit as checking model output.
</Listen>

<GoDeeper title="Index notation, and why matrix calculus identities aren't needed">
Every result above came from one recipe: write the forward pass with explicit indices, take the partial derivative of the scalar loss with respect to one entry, sum over every index that entry appears with, and then recognize the result as a matrix product. You never need a table of matrix-calculus identities, and you avoid their notational conventions (numerator versus denominator layout), which differ between sources. The recipe also extends to operations no table covers, such as attention's masked softmax or a custom normalization. If you want the general theory, the reverse-mode discussion in Baydin and colleagues' survey frames each of these as a vector-Jacobian product: the Jacobian of a matrix multiply with respect to W is never formed, only its product with the upstream gradient, which is X transpose times dY.
</GoDeeper>
