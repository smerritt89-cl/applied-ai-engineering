## A word that means too many things

"Agent" is the most overloaded word in AI engineering right now. Vendors call a chatbot with one tool an agent. Researchers use it for a system that plans and acts over hours. Your colleagues use it for anything that seems to do more than answer a question. That ambiguity has a cost: teams commit to "building an agent" before anyone has said what the system should decide on its own, and they discover the answer in production.

This studio uses a precise definition, taken from Anthropic's engineering post "Building effective agents" (Erik Schluntz and Barry Zhang, December 2024), which has become a common reference point. The post groups everything under the umbrella of **agentic systems** and then draws one line through it.

**Workflows** are systems where models and tools are orchestrated through predefined code paths. Your code decides what happens next. A model may write, classify, or check at each step, but the sequence and the set of branches are fixed by you.

**Agents** are systems where the model dynamically directs its own process and tool use, keeping control over how it accomplishes the task. The model decides what to do next, observes the result, and decides again, until it judges the task done or something stops it.

The question to ask of any system, then, is simple: **who chooses the next step, your code or the model?** Everything else in this week follows from that. Workflows are predictable and cheap to debug because you can read the control flow. Agents are flexible because they can handle paths you did not anticipate, and they pay for that flexibility in cost, latency, and errors that compound across steps.
</Listen>

## The building block: an augmented model

Both workflows and agents are built from the same brick, which the Anthropic post calls the **augmented LLM**: a model with access to retrieval, tools, and memory. You built most of one in Studio 1 (tool use) and Studio 2 (retrieval). The model can generate its own search queries, pick tools, and decide what to remember.

Microsoft's "AI Agents for Beginners" course describes the same thing in older vocabulary from classical AI. An agent has an **environment** it operates in (a booking system, a code repository, a project tracker), **sensors** that read the environment's state (tools that look things up), and **actuators** that change it (tools that write). That framing is worth keeping, because it makes risk visible. Sensors can return wrong or hostile data. Actuators can do damage. When you design an agent later in this studio, you will list both explicitly.

The Anthropic post's advice on the brick itself is practical. Tailor the augmentations to your use case, and give the model a well-documented interface to each one. It also recommends starting with the model API directly rather than a framework, because many patterns take only a few lines of code, and frameworks can hide the prompts and responses you need to see when something goes wrong. If you do use one, understand what it does underneath. This week you will write every pattern by hand for exactly that reason.
</Listen>

## Autonomy is a dial, not a switch

Hugging Face's smolagents documentation (Apache 2.0, adapted here) offers a sharper way to see the line: agency is a spectrum, measured by how much the model's output controls your program's flow. The table below adapts its levels and adds where each fits in Anthropic's terms.

Read it from top to bottom as handing over more control. At the top, model output is just data your code processes. Next, it flips a switch your code defined. Then it chooses which function runs and with what arguments. Then it decides whether the loop continues at all. Finally, one agent can start others.

Two consequences matter for you as the engineer. First, each step down multiplies the number of possible executions, which is what makes agents capable of novel paths and also what makes them hard to test: you cannot enumerate the trajectories. Second, you can usually choose the level. Most product features are best served at the top two or three rows, with a model making bounded choices inside code you can read. The smolagents guide puts it plainly: if a predetermined workflow fits your queries, code it, because it is more reliable; reach for agentic behavior when the predetermined workflow falls short too often.
</Listen>

| Level | The model's output... | Short name | Sketch | Anthropic's terms |
|---|---|---|---|---|
| 0 | has no effect on program flow | Simple processor | `summary = llm(text)` | Single call |
| 1 | picks a branch your code defined | Router | `if llm_says_bug(t): triage() else: faq()` | Workflow (routing) |
| 2 | chooses a function and its arguments | Tool call | `run(llm_tool, llm_args)` | Augmented LLM |
| 3 | decides whether to keep going | Multi-step agent | `while llm_continue(): step()` | Agent |
| 4 | starts other agentic workflows | Multi-agent | `if llm_delegate(): run_agent()` | Orchestrator-workers or agent teams |

## The agent loop at a glance

Strip away the frameworks and every agent runs the same loop. The Hugging Face Agents Course calls it the **Thought, Action, Observation** cycle. The model reasons about what to do (thought), emits a tool call with arguments (action), and your code runs the tool and feeds the result back (observation). The model reads the observation and either takes another action or produces a final answer. The course compares it to a while loop whose rules live in the system prompt and tool definitions.

The pattern has a research lineage. ReAct (Yao and colleagues, 2022) showed that interleaving reasoning traces with actions helped models on question answering and interactive tasks, partly because actions let the model look things up instead of hallucinating, and the reasoning helped it track and update a plan. Today's APIs build this in: in Studio 1 you saw that a Claude response with `stop_reason` equal to `tool_use` is the model asking your code to act, and the SDK's tool runner automates the loop.

What the model cannot do is stop the loop safely on its own. It may decide it is finished too early, or never. So every loop you write has at least two exits: the model's final answer, and a **budget** your code enforces (a maximum number of steps, tokens, dollars, or seconds). Real loops add more: a stop when a write needs human approval, a stop when the same tool call repeats with the same arguments, and an error path when a tool fails. Week 2 is entirely about building this loop well. For now, notice its shape, and notice where your code sits: between every action the model requests and the world.
</Listen>

## Four questions before you build an agent

Anthropic's post states the principle bluntly: find the simplest solution possible, and only increase complexity when needed, which may mean not building an agentic system at all. Agentic systems trade latency and cost for better task performance, so the question is always whether the trade is worth it. Often a single call, optimized with retrieval and good examples, is enough.

To make that judgment repeatable, this course uses four questions. They follow the checklist Barry Zhang, a co-author of the post, gives in his AI Engineer Summit 2025 talk (linked in the sources), phrased for a team decision.

1. **Complexity.** Is the task multi-step and hard to specify in advance? If you can draw the full decision tree, build the tree as a workflow: it is cheaper and you control every branch. "Turn this design doc into a working pull request" is open-ended. "Extract the decisions from this transcript" is not.
2. **Value.** Does the outcome justify the extra cost and latency? Agents explore, and exploration burns tokens. A task worth a few cents per run can't support a loop that costs dollars.
3. **Viability.** Can current models actually do each critical part of the task? Test the weakest link before you build around it. If one capability is shaky, narrow the scope until it isn't.
4. **Cost of error.** When the agent is wrong, how bad is it, and how quickly will you find out? Errors that are cheap and easy to detect (a failing test, a draft a person reviews) make autonomy tolerable. Errors that are costly or silent (a wrong refund, an email to a client) demand approvals, read-only access, or no agent.

If any answer is no, stay at a simpler tier. Coding agents are the standard example of a task that passes all four: the work is open-ended, valuable, within current models' reach, and verifiable by tests and review. That last property is the one teams most often skip, and lesson 3 is about why it matters.
</Listen>

<Callout type="pitfall" title="Building the agent first and the task definition later">
The most common failure is architectural, not technical: a team picks "an agent" as the solution before writing down what decisions the system must make on its own. The result is a loop with ten tools solving a problem that was a three-step workflow, and nobody can say why it chose a given path. Write the decision list first. Every decision your code can make deterministically should stay in code; give the model only the decisions that genuinely need judgment.
</Callout>

<GoDeeper title="Where the definitions disagree">
Not every source draws the line where Anthropic does. Andrew Ng's talk uses "agentic workflows" for designed iteration loops, which Anthropic would call workflows. Microsoft's course lists classical agent types (simple reflex, model-based, goal-based, utility-based, learning, hierarchical, multi-agent) borrowed from the AI textbook tradition, where even a thermostat counts as a simple reflex agent. The smolagents guide treats agency as continuous. None of these is wrong; they answer different questions. For engineering decisions, the control-flow definition is the most useful because it predicts what you will have to test and debug: if the model chooses the path, you need trajectory-level evaluation (Studio 3, lesson 11) and runtime guardrails (week 4). If code chooses the path, ordinary unit tests and per-step evals cover most of it.

Zhang's talk is about 15 minutes and expands on the post's three principles (keep it simple, show the agent's planning, invest in the tool interface). Watch it after lesson 3, when the cost and reliability arguments will be concrete.
</GoDeeper>

## What to carry into the next two lessons

You now have a vocabulary and a decision rule. A workflow is code choosing the path with models doing bounded work at each step. An agent is the model choosing the path inside a loop your code bounds. Autonomy is a dial, and the right setting is usually lower than the hype suggests. The four questions tell you when to turn it up.

Lesson 2 makes the workflow side concrete: five patterns from the Anthropic post, each in a few lines of code, and how to verify each one's output. Lesson 3 does the math on the agent side: why per-step reliability compounds, what a loop really costs, and what published measurements say about how long a task current agents can handle.
</Listen>
