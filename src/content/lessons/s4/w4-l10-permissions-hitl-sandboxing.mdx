## Two ways to cap the blast radius

In Studio 1 you gated one write tool behind an approval. An agent from this studio is a bigger problem: it chooses its own steps, holds several tools, and may run for many turns while you look elsewhere. You can't review every decision, so the question becomes how much damage the worst run could do, and how to bound it.

Anthropic's engineering post "How we contain Claude across products" (May 2026) frames the answer in two parts. The first is **supervision**: a human in the loop approves actions. The second is **containment**: limit what the agent is *able* to do, with sandboxes, virtual machines, scoped credentials, and egress controls (rules on which network destinations traffic may reach). The post also names three sources of risk to design against: a user who directs the agent to do harm (deliberately or carelessly), a model that takes a harmful action nobody asked for, and an external attacker who reaches the agent through tools, files, or network content.

The post's key distinction is between layers. Defenses in the **model** (system prompts, classifiers, training) shape what the agent tends to do; because models are probabilistic, they never reach 100%. Defenses in the **environment** set hard boundaries: if a credential never enters the sandbox, it cannot be stolen, whatever caused the attempt. And the **content** the agent reads (MCP servers, web results, files) is a third surface you limit by restricting tools and access.

Keep that split in mind for the whole week. Every control you add, ask: is this a tendency or a boundary? You want both, and you must know which is which.
</Listen>

## Least privilege, three ways

**Least privilege** means each part of the system gets the narrowest access that still does its job. For an agent, apply it on three axes.

**Tools.** Give the agent only the tools the task needs. OWASP's Excessive Agency entry lists excessive functionality as a root cause: an extension that only needs to read documents but can also delete them. Anthropic's Managed Agents security guide puts it as a default: start the agent toolset with every tool disabled, then enable the ones you need. A tool that is not loaded cannot be misused, and it also costs no context tokens.

**Credentials.** The tool's identity should be scoped to the task, not to you. A status-report agent needs read access to issues and permission to post in one channel, not an admin token for the whole tracker. GitHub's fine-grained personal access tokens, which you'll use in the project, can be limited to specific repositories and specific permissions. The Managed Agents guide goes further: keep credentials in a vault that injects them into outbound requests, so the secret never sits in the sandbox where the agent could read and leak it.

**Network.** Most damage from a fooled agent leaves through the network: an email, an HTTP request, a rendered image. Restrict egress to the hosts the task needs. The Managed Agents guide's recommended environment setting is limited networking with only the hosts the agent needs, and Claude Code's sandbox routes every connection through a proxy that checks the host against your allowed domains, which start empty.

Least privilege has one more benefit that matters to a PM: it makes the risk legible. "This agent can read issues in two repos and post to one channel" is a sentence a security reviewer can approve. "This agent has my token" is not.
</Listen>

## Read, write, and reversible

Studio 1 sorted tools into reads and writes. For agents, add a second axis: **reversibility**, meaning how cheaply you can undo the effect.

A useful grid has three rows. **Reads** (list issues, fetch a docs page) change nothing; their worst outcome is a wrong answer or, as you'll see next lesson, untrusted text entering the context. **Reversible writes** (create a draft, add a label, open a pull request) change state you can roll back. **Irreversible or external writes** (send an email, post to a customer channel, merge, delete, pay) cannot be recalled once they happen, and often affect people outside your system.

The grid tells you where to spend control. Reads can usually run without asking, as long as they cannot also carry data out (a "read" tool that fetches arbitrary URLs is also a way to send data in the query string; treat it as outbound). Reversible writes can run automatically inside a sandbox if you log them and can undo them. Irreversible writes get a human, or a design that makes them reversible: a **draft-then-approve** step, where the agent writes a draft and a person publishes it, turns "post to Slack" into "create a draft" plus one deliberate click. That pattern is the spine of this studio's project.

Two more properties make writes safer to automate. **Idempotency** (Studio 1): a retried call does not create a duplicate. And **dry runs**: a mode where the tool reports what it would do without doing it, which is also the cheapest way to show a reviewer the exact effect.
</Listen>

## Approval gates that people actually read

Approvals are the obvious control and the most often misused. Anthropic's containment post reports that Claude Code's telemetry showed users approved roughly 93% of permission prompts, and that the more approvals people see, the less attention they pay to each. Anthropic's sandboxing post (October 2025) calls this approval fatigue, and Simon Willison, writing about the CaMeL paper, describes users who are asked constantly falling into a state where they say yes to everything. A gate that is always clicked is not a gate.

Design for the reviewer's attention, as a scarce resource:

- **Ask rarely.** Do not ask for reads. Batch related writes into one decision (one status draft, not twelve posts).
- **Let rules decide what rules can decide.** A call to a non-allowlisted host, or private data in an outbound request, should be denied by code, not offered to a tired human. The lab proves this with a reviewer who approves everything: the attacks are still blocked.
- **Show the exact effect.** Display the real arguments, or better, a rendered preview or diff of what will change, never the model's summary of them. The summary is model output and can be wrong or manipulated.
- **Say why you are asking.** "Outbound request after untrusted content and private data entered the context" tells the reviewer what to look for.
- **Deny by default.** A timeout, a crashed UI, or an ambiguous answer is a no. Only an explicit yes runs the action.
- **Close the loop.** A declined call returns an error result telling the model not to retry, so the agent continues instead of asking again.

The MCP specification says applications should keep a human able to deny tool invocations, and OpenAI's agent-safety guide says to keep tool approvals on for MCP tools. Both are right, and both work only when the approvals are rare enough to mean something.
</Listen>

<Callout type="pitfall" title="Asking about everything, then trusting the clicks">
A gate on every call produces a log full of approvals that nobody read, which is worse than no gate, because it looks like oversight. If your approval rate is near 100% and the median decision time is a second or two, your reviewers are rubber-stamping. Measure both, and treat a high approval rate as a signal to remove asks (with rules or sandboxing in their place), not as evidence that the agent is safe.
</Callout>

## The permission modes you already use

You've used Claude Code for a year, so you have already lived inside this design. Its permission docs describe a tiered system: reads within the working directory run without asking, while shell commands (apart from a built-in read-only set), file edits, and web fetches ask in the default mode. Rules come in three kinds, **allow**, **ask**, and **deny**, written as `Tool` or `Tool(specifier)`, for example `Bash(npm run *)` or `WebFetch(domain:example.com)`. They are evaluated deny first, then ask, then allow, and the first match wins regardless of how specific a rule is. So a broad deny such as `Bash(aws *)` blocks `aws s3 ls` even if you also allowed that exact command. The docs also note that these rules are enforced by Claude Code, not by the model: instructions in CLAUDE.md shape what Claude tries, not what it is allowed to do.

The permission modes are presets on that system. At the time of writing the docs list six: `default` (reads only run without asking), `acceptEdits` (adds file edits and common filesystem commands), `plan` (analyze without editing), `auto` (a separate classifier model reviews actions before they run and blocks things like sending sensitive data to external endpoints, production deploys, or force pushes), `dontAsk` (only pre-approved tools; anything that would prompt is denied, suited to CI), and `bypassPermissions` (everything runs, recommended only in isolated containers or VMs). The docs warn that auto mode reduces prompts but does not guarantee safety.

Read that list as a design catalog. `dontAsk` is an allowlist with deny-by-default. `auto` replaces human approvals with a model-layer check, which helps with fatigue but is probabilistic. `bypassPermissions` is safe only when the environment is the boundary. The same three choices (rules, human, classifier) appear in every agent you will build.
</Listen>

## Sandboxes: the boundary that holds when the model is fooled

A **sandbox** is an execution environment whose limits are enforced below the model: by the operating system, a container, or a virtual machine. Anthropic's sandboxing post explains why it needs two parts. **Filesystem isolation** keeps the agent to specific directories, so a fooled agent can't modify sensitive files. **Network isolation** keeps it to approved hosts, so it can't leak data or download malware. Without network isolation, a compromised agent could send out your SSH keys; without filesystem isolation, it could escape the sandbox and reach the network anyway. The post reports that, in Anthropic's internal usage, sandboxing reduced permission prompts by 84%, which is the point: a strong boundary lets you ask less.

Claude Code's sandbox docs are precise about what is covered, and the details are where real gaps hide. The sandbox wraps shell commands and the processes they start; Claude's file tools, MCP servers, and hooks run outside it. By default sandboxed commands can write only to the working directory and a temp directory, but can read most of the machine, including credential files such as `~/.ssh`, unless you deny those reads. Network goes through a proxy with an allowlist that starts empty. Environment variables, including secrets, are inherited unless you scrub them. A sandbox is only as good as your knowledge of its edges.

For hosted agents, Claude Managed Agents runs each session in its own container, and its security guide lists the settings in order of importance: where the agent runs, limited networking with only the needed hosts, credentials in vaults, allowlists on web tools, a permission policy on each tool, the smallest tool set, keeping untrusted input away from powerful tools, a budget on each session, and transcript monitoring. The permission policies are a direct analogue of what you've built: `always_allow` runs the tool, `always_ask` pauses the session until your application sends a confirmation, and `auto` lets the server evaluate each call and run it, deny it, or pause for you. Those policies cover tools that Anthropic's servers execute (the built-in toolset and MCP tools); tools your own application executes still need your own gate.
</Listen>

<Callout type="note" title="Choosing where the boundary lives">
For a coding agent on a laptop, use your agent's sandbox (Claude Code's, or a dev container) plus deny rules. For a scheduled agent that touches company systems, prefer a hosted or containerized runtime with egress allowlists and vaulted credentials, so nothing secret lives where the model runs. For any provider (Claude, OpenAI's Agents tooling, Google's ADK, or an open model you host), the questions are the same: who executes the tools, where do credentials live, and what can the network reach? Read each platform's security page before you trust its defaults.
</Callout>

## Audit logs and reversibility

When something goes wrong, you need to answer three questions fast: what did the agent do, why was it allowed, and can we undo it? An **audit log** answers the first two. OWASP's logging cheat sheet recommends logging security-relevant events such as authorization failures and high-risk actions, with enough context (when, where, who, what) to reconstruct them, and it warns against writing secrets and sensitive personal data into logs.

For an agent, write one record per tool call, including the blocked ones: the run and step, the tool and its exact arguments (redacting secrets), the decision (allow, ask, deny), the rule that decided it, whether a human approved and who, whether it executed, and the result or error. Add the model id, prompt version, and token counts so you can connect behavior to configuration. Blocked calls are the most valuable rows: they show what the agent tried to do, which is your early warning that something in its inputs is steering it. The Managed Agents guide suggests going further with an optional offline reviewer that reads every finished transcript on a schedule.

Reversibility is the other half. For each write tool, decide before launch how you would undo it: delete the draft, revert the commit, close the issue, post a correction. If the honest answer is "we can't," that tool belongs behind a human, or out of the agent entirely. Write the undo procedure into your runbook, and test it once. A log tells you what happened; a tested undo path is what makes an incident small.
</Listen>

<GoDeeper title="Hooks, classifiers, and where each belongs">
Claude Code also lets you run your own code before and after tool calls (hooks); a PreToolUse hook can block a call, which makes it a place to put deterministic policy such as "never edit files under infra/". Auto mode's classifier is a model-layer defense that reviews actions in context; Anthropic's containment post reports it catches roughly 83% of overeager behaviors before they execute, which is useful and also a reminder that a probabilistic check has a miss rate. Managed Agents' `auto` policy makes the same trade on the server. A reasonable design uses rules for what can be stated precisely, a classifier to cut prompt volume on the rest, a human for irreversible actions, and a sandbox underneath all of it.
</GoDeeper>

<Listen>
## What a working engineer does with this

Before you give an agent a new tool, write one line for it in a table: read or write, reversible or not, which credential it uses and what that credential can reach, and what happens if it is called with the worst arguments you can imagine. Then choose the control per row: run freely, run in a sandbox, ask a human, or leave it out. Put the table in your design doc. It is the artifact a security reviewer will ask for, and it is the one you will use in the project to justify your design.
</Listen>
