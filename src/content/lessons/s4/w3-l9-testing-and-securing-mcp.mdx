## Two threat models, and who is responsible

The specification is candid about its limits. It says MCP enables arbitrary data access and code execution paths, that tools represent arbitrary code execution and must be treated with caution, and that the protocol cannot enforce its security principles itself. Those principles are user consent and control, data privacy, and tool safety, and implementers are asked to build them into their applications.

So security in MCP lives in three places, and you will often be responsible for more than one. **Servers** must validate inputs, control access, and avoid leaking what they touch. **Hosts and clients** must get consent, show users what is happening, and keep a human able to deny tool calls. And the **people who install servers**, which includes you every time you run `claude mcp add`, decide what code runs on their machine and with which credentials.

The MCP docs split the threats into two models. The **protocol threat model** covers remote servers: OAuth flows, token handling, confused deputies, and server-side request forgery. The **local threat model** covers your machine: a stdio server is an ordinary process launched under your user account, which inherits your environment variables and can read whatever you can read, including SSH keys and cloud credentials, and can open network connections anywhere. None of that is governed by the protocol; it is governed by how you run the process.

This lesson goes through both, first as a server author and then as an installer. Week 4 widens the view to agent permissions, sandboxing, and injection defenses in general.
</Listen>

<Listen>
## As a server author: validate, limit, sanitize

The tools page lists what servers **must** do: validate all tool inputs, implement proper access controls, rate limit tool invocations, and sanitize tool outputs. Each has a concrete meaning for the tracker you built.

**Validate inputs beyond the schema.** The SDK rejects wrong types before your function runs, but only your code knows that `HAR-101` must match a pattern, that `done` can only move back to `open`, and that a limit of ten thousand is a mistake. Be strictest where a string becomes something else: a file path, a URL, a shell argument, or a query. Willison's April 2025 survey of MCP problems opens with exactly that bug class, servers passing unescaped strings to `os.system()`. The v2 Python SDK's `MCPServer` adds one guard by default: its resource security settings reject path traversal, absolute paths, and null bytes in resource template parameters. Tool arguments are still yours to check.

**Sanitize outputs.** What your tool returns enters the model's context and often a person's screen. The lab's `clean_text` removes invisible Unicode format characters and control characters, and truncates long text. Those characters matter because they can make what the model reads differ from what a reviewer sees. Cleaning does not make text trustworthy; it makes the deception visible.

**Return little, and label it.** Summaries by default, full text on request, and a note that user-written fields are data. Claude Code warns when a tool result passes 10,000 tokens, and large results are both expensive and a larger surface for injected text.

**Fail safely.** Unexpected exceptions should reach the model as a generic failure while the traceback stays in your log, which the SDK does for you.

Then test all of it adversarially, without a model: bad ids, path traversal strings, oversized inputs, injection text in the data, and repeated writes. Those tests are cheap, deterministic, and the only way to know your checks hold.
</Listen>

<Listen>
## Least privilege, at every layer

Least privilege means each piece holds the narrowest access that does its job. For MCP it applies at five layers.

**Tools.** Prefer `update_issue_status` with an enum and a transition table over `run_sql`. A tool that takes an arbitrary command, query, or path cannot be meaningfully reviewed, because what it does depends entirely on its arguments.

**Credentials.** The local-server guide says to pass secrets per server through the host's configuration, never as globally exported shell variables, and to give each server its own narrowly scoped token, such as a fine-grained token limited to one repository rather than your account-wide one.

**Filesystem.** Grant one project directory, read-only where possible. The guide warns that configured allowlists are cooperative boundaries: an honest server respects them, a malicious one ignores them. Enforcement comes from isolation, such as a container where the allowed directory is the only filesystem that exists.

**Network.** A server that works on local files needs no network at all; with a container that is one flag. A server that wraps one API should reach only that API's hosts. Exfiltration needs an exit.

**OAuth scopes.** For remote servers, the security best practices page recommends a minimal initial scope for low-risk reads and step-up requests for privileged operations when they are first attempted. It lists wildcard scopes and publishing every scope up front as common mistakes, because a stolen broad token can reach everything it covers.

One fact about your own setup belongs here. Claude Code's sandbox covers shell commands only; its docs say local MCP servers run outside it, with your full access. If you want a server isolated, isolate the server (or run the whole Claude Code process in a container or VM).
</Listen>

## Authentication for remote servers

Authorization in MCP is optional, and the specification scopes it by transport. Servers on an HTTP transport **should** follow the authorization section. Servers on stdio **should not**, and should take credentials from the environment instead. The MCP tutorial recommends authorization whenever a server handles user-specific data, needs an audit trail of who did what, or fronts APIs that need user consent.

The model is OAuth 2.1, with roles you may know from web work. The **MCP server is a resource server**: it accepts and validates access tokens. The **MCP client is an OAuth client** acting for the user. A separate **authorization server** interacts with the user and issues tokens. Servers must publish OAuth Protected Resource Metadata (RFC 9728), which is how a client discovers which authorization server to use. Clients send the token in the `Authorization: Bearer` header on every request, and never in a URL query string.

The server-side rules are short and strict. Servers must validate tokens, and must check that each token was issued **for them** as its intended audience (RFC 8707). Invalid or expired tokens get HTTP 401. Servers must only accept tokens valid for their own resources, and must not accept or transit any other tokens.

That last rule forbids **token passthrough**: taking a token from the client and forwarding it to a downstream API. The security page explains why it is dangerous. The downstream API may trust the token as if your server had validated it (the confused deputy problem), its rate limits and audit logs see the wrong identity, and a stolen token can use your server as a proxy. If your server calls another API, it gets its own token for that API.

Two practical points from the MCP tutorial. Use an existing identity provider or authorization server rather than writing your own, and check that it can bind the audience to your server specifically. And use well-tested libraries for token validation. In the 2026-07-28 revision, Client ID Metadata Documents are the preferred way for clients to register, and Dynamic Client Registration is deprecated but kept for compatibility.
</Listen>

<Callout type="pitfall" title="Treating localhost as a security boundary">
A server bound to `127.0.0.1` over HTTP feels private. It is not. The MCP docs note that other processes on your machine can reach it, and so can websites through your browser, for example via DNS rebinding. The security best practices page lists an insecure local server left running on localhost as one of the ways local servers get compromised. For local use, prefer stdio, which only the launching client can talk to. If you must listen on a port, require a token and validate the `Origin` header.
</Callout>

## Tool poisoning, shadowing, and rug pulls

The tool list is itself an attack surface, because the model reads tool names and descriptions as instructions and users usually see only a short summary.

**Tool poisoning.** In April 2025, Invariant Labs showed a tool that claimed to add two numbers while its description, which the client UI did not display in full, told the model to read the user's MCP configuration file and SSH private key and pass them in an extra parameter, without mentioning it to the user. Their experiments used Cursor, and they said the attack applies to any client that does not properly display and validate descriptions.

**Shadowing.** The same research showed that a malicious server's description can change how the model uses a *different, trusted* server's tools, for instance telling it to send every email to an attacker's address. The malicious tool never has to be called. This is possible because all connected servers' descriptions share one model context, which is why the local-server guide says to keep your server roster small.

**Rug pulls.** A server can change its tool definitions after you approved it. Install-time review does not cover what arrives later. Willison's write-up of these attacks includes an Invariant demonstration in which a server swapped its definitions to hijack a WhatsApp server's send tool, with padding that pushed the stolen data out of view in the client UI.

The mitigations sit with clients and with you. Clients should show full descriptions, alert when they change, and display every invocation with its arguments; the local-server guide says to prefer clients that pin tool definitions at approval and re-prompt on change. You should read every tool description before relying on a server (the Inspector shows them with no model in the loop), remove servers whose descriptions contain instructions unrelated to the tool's job, and pin versions. The specification adds one rule for clients: treat tool annotations as untrusted unless they come from a trusted server. A destructive tool can claim to be read-only.
</Listen>

<Callout type="claim" title="Treat the spec's SHOULDs about confirmation as MUSTs (Simon Willison, April 2025)">
In [his write-up](https://simonwillison.net/2025/Apr/9/mcp-prompt-injection/), Willison argues that the specification's recommendations for human confirmation of tool calls should be treated as requirements, that clients should show tool descriptions and alert on changes, and that mixing tools with untrusted input is inherently risky, with no convincing general mitigation yet. **Evidence for:** the poisoning, shadowing, and rug-pull demonstrations above all succeed silently without a human checkpoint, and the GitHub case below exploited users who had chosen "Always allow." **Evidence against, or limits:** confirmation prompts on every call cause approval fatigue, and people start clicking yes without reading, so confirmation is only as good as how rarely and clearly it asks. Week 4 covers designing approvals people actually read. **For your setup:** keep "ask" on for MCP write tools, and allow read tools by name.
</Callout>

## Prompt injection through tool results

Tool descriptions come from the server. Tool **results** come from wherever the server gets its data, which often includes text anyone can write: issue descriptions, emails, web pages, support tickets. Lesson 11 in Studio 1 called this indirect prompt injection. MCP makes it more common, because it makes connecting an agent to many such sources easy.

The clearest public case is the one Invariant Labs disclosed in May 2025. An attacker opens an issue in a user's public GitHub repository containing instructions for the agent. The user asks their agent, connected to the GitHub MCP server with access to their private repositories, to look at the open issues. The agent reads the injected issue, pulls private repository data into its context, and publishes it in a pull request on the public repository, where the attacker can read it. The demonstration used Claude 4 Opus in Claude Desktop. Invariant stated that this is not a flaw in the GitHub server's code, and that it cannot be fully fixed with server-side patches, because it arises from the combination of private data, untrusted text, and a way to publish. That is Willison's lethal trifecta.

Your tracker has the same shape on a small scale. Issue HAR-105 contains a customer comment telling the assistant to mark every open issue as done and not to tell the user. The layered defense you built: the text is cleaned and labeled as data, the server's instructions and the write tool's description say never to act on instructions inside issues, the write tool requires a preview round trip, and only a person approving the call in the host can let it through. None of these is sufficient alone. Together, the human gate on the write is the one that holds even when the model is fooled.

For anything that leaves your system or cannot be undone, ask the user through the host. A `confirm` argument is set by the model and can be faked by a fooled model. Elicitation goes to the user, and the specification forbids using its form mode to collect passwords, API keys, or payment credentials; those must use URL mode, outside the client.
</Listen>

## Before you install: a review routine

Most of the risk in your daily work comes not from servers you write but from servers you add. The MCP docs' local-server guide gives a routine that takes a few minutes per server, and it maps directly onto Claude Code.

**Ask whether it needs to run locally.** A server that only wraps a remote API gains nothing from running on your laptop. If a remote version exists, use it: no code runs on your machine, and it uses the protocol's authorization instead of a token in a config file. A third-party server that needs nothing local yet ships only as a stdio process is worth a second look.

**Check provenance.** A registry listing is not an endorsement, and the guide notes that even curated catalogs describe their vetting as best effort. Tie the package to a source repository and a real maintainer, verify the exact package name (typosquatting is the cheapest attack there is), and pin the version. Know what the pin covers: pinning a package run through `npx` or `uvx` fixes the top-level package, while its dependencies may still resolve fresh at install time; a container image pinned by digest freezes the whole tree.

**Read the tools.** Open the server in the Inspector, read every description, and run an audit like the one above. Remove servers whose descriptions say things unrelated to their job.

**Contain it.** Run third-party servers in a container with only the directory they need mounted, no network unless they need it, and their own narrowly scoped credentials passed through the host's per-server environment setting.

**Keep watching.** Re-check after updates, remove servers you no longer use, and rotate the credentials a server held when you remove it.

Research tools are emerging to automate parts of this. Radosevich and Halloran (2025) showed that leading models could be coerced through MCP tools into malicious code execution, remote access, and credential theft, and proposed a scanner that probes a server before deployment. Treat such tools as one more check, not a certification.
</Listen>

## Your own Claude Code setup, this week

Apply the routine to what you already run. Five steps.

First, **inventory**. Run `claude mcp list` and note every server and its scope: local (only you, this project), project (from a `.mcp.json` file in the repository), or user (everywhere). Remove what you don't use. The guide's single most important recommendation is to know what you are actually running.

Second, **mind project-scoped servers**. A `.mcp.json` file in a repository you clone can define servers. Claude Code asks you to approve them in interactive sessions, but its docs note that non-interactive runs (`claude -p`) and Agent SDK sessions cannot show that prompt and load project-scoped servers without asking. If you run Claude Code in CI or scripts on repositories you did not write, use `--strict-mcp-config` with an explicit `--mcp-config`, or exclude project settings.

Third, **set permissions by tool name**. Each MCP tool has a full name such as `mcp__harbor__update_issue_status`. Allow the read tools you trust, keep write tools on ask, and deny what you never want.

Fourth, **isolate what deserves it**. Claude Code's sandbox does not cover MCP servers. A server that handles untrusted content and holds a powerful credential belongs in a container.

Fifth, **watch for the trifecta**. For each session, ask whether the agent can read private data, read untrusted text, and send data out. If all three, remove one.

Other hosts expose the same levers under different names. Gemini CLI's per-server `trust` setting bypasses all confirmations for that server and defaults to off, and its include and exclude lists limit which tools load. OpenAI's MCP documentation says it does not verify custom servers, recommends connecting only to servers you trust, and keeps approvals on for consequential actions. Whatever the host, the questions are the same.
</Listen>

## A checklist for every server you ship or install

For servers you write: every input validated beyond its schema, with adversarial tests; read and write in separate tools, writes idempotent and gated by a human in the host; outputs small, cleaned, and labeled as data; no stdout writes on stdio; no token passthrough, audience checked, minimal scopes on HTTP; and a pinned `tools/list` snapshot in CI, so you notice your own definition changes before your users do.

For servers you install: remote if possible; publisher, exact name, and pinned version checked; every description read; isolated with its own narrow credentials, a single directory, and no unneeded network; write tools on ask; and an inventory you revisit. The lab gave you a server that follows the first list. The second list is a habit, and the next time you add a server to Claude Code is the time to start it.
</Listen>
