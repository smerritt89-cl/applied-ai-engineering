## What fills the window over a long task

Picture the research agent from the lab, twenty steps into a question about a project's launch risks. Its context window now holds:

- the **system prompt** and **tool definitions**, sent on every request;
- the **task**, the user's original message;
- every **assistant turn**: text, thinking blocks, and `tool_use` requests;
- every **tool result**: search hits, document pages, error messages.

The first two are fixed. The last two grow with every step, and tool results usually grow fastest: one document read can be thousands of tokens, and the model rarely needs it again after it has extracted the fact it wanted. The Claude Agent SDK docs make the same observation about Claude Code's own loop: everything accumulates within a session, and large tool outputs consume significant context.

Growth costs you in three ways. Money and latency, because the whole history is resent on every request (prompt caching softens this, since an unchanged prefix is cheaper to read). Hard limits, because even a 1M-token window ends. And quality, which is the subject of the next section, because a model does not use a long context as well as a short one.

**Context engineering** is Anthropic's name for managing all of this. Their September 2025 post defines it as curating and maintaining the whole set of tokens the model sees at each step (instructions, tools, external data, message history), not just writing the first prompt. The guiding principle they give is to find the smallest set of high-signal tokens that makes the desired outcome likely.
</Listen>

## Context rot: why more context is not free

The Anthropic post uses two phrases you will hear often. **Context rot**: as the number of tokens grows, the model's ability to recall information from the context declines. **Attention budget**: every token added draws down a finite amount of attention. Their explanation is architectural (in a transformer, every token attends to every other, so relationships grow with the square of the length) plus a training one (models see fewer very long sequences). They describe the decline as gradual, not a cliff.

The best-known measurement is Chroma's July 2025 report "Context Rot," which tested 18 models from several providers. On deliberately simple tasks, performance fell as input length grew. Distractors (text similar to the answer but wrong) made it worse, and so did lower similarity between the question and the answer text. On a long-conversation memory benchmark, models did much better with a focused prompt of a few hundred relevant tokens than with the full history of about 113,000 tokens. Earlier, the 2023 "Lost in the Middle" paper (Liu and colleagues) found that models used information at the start and end of a long context more reliably than information in the middle.

Read the evidence carefully. Chroma is a vector database company, the report is not peer reviewed, and the tasks are synthetic. Models change, and some newer ones handle long inputs better than the ones tested. But the direction is consistent across independent studies and with Anthropic's own guidance, and it predicts what you will see in agent traces: an agent that has read thirty documents starts missing a fact it read in the fifth. The practical rule is not "keep contexts tiny." It is "keep contexts relevant," and measure on your own tasks.
</Listen>

## Up front or just in time

There are two ways to get information into the context. **Up front**: retrieve or paste everything that might be relevant before the model starts, the classic RAG pattern from Studio 2. **Just in time**: give the agent lightweight references (file paths, document ids, queries) and tools to load content when it decides it needs it.

Anthropic's context engineering post argues that agents increasingly benefit from just-in-time retrieval, because the agent can follow the trail, use metadata such as file names and folder structure as clues, and keep only what matters. Their Agent SDK post recommends starting with agentic search (letting the agent use tools like grep over files) and adding semantic search only when you need the speed or the variety of queries it handles. The trade-off is real: runtime exploration is slower, and it only works with good tools. An agent with a bad search tool wastes its budget opening the wrong documents.

Most real systems are **hybrid**. Claude Code is the standard example in the post: it loads `CLAUDE.md` files into context at the start, then uses glob and grep to find everything else as it works. You can apply the same split to your own agents. Put in up front the small, stable, always-relevant material (the task, the rules, a map of what exists). Leave the large, variable material (document bodies, logs, query results) behind tools that return small, paginated results.

The post's general advice fits here too: do the simplest thing that works. If your corpus is twenty pages and fits comfortably, paste it in and skip the tools.
</Listen>

## Inside one session: clearing and compaction

When a single long session outgrows its useful window, you have two server-side tools on the Claude API, both in beta.

**Tool-result clearing** (context editing, beta header `context-management-2025-06-27`, strategy `clear_tool_uses_20250919`). Once the input passes a trigger (by default 100,000 input tokens), the API clears the oldest tool results, keeps the most recent few (by default 3 tool uses), and replaces each cleared result with placeholder text so the model knows something was removed. You can exclude tools whose results must stay, optionally clear the tool inputs too, and set `clear_at_least` so that clearing happens only when it frees enough tokens to justify breaking the prompt cache. The response reports what was cleared in `context_management.applied_edits`. Anthropic's context engineering post calls tool-result clearing one of the safest, lightest-touch forms of compaction: once a result is deep in the history, the agent rarely needs to see it raw again.

**Compaction** replaces older turns with a summary that Claude writes on the server. The compaction docs now describe three ways to do it: compaction on demand (you request a summary and swap it in), compaction at a token threshold (the API does it inside an ordinary request), and your own summarizer on the client. Each has its own page and beta header, so read the overview before you choose.

The two are complementary. Clearing is mechanical and loses only content the agent can fetch again. Compaction can preserve decisions and open questions in prose, but a summary can drop the one detail a later step needs. Anthropic's advice for writing a compaction prompt is to maximize recall first, then trim for precision.

Both cost you the prompt cache at the point of the edit, so they are worth doing in large steps, not a few tokens at a time.
</Listen>

<Callout type="pitfall" title="Editing old tool results on the client breaks preserved thinking">
On current Claude models (including `claude-opus-5-5`, `claude-sonnet-5-5`, and `claude-haiku-5-5`), each thinking block you send back is bound to everything that came before it: the system prompt, the tool list, and every earlier message. The preserved thinking docs list clearing or shortening an earlier `tool_result` on the client as an edit that invalidates every later thinking block. On accounts created on or after August 31, 2026, that request fails with a 400; on some older accounts the invalid blocks are dropped or passed through, depending on the model.

So the obvious client-side trick, "shrink old tool results before each request," is the wrong default for Claude. Prefer, in order: **shorten results when you first create them** (pagination, snippets, size caps); **server-side context editing or compaction**, which the check treats as no edit because it compares what you sent; and, only if you must trim on the client, **strip the thinking blocks** at the same time, accepting the loss of that reasoning. The exercise below builds the client-side mechanism anyway, because you need to understand it, it is how you manage context with providers and open models that lack these features, and the lab pairs it with thinking-block stripping.
</Callout>

## Across sessions: memory files and notes

Clearing and compaction manage one session. Some agents need state that survives the end of a session, a crash, or a context reset. The general pattern Anthropic calls **structured note-taking**: the agent writes notes to storage outside the context window and reads them back later. The context engineering post gives examples from to-do lists to a `NOTES.md` file, and describes Claude playing Pokémon while keeping notes across thousands of game steps, which let it resume after context resets.

Claude's **memory tool** (`memory_20250818`) packages this pattern. It is client-side: Claude requests file operations (view, create, str_replace, insert, delete, rename) under a `/memories` path, and your code performs them against storage you control. When the tool is present, the API adds an instruction telling Claude to check its memory directory before starting and to record progress as it goes, assuming its context might be reset at any moment. The docs put the security burden on you: validate every path so `/memories/../../secrets.env` cannot escape the directory, cap file sizes, keep secrets out, and expire stale files. Context editing pairs with it: as the context nears the clearing threshold, Claude is warned to save what matters to memory before old results are cleared.

You don't need the memory tool to use the idea. Anthropic's post on harnesses for long-running agents used ordinary files: a JSON feature list (they chose JSON because the model was less likely to rewrite it inappropriately than Markdown), a progress log each session appends to, and git commits that let a later session see what changed and revert bad work. Each new session starts by reading the log and running a basic end-to-end check before touching anything.

The checks-and-balances point: memory is model-written text that a later run will trust. Treat it like any other model output. Keep it small and structured, review it now and then, and never let it become the only record of something that matters.
</Listen>

## Subagents: isolation, not savings

A **subagent** is a separate agent loop with its own fresh context window. The lead agent hands it a task ("find every open risk in the vendor documents"), the subagent spends as many tokens as it needs searching and reading, and it returns a condensed result. Anthropic's context engineering post describes subagents that may use tens of thousands of tokens exploring and return summaries of about 1,000 to 2,000 tokens. The lead's context grows by the summary, not by the exploration.

Two cautions from Anthropic's multi-agent research post keep this honest. First, cost: they report agents using about four times the tokens of a chat interaction and multi-agent systems about fifteen times, and they say multi-agent setups pay off mainly on valuable tasks with lots of parallelizable, separable work. Second, fit: tasks where every agent needs shared context, or with many dependencies between subtasks, are poor fits, and they name most coding tasks as examples. The same post suggests that subagents write large outputs to a file system and pass back lightweight references, so the lead does not have to copy them through its context.

For model selection, subagents are where cheaper models and lower effort often fit: reading-heavy, well-scoped subtasks can run on a smaller model while the lead stays on the strongest one. Measure it on your tasks before assuming it helps, and remember that a subagent's summary is model output the lead will trust. If the summary is the evidence for a decision, ask the subagent to include the source ids it relied on, and spot-check them.
</Listen>

## How Claude Code does all of this

You have used Claude Code for a year, so here is the same machinery in the tool you know.

**CLAUDE.md is the up-front half.** Claude Code loads `CLAUDE.md` files (project, user, and organization scopes) at the start of every session, in full, on every request, where prompt caching keeps the repeat cost down. The docs suggest keeping each file under 200 lines, because longer files cost context and reduce adherence, and moving instructions that apply to only part of a codebase into path-scoped rules under `.claude/rules/`, which load only when Claude works on matching files. `@path` imports help organize a file but do not reduce its cost, because imported files load with it. **Auto memory** is the note-taking half: Claude writes its own `MEMORY.md`, and the first 200 lines or 25KB load each session.

**Glob, grep, and reads are the just-in-time half.** That is why Claude Code can work in a large repository without loading it.

**Compaction happens automatically** near the limit, and you can trigger it with `/compact`. The Agent SDK docs warn that compaction can lose specific instructions from early in a conversation, and recommend putting persistent rules in CLAUDE.md, which is re-injected, rather than in a first message. You can also add a section to CLAUDE.md telling the compactor what to preserve.

**Subagents are the isolation half.** Built-in ones such as Explore (read-only search) and Plan run in their own context windows and return a summary; you can define your own in `.claude/agents/` with a description, an allowed tool list, and a model. A subagent starts fresh and does not see your conversation, so the task you give it must stand on its own.

Practical habits that follow: keep CLAUDE.md short and about rules, not history; send broad searches to a subagent; and start a fresh session for an unrelated task rather than dragging an old context along.
</Listen>

<Callout type="claim" title="Context engineering as the successor to prompt engineering (Anthropic, September 2025)">
**Claim.** Anthropic's [context engineering post](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) presents context engineering as the natural progression of prompt engineering: as agents run longer, the job shifts from writing one good prompt to curating the whole, changing context at every step.

**Evidence for.** The mechanisms are concrete and measurable: the context-rot studies above show that irrelevant tokens degrade results, and Anthropic's own products (Claude Code, the Agent SDK, Managed Agents) ship compaction, clearing, memory, and subagents as core features. In your traces you can see the effect directly when an agent misses a fact it read many steps earlier.

**Evidence against, or limits.** The post is guidance from a model vendor, not a controlled study, and it reports few numbers. "Prompt engineering" never meant only the first prompt; much of this is good software practice (caching, pagination, logs) under a new name. And the post itself predicts that smarter models will need less prescriptive engineering, so specific techniques may age quickly. **For you:** treat each technique as a hypothesis and keep the ones your evals show help.
</Callout>

<GoDeeper title="Choosing between the techniques, and testing that context survives">
Anthropic's post offers a rough mapping: compaction for tasks with lots of back-and-forth conversation, note-taking for iterative work with clear milestones, and multi-agent setups for complex research where parallel exploration pays off. Long-running agents often use all of them.

Whatever you choose, test it the way Studio 3 taught. Take a few real long transcripts, plant or identify facts that a late step needs (an owner's name from step 3, a constraint from the first message), apply your clearing or compaction, and check whether the agent still gets them right. Run the same check after changing your summarization prompt. This is a needle-in-a-haystack test on your own data, which is far more informative than a published benchmark for your use case. Also log what you cleared and when (the API reports `applied_edits`), so that when an answer goes wrong you can see whether the evidence was still in context.
</GoDeeper>
