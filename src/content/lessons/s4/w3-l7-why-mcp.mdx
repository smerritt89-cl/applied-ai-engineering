## The integration problem

In Studio 1 you gave a model tools by writing function definitions into your own application. That works well for one application. Now picture a team that uses four AI applications (a chat assistant, a coding agent, an IDE plugin, an internal bot) and wants each to reach six systems (the issue tracker, the wiki, the CRM, the data warehouse, the calendar, the file share). If every application writes its own connector to every system, that is 4 times 6, or 24 integrations, each with its own auth handling, bugs, and maintenance. Add a seventh system and you write four more.

This is the **N-by-M problem**, and it is what Anthropic named when it introduced the Model Context Protocol in November 2024: every new data source needed its own custom implementation, so connected systems were hard to scale. A shared protocol turns the product into a sum. Each application implements the client side once, each system implements a server once, and any pair can talk: 4 plus 6, or 10 pieces of work.

The specification says it took inspiration from the Language Server Protocol, which did the same thing for programming-language support across editors. The MCP docs use a hardware analogy, a USB-C port for AI applications.

Hold the arithmetic loosely. A protocol makes connections possible, not good. Servers still vary in quality, hosts support different subsets of the protocol, and models differ in how well they use tools. MCP removes duplicated plumbing; it does not remove the need to test each combination you depend on.
</Listen>

## Hosts, clients, and servers

MCP has three roles, and the names are precise.

The **host** is the AI application the user works in: Claude Code, Claude Desktop, an IDE. It owns the conversation and the model calls. It creates and manages connections, enforces security policies and consent, and decides what context reaches the model.

A **client** is a connector inside the host. Each client talks to exactly one server, so a host connected to five servers runs five clients. That one-to-one rule is a security boundary: the host, not the servers, decides what flows between them.

A **server** is a program that exposes capabilities: tools to call, resources to read, prompts to offer. It can be a local process on your machine or a remote service.

The specification's design principles are worth knowing because they explain the shape of everything else. Servers should be extremely easy to build, with the host absorbing orchestration complexity. Servers should be composable, each focused on one job. And servers should not be able to read the whole conversation, nor see into other servers: the full history stays with the host, and each server receives only what it needs. When you hear "MCP gave the agent access to X," the precise version is "the host connected a client to a server that exposes X, and the model can ask the host to call it."

Messages are JSON-RPC 2.0: requests with a method name and parameters, responses with a result or an error.
</Listen>

## Three server primitives, three different deciders

Servers offer three kinds of capability. The MCP docs organize them by **who controls them**, and that is the most useful way to remember them.

**Tools** are model-controlled. They are functions with a name, a description, and a JSON Schema for inputs, discovered with `tools/list` and invoked with `tools/call`. The model decides when to call one, based on the conversation. Tools can read or write: search flights, send a message, create a calendar event. Because a model can fire a tool without the user asking, the tools page says there should always be a human able to deny tool invocations, with clear indicators when tools run and confirmation prompts for operations.

**Resources** are application-driven. They are data identified by URIs, such as `file:///reports/q3.md` or `tracker://summary`, and a server can publish URI templates for families of resources. The host decides how to use them: a picker the user browses, search, or automatic inclusion. Resources are context, not actions.

**Prompts** are user-controlled. They are reusable templates with arguments that the user picks explicitly, typically as slash commands. The server writes the template; the user decides when to use it. A good prompt packages a workflow ("triage this issue using these tools") so users don't have to rediscover it.

Two details matter in practice. First, many hosts support tools far better than resources or prompts, so check what your target host actually surfaces before designing around a primitive. Second, the control model tells you where risk lives. A resource the user attaches is the user's choice. A tool call is the model's choice, so tools are where your validation and approval effort goes.
</Listen>

## Client features: what a server can ask of the host

The relationship also runs the other way. In the current revision, a server that needs something from the user or the host while handling a request can ask for it.

**Elicitation** is the active one. A server asks the client to collect information from the user. **Form mode** sends a message and a flat JSON Schema, and the client renders a form, letting the user review, edit, decline, or cancel. **URL mode** sends the user to a web page for interactions that must not pass through the client, such as signing in to a third-party service or making a payment. The specification is strict here: servers must not use form mode to request passwords, API keys, access tokens, or payment credentials, and must use URL mode for those. Elicitation is how a well-built server gets a real human decision, which you will use in lesson 9.

**Sampling** let a server ask the host's model for a completion, so the server could use an LLM without its own API key. **Roots** let a client tell a server which directories are in scope (informational guidance, not access control). Both are **deprecated** as of 2026-07-28. They keep working for at least twelve months, but new implementations should not adopt them. The suggested migrations are telling: call an LLM provider's API directly instead of sampling, and pass directories through tool parameters, resource URIs, or server configuration instead of roots. You will still meet both in existing servers and older tutorials.
</Listen>

## What changed in 2026-07-28: MCP became stateless

The revision current on this lesson's review date is **2026-07-28**, and it changed the protocol's foundations. If you learned MCP from material written in 2025, three changes matter.

**No more handshake.** Earlier revisions opened every connection with an `initialize` exchange that fixed the protocol version and capabilities for the session. Now every request carries its protocol version and the client's capabilities in its `_meta` field, under keys such as `io.modelcontextprotocol/protocolVersion`. A server accepts or rejects each request on its own; an unsupported version gets an error listing the versions it does support. Servers must also implement `server/discover`, which a client may call first to learn versions and capabilities up front.

**No server-initiated requests.** Earlier servers could send requests to the client in the middle of a call (to elicit, sample, or list roots). Now a server that needs input returns a result with `resultType` set to `input_required`, listing what it needs. The client gathers the answers and retries the original request with them attached. The changelog calls this the multi round-trip request pattern. Every result now carries a `resultType`, normally `complete`.

**No protocol sessions on HTTP.** The `Mcp-Session-Id` header is gone; servers that need state across calls mint explicit handles and pass them as ordinary tool arguments.

You rarely write this plumbing yourself. The official Python SDK's v2 release (July 2026) supports the new revision and still serves 2025-era clients from the same server object. But you will read logs, debug with the Inspector, and evaluate third-party servers, and knowing which era you are looking at saves confusion.
</Listen>

## Two transports

A transport defines how messages travel; the message meanings are identical on both standard transports.

**stdio.** The host launches the server as a child process and exchanges newline-delimited JSON-RPC messages over its standard input and output. Nothing listens on a port, and the server runs with your user account's privileges on your machine. One rule follows directly: **a stdio server must never write anything else to stdout**, because stdout is the protocol channel. A stray `print()` corrupts the stream and the host drops the connection. Log to stderr. For credentials, the authorization section says stdio servers should not use the OAuth flow and should take credentials from the environment instead.

**Streamable HTTP.** Each message is an HTTP POST to a single MCP endpoint, and the reply arrives as a JSON object or as a stream of server-sent events scoped to that request. This is the transport for remote and shared servers. It is where the specification's OAuth 2.1-based authorization applies, which lesson 9 covers. The older HTTP+SSE transport is deprecated; Claude Code's docs, for example, recommend HTTP and fall back to SSE only for servers that need it.

The choice is usually clear from what the server needs. Reading your project files or driving a local tool means stdio. Wrapping a shared internal service that many people use with their own permissions means Streamable HTTP, deployed once and patched in one place.
</Listen>

<Callout type="pitfall" title="Following a 2025 tutorial as if it were current">
MCP moved fast. Material from 2025, including good material, shows an `initialize` handshake, session ids, server-initiated sampling requests, the HTTP+SSE transport, and a Python class called `FastMCP`. On the review date, the current revision is stateless, sampling and roots are deprecated, and the Python SDK's v2 class is `MCPServer`. Before you copy a pattern, check the date on the page and the protocol revision it targets, then check the current specification's changelog. The same habit applies to anything AI-related that is less than two years old: date your sources.
</Callout>

## Who speaks MCP

The protocol's value depends on adoption, so check it against official pages rather than announcements.

**Claude Desktop** connects to local stdio servers listed in a `claude_desktop_config.json` file; the MCP site's server tutorial walks through it. **Claude Code** adds servers with `claude mcp add`, over HTTP (recommended for remote servers) or stdio, at three scopes: local (just you, this project), project (shared with your team through a `.mcp.json` file in the repository, which Claude Code asks you to approve before use in interactive sessions), and user (all your projects). Claude's apps also connect to remote MCP servers as connectors. Outside Anthropic, OpenAI documents MCP servers for ChatGPT and for its Responses API, where an MCP tool takes an allowed-tools list and an approval setting. Google's Gemini CLI reads MCP servers from its settings file and supports stdio and Streamable HTTP. VS Code and Cursor configure servers in project files. The MCP introduction lists more.

For model selection, this is the practical consequence: **one server can serve hosts backed by different models**. That makes MCP a fair way to compare models on your real tools. Connect the same server to two hosts, run the same tasks, and read the transcripts. Tool-use quality differs between models and versions, and the protocol guarantees only that the calls arrive well formed.

When is MCP the wrong choice? If one application you own calls a tool only it needs, a plain function tool from Studio 1 is simpler: no extra process, no protocol layer, nothing to install. Reach for MCP when several hosts need the same capability, when you want an off-the-shelf host like Claude Code to use your internal system, or when a team should share one maintained integration.
</Listen>
