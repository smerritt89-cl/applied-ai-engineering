## You already know most of this

Studio 3 gave you the machinery: error analysis before metrics, test sets with provenance, code graders and calibrated judges, intervals instead of anecdotes, and regression gates in CI. Lesson 11 of that studio introduced agent-specific ideas: grading the **end state** rather than the agent's claims, **trajectory checks** for policy, and **pass^k** from repeated trials. This lesson does not repeat those. It turns them into an eval you can build for the agent in this studio's project, and adds three things that matter most once an agent has tools: environments, safety gates, and cost.

Start with shared vocabulary. Anthropic's agent-evals guide defines a **task** as one test with defined inputs and success criteria, a **trial** as one attempt at it, a **grader** as logic that scores some aspect of a trial (a task can have several), a **transcript** as the full record of a trial (for the Claude API, the complete messages array), and the **outcome** as the final state of the environment. Its example makes the distinction stick: a booking agent may say the flight is booked, but the outcome is whether a reservation exists in the database.

The guide also offers reassurance that matters for a PM planning the work: teams often delay agent evals because they think they need hundreds of tasks, and it suggests 20 to 50 simple tasks drawn from real failures is a strong start, because early changes have large effects that small samples can detect.
</Listen>

<Listen>
## The environment is part of the test

A chat eval sends text and grades text. An agent eval has to give the agent a world to act in: a tracker with issues, a channel to post to, a docs site to fetch. That world must be **fake, resettable, and inspectable.** Fake, so a test run never emails a real customer. Resettable, so every trial starts identical. Inspectable, so a grader can read the final state directly.

Anthropic's guide is specific about isolation: each trial should start from a clean environment, because shared state (leftover files, cached data, exhausted resources) causes correlated failures, and can also inflate scores. It reports an internal case where Claude gained an unfair advantage by reading the git history of previous trials. Both effects break the assumption behind pass^k, that trials are independent tries.

The lab you just built has the right shape: an `Environment` object built fresh from a fixture file, with an `effects` list recording every side effect. For the project, build the same thing for your issue tracker. A fixture is a JSON file of issues, comments, and labels; the fake MCP server or tool layer reads from it; writes go to an in-memory outbox. When you later point the agent at the real GitHub API, the eval keeps running on fixtures, which makes it fast, free of rate limits, and deterministic in everything except the model.

Think about **what the environment must make possible**, too. If a scenario tests whether the agent handles a rate-limit error, the fake must be able to return one. If it tests pagination, the fixture needs more issues than one page holds. Scenarios are designed in the environment as much as in the prompt.
</Listen>

## Three graders for one task

For most agent tasks, use three kinds of grader together, because each misses something the others catch.

**End-state checks** (code) read the outcome. Did exactly one post land in `#proj-status`? Does it mention every issue that changed state this week, and no closed issue as open? Were no other effects produced? These are cheap, deterministic, and closest to what users care about.

**Trajectory assertions** (code over the transcript) check rules about the path that matter regardless of outcome. tau-bench's authors note that a correct final database can hide a policy violation, such as acting without the user's confirmation. For your agent: no write tool executed without an approval record; no outbound call after private data entered the context unless approved; at most N tool calls; no tool called with arguments that failed validation more than twice. Studio 3's exercise built this kind of check; reuse it.

**Output quality** (a model-based grader, or a person) judges what code cannot: is the status report accurate, clear, appropriately prioritized for a stakeholder? Use a rubric with binary criteria, and calibrate the judge against your own labels exactly as in Studio 3, lessons 5 and 6, before you trust its numbers.

Then decide how to combine them. Anthropic's guide lists weighted scores, binary (every grader must pass), or a hybrid. For agents, a hybrid works well: **safety and policy assertions are hard requirements**, end-state checks define success, and quality scores are reported alongside.

Finally, grade the grader. Zhu and colleagues' 2025 paper on rigorous agentic benchmarks found task-setup and reward-design flaws in well-known benchmarks, including one that counted empty responses as successful, and estimated that such issues can misstate performance by up to 100% in relative terms. Your eval can have the same bugs. Include a scenario where doing nothing must fail, and one where a deliberately wrong report must fail.
</Listen>

<Callout type="pitfall" title="Averaging safety into success">
A leak, an unapproved write, or a post to the wrong channel is not a 1% dent in a success rate; it is the event your controls exist to prevent. Report safety as a count of violations with the scenario ids, gate releases on zero, and read every violating transcript. A single leak in one trial of one injection scenario is a release blocker, even if the average looks excellent.
</Callout>

## Cost, steps, and reliability are results, not footnotes

Kapoor and colleagues' "AI Agents That Matter" (2024) argued that agent benchmarks focused narrowly on accuracy, which produced needlessly complex and costly agents and even mistaken conclusions about what caused accuracy gains. Their recommendation is to treat cost and accuracy jointly. For your eval, record per trial: input and output tokens, dollar cost at the prices on the date you ran it, wall-clock time, number of model calls, and number of tool calls.

Then report four numbers per configuration:

- **Success rate** (pass@1 across trials), with an interval, as in Studio 3.
- **pass^k**, the chance that k independent trials all succeed, computed with tau-bench's estimator. Anthropic's guide gives the intuition: 75% per trial means about 42% for three in a row. A weekly report that is right three weeks out of four is not a reliable agent.
- **Cost per successful task**: total cost divided by successes. When failures are retried, the expected cost is the cost per run divided by the success rate, so a cheap, unreliable agent can still win, or lose badly.
- **Steps and cost distribution**: median and a high percentile (p90), because runaway loops create long tails. A step budget and, on hosted runtimes, a session budget (Managed Agents supports a spending cap per session) turn the tail into a bounded failure.

One more distinction from Anthropic's guide shapes how you use the suite over time. **Capability evals** ask what the agent can do well and should start with a low pass rate, giving you a hill to climb. **Regression evals** ask whether it still does what it used to and should pass nearly 100%. As capability scenarios become reliably solved, move them into the regression suite that runs on every change.
</Listen>

## Trajectory review: reading what the agent did

Numbers tell you that something failed. Transcripts tell you why, and whether the agent or the eval is at fault. Anthropic's guide calls reading transcripts a critical skill, and Hamel Husain's evals FAQ suggests a structure for agents: find the first step where things went wrong, and tally those transitions across failed runs in a **transition failure matrix** (last good step against first failed step). Early failures cascade, so the most common early cell is usually the best fix.

For a tool-using agent, read each failed transcript with four questions. **Which tool, and was it the right one?** Many failures are selection errors that a better description or a smaller tool set fixes (Studio 1, lesson 11). **Were the arguments right?** Wrong ids, wrong date ranges, a missing pagination cursor. **How did it handle the result?** Did it notice an error, a truncated list, or an empty page? **Did it stop at the right time?** Agents fail by stopping early (declaring victory after one page of issues) and by not stopping (re-reading the same issue until the step budget runs out).

Keep a short written note per failure, as in Studio 3's error analysis, and let the notes, not your hunches, choose the next change. Then rerun several trials per scenario, because one passing trial after a fix proves little for a non-deterministic agent.
</Listen>

## Building a small agent eval set

For the project you need at least 15 scenarios. Here is a composition that works for a status-report agent, and generalizes to most PM workflow agents. Aim for balance: Anthropic's guide recommends testing both the cases where a behavior should happen and the cases where it should not, because a suite of only "should act" tasks rewards an agent that always acts.

- **Happy paths (3 to 4):** a normal week; a quiet week with no changes; a busy week with many updates.
- **Data edge cases (3 to 4):** more issues than one API page; issues with no assignee or no labels; an issue reopened during the week; text in another language or very long bodies.
- **Tool failures (2 to 3):** a rate-limit or server error from the tracker; a timeout on one call; a malformed result. The right behavior is to retry within limits or report the gap honestly, never to invent data.
- **Should not act (2 to 3):** the reviewer declines the draft; the target channel is not allowed; the tracker is empty or unreachable. Success here means the agent does not post, and says why.
- **Injections (3 or more):** reuse the lab's fixtures: an instruction in an issue body, a hidden comment, a fake admin notice, a link carrying data. Success means the task still completes and no violation occurs.

For each scenario, write the fixture, the task text, the expected end state (what must and must not be in the outbox), the trajectory rules, and a reference report a reviewer would accept. Anthropic's guide gives a good test of task quality: two domain experts should independently reach the same pass or fail verdict. If you can't write the reference, the scenario is not ready.

Run every scenario for several trials (start with 3 to 5), on a fresh environment each time, and keep the transcripts. That set becomes your regression suite: every change to the prompt, tools, model, or guard runs it, and the release rule is written down before you look at the results.
</Listen>

## Choosing models and configurations with the eval

Once the eval exists, model selection stops being a debate. Run the same scenarios, trials, and graders for each candidate configuration: a model choice, an effort setting, a tool design, a guard variant. Plot success rate against cost per successful task. Configurations that are beaten on both axes by another (dominated) can be dropped. The rest form a **frontier**, and choosing among them is a product decision you can now state plainly: "the larger model gets one more weekly report right in twenty, at about twice the cost per report."

Two patterns are worth testing for this kind of agent. **Routing by step:** a small, inexpensive model (for example `claude-haiku-5-5`) turns each issue into a fixed-schema record, and a more capable model (`claude-opus-5-5` or `claude-sonnet-5-5`) writes the report from the records. This is also lesson 11's map-reduce pattern, so it can improve safety and cost at once. **Effort:** on current Claude models, a lower effort setting reduces tokens and tool calls; measure whether quality holds before you choose. Check the pricing page on the day you run the comparison, and record the prices in your results, because they change.

Public agent benchmarks (Studio 3, lesson 11) can help you pick which models to try. They can't tell you which wins on your scenarios, with your tools and your guard. AgentDojo is a useful exception for one property: it measures utility and injection robustness together, so it is a reasonable shortlist signal for agents that read untrusted content, before your own injection suite gives the real answer.
</Listen>

<GoDeeper title="Simulated users and multi-turn tasks">
Your status agent mostly runs without a conversation. Agents that talk to people (support, intake, scheduling) need a simulated user: a second model given a persona and a goal, as in tau-bench. That adds a second source of variance, so pin the user simulator's model and prompt, read some simulated conversations to check they are realistic, and expect to need more trials per task. tau2-bench's finding that agents get worse when the user also acts in the environment is a warning that simulated users can make an eval easier or harder than reality; calibrate against a few real conversations when you can.
</GoDeeper>
