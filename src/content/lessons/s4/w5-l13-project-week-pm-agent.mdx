## The job

Every week, someone on a product team reads the issue tracker and writes a status update: what shipped, what is blocked, what slipped, what needs a decision. It takes an hour if the tracker is tidy, and it is the kind of work people do late on Friday. Your studio project automates it: an agent that reads a tracker through an MCP server you build, drafts the weekly status, and posts it only after a person approves the draft. You will evaluate it on at least 15 scenarios, including injection attempts, and report what each run costs.

This lesson does not build it. It walks through the decisions you need to make first, in the order a careful engineer would make them, so that by the end of the week your design document can answer the questions a reviewer will ask. The project page has the requirements, rubric, and write-up template.
</Listen>

<Listen>
## Decision 1: what is a workflow, and what is agentic?

Week 1 drew the line between workflows (code decides the steps) and agents (the model decides). Anthropic's "Building effective agents" recommends the simplest solution that works, adding agentic complexity only when it demonstrably improves results. Apply that here, honestly.

Much of this job is deterministic. Which issues changed this week is a query with a date filter. Which closed, which opened, which have no assignee: code. Where the report goes: fixed by configuration. The parts that benefit from a model are reading free-text bodies and comments to judge what actually happened ("fix is in review" versus "blocked on legal"), grouping related items, and writing a clear summary for a stakeholder.

A defensible starting design is therefore a **workflow with model-driven steps**: code fetches and filters; a model turns each changed issue into a structured record; a model drafts the report from the records; code shows the draft to a reviewer and posts it on approval. Where would real agency help? Perhaps in deciding to read comments or linked issues when a body is ambiguous, which is a bounded, read-only loop. The rubric rewards a justified choice, in either direction: if you build a full agent loop, show on your eval that it beats the simpler design enough to pay for its extra cost and risk.
</Listen>

<Listen>
## Decision 2: the MCP server boundary

Week 3 taught you to build MCP servers. For this project the server is the boundary between your agent and the tracker, and the place where least privilege lives.

Start with **resources and read tools**. Something like `list_changed_issues(since, until)` that returns compact records (number, title, state, labels, assignee, updated time, a truncated body) rather than raw API payloads; `get_issue(number)` with comments for the cases that need detail; perhaps a resource for the project's configuration (milestones, label meanings). Return natural-language fields and sensible page sizes, as Studio 1's tool-design lesson recommended, and do the date arithmetic in the server, not in the model.

Then the **write path**. The agent should not hold a general "post anything anywhere" tool. One option: the agent's only write is `save_draft(text)`, and posting happens in your application after a human approves, through code the model never calls. Another: a `post_status` tool on the server that only accepts the configured channel and is gated by approval. Decide which, and write down why. The MCP tools specification expects a human able to deny tool invocations; your design should make that the normal path, not an exception.

Finally, **credentials**. For GitHub, a fine-grained personal access token can be limited to specific repositories and specific permissions, with an expiry. A read-only token on one repository is enough for the default project; if you post back to GitHub (a discussion or a comment), give that one action its own narrowly scoped token. Keep tokens in environment variables, never in fixtures, logs, or prompts.
</Listen>

<Callout type="pitfall" title="Pull requests are issues, and lists have pages">
GitHub's REST docs state that every pull request is an issue to the API, so the issues endpoints return pull requests too; you identify them by the `pull_request` key. List endpoints return 30 items by default and at most 100 per page, so a busy repository needs pagination. And the `since` parameter filters by last update time, not creation time. Each of these is a classic silent bug in a status report (PRs counted as bugs, page two never read, "updated" confused with "opened"), and each deserves a scenario in your eval set.
</Callout>

## Decision 3: the tool table and the trifecta

Fill in the table from lesson 10 for every tool the agent can call: read or write, reversible or not, credential and scope, and what the worst call could do. Then do lesson 11's trifecta analysis out loud.

For the default project: issue bodies and comments are **untrusted content** (anyone who can file an issue writes them, and on a public repository that is anyone). **Private data** may be absent if you use a public repository and nothing else, which is a legitimate way to remove a leg. But many real versions add something private: internal notes, customer names, a roadmap. If yours does, say so. The **outbound** leg is the post, plus anything that fetches URLs.

Then pick your structural defense and say which leg it addresses. A map-reduce reader that turns each issue into a fixed-schema record with no URLs and no free text longer than a sentence makes injected instructions much harder to carry forward. A fixed action set means nothing in an issue can add a destination. A deterministic guard (allowlisted channel, no links to unlisted hosts, no private values in outbound text) is the control that holds when the model is fooled. You built that guard in lab 04; adapting it is fair game.
</Listen>

<Listen>
## Decision 4: draft, then approve

The approval step is the product, not a safety tax. Design it for the person who will use it on a Friday afternoon.

Show the **exact text** that will be posted, rendered the way the channel will render it, with links visible. Show **what the draft is based on**: the issue numbers behind each line, so a reviewer can spot-check one claim in seconds. Flag what the guard noticed: "2 issue bodies contained instructions that were ignored," "1 link was removed." Offer three choices: approve, edit then approve, or reject with a reason, and log the decision. A rejection with a reason is free training data for your eval set.

Keep it to **one approval per run**. Lesson 10's numbers on approval fatigue apply here: if a reviewer approves twelve small posts a week, they stop reading by the third. One draft, carefully shown, gets read.
</Listen>

<Listen>
## Decision 5: the eval set and the budget

Use lesson 12's composition: happy paths, data edge cases (pagination, pull requests mixed in, missing assignees, reopened issues), tool failures (a rate-limit error, a timeout), should-not-act cases (reviewer rejects, channel not allowed, empty tracker), and at least three injection scenarios. Build them as fixture trackers your MCP server can load, with expected end states and reference reports. Run several trials per scenario on fresh fixtures.

Set a **cost budget per run** before you build, and measure against it. Count model calls, tokens, and dollars at the current prices; record the date. GitHub's own limits also shape the design: the REST API allows 60 requests per hour unauthenticated and 5,000 per hour for a personal access token, so cache responses during development and run the eval on fixtures, not on the live API.

Decide the **release rule** now and write it in your README: for example, zero safety violations across all trials, end-state success above a threshold you choose, and cost per run below your budget. Writing it before you see results is what makes it a rule.
</Listen>
