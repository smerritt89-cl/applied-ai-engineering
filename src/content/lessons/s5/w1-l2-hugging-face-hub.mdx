## The Hub is git for models

The Hugging Face Hub hosts three kinds of repositories: **models**, **datasets**, and **Spaces** (small hosted apps). Each repo is a git repository with large-file storage, owned by a user or an organization, so every file has a history and every version has a commit hash. That one fact shapes good practice: a model name like `Qwen/Qwen3.8-27B` points at whatever is on the main branch today, while a commit hash points at exactly the files you tested.

A model repo usually contains the weights (one or more `.safetensors` files), `config.json` (architecture, layer counts, context length), tokenizer files including the chat template, and a `README.md` that the Hub renders as the **model card**. Many popular models also have derivative repos uploaded by others: fine-tunes, quantized versions in GGUF or MLX format, and adapters. The Hub links them to their source through the `base_model` field, and you can browse a model's quantizations and fine-tunes from its page.

The Hugging Face LLM Course, which this lesson adapts, covers the Hub in its chapter 4. The short video below from that chapter shows the model page layout, the filters, and where the files and card live.

## Reading a model card

Hugging Face's docs say a model card should describe the model, its intended uses and limitations (including biases and ethical considerations), the training parameters, the datasets used, and the evaluation results. The idea comes from "Model Cards for Model Reporting" by Mitchell and colleagues (2019), which proposed short documents that travel with a model and report how it performs for different groups and conditions. In practice, cards range from thorough to empty. Read five things, in this order.

**Intended use and out-of-scope use.** This tells you what the publisher designed and tested for. A model "intended for research" or "not for medical use" is a warning you need to carry into your own risk review.

**Training data.** Look for languages, the knowledge cutoff, and whether the data is named or only described. If the card says nothing, you can't rule out that your test set was in the training data.

**Evaluations.** Note which benchmarks, which settings (few-shot or zero-shot, with or without reasoning), and who ran them. These are the publisher's claims. They help you shortlist; they don't tell you how the model does on your task.

**License.** Read the metadata field, then the license text itself, as in lesson 1.

**Usage details.** The recommended generation settings, the chat template, the context length, and any special prompt format. Ignoring these is a common cause of "this model is worse than its benchmarks."
</Listen>

## Metadata, licenses, and gated access

The card's top section is YAML metadata between two `---` lines. The fields you will use most are `license` (an identifier such as `apache-2.0` or `mit`), `base_model` (for fine-tunes, adapters, quantizations, and merges), `datasets`, `pipeline_tag` (the task, such as `text-generation`), `library_name`, and `tags`. When the license is not on the Hub's list, the card says `license: other`, puts the text in a LICENSE file, and gives the license a name in `license_name` (and often a link in `license_link`). Because the metadata is machine-readable, you can audit a shortlist of models in code before anyone downloads gigabytes.

Some repos are **gated**. You must be logged in and request access, often by accepting the license and filling in fields such as your name, affiliation, and intended use. The publisher configures approval as automatic or manual; manual approval can take days. The card metadata can customize the gate with `extra_gated_prompt` and `extra_gated_fields`, and a gated repo can set `extra_gated_eu_disallowed: true` to refuse requests from the EU. Meta's Llama and Muse repos and some others are gated; Apache-licensed releases often are not.

Datasets work the same way. The `datasets` library loads a dataset by its Hub name (`load_dataset("org/name")`), can stream large datasets instead of downloading them, and caches what it downloads. A **dataset card** plays the role of a model card; the practice echoes "Datasheets for Datasets" by Gebru and colleagues (2018), which argued every dataset should document its motivation, composition, collection process, and recommended uses. Read a dataset's license and its collection description before you train on it, which you will do in week 2.
</Listen>

## The pipeline, and what it hides

The quickest way to run a Hub model in Python is the transformers `pipeline`. You name a task and a model; it downloads the files, builds the tokenizer and model, and handles pre- and post-processing. For chat models you pass a list of messages with `role` and `content`, the same shape you use with provider APIs, and the pipeline formats them with the model's chat template. The docs recommend `device_map="auto"` so the library places weights on the fastest device available, which on an Apple Silicon Mac is the `mps` backend.

The LLM Course's chapter 2 opens the pipeline up into three steps, and knowing them is what lets you debug. **Tokenize:** the tokenizer turns text into token ids using the model's own vocabulary. **Model:** a forward pass produces logits, one score per vocabulary entry, and generation repeats that loop token by token (Studio 1, lesson 1). **Post-process:** the ids are decoded back into text. Every model family has its own tokenizer, so the same sentence becomes a different number of tokens for different models, which matters for context limits and for any per-token cost comparison.
</Listen>

```python
# Runs locally; first call downloads several GB. Pin the revision you tested.
from transformers import pipeline

chat = [
    {"role": "system", "content": "Classify the ticket as billing, bug, or how-to. Answer with one word."},
    {"role": "user", "content": "I was charged twice for my October invoice."},
]
pipe = pipeline(
    task="text-generation",
    model="HuggingFaceTB/SmolLM2-1.7B-Instruct",
    revision="main",          # replace with the commit hash you evaluated
    dtype="auto",
    device_map="auto",
)
out = pipe(chat, max_new_tokens=8)
print(out[0]["generated_text"][-1]["content"])
```

## Chat templates: the format the model was trained on

A chat model was fine-tuned on conversations rendered in one specific text format, with special tokens marking where each role's turn starts and ends. The **chat template**, stored with the tokenizer, is a small program (written in Jinja) that renders your list of messages into exactly that format. The Transformers docs show two models fine-tuned from the same Mistral base that expect different templates, which is why you never hand-write the format and never reuse one model's template for another.

`tokenizer.apply_chat_template(messages, add_generation_prompt=True)` renders the conversation and appends the tokens that open an assistant turn, so the model writes a reply instead of continuing the user's message. Two details cause most silent bugs. If you render with `tokenize=False` and tokenize the string yourself later, set `add_special_tokens=False`, because the template already contains the beginning-of-sequence token and adding another degrades output; the docs call `tokenize=True` the safer option for this reason. And don't combine `add_generation_prompt` with `continue_final_message`, which do opposite things.

This is the same idea as the system, user, and assistant roles you used with Claude and other APIs in Studio 1. The difference is that a provider applies the format server-side, while with open weights it is your code's job, and getting it wrong does not raise an error. It just makes the model worse.
</Listen>

```python
from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained("HuggingFaceTB/SmolLM2-1.7B-Instruct")
text = tok.apply_chat_template(chat, tokenize=False, add_generation_prompt=True)
print(text)  # inspect the exact string the model will see
ids = tok.apply_chat_template(chat, add_generation_prompt=True)  # tokenize=True is the default
print(len(ids), "tokens")
```

<Callout type="pitfall" title="A model that seems dumb is often a formatting bug">
Before concluding that an open model can't do your task, print the rendered prompt and check it: the right chat template, one beginning-of-sequence token rather than two, a generation prompt at the end, and the generation settings the model card recommends. Then compare against the publisher's hosted demo or an Ollama build of the same model on two or three examples. If they disagree sharply on identical inputs, the problem is in your pipeline, not the weights. Fix it before you spend a week on fine-tuning.
</Callout>

## Safetensors, pickle, and running someone else's code

For years, PyTorch weights were saved with Python's **pickle** format. Hugging Face's security docs explain the problem plainly: unpickling can execute arbitrary code, so loading a malicious `.bin` file can run whatever its author wanted on your machine. The Hub scans pickles and shows their imports, but the real fix was a new format.

**Safetensors** stores tensors and nothing else. The format, documented in the project README, is simple enough to read with the standard library: the first 8 bytes are an unsigned little-endian 64-bit integer giving the length of a JSON header; the header maps each tensor name to its dtype, shape, and byte offsets in the buffer that follows; an optional `__metadata__` entry holds string-to-string metadata. There is no code to execute, files can be memory-mapped, and a loader can read just the header to learn the model's shapes, or load one tensor without the rest. In 2023 Hugging Face, EleutherAI, and Stability AI commissioned an external security audit of the library (performed by Trail of Bits) and said its results let them move toward making safetensors the default format for saved models; today it is the format you will find in nearly every major model repo.

Code execution can still come in through the front door. Models with custom architectures ship their own Python modeling files, and loading them requires `trust_remote_code=True`, which runs that code. The transformers docs advise extra caution and recommend loading such models from a specific commit hash with `revision=`, so the code you reviewed can't change. Make that a general rule: pin revisions in anything you deploy, prefer safetensors files, and treat `trust_remote_code` as a code review request.
</Listen>

## The checklist before a model enters your stack

On a team, put these in a pull request template for any new model. Repo and **commit hash**. License identifier and, for `other`, the license file reviewed. Base model, if it is a derivative, and the base model's license. Gate status and who holds the access. Weight format (safetensors, or GGUF and MLX for local runtimes) and whether `trust_remote_code` is needed. The card's intended use and any out-of-scope uses that touch your product. And the result of your own eval on a labeled sample, next to a frontier API on the same sample, because the card's benchmark table is the publisher's claim and your eval is your evidence. Lesson 3 adds the last line: whether it fits on the hardware you have.
</Listen>
