## What a serving engine does

When you ran a model locally in week 1, one request at a time, generation looked simple: tokenize, run the model, sample, repeat. A production server faces a different problem. Requests arrive at random times, with prompts and outputs of different lengths, and you are paying for the GPU every minute whether it is busy or not. The serving engine's job is to keep the GPU doing useful work while keeping each request's wait acceptable.

Two phases matter. **Prefill** processes the whole prompt in one pass and is compute-heavy: a 600-token prompt becomes a large matrix multiplication. **Decode** then produces output tokens one at a time, and each step must read essentially all of the model's weights from GPU memory to produce a single token per sequence. Decode is limited by memory bandwidth, not arithmetic, which is the key to everything that follows: if each step reads the weights once anyway, producing a token for 32 sequences in that step costs little more than producing one.

During decode the model also keeps a **KV cache**: the attention keys and values for every token so far, so it doesn't recompute them each step. The KV cache grows with sequence length and with the number of sequences in flight, and it competes with the weights for GPU memory. How many requests you can serve at once is often set by how much KV cache fits.

For your extraction task this shape is favorable. Prompts are short once the model is fine-tuned (no long instructions or few-shot examples), and outputs are a small JSON object. Short prompts and short outputs mean many sequences fit in memory at once, which is exactly where batching pays.
</Listen>

## Throughput versus latency, and continuous batching

**Throughput** is how much work the server completes per unit time (tokens per second, or tasks per hour). **Latency** is how long one request waits. Batching trades one for the other. Put more sequences into each decode step and throughput rises, because the weight reads are shared; but each request now waits for a step that does more work, and new requests may queue.

Older servers used static batching: collect a batch, run it until every sequence finishes, then start the next. Short requests sat idle waiting for the longest one. **Continuous batching** schedules at the level of individual decode steps: when a sequence finishes, a waiting request takes its slot at the next step. Every current engine in this lesson does this.

The other big idea came from the vLLM paper (Kwon and colleagues, 2023). Allocating each request's KV cache as one contiguous block wastes memory, because you must reserve space for the longest possible output. **PagedAttention** stores the KV cache in fixed-size blocks, like pages in an operating system's virtual memory, allocated as the sequence grows. Less waste means more sequences in flight. The paper reports two to four times the throughput of the systems it compared against at similar latency, with larger gains for longer sequences.

The practical consequences for your benchmark: throughput is not a property of the model, it is a property of the model, the hardware, the engine, the batch settings, and the traffic. Measure it under the concurrency you expect, and report it with those settings. The cost-per-task number from lesson 10 is only as good as that measurement.
</Listen>

## The serving options, and what each is for

The landscape changes quickly, so here is the state at this lesson's review date, from each project's own documentation.

**vLLM** is the general-purpose GPU server most teams reach for. Its docs list continuous batching, PagedAttention, prefix caching, many quantization formats (FP8, INT8, INT4, GPTQ, AWQ, GGUF, and others), multi-LoRA serving, speculative decoding, and an OpenAI-compatible API server. **SGLang** is a comparable high-performance serving framework, which its project describes as optimized for agentic workloads and large-scale serving. Choose between them by benchmarking your model on your hardware.

**llama.cpp** and its `llama-server` run GGUF models (usually quantized) on CPUs, Apple silicon, and GPUs. The server offers OpenAI-compatible routes, continuous batching with parallel slots, and grammar- or JSON-schema-constrained output. It is the natural choice for laptops, edge devices, and modest single-machine deployments.

**Ollama** wraps local models in a simple tool and API for desktops and developer workflows, with structured outputs and OpenAI-compatible endpoints. It is excellent for development and prototypes; for a shared, high-traffic service, a dedicated engine gives you more control over batching and memory.

**Text Generation Inference (TGI)**, Hugging Face's own server, is now in maintenance mode. Its documentation says it will accept only minor fixes and recommends vLLM, SGLang, llama.cpp, or MLX going forward. You will still find TGI in older tutorials and deployments; don't start new work on it.

**Hugging Face Inference Endpoints** is a managed option: you pick a model and a GPU instance, and the service runs a supported engine (vLLM among them) with autoscaling, billing per minute while the endpoint is running. Cloud providers offer comparable managed services. Managed hosting removes the operations work in exchange for a markup on GPU time and less control.

A reasonable default for the project: develop locally with Ollama or llama.cpp, benchmark and serve with vLLM on a single rented GPU, and say in your write-up what you would change for production traffic.
</Listen>

## Serving your adapter, with schema-constrained output

A LoRA adapter is a small set of extra weights that sits on top of an unchanged base model. You can **merge** it into the base weights and serve the result as an ordinary model, or serve it **unmerged**, which lets one server host the base model plus several adapters and pick one per request. vLLM supports the second: start the server with `--enable-lora`, register each adapter under a name with `--lora-modules`, and clients choose the adapter by sending that name as the model. Set `--max-lora-rank` to the highest rank among your adapters; setting it much higher wastes memory.

The other half is **structured output**. In Studio 1 you saw that constrained decoding (Willard and Louf, 2023) masks invalid tokens at each step so the output must match a grammar or schema. Open-model servers expose this directly, which removes the most common failure of small models: invalid JSON. In vLLM the request field is `structured_outputs`, with options for a JSON schema, a regex, a fixed set of choices, or a grammar; the older `guided_json` family of fields was removed in version 0.12.0. vLLM also accepts the OpenAI-style `response_format` with a JSON schema. llama.cpp's server accepts a JSON schema or a GBNF grammar, and Ollama's `format` field accepts a JSON schema.

Constraining decoding changes what the model can say, so benchmark with the same constraint you will use in production, and keep validating with your Pydantic model on the way back. Constrained output guarantees shape, not truth (Studio 1, lesson 9).
</Listen>

## Quantized serving, and how to check what it cost

Quantization stores weights in fewer bits than the 16 used in training: 8-bit, 4-bit, or formats such as FP8. Smaller weights mean less memory (a cheaper GPU, or more room for KV cache and larger batches) and less data to read per decode step, which often means faster decoding. Weight-only methods such as GPTQ (Frantar and colleagues, 2022) and AWQ (Lin and colleagues, 2023) quantize after training using a small calibration set; GGUF is llama.cpp's file format with its own family of quantization schemes. You met QLoRA in week 3, which trains adapters on a 4-bit base; serving is a separate decision about how the final weights are stored.

Quantization is lossy, and how much it costs depends on the model, the method, the bit width, and your task. Published averages on general benchmarks won't tell you how a 4-bit version handles your house priority convention. So treat a quantized model as a new system: run the frozen benchmark on it and report the paired difference against the 16-bit version, alongside the memory, throughput, and cost gains. If you serve an adapter, check that the quantized base plus adapter matches what you evaluated; an adapter trained on one version of the weights can behave differently on another.

A sensible order for the project: benchmark in 16-bit (or the precision you trained in), then try one quantized variant only if memory or cost requires it, and keep it only if its paired interval stays within the margin you wrote down in advance.
</Listen>

<Callout type="pitfall" title="Benchmarking one system, deploying another">
The quality numbers in your report came from one configuration: a precision, an engine version, a decoding constraint, a prompt format, an adapter. Change any of them on the way to production (switch to a 4-bit file to fit a cheaper GPU, upgrade the engine, merge the adapter, drop the schema constraint for speed) and you are serving a system you haven't measured. Record the full serving configuration with every benchmark run, and re-run the frozen benchmark whenever the configuration changes. It is cheap, and it is the only evidence that the deployed system is the one you approved.
</Callout>

## Self-hosting versus an API: the cost math

Now put prices on it. An API charges per token, so its cost scales linearly with volume: cost per task times tasks. A rented GPU charges per hour, so its monthly cost is flat as long as one GPU can keep up, then steps up by one GPU's cost each time you need another. Hugging Face lists one NVIDIA L4 on AWS at $0.80 per hour and one A100 80GB at $2.50 per hour at the time of writing; an always-on GPU runs about 730 hours a month.

Two facts give you the whole picture. First, the GPU's **best-case cost per task** is its hourly price divided by the tasks it completes per hour at the highest utilization you would plan for (planning for 100 percent leaves no headroom for traffic spikes). If that number is above the API's cost per task, self-hosting never wins on cost, at any volume. Second, if it is below, the **break-even volume** is the monthly GPU cost divided by the API's cost per task: below that volume you are paying for an idle GPU, above it you are saving money.

Run the numbers with real prices and a pattern appears. Against a frontier model with a long few-shot prompt, a small fine-tuned model on one GPU breaks even at a few hundred thousand tasks a month. Against a small, cheap API model, it may never break even. Anthropic lists Claude Haiku 5.5 at $0.10 per million input tokens and $0.50 per million output tokens at the review date, so a 600-token extraction costs a few hundredths of a cent. That is why model selection in this program always compares against the cheapest API model that passes your benchmark, not only against the most capable one.

Cost is rarely the only reason to self-host. Data that can't leave your network, latency targets an API can't meet, independence from a provider's deprecation schedule, or a model no API offers are all legitimate reasons. Name the reason in your write-up, so cost isn't doing work it can't support.
</Listen>

<GoDeeper title="Why decode is memory-bound: a back-of-envelope estimate">
A 4-billion-parameter model in 16-bit precision is about 8 GB of weights. A GPU with roughly 300 GB/s of memory bandwidth (the class of an L4) can read those weights at most about 37 times per second, so a single sequence decodes at best a few dozen tokens per second, however fast the arithmetic units are. Batch 32 sequences and the same weight read yields 32 tokens, so aggregate throughput can approach 32 times higher until the arithmetic or the KV-cache memory runs out. Quantizing to 4 bits cuts the bytes per read by about four, which is why quantized models often decode faster even though dequantizing adds arithmetic. The numbers here are rough on purpose (check your GPU's datasheet), but the shape of the argument is why serving engineers obsess over batch size, KV-cache memory, and bytes per weight.
</GoDeeper>

## What a working engineer would do

For the project, keep serving boring and measured. Pick one engine and pin its version. Serve the base model and your adapter from the same server, so the base-versus-tuned comparison isolates the adapter. Use schema-constrained decoding for both, plus Pydantic validation on the way back. Measure throughput and p50 and p95 latency at two or three concurrency levels with a small load script, and record the hardware, precision, and settings next to the numbers. Then compute cost per 1,000 tasks at the utilization you can honestly expect, and the break-even volume against both the frontier model and the cheapest API model that passes your benchmark. If the cost case doesn't hold, say so: a write-up that concludes "fine-tuning matched quality, but a small API model is cheaper at our volume" is a successful benchmark.
</Listen>
