## Two questions: does it fit, and how fast is it?

Running a model on your own machine comes down to two numbers. **Memory:** the weights, plus a cache that grows with the conversation, plus runtime overhead, must fit in the memory your accelerator can use. On an Apple Silicon Mac that is unified memory shared by CPU and GPU. Apple's spec page, read today, lists the M5 Max MacBook Pro with 36 GB of unified memory on the 32-core GPU version, and 48, 64, or 128 GB on the 40-core GPU version. **Speed:** how long until the first token appears, and how many tokens per second after that.

Those two speed numbers come from two different phases. **Prefill** processes your whole prompt in parallel and is limited mostly by compute; its result is the time to first token. **Decode** produces one token at a time, and the Transformers docs explain why it is slow: each active parameter has to be read from memory for every generated token, so decoding is limited by **memory bandwidth**, and adding compute barely helps. That gives you a handy upper bound. Apple lists 460 GB/s of memory bandwidth for the 32-core GPU M5 Max and 614 GB/s for the 40-core version. A model whose weights are 5 GB can't decode faster than about 614 / 5, roughly 120 tokens per second, on the faster chip, and real numbers come in below that bound.

Both questions lead to the same lever: use fewer bytes per weight. That is quantization.
</Listen>

## Quantization: fewer bits per weight

Models are usually trained and published in 16-bit floating point (FP16 or BF16): 2 bytes per parameter, so an 8B model needs about 16 GB just for weights. **Quantization** stores the weights with fewer bits, typically 8, 6, 5, or 4, and converts them back to higher precision on the fly during computation.

Modern schemes quantize in **blocks**. A group of weights (for example 32, 64, or 256 of them) shares a scale, and sometimes an offset, stored at higher precision, so each block can use its small range of integers well. Those scales cost bits, which is why a "4-bit" format has more than 4 effective bits per weight. llama.cpp's quantize README measures this on Llama 3.1 8B: Q4_K_M comes to 4.89 bits per weight (4.58 GiB), Q5_K_M to 5.70, Q6_K to 6.56, Q8_0 to 8.50, and F16 to 16.0 (14.96 GiB). The "K_M" variants are mixes that keep some sensitive tensors at higher precision. MLX's converter defaults to 4-bit affine quantization with a group size of 64.

What do you give up? The same README says quality loss is usually measured as **perplexity** (how surprised the model is by reference text) or **KL divergence** from the unquantized model's output distribution. The research gives a consistent picture. Dettmers and Zettlemoyer (2022) ran more than 35,000 experiments across model families and found that, for a fixed memory budget, 4-bit precision was almost universally the best trade-off between total model bits and zero-shot accuracy, with small block sizes helping. In other words, a bigger model at 4 bits usually beats a smaller one at 8. Below 4 bits, things degrade: Huang and colleagues (2024) found Llama 3 suffered non-negligible degradation at very low bit widths. Methods such as GPTQ and LLM.int8() (both in the sources) are different ways of quantizing with less damage.

The engineering rule: 4 to 6 bits is the usual starting range. Treat anything lower as an experiment, and measure on your own task, because averages over benchmarks can hide a sharp drop on exactly the thing you need, such as precise extraction or long-context retrieval.
</Listen>

## The KV cache: memory that grows with context

Weights are a fixed cost. The second big consumer grows with every token. During generation, each attention layer stores a **key** and a **value** vector for every token so far, so they are not recomputed at each step; the Transformers docs describe this cache as tensors of shape batch × heads × sequence length × head dimension, per layer. Its size is

KV cache bytes = 2 × layers × KV heads × head dimension × context length × bytes per value × batch size.

The 2 is for keys and values. The PagedAttention paper (Kwon and colleagues, 2023) gives a worked example: for OPT-13B, one token of KV cache is 2 × 5,120 × 40 layers × 2 bytes, about 800 KB, so a 2,048-token sequence needs up to 1.6 GB.

Modern models shrink this with **grouped-query attention** (Ainslie and colleagues, 2023): many query heads share a few key-value heads. Llama 3.1 8B has 32 layers, 8 KV heads, and a head dimension of 128, so in FP16 one token costs 2 × 32 × 8 × 128 × 2 = 131,072 bytes, or 128 KiB. Hugging Face's Llama 3.1 post lists the FP16 cache at about 2 GB for 16,000 tokens and 15.6 GB at 128,000, and notes that for the small model the cache can use as much memory as the weights near the maximum context. At 4-bit weights the cache is the bigger number.

Three things change the estimate. **Sliding-window layers** only keep the last W tokens: Ai2's Olmo 3.1 32B config uses a 4,096-token window on three of every four layers, which caps most of its cache. **KV cache quantization** stores keys and values in 8 or 4 bits; Ollama's FAQ lists the default cache type as f16 with quantized options. And **parallel requests** multiply the cache, which Ollama's FAQ also notes. For mixture-of-experts models, memory depends on the total parameters (every expert must be loaded), while decode speed depends on the active parameters.

<Callout type="pitfall" title="The context you think you have is not the context you get">
Runtimes don't always give you the model's full context window. ## GGUF and llama.cpp

**llama.cpp** is a C and C++ inference engine that runs on CPUs and GPUs with few dependencies; its README calls Apple silicon a first-class citizen, optimized through ARM NEON, Accelerate, and Metal. It introduced **GGUF**, a single-file binary format designed for fast loading and memory mapping. A GGUF file holds the tensors plus key-value metadata: architecture, context length, tokenizer, chat template, and quantization type. That is why one GGUF file is enough to run a model, unlike a transformers repo with separate config and tokenizer files. File names follow a convention that encodes the base name, size, fine-tune, version, and quantization, so `...-8B-Instruct-Q4_K_M.gguf` tells you what you have.

You get GGUF files in two ways: download them from the Hub (many popular models have official or community GGUF repos, linked through `base_model`), or convert a transformers model and quantize it with `llama-quantize`, optionally using an importance matrix computed on sample text to reduce quality loss. `llama-server` serves a model over HTTP with OpenAI-compatible endpoints such as `/v1/chat/completions` and `/v1/models`. Note a recent change: the server README now gives the default address as 127.0.0.1 on port **9931**, changed in October 2026 from the long-standing 8080, so older tutorials will point you at the wrong port. Check the README or pass `--port` yourself.
</Listen>

## Ollama and LM Studio: packaged local inference

**Ollama** packages model download, storage, and serving behind one command. `ollama pull llama3.2:3b` fetches a quantized model from its library (the Llama 3.2 3B tag is about 2 GB), and the background server listens on `localhost:11434`. Its native API has `/api/chat` and `/api/generate` endpoints that stream newline-delimited JSON by default; the last chunk, marked `done: true`, carries the timing fields that the lab uses: `load_duration`, `prompt_eval_count` and `prompt_eval_duration` (prefill), `eval_count` and `eval_duration` (decode), and `total_duration`, all durations in nanoseconds. The API reference gives the decode speed formula directly: `eval_count` divided by `eval_duration`, times 10 to the 9th. Ollama also accepts a JSON schema in the `format` field for structured output, keeps a model loaded for five minutes after use by default (`keep_alive`), and exposes an OpenAI-compatible API under `/v1`.

**LM Studio** is a desktop app for finding, downloading, and chatting with models, with a local server for code. Its docs say it runs llama.cpp (GGUF) models and, on Apple Silicon Macs, MLX models too, and it ships an `lms` command-line tool for loading models and starting the server. Its OpenAI-compatible endpoints include `/v1/chat/completions`, `/v1/responses`, `/v1/embeddings`, and `/v1/models`, and its examples use `http://localhost:1234/v1`. It is a good choice when you or a teammate want a GUI to compare models before writing code.

Choosing between them is mostly about workflow. Ollama is convenient for scripts, servers, and teammates who live in a terminal. LM Studio suits interactive comparison and people who prefer a GUI. llama.cpp directly gives you every knob and the newest features first. All three serve GGUF models, so a quantized file you trust can move between them.
</Listen>

```bash
ollama pull llama3.2:3b
curl -s http://localhost:11434/api/chat -d '{
  "model": "llama3.2:3b",
  "messages": [{"role": "user", "content": "Name one prime number."}],
  "stream": false,
  "options": {"num_ctx": 8192}
}' | python3 -c 'import json,sys; r=json.load(sys.stdin); print(r["message"]["content"], r["eval_count"] / r["eval_duration"] * 1e9, "tok/s")'
```

## MLX on Apple Silicon

**MLX** is Apple's open source array framework for machine learning on Apple silicon. Its README highlights the design choice that matters here: arrays live in **unified memory**, so CPU and GPU operate on the same data without copying it between them. **mlx-lm** builds LLM inference and fine-tuning on top. `pip install mlx-lm` gives you `mlx_lm.generate` and `mlx_lm.chat` on the command line, and a Python API in which `load` returns a model and tokenizer, and `stream_generate` yields responses that report `prompt_tps` (prefill tokens per second), `generation_tps` (decode tokens per second), and `peak_memory` in GB. `mlx_lm.convert` with `-q` quantizes a Hugging Face model, by default to 4 bits with a group size of 64, and the `mlx-community` organization on the Hub hosts many models already converted. `mlx_lm.server` offers an HTTP API modeled on OpenAI's chat API, which its docs say is not recommended for production.

On a Mac, MLX and the GGUF runtimes are both reasonable; which is faster for a given model and quantization is an empirical question that changes with releases, so measure both on your machine. The WWDC25 session below, from Apple's MLX team, walks through running, quantizing, and fine-tuning LLMs with mlx-lm.

## One client, many backends: OpenAI-compatible endpoints

Ollama, llama-server, LM Studio, and mlx-lm's server all expose an OpenAI-style chat completions endpoint. In practice that means you can point the official `openai` Python client at `http://localhost:11434/v1` (Ollama's docs pass a placeholder API key, which it ignores) and reuse code written for a hosted API. That is useful for swapping backends in an eval harness, and for tools that only speak that protocol.

"Compatible" is a promise about the shape of requests, not about behavior. Ollama's docs say it supports a subset of the OpenAI API. Model names differ per server, some parameters are ignored, structured output support varies, and usage numbers come from each server's own tokenizer. So verify three things on any local endpoint: which model actually answered (list `/v1/models`, or `ollama ps`), which quantization it is running (in the model tag or GGUF name), and that a field your code depends on is really honored, by testing it rather than reading about it.
</Listen>

```python
from openai import OpenAI

local = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")  # key is required but ignored
reply = local.chat.completions.create(
    model="llama3.2:3b",
    messages=[{"role": "user", "content": "Reply with the word ready."}],
)
print(reply.model, reply.choices[0].message.content, reply.usage)
```

Discard a warm-up run, report the median and the worst of several runs, report cold-start load time separately, and write down the quantization, context setting, and runtime version next to every number. The lab builds exactly this.

<GoDeeper title="Why decode speed has a bandwidth ceiling">
For a single conversation, generating one token requires reading every active weight from memory once (plus the KV cache so far), while the arithmetic per weight is only a couple of operations. Dividing a chip's memory bandwidth by bytes read per token therefore bounds decode speed from above. For an 8B model at Q4_K_M (about 4.9 GB) on a 614 GB/s M5 Max, the bound is about 125 tokens per second; long contexts lower it further, because the cache is read too. This is also why the Transformers docs point to speculative decoding, where a small draft model proposes several tokens and the large model checks them in one pass, as a way around the bandwidth limit, and why it helps dense models more than mixture-of-experts models. Prefill is different: the whole prompt is processed in parallel, the arithmetic per weight read is large, and the chip's compute becomes the limit. That is why a long prompt costs time to first token, and a long answer costs decode time.
</GoDeeper>

## Choosing what to run, with evidence

A working engineer picks a local model the same way as an API model, with two extra constraints. Start from the hardware: subtract a safety margin for the operating system and other apps from your memory, then use your estimator to list which model sizes and quantizations fit at the context length you need. Shortlist two or three models whose licenses fit (lesson 1) and whose cards suit the task (lesson 2). Try the shortlisted quantizations on a labeled sample: if Q4_K_M matches Q8_0 on your task, take the smaller one; if it doesn't, the extra memory is the price of accuracy. Measure time to first token, decode speed, and seconds per task on warm runs. Finally, run the same sample through a frontier API, so you know exactly what local inference costs you in quality and what it saves you in privacy, money, or latency. That comparison is the core of this studio, and the lab is your first version of it.
