## A score is only as good as the data behind it

In week 4 you will put a number on your fine-tuned model: accuracy on the extraction task, side by side with a frontier model. That number will drive a decision about cost and quality. This lesson is about the ways that number can be wrong before any model runs, because the data that produced it was flawed: duplicates that let the model see test answers in training, related documents split across train and test, labels that are themselves mistakes, or a test set that doesn't look like production.

None of this is new to you. Studio 3 built test sets, kept test cases out of prompts, and put error bars on pass rates. Fine-tuning raises the stakes, because now the same pool of labeled data feeds both training and evaluation, and anything that crosses from one to the other inflates the score. Kapoor and Narayanan (2022) surveyed machine-learning-based science and found leakage errors affecting 329 papers across 17 fields, often producing overly optimistic results. Careful researchers made these mistakes; you will be tempted to make them too.
</Listen>

## Three splits, three jobs

The **training set** is what the model learns from. The **validation set** (also called the dev set) is what you use to make decisions: how many epochs, which learning rate, which checkpoint, whether a data change helped. Gekhman and colleagues' new-knowledge result from lesson 4 depended on it: stopping when validation accuracy peaked avoided most of the harm from training too long. The **test set** is what you report, ideally once per decision you're making.

The reason for separating validation from test is a statistical fact you already know. If you measure ten checkpoints on the same set and pick the best, the best score is biased upward: you selected partly on noise. The more choices you make on a set, the more optimistic its numbers become. The validation set absorbs that bias so the test set doesn't. Hamel Husain and Shreya Shankar's evals FAQ applies the same rule to LLM judges: tune on one split, measure on another.

How big should each be? The test set must be large enough that the differences you care about exceed its margin of error. In Studio 3 you computed that 50 cases at 80 percent give roughly plus or minus 11 points, which can't separate 80 from 85. For fine-tuning, a common pattern is to fix the test set's size from that calculation first, set aside a similar or smaller validation set, and give everything else to training. The lab's 70/15/15 split of 44 documents is far too small for a real benchmark, and saying so out loud is part of the exercise.
</Listen>

## Splitting: random is not enough

A random split assumes every example is independent. Real data rarely is.

**Stratify** when you have categories whose proportions matter. If 10 percent of documents are support tickets, a random split of a small dataset can put almost none of them in the test set. Stratified splitting allocates each category to each split in proportion, so every split has every kind of document. scikit-learn's splitters (StratifiedKFold and relatives) do this for you; the lab implements it by hand so you can see it.

**Group** when examples are related. An email and its reply, three messages from one support thread, ten tickets from one customer, five chunks of one long document: if one lands in training and another in test, the model has effectively seen part of the test answer. Group-aware splitting assigns whole groups to a single split (scikit-learn's GroupKFold and StratifiedGroupKFold). Choose the group by asking what production looks like. If your model will see new customers, group by customer, so the test set measures performance on customers it never saw.

**Split by time** when production is the future. If the model will run on next quarter's documents, train on older data and test on the most recent, because vocabulary, products, and formats drift. A random split hides that drift; a time-based split measures it.

These constraints compete in small datasets, which is why the lab fills each stratum with whole groups until it reaches its target, then moves on. Expect split sizes to be close to the requested fractions, not exact.
</Listen>

## Duplicates and near-duplicates

Duplicates are the most common leak, and they hurt in two places. In training, a repeated example counts several times, overweighting whatever it says. Across splits, a duplicate in both train and test lets the model score by recall. Lee and colleagues (2021) found that standard language-modeling datasets were full of near-duplicates, that train-test overlap affected over 4 percent of the validation sets they examined, and that deduplicated training data made models emit memorized text ten times less often.

Detect duplicates in two passes.

**Exact duplicates**: normalize the text (lowercase, collapse whitespace, strip punctuation if formatting differences don't matter for your task), hash it, and group identical hashes. This catches the same email exported twice.

**Near-duplicates**: break each normalized text into word **shingles** (every run of k consecutive words) and compare sets with **Jaccard similarity**, the size of the intersection over the size of the union. A forwarded ticket with an added header, a meeting note re-posted with one typo fixed, or a templated email with a different customer name will share most of their shingles. Choosing k and the threshold is an empirical step: compute similarities, sort the pairs, and read a sample around your candidate threshold. Templates are the hard case. Two invoices generated from the same template differ only in names and numbers, and whether they count as duplicates depends on what you want the test set to measure: if production is full of that template, you want it in training, but you also want test cases that the model can't solve by having memorized one filled-in copy.

Comparing every pair is quadratic, which is fine for thousands of documents and hopeless for millions. At scale, **MinHash** compresses each shingle set into a short signature whose agreement rate estimates Jaccard similarity, and **locality-sensitive hashing** (LSH) buckets signatures so only likely pairs are compared. The datasketch library documents both.
</Listen>

## The many ways test data leaks

Duplicates and split groups are the obvious leaks. Here is the fuller list to check for when you build a fine-tuning dataset, most of which you've met in earlier studios:

- **Shared source.** Several examples derived from one document (chunks, threads, revisions) landing in different splits.
- **Templates.** Machine-generated documents that differ only in names and numbers.
- **The answer in the input.** A label pasted into the prompt as an example, or an input field that encodes the label (a ticket's "resolution" field, when the task is to predict the resolution). Lesson 5's validator checks the first case.
- **Test cases in prompts and few-shot examples.** Studio 3's rule applies unchanged: examples you put in a prompt come from training data, never from the test set.
- **Synthetic data seeded from test cases.** If you generate training examples by asking a model to vary existing examples, seed it only from the training split, or the variations become near-duplicates of your test set.
- **Repeated test-set use.** Every time you look at test failures and change something, the test set leaks into your decisions. That's the knowledge-check scenario above.
- **Pretraining contamination.** For public benchmarks, the base model may have seen the test data during pretraining. Deng and colleagues (2023) found evidence of this for popular benchmarks, and Zhang and colleagues (2024) built a fresh look-alike of the GSM8K math benchmark and saw some models' accuracy drop by up to 8 percent. Your own labeled test set, built from your own documents, is protected from this by construction, as long as it never gets published.
</Listen>

<Callout type="pitfall" title="The test set that quietly became a training set">
It rarely happens in one step. Someone adds "a few hard test cases" to the training data to fix a failure. Someone else generates synthetic variations of the test failures. A month later the test score is up 8 points and production complaints haven't changed. Protect the test split mechanically: keep it in a separate file with a fingerprint (a hash of its contents) recorded in the dataset manifest, check new training data against it with the near-duplicate finder before every run, and require a second person's review for any change to the test file.
</Callout>

## Label noise: when the gold is wrong

Every labeled dataset contains errors, and test sets are no exception. Northcutt and colleagues (2021) estimated at least 3.3 percent label errors on average across ten widely used test sets in vision, language, and audio, and showed that correcting them could change which model looked better. If two fine-tuned models differ by two points on a test set with three percent bad labels, you don't yet know which is better.

Noise does different damage in each split. In **training**, the model learns the errors: a consistent labeling mistake becomes a consistent model mistake, which is one reason guideline consistency matters more than volume. In **test**, errors cap the accuracy you can measure and blur comparisons.

Practical ways to find and reduce it:

- **Mechanical checks first.** For extraction, the evidence-quote check from Studio 1 and the lab catches labels whose quotes aren't in the document. It's cheap and certain, and in the lab it catches a third of the planted errors on its own.
- **Double labeling on a sample.** Two people label the same examples independently; measure agreement (Studio 3, week 4) and adjudicate disagreements. Disagreement clusters usually point at an ambiguous guideline rule.
- **Model-disagreement review.** Run a strong model over the labeled data and send the examples where it disagrees with the gold label to a person. This finds errors efficiently, but the person decides, not the model: otherwise you are slowly replacing your labels with the model's opinions and then measuring the model against itself.
- **Fix the guideline, then relabel.** When you change a rule, relabel every affected example, in all splits, and record the guideline version in the dataset card.
</Listen>

## A frozen test set that matches production

Pull the threads together into one rule: the test set is a measuring instrument, so build it to match what you'll measure, then stop touching it.

- **Match production.** Sample test documents from the same sources, time period, and mix your deployed model will see. If production is 40 percent chat messages, the test set should be roughly 40 percent chat messages, plus deliberate extra coverage of the rare cases you care about, reported separately so they don't distort the headline number.
- **Label it with the most care.** Every test label gets human review, two reviewers if you can afford it. Model-drafted labels never enter the test set unreviewed.
- **Freeze and version it.** Record a fingerprint of the test file in the manifest. Any change produces a new version with a new fingerprint and a note saying why.
- **Refresh deliberately.** Production drifts and repeated looks bias the score. Periodically build a new test version from fresh production samples, and score current models on both versions so you can tell model changes from test changes. The evals FAQ calls stale gold data out as a common failure.
- **Report with error bars.** State the test-set size and the margin of error (Studio 3, week 3; Miller's paper on error bars for evals), so nobody reads a two-point difference on 200 examples as a result.
</Listen>

<GoDeeper title="Why MinHash estimates Jaccard, and what banding does">
Pick a random permutation of all possible shingles and record, for each document, the first of its shingles in that order. Two documents record the same shingle exactly when the first shingle of their union lies in their intersection, which happens with probability |A intersect B| / |A union B|: the Jaccard similarity. Repeat with n independent hash functions (standing in for permutations) and the fraction of agreements is an unbiased estimate of Jaccard, with variance shrinking like 1/n.

LSH then cuts each n-value signature into b bands of r rows. Two documents become candidates if they agree on every row of at least one band. One band matches with probability s to the power r, so at least one of b bands matches with probability 1 - (1 - s^r)^b. That S-shaped curve rises sharply around a threshold of roughly (1/b) to the power 1/r, which is how datasketch chooses b and r for the threshold you request. Candidates still get an exact Jaccard check, because the curve has tails: some dissimilar pairs become candidates (false positives) and some similar ones don't (false negatives).
</GoDeeper>

## What a working engineer would do

Build the dataset with a script, never by hand in a spreadsheet, so every step is repeatable and reviewable: validate, quarantine, deduplicate, split with groups and strata, check leakage, freeze the test set, write a manifest. Run it in CI when the data changes, the same way Studio 3 gated prompt changes on evals. Read samples at every stage: the pairs near your near-duplicate threshold, the quarantined labels, a random handful of each split. And keep two habits that protect the score: iterate on validation, report on test, and refresh the test set from production on a schedule instead of polishing the old one.

The lab puts all of this together for the action-item task, and its output is in the format next week's training tools accept.
</Listen>
