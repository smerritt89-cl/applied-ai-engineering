## Retrieval can only find what ingestion kept

Week 1 gave you embeddings and similarity search over clean strings. Real knowledge lives in PDFs exported from slide decks, scanned contracts, wiki pages wrapped in navigation menus, spreadsheets, and the same policy saved in four places. **Ingestion** is everything between "a file exists" and "clean text with metadata is ready to chunk": parsing, cleaning, attaching metadata, and removing duplicates.

It deserves a whole lesson because it sets a ceiling on everything after it. If the parser dropped a table, no embedding model will retrieve the number that was in it. If a scanned page came back empty, the document silently does not exist as far as search is concerned. If a navigation menu was kept, every chunk from that site shares the same twenty words of noise, and similarity scores drift toward boilerplate. Teams that debug retrieval quality by swapping embedding models often find the problem was upstream.

Before building any of this, ask whether you need retrieval at all. Anthropic's Contextual Retrieval post makes a point worth repeating: if the whole knowledge base fits in the prompt (it suggests a rough threshold of 200,000 tokens, about 500 pages), you can often skip retrieval and send everything, using prompt caching to keep it affordable. Ingestion still matters in that case, since the model reads whatever your parser produced, but chunking and vector stores may not.

This lesson works through the formats in order of difficulty, then covers the three things you add on the way out: cleaning checks, metadata, and deduplication. The lab at the end of the week builds the whole pipeline on a small fictional corpus.
</Listen>

## Why PDFs are hard

A PDF is a set of instructions for painting a page: put these glyphs at these coordinates in this font. It is not a document with paragraphs and headings. The pypdf documentation puts it plainly: PDF files have no semantic layer, so headings, paragraphs, and tables have to be inferred from positions. That one fact explains most of what goes wrong:

- **Reading order.** Two-column layouts, sidebars, and figure captions can come out interleaved, because the extractor has to guess which block follows which.
- **Whitespace.** Spaces are often positioning adjustments rather than characters, so words get glued together or split apart, and hyphenated line breaks survive as broken words.
- **Tables.** A table is usually just text placed at positions. A naive extractor flattens it into a stream of cells with no rows or columns, and the number "60" loses the label "days" two columns away.
- **Headers and footers.** "Confidential, page 3 of 40" repeats on every page and lands in the middle of sentences that cross page breaks.
- **Scans.** A scanned page is an image. A text-layer parser such as pypdf is not OCR software and returns little or nothing, without raising an error.

pypdf is still the right first tool for digitally born PDFs: it is local, fast, free, and reads the real characters, which is more reliable than OCR when a text layer exists. The point is to know which of these failures your documents trigger, and to check for them.
</Listen>

## The toolbox, from cheap to expensive

Think of four tiers, and route documents to the cheapest tier that handles them well.

**Text-layer parsers** (pypdf and similar) read the embedded characters. Use them for born-digital, single-column documents. Cost is near zero, so run them on everything first and use their output to decide what needs more.

**Layout-aware parsers** run layout models to recover structure. Docling, started at IBM Research Zurich and now hosted by the LF AI and Data Foundation, parses PDF, DOCX, PPTX, XLSX, HTML, images, and more; recovers reading order, table structure, code, and formulas; runs OCR for scanned pages; and exports Markdown or lossless JSON. It is MIT licensed and runs locally, which matters for sensitive documents. Unstructured partitions documents into typed elements (titles, narrative text, tables) with metadata; note that its own docs describe the open-source library as suited to prototyping, with stronger table extraction in its paid API. These tools turn "a stream of characters" into "headings, paragraphs, and tables", which the structure-aware chunking in lesson 5 depends on.

**OCR engines** such as Tesseract turn page images into text. They are local and cheap but struggle with complex layouts, and they introduce character errors (an "l" read as "1") that a text layer would not have.

**Vision-capable models** read the rendered page. Claude's PDF support converts each page to an image and also passes the extracted text, so the model sees both; Gemini and OpenAI document inputs work similarly. They handle charts, handwriting, and messy layouts that defeat rule-based tools, and they can transcribe a page into clean Markdown. They are also the most expensive tier per page, they have request limits, and, like any model output, a transcription can be fluent and wrong.
</Listen>

## Costing the vision tier before you use it

Do the arithmetic before routing a corpus to a model. At the time of writing, Anthropic's PDF docs estimate 1,500 to 3,000 text tokens per page, plus image tokens for each page image, with limits of 600 pages per request (100 when the request's context window is under one million tokens) and no password-protected or encrypted files. Google's docs count each PDF page as 258 tokens and allow up to 1,000 pages or 50 MB per document. OpenAI's file inputs send both extracted text and page images to vision-capable models, with a 50 MB limit per request. These numbers change, so check the pages linked in the sources before you budget.

A worked example: 10,000 pages at roughly 3,000 total tokens per page is 30 million input tokens, before any output. At the review-date list price for Claude Haiku 5.5 ($0.10 per million input tokens for prompts up to 100,000 tokens) that is about three dollars of input; on a frontier model it is tens to hundreds of dollars, and the output (the transcribed Markdown) is billed at the higher output rate. That is often worth paying for the 5 percent of pages a cheap parser mangles, and rarely worth paying for the 95 percent it handles fine.

Model selection here is an evidence question, not a brand question. Take 30 to 50 pages that represent your corpus (include the ugly ones: tables, scans, two-column layouts), run two or three candidates (pypdf, Docling, one or two vision models), and score each page on the things your application needs: are the numbers in the tables right, is the reading order right, did anything get dropped? A half-day of this beats a month of debugging retrieval on bad text.
</Listen>

Here is the shape of a vision-tier call with the Claude Python SDK, transcribing one PDF to Markdown. It follows the PDF support docs: the document block goes before the instruction, and a small model keeps per-page cost down.

```python
import base64
import pathlib

import anthropic

client = anthropic.Anthropic()
pdf_b64 = base64.standard_b64encode(pathlib.Path("q3-review.pdf").read_bytes()).decode("utf-8")

response = client.messages.create(
    model="claude-haiku-5-5",
    max_tokens=16000,
    messages=[{
        "role": "user",
        "content": [
            {"type": "document", "source": {"type": "base64", "media_type": "application/pdf", "data": pdf_b64}},
            {"type": "text", "text": (
                "Transcribe this document into Markdown. Keep every heading, keep tables as Markdown tables, "
                "copy numbers exactly, and drop repeated page headers, footers, and page numbers. "
                "Write [illegible] for anything you cannot read. Output only the Markdown."
            )},
        ],
    }],
)
if response.stop_reason != "end_turn":
    raise RuntimeError(f"transcription incomplete: {response.stop_reason}")
markdown = "".join(block.text for block in response.content if block.type == "text")
```

<Callout type="tip" title="Verify a transcription the way you verified extractions">
A model transcription is model output, so check it like the Studio 1 extractions. When the PDF has a text layer, compare: every number in the transcription should appear in the pypdf text of the same page, and a large gap in character counts means something was dropped or invented. When there is no text layer, spot-check a random sample of pages by eye, prioritizing tables, and keep the page images so a reviewer can compare. Track the "[illegible]" rate per document as a quality signal.
</Callout>

## HTML, Office files, and tables

**HTML** looks easier because the structure is explicit, but web and intranet pages wrap a little content in a lot of chrome: navigation, cookie banners, footers, related-article lists, scripts. Keep the main content, and keep the structure: convert headings to Markdown headings rather than flattening them, because headings become chunk boundaries and context in lesson 5. Libraries such as Trafilatura specialize in extracting the main text from web pages; for an intranet with one template, a few lines of parser code that skip `nav`, `footer`, `script`, and `style` are often enough, which is what the lab does.

**Office files** (DOCX, PPTX, XLSX) are zipped XML with real structure, so layout-aware tools like Docling read them well. Two traps: slide decks put meaning in visual arrangement and speaker notes (decide whether notes are content), and spreadsheets are tables, not prose. A model given a raw CSV dump of a 5,000-row sheet will not retrieve well; a sheet is often better served by a SQL or tool lookup than by embedding.

**Tables** deserve their own rule: never split a table across chunks without its header row. A row like "Unused, no receipt | 60 days | Store credit" is answerable; the same row without the header is a riddle. Common approaches are to convert each table to Markdown and keep it whole if it fits, or to emit one line per row with the header repeated ("Item type: Unused, no receipt. Return window: 60 days. Refund type: Store credit."). Test with real questions about your tables, because which one works better depends on the embedding model.
</Listen>

## Cleaning without losing meaning, and catching silent failures

Cleaning should remove noise and leave the words alone. A safe default set: Unicode normalization (NFKC turns the "fi" ligature that PDF extractors often emit back into "f" and "i"), consistent line endings, removing soft hyphens, collapsing runs of blank lines, and stripping headers, footers, and page numbers that repeat across pages. Be careful with anything more aggressive. Lowercasing, removing punctuation, or "fixing" typos changes what a citation can quote, and the Studio 1 rule still holds: if you will verify quotes against the source later, the stored text has to be the source.

The more important job is detecting failures that raise no error. Run deterministic checks per page and per document at ingest time:

- **Characters per page.** A page with almost no text is probably a scan or an image-only slide. Route it to OCR or the vision tier.
- **Replacement characters.** A high share of U+FFFD (the "unknown character" symbol) means the font encoding defeated the extractor.
- **Zero chunks.** Any document that produces no chunks should be an alert, not a log line.
- **Hidden text.** OWASP's guidance on vector and embedding weaknesses recommends extracting text in ways that expose hidden content and auditing the knowledge base for poisoning. White-on-white text or tiny fonts in an uploaded file can carry instructions that end up in your model's context. Decide whether ingested text may contain instructions (it may) and treat retrieved text as data in your prompts, as Studio 1 taught for tool results.

The exercise below builds the first three checks.

<Callout type="pitfall" title="Boilerplate detection that eats real content">
A line that repeats on most pages is usually a header, but not always. A contract that says "Subject to Section 12" on every page, or a table whose header row repeats across page breaks, would lose meaningful text. Require at least three pages of evidence, compare full lines rather than words, and log what you removed so you can audit it. When in doubt, keep the line: a little noise costs less than missing content.

## Metadata you will want later

Every document, and every chunk cut from it, should carry a metadata record. Capturing it now is cheap; reconstructing it after a million chunks are indexed is not. A record that pays for itself:

- **Source identity.** A stable id, the original location (path, URL, or system record id), and the title. Week 4's citations link here.
- **Location within the source.** Page number for PDFs, heading path for structured documents, and character offsets into the cleaned text. Claude's citations feature, for example, reports page ranges for PDFs and character ranges for plain text, so offsets let you map a citation back to the exact place in the original.
- **Time and version.** Document date or version, plus when you ingested it. Retrieval can then prefer the current policy over last year's, and you can find stale content.
- **Permissions.** The groups or users allowed to read the source, copied from the source system. Lesson 6 makes the store filter on this before ranking. If a document has no permission record, fail closed: make it visible to nobody until someone fixes the record.
- **Provenance.** A content hash, the parser and its version, and the strategy used. When you upgrade a parser, you can find exactly which chunks to rebuild.

A useful test: for every field, name the query, filter, or audit that will use it. Fields nobody uses are clutter; filters without fields are bugs waiting for a deadline.
</Listen>

## Deduplication, and which copy wins

Enterprise corpora are full of copies: the same policy in the wiki and the shared drive, a contract and its signed scan, a deck and its PDF export. Duplicates hurt retrieval directly. If five copies of one paragraph are the most similar chunks to a question, they fill all five top-k slots and crowd out the second source the answer needed. They also make conflicts invisible: two near-identical copies that disagree on one number look like agreement.

Research on training data shows how common this is at scale. Lee and colleagues (2021) found a single 61-word sentence repeated over 60,000 times in the C4 dataset, and reported that models trained on deduplicated data emitted memorized text about ten times less often. Retrieval corpora are smaller, but the same lesson applies: you will not know how much duplication you have until you measure it.

Two levels catch most of it. **Exact duplicates**: hash the cleaned text (SHA-256) and keep one copy per hash. **Near duplicates**: break each document into word **shingles** (overlapping runs of about five words), and compare sets with the Jaccard similarity, the size of the intersection over the size of the union. Pairs above a threshold (0.8 is a reasonable start, then inspect what it catches) are near copies. Comparing every pair is quadratic, so at scale use MinHash with locality-sensitive hashing, which estimates Jaccard similarity from small signatures and finds candidate pairs without comparing everything; the datasketch library implements it.

Then decide, and write down, which copy wins: the newest by date, the one from the system of record, or the one with the most permissive or most restrictive access (careful: merging copies with different permissions can leak). When two near copies disagree on content, consider keeping both and flagging the conflict for an owner rather than silently picking one.
</Listen>

## What a working engineer does on day one

Inventory before you build. List the document types and their counts, open ten of each, and note which ones are scanned, which have tables that matter, and which systems hold their permissions. Route each type to the cheapest parser that passes a small measured sample. Add the silent-failure checks before the first full run, attach the metadata record, deduplicate with a written policy, and keep offsets back into the source. Then, and only then, start chunking, which is the next lesson.
