## What a vector store actually does

Strip away the marketing and a vector store does five jobs. It **stores** vectors alongside an id, the chunk text, and metadata. It **searches**: given a query vector, return the k nearest stored vectors by cosine similarity, dot product, or Euclidean distance. It **filters**: restrict the search to records whose metadata matches a condition (this tenant, these groups, documents after this date). It **updates**: insert, replace, and delete records as documents change. And, for most production systems, it **persists and serves** this reliably, with backups, concurrency, and access control.

You built the first three in week 1 with a list and a loop, and the lab this week adds the rest in about a hundred lines. Every product in this lesson is a faster, more durable, more operable version of that loop. That framing helps you evaluate them: ask how each one does search, filtering, updates, and operations, and which of those your application stresses.

One more distinction does a lot of work. **Exact** (brute-force) search compares the query with every stored vector, so it always returns the true nearest neighbors. **Approximate nearest neighbor** (ANN) search uses an index to look at a small fraction of vectors and return results that are usually, not always, the true nearest neighbors. The dominant ANN index today is HNSW (Hierarchical Navigable Small World graphs, introduced by Malkov and Yashunin in 2016): a layered graph in which a search hops greedily toward the query, coarse layers first, then fine ones. It is fast and accurate, and it costs memory and build time. pgvector's README summarizes the trade-off well: by default it does exact search with perfect recall, and once you add an approximate index you trade some recall for speed, so the same query can return different results than before.
</Listen>

## When a NumPy array is enough

Before choosing a database, do the arithmetic. A float32 vector of dimension d takes 4d bytes. A corpus of n chunks takes 4nd bytes: 100,000 chunks at 1,024 dimensions is about 410 MB, and 10,000 chunks is about 41 MB. Exact search is one matrix-vector product (n times d multiply-adds) followed by a partial sort for the top k (NumPy's `argpartition` does this without sorting everything). On a laptop, that is a few milliseconds for tens of thousands of chunks and still well under a second for a few hundred thousand.

So for an internal tool over a few thousand documents, a nightly batch job, a prototype, or an evaluation harness, a NumPy array plus a JSON or Parquet file of metadata is often the right answer: zero infrastructure, exact results, and trivially reproducible. The lab's store is this design. You can shrink it further: Voyage AI's documentation (which Anthropic's embeddings guide points to) notes that int8 and binary quantization cut storage by 4 and 32 times respectively, and its embeddings are normalized to length 1, so a dot product equals cosine similarity.

A single array stops being enough when one of these becomes true: the vectors no longer fit comfortably in memory; you need many concurrent writers or readers; documents change continuously and you need updates without rebuilding; you need durable storage with backups and access control; or you need filters and keyword search that you don't want to write yourself. Those are operational reasons, not quality reasons. A database does not make retrieval more accurate, and an ANN index makes it slightly less accurate.
</Listen>

## The landscape, by how much you have to run

Group the options by operational weight, lightest first.

**Embedded libraries** run inside your process and store data in local files. **sqlite-vec** adds vector search to SQLite through `vec0` virtual tables, runs anywhere SQLite runs (including the browser through WebAssembly), and supports metadata and partition-key columns; its README describes it as pre-v1, so expect breaking changes. **Chroma** can run embedded or as a server, with metadata filters (`where`, with operators such as equality, ranges, `$in`, `$and`, `$or`, and `$contains` for array fields) and document-content filters. **LanceDB** stores data in the Lance columnar format and supports full-text indexes and hybrid search. Faiss, from Meta, is the classic library of ANN index types if you want indexes without a database.

**Your existing database.** **pgvector** adds a vector type, distance operators, and HNSW and IVFFlat indexes to Postgres. If your application already runs on Postgres, this is often the strongest default: vectors live next to the rows they describe, in the same transactions, backups, and access controls, and you can join against your other tables. Note its indexing limits (the standard `vector` type can be indexed up to 2,000 dimensions, `halfvec` up to 4,000), which matter for some embedding models.

**Dedicated vector databases** such as **Qdrant** (open source, also offered as a managed cloud) run as their own service, with rich payload filtering, multitenancy features, and hybrid queries that fuse dense and sparse results.

**Managed services** such as Pinecone (and managed versions of the open-source engines) run everything for you: scaling, replication, backups. You pay per usage and accept a network hop and a vendor dependency.

The honest way to choose is by constraints, not benchmarks. Public benchmarks such as ANN-Benchmarks are useful for comparing index algorithms on standard datasets, but at the scale of most company knowledge bases, every option here is fast enough, and the deciding factors are where your data already lives, who will operate it, and whether its filtering and deletion model fits your access-control needs.
</Listen>

## Metadata filtering, and the post-filter trap

Almost every real query has a filter: this tenant, these permission groups, this product line, documents from the current year. How the store combines the filter with nearest-neighbor search matters more than any benchmark number.

There are two basic orders. **Pre-filtering** restricts the candidates to records that match, then ranks them. **Post-filtering** ranks first, takes the top candidates, then drops the ones that don't match. Post-filtering is simpler for an ANN index, and it fails in a specific way: when the filter is selective, most of the top candidates are discarded and you get fewer results than you asked for, sometimes none. The pgvector README spells out a concrete case: with an HNSW index, a filter matching 10 percent of rows, and the default candidate list of 40, you get about 4 rows on average. Its fixes include iterative index scans (added in version 0.8.0, which keep scanning until enough rows match), partial indexes for common filter values, and partitioning.

For permissions, post-filtering is worse than a performance problem. It lets restricted documents take part in ranking, it returns empty results that look like "no answer exists," and it puts the safety of the system on a step that is easy to forget. The exercise below makes the difference visible. Dedicated databases like Qdrant and Chroma apply filters during the search, and Qdrant recommends creating a payload index on every field you filter by; check how your store does it, and test with a selective filter before you trust it.
</Listen>

## Hybrid search, updates, and deletes

**Hybrid support.** Embeddings miss exact terms (product codes, error numbers, names), and keyword search misses paraphrases, so most production retrieval combines both. Week 3 builds this properly; for now, know what each store offers. pgvector pairs with Postgres full-text search, and its README suggests merging the two result lists with Reciprocal Rank Fusion (RRF) or a cross-encoder. LanceDB builds a full-text index and uses RRF as its default reranker for hybrid queries. Qdrant runs dense and sparse (or BM25) sub-queries as prefetches and fuses them with RRF or distribution-based score fusion. Whether a store does this natively, or you merge two result lists in your code, is mostly a convenience question; RRF is a few lines either way.

**Updates.** Documents change, and re-ingestion has to be idempotent: running it twice must not duplicate chunks, and running it after an edit must not leave stale chunks behind. The simplest correct pattern is "delete every chunk of this document, then insert the new chunks," in one transaction where the store supports it. Upserting by `doc_id:chunk_index` alone breaks when the new version has fewer chunks. Use the content hash from ingestion to skip unchanged documents entirely.

**Deletes.** When a document is deleted or its access is revoked in the source system, it must disappear from the index promptly, because a retrieval system that still serves a revoked document is a data leak with extra steps. Chroma, for example, deletes by ids or by a `where` filter, and its docs warn that deletion is permanent. Run a periodic reconciliation job that compares the index's document ids and permission records against the source of truth.

**Model changes.** Vectors from different embedding models (or different versions of one model) are not comparable. Store the model name in each record's metadata, and plan a full re-embed, ideally into a new index you switch to after it passes your eval set, whenever you change models.
</Listen>

## Multi-tenancy and access control

If your system serves more than one customer, team, or permission level, the most damaging retrieval failure is not a wrong answer. It is a right answer from a document the user was not allowed to see. OWASP's 2025 entry on vector and embedding weaknesses lists exactly this: weak access controls exposing sensitive embedded data, and cross-context leaks in multi-tenant systems that share one vector database. It also notes that embeddings can be partially inverted to recover source text, so treat vectors as being as sensitive as the documents they came from.

The isolation mechanisms differ by store:

- **Namespaces or collections per tenant.** Pinecone recommends one namespace per tenant: each is stored separately, which gives physical isolation and makes offboarding a tenant one delete. Qdrant, by contrast, says a collection per tenant is rarely efficient and is best kept for a few tenants that need strict isolation.
- **One collection with a tenant field.** Qdrant's recommended default for many small tenants: a `group_id`-style payload field filtered on every request, with the payload index marked `is_tenant` (version 1.11 and later) so each tenant's data is stored together. Its docs add a subtle warning: BM25 and IDF statistics are shared across tenants by default, so keyword scores can be influenced by other tenants' documents unless you scope them.
- **Row-level security.** In Postgres, a row security policy makes the database itself add the tenant condition to every query for a given role. Mind the Postgres docs' caveats: superusers and roles with the BYPASSRLS attribute always bypass row security, and table owners do too unless you set FORCE ROW LEVEL SECURITY, so the application must connect as an ordinary role. A table with row security enabled and no policy denies everything, which is the fail-closed default you want.

Whatever the mechanism, the rules are the same. The tenant and group values come from the authenticated session on the server, never from request input or from the model. The query path makes the filter impossible to skip (a required argument, a policy in the database, a per-tenant client). Permission changes in the source system propagate to the index on a schedule you can state. And a test plants **canary documents** in one tenant and fails the build if any query from another tenant ever returns them. Log every retrieval with the identity and filter used, so you can answer "who could have seen this?" after an incident.
</Listen>

Here is a minimal pgvector schema that puts these rules into the database. The HNSW index and the `<=>` cosine-distance operator follow the pgvector README; the policy uses standard Postgres row-level security.

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
  id          text PRIMARY KEY,           -- "<doc_id>:<chunk_index>"
  doc_id      text   NOT NULL,
  tenant_id   bigint NOT NULL,
  groups      text[] NOT NULL,            -- permission groups copied from the source system
  headings    text,
  body        text   NOT NULL,
  embed_model text   NOT NULL,
  embedding   vector(1024) NOT NULL
);
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON chunks (tenant_id, doc_id);

ALTER TABLE chunks ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON chunks
  USING (tenant_id = current_setting('app.tenant_id')::bigint);

-- Per request, inside a transaction, as an application role that does not own the table:
SET LOCAL app.tenant_id = '42';               -- from the authenticated session, never from the request body
SET LOCAL hnsw.iterative_scan = strict_order; -- keep scanning when the group filter is selective
SELECT id, body
FROM chunks
WHERE groups && ARRAY['all-staff', 'ops']     -- the user's groups, also from the session
ORDER BY embedding <=> $1
LIMIT 5;
```

<Callout type="pitfall" title="Permissions that live only in the prompt">
"Only use documents the user is allowed to see" in a system prompt is not access control. Once a restricted chunk is in the context, the model can quote it, summarize it, or be talked into revealing it by a prompt injection hidden in another document. Enforce permissions in the retrieval layer, before ranking, so that restricted text never reaches the model. Then verify it with canary tests, not with a prompt.
</Callout>

## Cost and operations trade-offs

The costs that matter are rarely the vector math.

**Embedding cost** is paid at ingestion and again on every re-embed (a model change, a chunking change, contextual retrieval). Estimate it as total tokens times the embedding price, and keep the content hash so unchanged documents are never re-embedded.

**Storage and memory** scale with chunks times dimensions; smaller chunks and overlap multiply both. HNSW indexes add graph memory and take time to build; pgvector notes HNSW has a better speed-recall trade-off than IVFFlat but slower builds and more memory.

**Operations** is where options differ most. An embedded store has no server to run but one process owns the files. pgvector inherits everything your team already does for Postgres: backups, monitoring, migrations, access control. A dedicated database is one more service to secure, upgrade, and page someone about. A managed service removes that work in exchange for usage-based pricing, data leaving your network, and lock-in, which you can reduce by keeping your ingestion pipeline and chunk store portable (the lab's JSON file is a crude version of this: you can rebuild any index from it).

A defensible decision for most teams: NumPy or an embedded store while the corpus is small and you are still changing chunking; pgvector if you already run Postgres; a dedicated or managed vector database when scale, multitenancy features, or hybrid search at high volume justify running or buying one. Revisit the choice with numbers (latency at your p95, recall@k with the ANN index versus exact search, monthly cost) rather than with a vendor's benchmark chart.
</Listen>

<GoDeeper title="How HNSW finds neighbors, and what its knobs do">
HNSW builds a multi-layer graph. Every vector is a node in the bottom layer; a random, geometrically shrinking subset also appears in each higher layer, so the top layer is a sparse "highway" and the bottom layer is dense. A search enters at the top, greedily moves to the neighbor closest to the query, drops a layer when it can't improve, and repeats, keeping a candidate list in the bottom layer. Malkov and Yashunin's paper reports logarithmic complexity scaling for search. The knobs map onto that picture. `m` is how many neighbors each node keeps (pgvector's default is 16): more means better recall and more memory. `ef_construction` is the candidate list size while building (default 64): larger builds a better graph, slowly. `ef_search` is the candidate list size at query time (default 40): larger raises recall and latency, and it is also the cap that causes the post-filter shortfall. To tune, measure recall@k of the ANN index against exact search on your own query set, at your production k, and pick the smallest settings that keep recall within your tolerance. The Faiss documentation and ANN-Benchmarks are good next stops for other index families (IVF, product quantization) and how they compare.
</GoDeeper>
